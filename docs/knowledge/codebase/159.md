# #159 — make the wait primitives notice process death

[Issue](https://github.com/pyrycode/tui-driver/issues/159) · [Spec](../../specs/architecture/159-wait-notices-process-death.md) · Commit `dbdc307` · Size: XS (PO sized S; architect override) · Not security-sensitive (process-lifecycle plumbing, no attacker-influenceable classification)

## Summary

`WaitReady` used to poll a dead session for the **entire ctx timeout** before failing, then surface the generic ctx cause — hiding the real reason (the child process is gone). Root cause: `WaitReady` gates on `WaitUntil(IsIdle)`, and `WaitUntil` only returns on predicate-true or ctx-cancel. If `claude` dies during startup the idle predicate never becomes true, so the wait spins until the deadline.

The fix adds a session-aware sibling of `WaitUntil` — unexported `(s *Session).waitUntilOrExit(ctx, predicate)` in `wait.go` — that mirrors `WaitUntil`'s ticker+select loop but adds a third select arm watching `s.exited` (the channel the `cmd.Wait` observer goroutine closes on process exit). On that arm it returns a new typed `*ProcessExitedError` wrapping `s.exitErr`. `WaitReady`'s single call site is redirected from `WaitUntil` to `s.waitUntilOrExit`; everything else in `WaitReady` (the zero-`Readiness`-on-error contract, the trust/mcp/network classification on the idle path) is unchanged. **`WaitUntil` is left byte-for-byte untouched** — it stays a standalone exported primitive with no `Session` in scope.

Net effect: when the process dies before idle, `WaitReady` returns promptly with a `*ProcessExitedError` the consumer (`pyry agent-run`) can match via `errors.As` and whose `.Err`/`Unwrap` reaches the underlying `cmd.Wait` exit status — fail-fast with the real cause instead of a full-timeout collapse into a generic ctx error.

## Patterns established

- **First typed error in `pkg/tuidriver` — the template for the next one.** The package had no typed errors before this (all prior errors were `fmt.Errorf("tuidriver: <op>: …%w", …)` strings, per `answer.go`). `ProcessExitedError{Err error}` sets the shape: a single wrapped-cause field, `Unwrap() error` returning it, `Error()` keeping the `tuidriver:` prefix (`"tuidriver: process exited before ready[: <Err>]"`), matchable with `errors.As(err, new(*ProcessExitedError))` and reachable with `errors.Is(err, <cause>)`. It lives in `ready.go` beside `Readiness` because both are `WaitReady`'s public return contract and should be discovered together, not in a separate `errors.go`. Reuse posture: the next typed error in the package copies this shape (wrapped-cause field + `Unwrap` + prefixed `Error`), and lives next to the API that returns it.
- **A nil channel that blocks forever is a *feature* of the select, not a case to guard.** A directly-constructed `&Session{…}` (the unit-test fixture) has a nil `exited`; receiving on a nil channel blocks forever, so the exit arm is inert and `waitUntilOrExit` degrades to *exactly* `WaitUntil`'s two-arm behaviour. No explicit `if s.exited == nil` guard — the language guarantees it. This single fact does double duty: (1) it's the correct "process still running / no exit awareness" path, so `TestWaitReadyContextCancelled` (nil `exited`, never idle, short ctx) still returns the ctx cause with zero code change; (2) it makes the exit path unit-testable with no real binary spawn — a test pre-closes `exited` and sets `exitErr` on the same struct-literal fixture. Reuse posture: when adding a select arm on an optional channel, prefer leaving it nil-when-absent over a boolean+guard; the nil-blocks-forever semantics *are* the guard.
- **Duplicate the loop; don't refactor the shared primitive.** `WaitUntil` is exported, has 7 tests, and is consumed externally — the spec's explicit constraint was "do not modify this function." So `waitUntilOrExit` is a *sibling* (a `*Session` method that copies the ~15-line ticker+select shape and adds one arm), not a shared helper both call. The duplication is deliberate and cheap: it freezes `WaitUntil`'s exported contract at zero risk to its callers, and the two loops read identically so drift is visually obvious. Reuse posture: when a variant needs one more arm on a frozen exported primitive, copy the small loop rather than parameterising the original into a shared core.
- **Reuse the existing happens-before edge — add no synchronisation.** Reading `s.exitErr` only *after* the `<-s.exited` receive succeeds is race-free: `close(s.exited)` in the observer goroutine happens-after `s.exitErr = cmd.Wait()`, the same edge `Session.Wait()` already relies on. `waitUntilOrExit` reads the same signal but must **not** additionally block on `readerDone` — it fires on process exit, not on final-byte drain. No new goroutine, no new lock, no new channel.

## Lessons learned

- **A clean exit before ready is still a failure, not a success.** When the process exits with status 0 before reaching idle (`exitErr == nil`), `WaitReady` still returns a `*ProcessExitedError` — with `.Err == nil`. "Process exited before we saw the input prompt" is the error regardless of the exit code; a nil cause means "clean exit, no diagnostic status," not "ready." Pinned by `TestWaitReadyProcessExitedCleanExit`. The `.Err == nil` branch of `Error()` emits the bare `"tuidriver: process exited before ready"` so the message stays sensible when there's no cause to append.
- **Ready wins a same-instant race with exit — pinned, not left to select's fairness.** The entry short-circuit `if predicate() { return nil }` runs before the loop, so an already-idle session returns ready even if the process has *also* exited (both `exited` closed and predicate true). This is intentional: if claude reached the input prompt, the consumer should proceed regardless of a simultaneous exit signal. Go's `select` picks a ready arm pseudo-randomly, so this precedence could **not** be left to the loop — it's the explicit entry short-circuit that guarantees it, and `TestWaitUntilOrExitPredicateTrueBeatsExit` pins it (predicate-true + `exited` closed → `nil`).
- **Typed-only, no sentinel — deferred on the evidence rule.** The spec's open question (sentinel `var ErrProcessExited` + `Is` method for a boolean `errors.Is` check vs. typed-only) resolved to typed-only: `errors.As` + the `.Err` field satisfy both AC clauses (identifiable process-exit error; underlying cause available). No consumer has asked for a boolean sentinel, so none was added — if the pyrycode consumer later prefers `errors.Is(err, ErrProcessExited)`, add the sentinel + an `Is` method then. Cheap to add later, impossible to un-ship early; deferred per the evidence-based-fix rule.
