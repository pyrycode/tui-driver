# #150 — Rendered-grid refactor 1/6: addressable rendered-grid accessor (`Grid`)

[Issue](https://github.com/pyrycode/tui-driver/issues/150) · [Spec](../../specs/architecture/150-rendered-grid-accessor.md) · [PR #175](https://github.com/pyrycode/tui-driver/pull/175) · Commit `8cc1aa4` · Related: [`Render`/`trimGridText`](../../../pkg/tuidriver/grid.go), [#146](146.md)/[#147](147.md) (Render-consuming modal reader/writer), [#90](90.md) (Render-vs-StripANSI split), [#81](81.md) (parsed-shape stability)

**Slice 1 of 6 of the rendered-grid refactor (Cross-Repo Code Review 2026-07-03; the chain fixes CRITICAL A + B).** Both criticals share one root cause: **state is classified by `strings.Contains` over the raw append-only *history* buffer, not the rendered *screen*.** `Render` already interprets a `Buffer.Snapshot()` as a VT100 grid and returns the correct on-screen text, but flattens it to one joined string; every structure-aware detector (`agents.go:42`, `mcp.go:72`, `permission.go:73`) then re-splits or re-scans that string ad hoc, and other predicates substring-match the history bytes directly. Text that has scrolled off the top of the visible grid still lives in the history buffer, so a substring match over that buffer classifies stale/off-screen text as on-screen. This slice ships the addressable-grid foundation the rest of the chain builds on — **it wires no detector and changes no behaviour.** Slices 2–6 migrate the detectors onto it.

## Summary

Purely additive to the existing `pkg/tuidriver/grid.go` (no new production file, no existing symbol touched, no consumer wiring — codegraph confirmed zero pre-existing `Grid`/`NewGrid` symbol and zero callers). Adds one type + constructor + three accessors:

- `Grid struct{ rows []string }` — an immutable value over the rendered VT100 screen. Constructed once per snapshot; caches the rendered rows so predicates hit the cached slice (no re-render per call).
- `NewGrid(snap []byte, cols, rows int) *Grid` — a **one-liner over `Render`**: `text := Render(snap, cols, rows)`. Dimension fallthrough (`0` → `DefaultGridCols`/`DefaultGridRows` = 120×40; non-zero overrides) is **delegated entirely to `Render`, not re-checked here**. Empty/whitespace-only render special-cased to **zero rows** (see Lessons). Returns `*Grid` per the package's `New*` pointer convention.
- `Rows() []string` — the cached rows top-to-bottom, each right-trimmed, trailing empties dropped (exactly what `Render` emits per line). Returns the **backing slice, documented read-only** — matches how `AgentList`/`McpStatus` expose their slices; no defensive copy (evidence-based: no mutating consumer exists).
- `ContainsInLastRows(sub string, n int) bool` — region-scoped: `n <= 0` → false; `n` clamped to the row count via the `min` builtin; scans only `rows[len-n:]` with `strings.Contains`. A match must fall inside a single row — never across a row boundary. **This is the whole point:** off-screen/above-region text does not count.
- `RowHasPrefix(i int, prefix string) bool` — `strings.HasPrefix` on row `i` (0-based); out-of-range `i` returns false **rather than panicking** — a hard AC, so migrated detectors can probe rows without length guards.

No error returns anywhere (mirrors `Render`, which swallows the vt10x write error and cannot fail a caller). Every degenerate input is absorbed, not rejected. Pipeline ran clean: RED→GREEN, `go test -race`/`go vet` green, code-review **PASS**. Not `security-sensitive` (pure-function accessor over the local claude subprocess's rendered output; no auth/network surface, no detector behaviour change).

## Patterns established

- **`Render` is the single rendering source of truth; `Grid` composes over it, never around it.** `NewGrid` is `strings.Split(Render(...), "\n")` with the empty-render guard — no re-implemented rendering, trimming, or dimension defaulting. This keeps the vt10x dependency and the right-trim/drop-trailing-empties contract in exactly one place (`grid.go`'s `Render`/`trimGridText`), so a future renderer change propagates to `Grid` for free. The ticket's explicit instruction ("Reuse it; do not re-implement rendering") is now a structural property, not a review note.
- **Screen-region semantics vs. raw-history substring — the accessor that ends the criticals.** Two distinct layers combine to fix the root cause: (1) `Render`/vt10x gives you the *visible grid* — text scrolled past the 40-row top is genuinely gone from its output, unlike the append-only history bytes; (2) `ContainsInLastRows` adds region-scoping *within* that visible grid. A detector migrating from `strings.Contains(snapshot, x)` to `grid.ContainsInLastRows(x, k)` therefore stops false-positiving on **both** scrolled-off-history text and on-screen-but-wrong-region text. The headline AC test pins layer (2) deterministically: the same modal string is in the raw bytes of two snapshots (raw `strings.Contains` true for both), but `ContainsInLastRows(modal, k)` is true when it renders into the bottom region and false once extra rows push it above the last-`k` window.
- **Out-of-range returns false, never panics — a load-bearing contract, not a convenience.** `ContainsInLastRows` (`n<=0`, `n>len`) and `RowHasPrefix` (`i<0`, `i>=len`) all fall through to a defined `false`. This is specced as an AC precisely so slices 2–6 can migrate detectors without wrapping every access in a length check — the same "absorb degenerate input" posture as `Render` and the `AssistantText`/`ParseToolUse` zero-value-on-mismatch family.
- **Region-predicate method set grows on demand, not speculatively.** Ships exactly the three operations the chain needs (`Rows`, `ContainsInLastRows`, `RowHasPrefix`). Future slices may want `FirstRowWithPrefix`, `ContainsInFirstRows`, etc. — add them **when a detector migration actually needs one**, on the `*Grid` method set, not now (evidence-based; explicit Open Question in the spec).

## Lessons learned

- **`strings.Split("", "\n")` returns `[""]` (one empty row), which is wrong for an empty screen — special-case it.** `Render` returns `""` for an empty/whitespace-only snapshot; a naive split would give a one-row grid whose single row is `""`, silently breaking every `RowHasPrefix(0, …)` and `Rows()` length check downstream. `NewGrid` guards: `if text == "" { return &Grid{} }` so an empty screen has **zero** rendered rows, consistent with "trailing empty rows dropped." Pinned by a test (empty snapshot + whitespace-only snapshot both ⇒ `len(Rows()) == 0`). The architect flagged this as the one non-obvious contract; it is the easiest thing to get wrong in this slice.
- **vt10x treats a bare `\n` as line-feed-only (no carriage return) — multi-row test fixtures need `\r\n` or they render as a staircase.** The developer verified this empirically before building the inline `[]byte` fixtures. A fixture written `"top\nbottom"` renders `bottom` starting at the column where `top` ended (diagonal drift), not on a fresh row 0; `"top\r\nbottom"` renders the two rows as intended. Every `Grid` fixture (and any future `Render`-fed fixture) must use `\r\n` between rows. This is a property of feeding raw VT100 bytes through the emulator, not of `Grid`.
- **Empty-`sub` in `ContainsInLastRows` inherits `strings.Contains` semantics (returns true for any non-empty region) — left as-is, deliberately.** Code review raised this as a NIT with **explicitly no change requested**: defending an unobserved input would violate evidence-based fix selection. `strings.Contains(row, "")` is `true`, so `ContainsInLastRows("", n>0)` is true whenever the grid has rows. No detector passes an empty needle; if one ever does, that is the slice that adds the guard.
- **No new feature doc, no new ADR — same posture as [#146](146.md)/[#147](147.md).** `Grid` is a rendered-grid mechanic living alongside `Render`, not a standalone product feature (nothing consumes it yet) and not an ADR-weight decision (the "rendered screen over raw history" call was already made by the Cross-Repo Code Review that filed the chain). Documented as a bullet in [system-overview](../architecture/system-overview.md) beside the `Render`/modal bullets, not a per-type feature page. The chain's design rationale lives in the review + this file; slices 2–6 each get their own `codebase/<N>.md`.
