# #147 — `AnswerModal` safe modal-answer: abstract choice → keystroke + confirm dismissal

[Issue](https://github.com/pyrycode/tui-driver/issues/147) · [Spec](../../specs/architecture/147-safe-modal-answer.md) · [PR #149](https://github.com/pyrycode/tui-driver/pull/149) · Commit `9898ac3` · Predecessors: [#146](146.md) (the reader), [#13](13.md), [#100](100.md); structural template [`deliver.go`](../../../pkg/tuidriver/deliver.go)

**Phase 3 screen-side modal *writer* of pyrycode#597 (substrate seal / mobile-remote-head).** The counterpart to the modal *reader* shipped in [#146](146.md) (`ParseModalContent` → `ModalContent` / `ModalOption`). The reader projects a permission / trust-folder modal into a neutral typed value (class + ordered options, each carrying claude's rendered 1-based `Index`); this child sends the keystroke that selects a chosen option **by its `Index`** and re-reads the screen to confirm the modal dismissed. Permission and trust prompts have **zero JSONL footprint** ([jsonl-layout § Permission modals](../architecture/jsonl-layout.md)), so the substrate seal makes tui-driver the sole owner of claude's per-class keystroke knowledge: the daemon supplies an abstract choice and never touches screen text or raw key bytes. The permission *decision* (which option, who may answer, timeout/audit) stays in the consumer (ADR 025); tui-driver owns only the screen↔keystroke mechanics.

## Summary

One new file, `pkg/tuidriver/answer.go`, plus its test — purely additive, no existing file touched, no exported symbol changed, **no new fixtures** (reuses #146's two `.bin` files for the "still present" re-read; idle bytes for "dismissed"). It adds:

- `Session.AnswerModal(ctx, AnswerModalOpts) error` — sends the per-class keystroke that selects `opts.Choice` for `opts.Class`'s modal via the **sealed** `Answer` surface, then polls the screen until the modal dismissed. Returns `nil` once the modal is no longer detected; returns an error if the class is unsupported, the choice is invalid, the keystroke send fails, or the modal is still present after `ConfirmTimeout` (so the daemon can retry or degrade rather than assume success).
- `AnswerModalOpts{Class ModalClass; Choice int; ConfirmTimeout time.Duration}` — carries **Class + Choice only**, never the full `*ModalContent`: by answer time the daemon holds the class it parsed plus the `Index` returned from the phone, nothing more. No `Label`, no command detail, no screen text crosses this API. Mirrors `DeliverOpts` (struct over positional args, for the package idiom + forward-compat).
- `DefaultAnswerConfirmTimeout = 2 * time.Second` (exported; bounds the dismissal re-read when `ConfirmTimeout == 0`) + unexported `answerConfirmPoll = 150ms` (the re-read cadence, matching `deliver.go`'s `promptCommitPoll`).

The whole path mirrors `DeliverPrompt`'s deliver→re-read→confirm structure and its injectable seams almost line-for-line: the public method wires real session methods into an `answerDeps{answer, dismissed}` struct (cf. `deliverDeps`); the unexported pure driver `answerModal(opts, deps)` dispatches the keystroke then confirms; tests call the driver with fakes, no PTY. The confirm poll `modalDismissed(ctx, class, snapshot, timeout)` mirrors `promptDidCommit` exactly — same `time.NewTimer` + `time.NewTicker` + `select { ctx.Done / deadline / tick }` shape, swapping the commit predicate for `DetectModalClass(snap) != class`.

Pipeline ran clean: RED→GREEN, code-review PASS, `make check` green. Carried the `security-sensitive` label; the architect's security review verdict was **PASS** (spec § Security review) — this *sends* a grant-selecting keystroke on a live claude (more security-relevant than #146's read-only parse), and the grant-redirection threat is mitigated structurally (see Patterns).

## Patterns established

- **The writer mirrors `DeliverPrompt`'s method→pure-driver→fakes seam pattern.** `AnswerModal` (public, wires `s.Answer` + a `modalDismissed` closure over `s.Snapshot`) → `answerModal(opts, answerDeps)` (unexported, pure, the binding contract the tests drive) → fake `answer` / `dismissed` seams in `answer_test.go`. This is the package's established testable-write shape (`deliverDeps`, `runWatchdogLoop`, `mergeEvents`): the keystroke + dismissal outcome are scripted with closures, so each supported class's answer-and-confirm path is covered in both the dismissed (success) and still-present (error) outcomes with **no live PTY** (AC3). `ctx` is captured in the `dismissed` closure, so the unexported driver takes no `ctx` — same as `deliverPrompt`.
- **Per-class dispatch is one `switch`; both supported classes share a single number-select `case`.** Both classes `ParseModalContent` returns today (`permission`, `trust-folder`) are number-select, so both map to `Answer(strconv.Itoa(Choice))` in one combined `case` — the elegant expression of "both use the number-select strategy" rather than two identical arms. The `switch` **is** the extension seam: a future non-number-select class (y/n, arrow+enter) slots in by adding a `case` with its own keystroke strategy (and its own seam on `answerDeps`, e.g. `navigate` / `sendEsc`) — but **only once it has a fixtured reader**. Evidence-based: do NOT pre-build handlers for unfixtured classes (the #146 follow-up defers destructive / plan-confirm until fixtured). The `default` arm makes the unsupported-class path a returned error that **sends nothing** — a number-select keystroke must never reach a class that uses a different selection strategy.
- **Routes on `Choice` = `ModalOption.Index`, never `Label` — the #146 security contract, now enforced on the write side.** The reader established that `Index` (claude's own rendered number) is the security-relevant selector and `Label` is advisory and prompt-/tool-influenceable; this writer is where that contract becomes load-bearing. The single trust boundary (operator `Choice` → `Answer(strconv.Itoa(Choice))` → claude's TUI grant) is one named function, and a spoofed label can mislead a *human* but cannot change which grant a given number selects. The `AnswerModalOpts.Choice` doc-comment marks it as the Index and forbids `Label` routing, exactly where a future caller would otherwise drift.
- **Confirm-by-re-read is class-level (`DetectModalClass`), not content-level — a hostile screen cannot spoof "dismissed".** `modalDismissed` returns dismissed the moment `DetectModalClass(snapshot()) != class`. `DetectModalClass` reads claude's structural anchors (cheap, no `Render`), **not** the prompt-/tool-influenceable option text, so the dismissal signal is unforgeable from prompt content. Using `DetectModalClass` (not `ParseModalContent`) is sufficient and cheaper: the confirm only needs "is this class still the active modal," not its parsed content. `!= class` treats **any** non-matching screen — idle, *or a different modal that popped after the answer landed* — as dismissed, which is correct: the class the operator answered is gone, and the daemon handles any new modal as a fresh parse→answer cycle.
- **Substrate seal upheld both directions: typed-in, typed-error-out.** The public surface is `ModalClass` (enum) + `int` + `time.Duration`; the keystroke is a computed digit string through the sealed `Answer` → `writeRaw` path (never the spike-only `SendKeys` / a raw `Write`); error messages carry **only** the `ModalClass` enum value and the integer `Choice` — never the option `Label`, the prompt text, the command detail, or any screen literal. No new claude wording is introduced (classification reuses the shipped `DetectModalClass`). Same "nothing secret crosses the boundary" posture as #146's action-detail omission.
- **`AnswerModal({trust-folder, 1})` subsumes `AcceptTrust` but does not migrate it.** It sends the same `1\r` as `AcceptTrust` (byte-identical for `Choice == 1`) while *also* honouring `Choice == 2` (decline), which the hardcoded `AcceptTrust` cannot. `AcceptTrust` stays as the spike convenience; no consumer call site is migrated by this ticket (additive only — out of scope).

## Lessons learned

- **A still-present same-class modal is a deliberate conservative false-negative, not a bug.** If answering permission modal A immediately surfaces permission modal B, `DetectModalClass` still reports `permission`, so `modalDismissed` reads "still present" and `AnswerModal` returns the still-present error even though A was dismissed. This is intentional: the daemon retries / degrades, re-reads, sees the (new) modal, and the operator answers again — **never a silent wrong-grant**. Content-diffing A vs B to distinguish them would route on the prompt-/tool-influenceable screen text the security model forbids trusting, so it is deliberately not done. Tighten only if the back-to-back-same-class case is actually observed (evidence-based fix selection).
- **`ctx`-cancelled-during-confirm surfaces as the still-present error, and that's the cheap-false-negative posture by design.** `modalDismissed` returns `false` on `ctx.Done()`, which becomes the "still present" error even though the keystroke may have landed. Matching `promptDidCommit`, a false negative costs the caller one re-read, never a corrupted grant — the keystroke write is atomic, so there is no partial state on cancel.
- **Answer-keystroke *staleness* is consumer-owned (ADR 025), and the contract is honest about it.** If the on-screen modal changed between the daemon's parse and the answer, the keystroke targets whatever is on screen now. tui-driver's contract is deliberately narrow — "given the class you name, I send that class's keystroke and confirm that class is gone" — and the confirm-by-re-read is the deterministic backstop for the common "answer didn't land" case. Freshness / replay / who-may-answer (did the operator answer the modal they actually saw) is the daemon's permission-flow concern (epic pyrycode#597 / ADR 025), not the screen↔keystroke mechanic.
- **No new feature doc, no new ADR — same posture as #146.** Like the modal reader, this is a screen↔keystroke mechanic following an already-decided convention (mirrors `DeliverPrompt`), so it lives in [system-overview](../architecture/system-overview.md) beside the modal reader + approve-keystroke bullets, not a per-helper feature page. The Index-not-Label trust boundary is a substrate-seal *pattern* (#146 already captured it; this ticket enforces it on the write side), not an ADR-weight decision; the remote-permission security model and ADR 025 live in pyrycode.
