# #168 — Kill the whole process group on Close

[Issue](https://github.com/pyrycode/tui-driver/issues/168) · [Spec](../../specs/architecture/168-close-kills-process-group.md) · [PR #212](https://github.com/pyrycode/tui-driver/pull/212) · Commit `5a39443` (spec `785edac`) · Touches [`session.go`](../../../pkg/tuidriver/session.go) + new [`session_signal_other.go`](../../../pkg/tuidriver/session_signal_other.go) / [`session_signal_windows.go`](../../../pkg/tuidriver/session_signal_windows.go) · Disjoint sibling: [#169](https://github.com/pyrycode/tui-driver/issues/169) (parent-death `Pdeathsig`)

**S process-lifecycle fix from the Cross-Repo Code Review 2026-07-03 inbox filing.** Not `security-sensitive` (verified on the issue labels) — the PGID is OS-derived from the child's own PID, not attacker-influenceable input; this is pure lifecycle cleanup outside the label's threat model. The `kill(-1)` footgun is a correctness guard, not a trust-boundary trigger.

## Summary

`Session.Close` signalled only the **leader** process — `s.cmd.Process.Signal(SIGTERM/SIGKILL)`. Tool subprocesses `claude` forks (Bash running a long command, etc.) inherit the leader's process group but were never signalled directly, so on a *hard* Close — where the leader is SIGKILLed before it can wind down its own children — they orphan (reparent to init) and keep running. For a `claude` session that means live tool processes with nobody driving them, burning subscription quota.

The fix signals the child's **process group** (negative PGID) instead of the single leader PID, for both the initial SIGTERM and the escalated SIGKILL. Because `creack/pty`'s `Setsid` already made the child a group leader (`PGID == PID`) at spawn, the group is addressed by negating the leader PID — `kill(-pid, sig)` reaches the leader and every process in its group in one call. **No `SysProcAttr`/`Setpgid` change** — which is exactly what keeps this ticket off the same spawn-attr surface as #169 and lets the two stay independent (WIP=1 serialises them regardless; no native blocker was set).

`Close`'s two `s.cmd.Process.Signal(...)` calls now delegate to a new unexported `signalShutdown(sig)` method. Every other shutdown step — the 3 s grace race, PTY close, `readerDone` join, recorder close, `shutdownOnce` idempotency, `exitErr` return — is untouched, and `Close`'s signature is unchanged.

## Design

Three production files; `Close` stays cross-platform and delegates the signalling to a per-GOOS method.

- **`session.go`** — the two `Process.Signal` calls become `s.signalShutdown(syscall.SIGTERM)` / `s.signalShutdown(syscall.SIGKILL)`. Keeps its `syscall` import (`SIGTERM`/`SIGKILL` are cross-platform constants, `syscall.Signal` a cross-platform type). Doc-comment updated to say "process group … falling back to the leader alone".
- **`session_signal_other.go`** (`//go:build !windows`) — two symbols:
  - `groupSignalTarget(pid int) (target int, ok bool)` — pure, no syscalls. `pid <= 1 → (0, false)`; `pid > 1 → (-pid, true)`. The catastrophe guard: `kill(-1)` signals every process the caller may signal, `kill(0)` signals the caller's own group, so any `pid <= 1` (which would negate to `0`/`-1`) is rejected. Invariant: whenever `ok`, `target < -1` — never `0`, never `-1`.
  - `func (s *Session) signalShutdown(sig syscall.Signal)` — `groupSignalTarget(pid)`; if `ok`, `syscall.Kill(target, sig)` and return on nil error; otherwise (guard rejected the PID **or** the group signal errored) fall back to `s.cmd.Process.Signal(sig)`, the pre-fix leader-only path. Errors are intentionally swallowed (matches the pre-fix `_ =` posture — shutdown is best-effort by contract).
- **`session_signal_windows.go`** (`//go:build windows`) — leader-only stub, one line `_ = s.cmd.Process.Signal(sig)`. Windows has no POSIX process groups and no `syscall.Kill`; zero behaviour change.

### Why `-pid`, not `syscall.Getpgid(pid)`

The group-leader invariant is guaranteed by `creack/pty`'s `Setsid` and pinned by a unit test (AC #1), and `-pid` **degrades safely** even if that invariant were ever broken: for `pid > 1`, `-pid` is always a specific group id `< -1`, so a stale/absent group yields `ESRCH` and the leader-only fallback fires — never a catastrophic `kill(-1)`/`kill(0)`. Querying `Getpgid` buys nothing here and adds a syscall.

## Patterns established

- **New syscall-based code needs `//go:build !windows` + a `_windows.go` stub, not a `runtime.GOOS` skip.** `syscall.SIGTERM`/`SIGKILL`/`Signal` exist on Windows (which is why the pre-fix leader-only `session.go` compiled there), but `syscall.Kill`/`syscall.Getpgid` are **Unix-only** (`undefined: syscall.Kill` on `GOOS=windows`). A `runtime.GOOS == "windows"` runtime skip — the idiom in `session_test.go` — is insufficient because it doesn't stop *compilation*. Mirror the repo's existing `cwd_darwin.go`/`cwd_other.go` split (explicit `//go:build` tag line, `_other.go` catch-all) for both the production code **and** the tests. This corrected the ticket body's claim that the group signal "needs no new build tag" (it would break the `GOOS=windows` build, which succeeds today because `creack/pty` ships a Windows stub). The architect saved this as a project memory — #169's `Pdeathsig` is the same shape.
- **A pure deterministic guard is the belt-and-suspenders safety net (different fabric: code, not another agent).** `groupSignalTarget` performs no syscalls and makes the `kill(-1)`/`kill(0)` catastrophe *structurally* unreachable, table-tested with a cross-cutting `target < -1` assertion over every `ok == true` row. A real spawned child always has a kernel PID `> 1`, so the guard never fires in practice — it exists to make the failure impossible regardless.
- **Prefer the safe-degrading single-syscall form over the "correct" query.** `-pid` over `Getpgid` — one syscall, and a broken invariant degrades to `ESRCH` → fallback rather than a catastrophic signal.

## Lessons learned

- **The plain-sleeper AC #3 test is a FALSE GREEN — `Close`'s own `s.pty.Close()` masks the bug.** `Close`'s final PTY close delivers `SIGHUP` to the whole foreground process group, which on its own reaps an *ordinary* backgrounded sleeper — so a plain `sleep 300 &` grandchild dies on Close **even under the pre-fix leader-only signal**, and the test passes with the bug present. The developer's RED check caught this. Fix: the grandchild must **ignore SIGHUP** (`sh -c 'trap "" HUP; exec sleep 300'` — the empty-handler `SIG_IGN` survives the `exec` into `sleep`) so that *only* the explicit process-group SIGTERM/SIGKILL can reap it. Both directions were verified: leader-only → grandchild survives Close; group signal → reaped. When a lifecycle test's own teardown can produce the asserted outcome, the synthetic subject must be immunised against every teardown side-channel *except* the one under test. (Matches memory `pty-close-sighup-masks-group-kill-tests`.)
- **Build-tagged files slip past QA's native gate — cross-compile in review.** QA's `go build ./...` runs natively on darwin, which **excludes** `session_signal_windows.go`, so a Windows-stub compile error would structurally not be caught. Code review closed the gap by cross-compiling `GOOS=windows`/`GOOS=linux go build` + `GOOS=windows go vet` on `pkg/tuidriver/`. Any ticket that adds a `_windows.go` / build-tagged file must be cross-compiled explicitly, not trusted to the native gate.

## Deferred / out of scope

- **Self-`setsid`/daemonizing tool children** that fork into their *own* new process group escape any single group kill — a known property of the idiom, not a bug solved here. No machinery built (no observed occurrence).
- **PID-reuse / reap-race TOCTOU** (leader exits *and* is reaped *and* its PID is reused *as a new group leader* between the grace timer firing and the `Kill` call) — astronomically unlikely at a 3 s grace and unobserved; not defended, per *Evidence-Based Fix Selection*. The leader-only fallback retains Go's `os.Process` reaped-PID guard (`ErrProcessDone`).
- **Live-`claude` confirmation is a manual note, not a gating AC.** Mirror `docs/specs/architecture/11-spike-cancel.md`'s §"no orphans" `pgrep -lf` orphan-check: drive a real Bash tool running a long `sleep`, `Close`, then `pgrep` the sleeper for zero orphans. Requires `make e2e` / live `claude`, so it cannot run in the developer's `make check` gate.
