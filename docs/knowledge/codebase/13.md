# #13 — spike: permission-prompt modal (trigger, detect, auto-respond, escalation contract)

[Issue](https://github.com/pyrycode/tui-driver/issues/13) · [Spec](../../specs/architecture/13-spike-permission.md) · Code: `cmd/spike-permission/`

## Summary

Fourth spike binary in the repo: `cmd/spike-permission/main.go` (~1400 LOC) plus `cmd/spike-permission/README.md` (~620 lines of empirical log). Drives three probes across **two** sequential `claude` sessions (Probe 1 in Session A; Probes 2 + 3 in Session B) to surface the permission-prompt modal end-to-end — what shape it has in the PTY, whether it emits anything to the JSONL, what keystroke approves it, how the post-approve state machine resumes the turn, and how much modal text + tool name is extractable for a hypothetical consumer escalation callback. Spawn line drops `--permission-mode bypassPermissions` (the crutch the prior three spikes used to skip modals) so prompts actually fire.

Reuses spike #11's primitives verbatim under `// copied from cmd/spike-cancel/main.go — keep in sync until library extraction` (every const, regex, glyph, `rollingBuffer`, `tracker`, `waitUntil`, `projectsDir`, `encodeCwd`, `tailJSONL`, `extractByMsgID`, `typePrompt`, `clearInputLine`, `isIdle`, `matchSpinner`, `hasSpinnerGlyph`, `isEndTurn`, `isToolUse`, `msgIDOf`, `rollingBuffer.quietFor`) and adds: `runSession` (two-session orchestrator; takes a probe list and owns one claude subprocess), `runObserve` / `runAutoRespond` / `runEscalate` per-probe drivers, `hasModal` (two predicate variants, see below), `extractModalText` (last-dash-run anchor; the working strategy after two alternatives failed), `extractToolName` (known-token list), `cleanModalLines`, `sendKeystroke` (renamed from spike #11's `sendCancel` because both approve + cancel share the same single-byte bulk-write semantics), `writeTempSnapshot` (0600-mode), `logObservationEvent`, `waitForModal`, `parseApproveKeystroke` + `-approve-keystroke` flag, `parseModalPredicate` + `-modal-predicate` flag, `newSessionID` (suffix-tagged), and an `oscRe` (`\x1b][^\x07]*\x07`) that strips OSC sequences alongside CSI.

Five empirical answers (one per open question this spike was filed to resolve):

1. **Approve keystroke is `1\r` (`31 0d`), 2 bytes, single bulk write.** Matches the on-screen `❯1.Yes` numbered default. `y\r`, bare `\r`, and `\x1b[B\r` (down + enter) all also work; the latter selects option 2 (the broader project/session-scope grant) and is ~1 s slower. Library default for "approve once" should be `1\r`; the down-arrow variant is a different product affordance, not a fallback.
2. **Permission modals have ZERO JSONL footprint.** Probe 1's 5 s observation window captures `events=0`. `assistant(stop_reason=tool_use)` does not arrive until AFTER the modal is approved or cancelled. Consequence: **modal detection MUST be PTY-side.** Architecturally consistent with cancellation (spike #11 finding) — both modals and cancellation live on signal paths that the assistant-only JSONL tailer does not surface.
3. **Modal text renders with two different space-stripping patterns, tool-dependent.** Bash modal uses CSI cursor-forward (`\x1b[1C`) between every word; after ANSI strip the buffer reads `Doyouwanttoproceed` (no interword spaces) — same root cause as spike #1 finding #8 for the spinner verb. Read modal uses literal spaces; stripped buffer reads `Do you want to proceed` (normal spacing). Detection + extraction logic must handle both variants. The literal-text predicate's substring list carries both forms (`Doyouwanttoproceed` AND `Do you want to proceed`); the universal "Esctocancel" marker is always no-space regardless of tool.
4. **Post-approve, the JSONL stream is identical-shape to a non-modal tool-use turn.** `assistant(stop_reason=tool_use, thinking)` → `assistant(stop_reason=tool_use, tool_use)` → `user(tool_result)` → `assistant(stop_reason=end_turn, text)`. No new envelope types, no new `stop_reason` values, no acknowledgement of the modal. End-to-end `prompt-written → end-turn-detected` is ~9 s across 5 runs (3.2 s to reach `modal-detected`, instant keystroke, then ~5–6 s for `keystroke-sent → end-turn-detected`, dominated by the 1500 ms PTY-quiescence debounce + tool execution + redraw).
5. **Modal text + tool name are reliably extractable for the escalation contract.** The cleaned-up modal text (`Text` field), the full raw rolling-buffer snapshot (`RawBytes`, written to a 0600 tempfile under `/tmp/spike-permission-probeN-bytes-<ts>.bin`), and the tool name (`Tool`, via a known-token list of Bash/Read/Write/Edit/Glob/Grep/WebFetch/WebSearch/Task) all come out high-confidence. Options-list parsing was not attempted (would be a per-modal sub-parse); `SuggestedResponse` for "approve once" is universally `1\r` for the permission-modal class.

Two implementation deviations from the architect's spec, both prompted by behavior the spec's open questions explicitly flagged:

- **`extractModalText`'s working strategy is "last `─{20,}` run before the proceed-marker → start; line containing `Esctocancel` → end."** The spec sketched a region-based strategy (find the contiguous block of lines containing `│`, strip borders, concatenate). That didn't survive the Read modal, where the dash separator is **inline** on a single line with the modal content — there's no top/bottom box border to anchor on. Two alternatives also failed during iteration: `modalSepRe.Split` (returns one segment for Read modal), and walk-back-N-newlines from the marker (different N needed per modal variant; no universal value works). The last-dash-run anchor is robust because both Bash and Read modals prefix the modal block with a long horizontal-dash run even though the surrounding layout differs.
- **`oscRe` was added alongside `ansiRe` for text extraction.** Claude emits OSC sequences (`\x1b]...BEL`) for window-title metadata throughout the PTY stream. The spec's "ANSI strip" sketch only mentioned CSI sequences; in practice the OSC payloads contaminated the stripped buffer enough that the literal-text predicate would have to match around them. Stripping both CSI and OSC first is cleaner. `oscRe = regexp.MustCompile(`\x1b\][^\x07]*\x07`)`.

Five green runs with the default `-approve-keystroke 1-enter -modal-predicate literal-text`. Total wall ~24–27 s per run. The `modal-cleared → end-turn-detected` gap is consistently small (~300–400 ms) — the `end_turn` envelope arrives within ms of the modal clearing on the PTY side.

## Patterns established

- **Modal detection is PTY-side, predicate is literal-text.** Two predicate variants implemented behind `-modal-predicate`; the cheap box-drawing predicate (`bytes.ContainsAny(stripped, "╭╮╰╯│─┌┐└┘├┤")`) fires at idle because claude's own input box uses box-drawing for its border — `idle-predicate-check has_modal=true` baseline makes the cheap predicate structurally unusable. The literal-text predicate (substring match against `Esctocancel`, `Doyouwanttoproceed`, and `Do you want to proceed`) is false-positive-free at idle. The eventual `pkg/tuidriver/` modal detector should ship literal-text as the default. A region-restricted box-drawing predicate (ignore anything inside the input box's known position) is a possible future enhancement but not worth the bookkeeping until literal-text breaks against a new claude version.
- **Dual-form substring matching for tool-dependent rendering.** Claude's permission modal renders the proceed-prompt text two different ways depending on which tool is being requested — Bash uses CSI cursor-forward between every word (stripped output has NO interword spaces); Read uses literal spaces (stripped output has normal spacing). Both forms must be in the literal-text predicate set. This generalises: any pattern-match against claude TUI text that's known to be tool-dependent should carry both space-stripped and space-literal variants in the match set until proven otherwise. The "Esctocancel" marker is the safest universal anchor — it's CSI-rendered in both cases.
- **Modal text extraction via last-`─{20,}`-run-before-marker anchor.** Anchored start (last horizontal-dash run preceding the proceed-marker), anchored end (line containing `Esctocancel`), strip box-drawing borders + whitespace per line, drop empties, join with `\n`. Robust across both Bash and Read modal variants observed. Documented in `extractModalText`'s comment block. The two alternatives that failed (`modalSepRe.Split` + take-segment-with-marker; walk-back-N-newlines from marker) are noted so future readers don't redo them.
- **OSC strip alongside CSI for text extraction.** `oscRe = regexp.MustCompile(`\x1b\][^\x07]*\x07`)` removes the window-title metadata claude emits throughout the stream. The future library should treat OSC strip as part of "normalise the PTY buffer to inspectable text," not as a separate concern.
- **Two-session orchestration for "I need a fresh permission prompt to validate the recovery, but the prior session deliberately left a modal open."** Probe 1 SIGTERMs claude with the modal still rendered; Probe 2 needs a clean session to validate the auto-respond → `SUCCESS` path; Probes 2 + 3 share Session B because the AC specifies "in the same session" for the escalation probe. `runSession` is the per-session driver (owns PTY allocation, reader, watchdog, tailer-open hook, shutdown defer; takes a probe list); `run` calls it twice with different `(sessionID, probes)` pairs. Future modal-class spikes (multiselect, trust-workdir) will likely want the same shape — at minimum a fresh session for the "observe with modal open" probe, and a shared session for "do X and recover."
- **Different tool in Probe 3 forces a fresh permission prompt.** Probe 2 approves Bash (`list the files in /tmp`); Probe 3 uses Read (`read /etc/hostname`) so claude does NOT silently honour any "yes, allow X from this project" Probe 2's option-2 grant might have created. Probe 3 explicitly uses option-1 (single-shot) semantics for Probe 2 to keep the grants narrowest, but using a different tool is the belt-and-suspenders defense. Future spikes that need "two fresh permission prompts in one session" should follow the same pattern: never trigger the same tool twice and expect both modals to fire.
- **Tempfile snapshots for raw modal bytes use `os.OpenFile(..., O_WRONLY|O_CREATE|O_TRUNC, 0600)`, not `os.WriteFile`.** The spec's security review required explicit 0600 mode (defensive against multi-user systems); the spike's `writeTempSnapshot` helper bakes it in. Pattern: any raw-PTY-byte capture the library or future spikes write to disk should go through a 0600-mode helper, not a default-0644 convenience function.
- **`sendKeystroke` (renamed from spike #11's `sendCancel`) is the canonical single-byte bulk-write helper.** The cancel keystroke and the approve keystroke share semantics: short byte slice, one `pty.Write`, no inter-byte delay, `\r` is intentional iff included in the byte slice. The rename is the right shape — the writer is generic; the keystroke choice is the variable. The eventual library should expose a generic `WriteKeystroke([]byte)` (or similar) separate from the char-by-char `typePrompt` path; they have structurally different write semantics and conflating them costs the prompt-submission reliability that `typePrompt` painfully achieves.

## Lessons learned

- **The "ZERO JSONL footprint" finding closes the modal-detection design question.** Pre-spike, the modal could plausibly have signaled in the JSONL via a new envelope type, a new `stop_reason` value, or an embedded field on the deferred `assistant` event. Five runs confirm: none of those. The assistant message claude eventually writes (post-approve) is shaped identically to a non-modal tool-use turn — the modal is purely a PTY-side affordance. This is structurally analogous to spike #11's finding for cancellation (also lives on a signal path the JSONL tailer doesn't surface), and the architectural rule emerges: **modal class events and cancellation live on PTY rather than JSONL; consumers needing those signals must subscribe to the PTY-side state stream the library will expose, not the JSONL stream.** The post-spike library API should make this distinction explicit.
- **The cheap predicate was always going to fail at idle.** `hasModal` via "any box-drawing char in the stripped buffer" would have been the simpler implementation, but claude's input box border uses `╭ ╰ │` continuously — false-positive at idle was structurally guaranteed once the spec called the false-positive baseline out as an open question. The cheap predicate was useful as a deliberately-shipped diagnostic (the `-modal-predicate box-drawing` flag is the only way for a future reader to reproduce the false-positive baseline without rebuilding the predicate from scratch) but never as a runtime default. Lesson: when the spec flags a false-positive baseline as something the spike must measure, it's because the predicate is plausibly unusable; design the spike so the baseline measurement is also the deprecation evidence.
- **Tool-dependent rendering is a real source of detection-pattern flakiness.** The Bash-vs-Read divergence (`\x1b[1C` between words for Bash, literal spaces for Read) is the same root cause as spike #1 finding #8 for the spinner verb — claude's TUI selectively renders text via CSI cursor-forward when the layout requires precise positioning. Both forms must be in the match set. Generalising: any literal-text pattern the library matches against claude's TUI output should be **dual-form** (with and without interword spaces) unless the spike's evidence shows a particular phrase is universally one or the other (`Esctocancel` happens to always be no-space). The detection layer cannot rely on "what the human sees" because that gets reconstructed from cursor movements at terminal-render time, not character-emission time.
- **The first extraction strategy I'd reach for fails for one of the two modal shapes.** Region-based extraction (find the block of `│`-containing lines, strip borders, concatenate) is the natural shape for "modal in a box." But the Read modal has no separate box top/bottom — the dash separator is inline with the modal content on a single line. `modalSepRe.Split` and walk-back-N-newlines both also fail. The working strategy is the LAST `─{20,}` run BEFORE the proceed-marker as the start anchor; that's robust because both variants prefix the modal block with a long dash run regardless of whether the rest of the layout is multi-line-bordered or inline-bordered. Generalising: extraction strategies for TUI structures should anchor on the **most resilient single feature** across variants, not on assumptions about overall layout shape.
- **OSC sequences contaminate the stripped buffer in ways the spec didn't flag.** The spec talked about ANSI strip in CSI terms only; in practice the OSC payloads (window-title metadata) showed up in the literal-text matches and forced the predicate to either tolerate trailing OSC text on otherwise-matching lines, or strip OSC first. Stripping first is much cleaner; the `oscRe` predicate (`\x1b\][^\x07]*\x07`) is a 1-liner. Generalising: any "ANSI strip" pass intended to normalise PTY output for text inspection should strip BOTH CSI and OSC sequences. The library's text-normalisation helper should bake both in by default.
- **Probe 3's "different tool to force a fresh modal" was load-bearing.** Probe 2 approves Bash with `1\r` (single-shot grant); Probe 3 then triggers a new permission prompt by switching to Read instead of by reissuing the same Bash prompt. The Probe 2 grant is supposed to be single-shot, but defending against "claude remembers the prior approval" via tool switching is cheap and unambiguous. If Probe 3 had used Bash too and gotten no modal, the spike wouldn't have known whether the missing modal was a claude bug, a config issue, or a deliberate "yes for the rest of this session" behavior. The Read switch eliminates that ambiguity. Generalising: future modal-class spikes that need "two fresh modals in one session" should use distinct tools as the trigger, not the same tool with the same grant scope.
- **`modal-detected → response-keystroke-sent` is effectively zero, no debounce needed.** The 50 ms poll interval means the first `hasModal` true → next tick fires the keystroke; observed gap is well under 1 ms (Go's `log` library's microsecond resolution shows 0 ms in the logs). No flake where the predicate fires then unfires before the keystroke can be sent. The library doesn't need a "modal stable for N ms" check before responding — the first detection is reliable. Useful piece of context for designing the auto-respond API: it can be edge-triggered, not level-triggered with a debounce.
- **The cleanup posture from spike #11 carries forward unmodified.** `pgrep -lf 'claude --session-id'` returns nothing after all observed green runs even though Probe 1 deliberately SIGTERMs claude with the modal still rendered. No "stuck modal" failure mode. The shutdown defer's SIGTERM → 3 s grace → SIGKILL → close PTY chain handles permission-prompt state the same as any other state. Pattern from spikes #9 and #11 (no process-group kill via `Setpgid`; rely on SIGTERM + pgrep verification) is sufficient for this spike too; the library extraction can revisit it as a single policy decision when there's enough integration pressure to justify the bookkeeping.
