# #64 — e2e: drop version pin from `claude-version-lock`; keep flag + value presence checks

[Issue](https://github.com/pyrycode/tui-driver/issues/64) · [Spec](../../specs/architecture/64-claude-version-lock-policy.md) · [PR #65](https://github.com/pyrycode/tui-driver/pull/65) · Feature doc: [e2e harness](../features/e2e-harness.md)

## Summary

`claude-version-lock` previously asserted strict string equality between `parseClaudeVersion(claude --version)` and `lockFile.Version`, AND that every pinned `flag=` / `value=` entry still appeared as a substring of `claude --help`. Both had to pass for the check to be green. The version-equality assertion is **removed** — claude patch drift between the installed binary and the lock's `version=` field is now intentionally tolerated. The flag/value presence loops are unchanged: any pinned flag or value missing from `claude --help` still produces an actionable FAIL with `missing_flags` / `missing_values` populated and per-line stderr (`claude --help no longer mentions {flag,value} X; review <lockPath>`). The check still runs first, still emits the same four `extra` fields on every code path (`installed_version`, `expected_version`, `missing_flags`, `missing_values`), and still short-circuits the rest of the run on a non-pass status — only the equality branch and its `claude version X does not match …` stderr line are gone. Implementation extracts a pure helper `evaluateClaudeVersionLock(lf, installedVersion, helpOut) (status, extra)` from the I/O-laden `runClaudeVersionLockCheck` wrapper so the new "patch drift above lock + flags present → PASS" and "missing flag/value → FAIL with named entry" behaviours are mechanically table-tested in `TestEvaluateClaudeVersionLock` (9 rows) without requiring a real `claude --help` exec. Wrapper signature unchanged; closure built in `main` calls it identically; `parseLockFile` and `parseClaudeVersion` untouched (the lock's `version=` line is still required at parse time as a grep target for the snapshot-drift re-record discipline, just no longer enforced at runtime). Lock-file leading comment block updated to encode the new policy: "version= informational; flag=/value= enforced." Concrete impact: #57 burned 4 code-review cycles where every per-diff verdict was PASS and every FAIL was the equality assertion firing on reviewer-side claude auto-updates (2.1.144 → 2.1.146 across three machines in ~30 minutes). That spurious-FAIL class is closed; the substantive flag/value contract is preserved.

## Patterns established

- **Pure-function extraction is the right shape when a check's pure logic is wrapped in unavoidable I/O.** `runClaudeVersionLockCheck` does four I/O things (read lock file, exec `claude --help`, emit stderr lines, branch on captured-version sentinel) interleaved with pure logic (substring containment + status derivation). Extracting `evaluateClaudeVersionLock(lf, installed, helpOut) (status, extra)` lets the table test cover the AC scenarios (patch drift above/below lock; minor drift; missing flag/value; both; drift + missing) without faking exec or filesystem. The wrapper iterates the helper's returned `missing_flags` / `missing_values` to emit the per-line stderr. This shape generalises to any future in-process check whose I/O surface is incidental to the assertion it makes — extract the assertion as a pure helper, leave the I/O in the closure built by `main`.
- **`failExtra(installed, expected)` closure for early-return failure paths.** Three paths in `runClaudeVersionLockCheck` short-circuit before reaching `evaluateClaudeVersionLock`: lock-file missing/parse error, `capturedVersion == "unknown"`, `claude --help` exec failure. Each must still return the canonical four-field `extra` map. A top-of-function `failExtra := func(installed, expected string) map[string]any { return map[string]any{...} }` keeps the literal map shape in one place; the success path lets the helper produce its own `extra` (overwriting any pre-built outer map was a real NIT the first cycle's review caught — see "Lessons learned" below). Reusable for any future in-process check with multiple early-return failure modes that share an extra-map schema with the success path.
- **Drop a proxy assertion when it adds no signal beyond a direct assertion downstream of it.** The version-equality assertion was a proxy for "the flags we expect are where we expect" — but the flag/value presence loop already asserts that directly. Removing the proxy did not weaken the substantive contract; it closed a spurious-FAIL class entirely. Generalises: when two assertions are in series and one is a proxy for the other, ask whether the proxy catches anything the direct check doesn't. If not, prefer dropping the proxy to layering "and also" gates.
- **Direction-agnostic policy framing for tolerated drift.** The new test table includes both "patch drift above lock" and "patch drift below lock" rows (and a "minor drift above lock" row), all → PASS. The policy is "version mismatch is informational only," not "newer versions allowed." This avoids a comparator (lexicographic fails on `2.1.9` vs `2.1.10`; cross-major edge cases) and matches the substantive intent — the lock no longer gates on the version field at all. Future drift-tolerance policies should similarly avoid implicit "above OK / below not" semantics unless the comparator is explicitly load-bearing.

## Lessons learned

- **A code-review NIT can be acted on by a follow-up commit on the same branch — the dispatcher's gate is per-PR, not per-commit.** PR #65 cycle 1 review left a "[NIT] outer extra-map init is silently overwritten" observation against commit `080cea8`. Cycle 2 addressed it via `2a814ca` (introduce `failExtra` closure; drop the outer init and `extra["expected_version"] = lf.Version` set). The fix landed despite the e2e gate still being red on out-of-scope fixture drift (`spike-multi-turn`, `spike-cancel`, `spike-permission`, `spike-ask-user`, `snapshot-drift` all failing under reviewer-side claude 2.1.146). The reviewer's cycle-2 verdict treated the NIT as a clean follow-up and confirmed per-diff PASS. Reusable: a non-blocking NIT does not require a separate ticket when the fix is mechanical and the developer is mid-rework cycle anyway — fold it into the next commit.
- **Reviewer-side claude drift is the failure surface this ticket exists to close, and the ticket's own review cycle proved it.** The PR #65 review record empirically confirmed the fix: reviewer's claude was 2.1.146; lock pinned 2.1.144; the new `claude-version-lock` policy passed in 89 ms with `missing_flags=[]`, `missing_values=[]`. The remaining red checks (TUI-byte-stream cascades) are the exact failure mode [#47](47.md)'s lock+fixture coupling lesson names — those would have masked the version-lock failure under the old policy, hiding nothing useful. Generalisable observation: when a ticket's purpose is "close failure mode X," the ticket's own review cycle is the cleanest place to verify X is closed — operator-override pressure on the remaining red checks is a *separate* failure surface with its own ticket-shaped solution.
- **The `version=` field's required-at-parse-but-not-enforced-at-runtime semantics is load-bearing for the snapshot-drift discipline, not just historical inertia.** A first-cut "drop the field entirely from the lock file" approach would have saved 1 line of parser code and removed a grep target that re-record sweeps depend on. The maintainer who re-records `pkg/tuidriver/testdata/{picker,mcp,agents}-snapshot.bin` (or the spike fixtures) needs to know which claude version those fixtures were captured against; `grep '^version=' claude-version.lock` is the canonical answer. Keeping the field required at parse (with no runtime check) costs zero and preserves the annotation. Generalisable: when narrowing a configuration field's semantics, ask whether downstream tooling (or human convention) reads the field for purposes orthogonal to the original gating role. If yes, narrow the semantics without dropping the field.
- **Operator override remains the escape hatch for cascading fixture failures, even after this ticket closes the spurious-version-lock-FAIL class.** PR #65's gate ended red despite the per-diff change being correct because reviewer-side claude 2.1.146 caused `spike-multi-turn`, `spike-cancel`, `spike-permission`, `spike-ask-user`, and `snapshot-drift` to fail against fixtures recorded at 2.1.144 — Option C territory from the ticket body, explicitly carved out of scope per spec § "Out of scope: `snapshot-drift` behaviour." Resolution mirrors [#57](57.md)'s `56d947f`: operator manually advances `done:code-review` → documentation. The cascade is the next ticket-shaped problem (atomic lock-bump + fixture re-record sweep). Reusable: closing one spurious-FAIL class does not close all of them; track the next one as a separate ticket rather than expanding the current ticket's scope to chase it.
