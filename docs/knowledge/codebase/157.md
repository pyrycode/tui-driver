# #157 — emit the idle/thinking rising edge even when a modal was active

[Issue](https://github.com/pyrycode/tui-driver/issues/157) · [Spec](../../specs/architecture/157-idle-edge-across-modal.md) · Predecessors: [#61](61.md), [#100](100.md)

## Summary

Fixed the deferred `prev*`-update leak first flagged on #61's PR #94 review (decision PASS-with-flag) and re-deferred by #100. `mergeEvents` suppresses idle/thinking rising-edge emissions while any modal is active (the modal axis dominates — a permission/trust/MCP prompt paints `❯` with no busy anchor, so `IsIdle` would otherwise fire a false "ready for next prompt" signal), but `prev = cur` ran unconditionally at the end of every tick. Because the modal renders `❯` throughout its lifetime, `IsIdle` classified the buffer idle across the whole modal-active window and `prev.idle` quietly became `true` *while emission was suppressed*. When the modal then cleared with claude still idle, the clear tick computed `cur.idle=true && !prev.idle=true → false`, so no `EventKindPtyIdle` fired after `EventKindPtyModalHidden` — hanging any "answer the modal, then wait for idle" consumer (e.g. pyrycode's permission auto-answer daemon / ptyrunner's continuous modal monitoring, [pyrycode#513](https://github.com/pyrycode/pyrycode/issues/513)).

The fix is candidate **(a)** from #61's review — *symmetric suppression of the `prev` trackers*: a single guard immediately before the existing `prev = cur`, `if cur.modal != ModalClassUnknown { cur.idle, cur.thinking = prev.idle, prev.thinking }`. While a modal is active the idle/thinking `prev` trackers are frozen at their pre-modal values, so the pre-modal rising edge survives the modal window and fires on the clear tick — after `EventKindPtyModalHidden`, which the modal-dominance block above already emits first. Three production lines + a 10-line comment in `events.go`; one additive test in `events_test.go`. No new exported symbols, no signature changes.

## Patterns established

- **When you suppress emissions on one axis based on another axis's state, freeze the suppressed axis's `prev` trackers symmetrically.** This is the invariant #61 identified and this ticket finally applies: *updating `prev*` without emitting is the failure mode*; the compensation is either (a) freeze the `prev` trackers symmetrically with the emission suppression, or (b) force-emit the suppressed axes on the suppressing-axis-clear transition. (a) was chosen and is the smaller, safer diff — it adds **no** emission path, only changes what advances into `prev`, so it can't double-emit. (b) was rejected because it fires idle on *every* modal clear where `cur.idle` holds (including the "idle already emitted before the modal" case), producing a phantom "rising edge" that isn't a real `false→true` transition — a strict-edge consumer would see a spurious duplicate. Reuse posture: any future axis added to the merge loop that is suppressed under modal dominance must freeze its `prev` tracker under the same guard; the guard is the single extension point.
- **Rewrite `cur` (not a field-wise `prev` update) at the end of the ticker arm — it's the minimal, safe shape.** `prev = cur` is the last statement in the arm and nothing reads `cur` after it. Every emission decision on the tick — modal, idle/thinking, banners, stall — has already run against the *classified* `cur` before the freeze line. Overwriting `cur.idle`/`cur.thinking` there therefore affects only what carries into `prev` for the next tick, which is exactly the intent, and it preserves the clean single `prev = cur` assignment. Critically, this is safe *because* `stalled` is the one `ptyState` axis `classify` does **not** set: `cur.stalled` is computed inline earlier in the arm (from the quiet timings) and the stall emitter reads `prev.stalled`, so freezing `cur.idle`/`cur.thinking` at the tail cannot perturb the stall axis. Reuse posture: mutate `cur` at the `prev = cur` site to change next-tick carry-over; never earlier in the arm, where it would corrupt this-tick emission decisions.
- **A test that transitions through a resetting intermediate state masks a suppression-leak bug — reproduce the *direct* path.** `TestMergeEvents_ModalShowAndHide` passes today and *masks* the bug: it transitions Permission → MCP → idle, and the MCP detour snapshot (`ManageMCPservers`, no `❯`) resets `prev.idle` to `false`, so the idle edge happens to coincide with the modal clear and is emitted. The new `TestMergeEvents_ModalClearRevealsSuppressedIdleThenThinking` drives the direct Permission → idle path (`❯` present throughout the modal's lifetime, then cleared while still idle) — the exact shape that leaked the edge. It fails against the pre-#157 code (times out waiting for `EventKindPtyIdle`; only `ModalHidden` arrives) and passes after. Reuse posture: when a bug hides behind a happy-path test, the regression test must exercise the path *without* the incidental reset — here, no MCP detour.

## Lessons learned

- **The #61-recommended fix was correct on the first pass three tickets later — because the invariant was written down.** #61's Lessons named the mechanism, both candidate fixes, and the recommendation ((a), "minimal and symmetric"); #100 documented *why* it deliberately kept the two banner axes non-suppressed so they wouldn't reproduce the leak shape. By the time #157 opened, the fix contract was fully pre-decided — the architect's job was choosing (a) over (b) with the trade-off already spelled out, and the developer's was three lines under one guard. This is the payoff of the "write the cross-axis behaviour down in the codebase doc, not just the code" discipline: a deferred fix stays cheap to pick up because the reasoning didn't have to be re-derived. Reuse posture: when deferring a known bug, record the candidate fixes and the recommendation in the predecessor's `codebase/<N>.md` Lessons — the deferral cost drops to near-zero.
- **The masking test stays green after the fix — for a different internal reason — and that's the correct outcome, not a red flag.** `TestMergeEvents_ModalShowAndHide` (Permission → MCP → idle) passed before the fix because the MCP snapshot reset `prev.idle` to `false`; after the fix it passes because `prev.idle` is *frozen* at `false` across both modal phases. Same observable result, different mechanism. AC 6 required it to stay green unchanged, and it does — but a documentation reader tracing "why does this still pass?" needs the trace, which is why the spec's Testing strategy wrote it out. Reuse posture: when a fix changes *why* an existing test passes without changing *whether* it passes, note the mechanism shift so a future reader doesn't mistake the unchanged green for the fix having no effect on that path.
- **The rising-edge semantics are preserved in both directions — freezing does not double-emit.** When a modal appears while `prev.idle=false` (claude was thinking, or transition-blind start), the freeze holds `prev.idle=false` and the clear tick fires `EventKindPtyIdle` — hang fixed. When a modal appears while `prev.idle=true` (idle already emitted, consumer already notified), the freeze holds `prev.idle=true` and the clear tick computes `true && !true → false` — correctly *no* re-emit, because no new low→high transition occurred. The new test's phases 3–4 pin exactly this: re-entering the modal with `prev.idle` already true emits only `ModalShown`, and clearing to a spinner-present snapshot fires `EventKindPtyThinking` (not a spurious `EventKindPtyIdle`), confirming the freeze applies symmetrically to `prev.thinking`.
