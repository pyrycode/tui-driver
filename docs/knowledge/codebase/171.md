# #171 — Serialize all PTY write paths against one write mutex

[Issue](https://github.com/pyrycode/tui-driver/issues/171) · [Spec](../../specs/architecture/171-serialize-pty-write-path.md) · [PR #215](https://github.com/pyrycode/tui-driver/pull/215) · Commit `a9da2de` (spec `2201573`) · Touches [`keys.go`](../../../pkg/tuidriver/keys.go) + [`session.go`](../../../pkg/tuidriver/session.go) + [`write_serialize_test.go`](../../../pkg/tuidriver/write_serialize_test.go) (new) · Sibling surface: [#136](136.md) (`AttachInput` — the concurrent racer this protects) · Feature doc touched: [attach-mirror-surface.md](../features/attach-mirror-surface.md)

**XS correctness/concurrency fix.** Not `security-sensitive` (verified on the issue labels) — no attacker-influenceable content classification, no auth/parsing/trust surface; a byte-interleaving guard on a shared write FD. No new type, exported symbol, config knob, or signature change: one unexported `writeMu sync.Mutex` field + four lock acquisitions + one one-line simplification.

## Summary

`Session` had several independent write paths onto the same PTY master FD with **no synchronization** between them: the `writeRaw` funnel (all keystroke methods — `AcceptTrust`, `Answer`, `SendEsc`, `Navigate`, `SendKeys`, and the production `AttachInput`) and the prompt-delivery helpers (`WritePrompt`, `TypePrompt`, `ClearInputLine`), which wrote to `s.pty` **directly, bypassing `writeRaw`**. The fix adds a session-level `writeMu` held for the full duration of each *logical* write, so no writer can land inside another's byte stream.

- `writeRaw` (`keys.go:38`) — `Lock()`/`defer Unlock()` around its one `s.pty.Write`. Covers every keystroke path.
- `WritePrompt` (`session.go:307`) — one buffer (`bracketedPaste(text)`), so its body collapses to `return s.writeRaw(bracketedPaste(text))`, inheriting the lock and dropping a duplicated `pty.Write`. **One** acquisition (through `writeRaw`), never a second.
- `TypePrompt` (`session.go:341`) — `Lock()`/`defer Unlock()` at the top, spanning the **entire** byte-by-byte loop + inter-byte `sleepFn` settles + the `\r` commit. Keeps its **direct** `s.pty.Write` calls — must **not** route through `writeRaw` (`sync.Mutex` is non-reentrant → self-deadlock).
- `ClearInputLine` (`session.go:374`) — same shape: `Lock()`/`defer Unlock()` across the Ctrl-U (`0x15`) write + `ClearLineSettle`, direct `s.pty.Write`.

The pipeline ran clean: QA PASS (baseline-compared: no regressions; the two RED e2e checks are pre-existing — see Lessons), code-review PASS (one non-blocking NIT).

## Where the real race was (load-bearing — drives both the design and the test)

Go's `os.File.Write` holds an internal per-FD write lock (`internal/poll.FD.writeLock`) across the **entire** call, including its partial-write retry loop. So two concurrent *single* `os.File.Write` calls on the same `*os.File` **already** cannot split each other at the byte level — `WritePrompt` vs. `AttachInput` (one `Write` each) were never the vulnerability.

The genuine race is **`TypePrompt`'s multi-write sequence**: `len(text)+1` separate `os.File.Write` calls. The per-FD lock serializes each *individual* byte-write but **not the sequence** — any other writer's `Write` (an `AttachInput`, an `Answer`, a `WritePrompt`) could land *between* two of `TypePrompt`'s byte-writes, splitting the prompt and corrupting an escape sequence or the paste boundary. The shared `writeMu` is what protects the multi-write sequence; the per-FD `writeLock` (which the single-write paths already benefit from) does not. Adding the lock to the single-write paths is cheap and makes the invariant uniform — but its *load-bearing* role is serializing them **against** `TypePrompt`.

The original review filing described `writeRaw` as "the single funnel for keystrokes, prompt delivery, and `AttachInput`" — inaccurate against current code (prompt delivery bypasses `writeRaw`). Guarding `writeRaw` alone — the filing's proposed fix — would have left the actually-dangerous `TypePrompt`-vs-`AttachInput` race unguarded. The ticket refinement corrected the scope to *all* write paths, and the spec's design followed.

## Patterns established

- **`writeMu` is the write-side leaf lock — the counterpart to the read-side mutexes.** Before #171 every `sync.Mutex` in the package (`Buffer`, `castRecorder`, `tracker`) guarded read-side state; none guarded the write FD. `writeMu` is now the single serialization point for **every** byte written to `s.pty`. It is a **leaf lock**: while held, the code calls only `s.pty.Write` and `sleepFn`, never another `writeMu`-guarded method and never a different lock — so no lock-ordering deadlock is possible. It does not interact with the reader goroutine (`writeMu` guards writes only; the read side is untouched) nor with `Close`/`Wait` (`Close` does not acquire it, so a writer blocked in `pty.Write` cannot wedge `Close` on the mutex). Any future write path onto `s.pty` MUST acquire it.
- **Funnel single-buffer writes through `writeRaw`; acquire directly for multi-write spans.** The re-entrancy rule is the design's whole subtlety: a one-`Write` helper (`WritePrompt`) reroutes through `writeRaw` for zero new lock code; a multi-`Write` helper (`TypePrompt`/`ClearInputLine`) acquires `writeMu` directly and keeps raw `s.pty.Write` calls, because funnelling a span through the non-reentrant `writeRaw` would self-deadlock on the second acquisition. When adding a write path, ask "one `Write` or many?" — one → `writeRaw`; many → `writeMu.Lock()` + direct `s.pty.Write`.
- **`defer Unlock()`, not a trailing `Unlock()`, on the multi-write paths.** Both `TypePrompt` and `ClearInputLine` `return` on a mid-sequence `pty.Write` error; a bare `Unlock()` at the end would leak the lock on that early return and deadlock every subsequent writer. `defer` releases on every path.
- **Holding the lock across the inter-byte sleeps is the intended semantics, not a cost to minimise.** `TypePrompt` holds `writeMu` for the whole prompt-typing span (payload length × `PromptInterByteDelay` + `PromptCommitSettle`), blocking any concurrent writer — including an `AttachInput` keystroke from an attach head — for that duration. This is deliberate and AC-blessed: a keystroke injected *mid-prompt* would corrupt the prompt. The hold-duration tradeoff was explicitly confirmed acceptable in the spec's concurrency section and documented on the `writeMu` field + `TypePrompt`'s comment.

## Lessons learned

- **`-race` alone cannot prove this fix — the test must race `TypePrompt`'s multi-write sequence.** Go's per-FD `writeLock` already serializes each single `os.File.Write`, so a concurrency test that raced only single-write paths (`WritePrompt` vs. `AttachInput`) would pass **even without the lock** — a false green. This is the concrete form of the AC's "`-race` alone will not prove serialization." `TestWriteSerialize_NoInterleave` therefore uses **two `TypePrompt` writers** (alphabets `A` and `C`) racing one `AttachInput` (`B`) over an `os.Pipe` (lossless, order-preserving — no rolling-buffer cap or drop-newest to confound the assertion), swaps `sleepFn` for `runtime.Gosched` to force a scheduling point between every byte-write (widest interleaving window, sub-second runtime), and asserts every maximal single-letter run is exactly `markerLen` (a foreign byte inside a run splits it) **and** the complete-token count per alphabet equals the write count (catches drops). Self-checked once by removing only `TypePrompt`'s lock → the run-length assertion fails on a split run, proving the test has teeth. When a fix's correctness *is* a concurrency policy, the highest-value test exercises the exact failure the policy prevents — same lesson shape as [#136](136.md)'s "never-drain-then-`Close` returns" test.
- **The uncontended path is unaffected — which is why the QA flakes are not regressions.** `spike-one-turn` (a single-writer one-turn flow, `writeMu` uncontended) flagged a naive single-run FAIL but re-sampled 3/3 PASS — the known flake [#185](185.md), not a serialization bug (a real one would fail deterministically). `spike-permission` TIMEOUT is the deterministic pre-existing hang [#180], RED on baseline too. QA's baseline-comparison verdict: no regressions introduced. (Memory `snapshot-drift-tracker-deferred` / `qa-baseline-run-hygiene` — single-run comparison is defeated by flaky checks; override with deterministic re-sampling, not reasoning.)
- **This lock's home is tui-driver, and the consumer already deferred it here.** pyrycode's #595/#597 (`pyry attach` two-heads) explicitly **declined** to add a PTY-write mutex on the consumer side: *"the only correct place for such a lock is tui-driver (it owns `s.pty`)… shipping a lock now would defend an unobserved failure"* (Evidence-Based Fix Selection + owns-the-resource). #171 is that lock landing on the correct side — surfaced by the Cross-Repo Code Review 2026-07-03, where the byte-interleaving concern was strong enough to warrant the guard now that the attach surface ([#136](136.md)) makes concurrent writers a real production shape, not a hypothetical.

## Deferred / follow-ups

- **`DeliverPrompt` clear-then-write atomicity — out of scope, deliberately not implemented.** `DeliverPrompt` (`deliver.go`) calls `ClearInputLine` then `TypePrompt`/`WritePrompt` as **two separate** locked operations; `writeMu` is released between them, so a concurrent writer could still inject in that gap. Making the whole clear+deliver sequence atomic is a higher-level concern (a different lock scope + a policy question about whether an attach keystroke should ever preempt an in-flight delivery). Flagged in the spec so the lock was **not** widened to span `DeliverPrompt`. Build it only if an observed consumer needs cross-call atomicity.
- **Write-after-`Close` ordering — out of scope (ticket).** A write racing a `Close` still returns the closed-file error; `writeMu` does not change that. Separate lifecycle concern.
- **NIT (pre-existing, not introduced): `WritePrompt`'s doc comment** (`session.go:305`) still says short prompts "should still use `Write`, not `WritePrompt`", but the public `Write` seam was removed at the v1.0.0 seal (the current alternatives are `Answer("1")` / `TypePrompt`). Flagged in the [#215](https://github.com/pyrycode/tui-driver/pull/215) code review only because this PR touches `WritePrompt`'s body; never blocks. Same stale-`Write`-reference family as the [#136](136.md)-flagged `Session` struct doc comment — worth folding into a future doc-sweep ticket.
