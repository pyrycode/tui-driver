# #112 — spike-cleanup: migrate spike-one-turn + spike-multiselect off duplicated helpers

[Issue](https://github.com/pyrycode/tui-driver/issues/112) · [Spec](../../specs/architecture/112-spike-cleanup-one-turn-multiselect.md) · [PR #115](https://github.com/pyrycode/tui-driver/pull/115) · Predecessors: [#58](58.md), [#59](59.md), [#60](60.md), [#62](62.md), [#87](87.md), [#89](89.md), [#97](97.md)

## Summary

Mechanical deletion-heavy migration that closes two of the six [#89](89.md) follow-ups. `cmd/spike-one-turn/main.go` and `cmd/spike-multiselect/main.go` now consume library primitives instead of hand-rolled copies, following `cmd/spike-long-prompt/main.go` as the canonical post-migration shape. spike-one-turn drops `projectsDir` / `openSessionJSONL` / `tailJSONL` / `isEndTurn` / `extractAssistantText` / `matchSpinner` + `spinnerRe` and the wg-driven tail goroutine and the inline 1 Hz watchdog goroutine; spike-multiselect drops `matchSpinner` + `spinnerRe` + the inline watchdog goroutine. Net diff: 311 lines down (49 added, 262 removed) across two files. The four `func`-named ACs grep returns empty; `go build ./...`, `go vet ./...`, `go test -race ./...`, and `make e2e` all pass; the three snapshot-drift fixtures (`picker`/`mcp`/`agents`) match.

The non-mechanical part of the diff is two specific shape choices the spec called out. First, **the PTY-quiescence termination predicate at `cmd/spike-one-turn/main.go:188-227`** (the `check()` closure + outer `for !check()` ticker loop, with the three-clause conjunction `gotEndTurn && bytes.Contains(StripANSI(snap), tuidriver.IdleGlyph) && rb.QuietFor() >= ptyQuietWindow`) is preserved byte-for-byte — including the ~60 lines of rationale comments citing [#97](97.md). spike-long-prompt's event-driven `gotEndTurn && (!thinkingObserved || spinnerGone)` shape was the wrong template here; [#97](97.md) documented the 1/5 wedge rate that shape produced against `claude 2.1.150`, and the architect explicitly forbade collapsing. Second, **the channel-close sentinel** at `cmd/spike-one-turn/main.go:237-244`: when `TailJSONL`'s library-owned goroutine closes `eventCh` on rootCtx-cancel, the naive `case ev := <-eventCh` would ready-receive the zero value at every tick and spin the select. The fix is `case ev, ok := <-eventCh:` + `if !ok { eventCh = nil; continue }`. A `nil` channel in a `select` case is the Go idiom for "this case is permanently disabled"; the loop continues ticking until `check()` flips or the watchdog wedges rootCtx.

`resolveSession` was reshaped to mirror spike-long-prompt L283 — takes only `flagValue string`, returns `(sessionID, err)`, no `dir` arg, no `jsonlPath` return. The caller composes `home, err := os.UserHomeDir(); cwd, err := os.Getwd(); jsonlPath := tuidriver.SessionJSONLPath(home, cwd, sessionID)` directly. The legacy `projects-dir path=...` startup log line is dropped (already dropped from spike-long-prompt — `jsonl=...` contains the projects dir suffix); the e2e harness does not assert on that line and no consumer noticed.

Four follow-ups from [#89](89.md)'s list remain: `spike-multi-turn`, `spike-cancel`, `spike-permission`, `spike-ask-user`. Each is the same shape as the spike-multiselect half of this PR (watchdog goroutine collapse + `matchSpinner` + `spinnerRe` + `watchdogTick` + `regexp` import deletions). spike-ask-user additionally has [#87](87.md)'s `TypePrompt` migration outstanding; the two extractions are orthogonal and either can land first.

## Patterns established

- **Migrate-to-template, not rebuild-on-template.** spike-long-prompt is the canonical post-extraction shape for "consume the library primitives," but it is **not** the canonical shape for the consumer's predicate logic. Where the consumer's local logic intentionally diverges from the template — here, spike-one-turn's PTY-quiescence termination per [#97](97.md) — the migration touches the helper-replacement sites and **stops**. Don't extend the diff to collapse the divergent predicate onto the template's event-driven shape "for consistency"; the divergence is load-bearing and was paid for in a separate ticket. Reuse posture: when porting a binary onto a library that has a sibling reference consumer, draw the diff boundary at "replace helpers + add channel-close handling," not at "make this look like the reference consumer." The spec frames this as "the two `main` files should look like spike-long-prompt's, not like spike-long-prompt-but-improved" — the inverse also holds: not like spike-long-prompt-stripped-of-divergent-rationale either. Look at the rationale comments in the existing file before deciding what to preserve.
- **Channel-close sentinel for library-owned goroutines that close their output on ctx-cancel.** `TailJSONL` (and any future library primitive that returns `<-chan T, error` and owns a goroutine internally) closes the output channel when its rootCtx is done. Consumers selecting on that channel inside a longer-lived loop need `case ev, ok := <-eventCh:` + `if !ok { eventCh = nil; continue }`. The `nil`-channel assignment is the Go idiom: a `select` case reading from a `nil` channel blocks forever, so the case is permanently disabled and the loop only fires on its other cases. Without the sentinel, the closed-channel ready-receive of the zero value spins the select at every tick — a hot loop disguised as a poll loop. Reuse posture: any consumer composing a library `Events()`-style channel into a longer-lived outer loop (i.e. a loop that survives the producer goroutine's exit) needs this pattern. spike-long-prompt's `for ev := range events` shape side-steps the issue because the `range` loop exits on channel close; binaries with a separate termination predicate (spike-one-turn's `for !check()`) need the sentinel.
- **resolveSession-shape reduction is a generic post-extraction simplification.** Pre-extraction, the helper returned `(sessionID, jsonlPath, err)` because it owned `projectsDir` composition. Post-`SessionJSONLPath`, the path composition is a three-line caller-side recipe (`UserHomeDir` + `Getwd` + `SessionJSONLPath`) and the helper collapses to `(sessionID, err)`. Reuse posture: when migrating a consumer onto a library API that absorbs a composition step, look for adjacent helpers whose return tuples included the absorbed step's output — those tuples shrink, and the call sites get easier to read. Don't keep the wider tuple "for symmetry" with the pre-migration shape; the symmetry is gone.

## Lessons learned

- **The `sync.WaitGroup` in spike-one-turn was already vestigial pre-migration — declared, never `.Wait()`'d.** Pre-migration, `var wg sync.WaitGroup` was declared with two `wg.Add(1)` calls (the watchdog goroutine + the tailer goroutine), but no `wg.Wait()` call existed anywhere in the file (`grep -n wg.Wait cmd/spike-one-turn/main.go` was empty). The watchdog and tailer were lifecycled by rootCtx cancellation, not by WaitGroup synchronisation, and the `Add(1)` + `defer Done()` pairs were doing nothing observable. The migration deletes the WaitGroup entirely — spike-long-prompt's mirror has none either — and the binary behaves identically. Lesson: when migrating a spike, audit the surviving synchronisation primitives against their actual call sites. Vestigial wg/once/mutex declarations are common in spikes that started life with a different concurrency shape and got refactored around. The migration is the right moment to delete them — leaving the declaration in place after extraction would have invited a future reader to assume the goroutine lifecycle depends on it, which it doesn't.
- **Import-list deletions scaled with helper count, exactly matching [#87](87.md)'s prediction.** [#87](87.md)'s lesson set noted that the deletable imports are the ones unique to the deleted helpers. spike-multiselect dropped only `regexp` (one helper deleted: `matchSpinner`). spike-one-turn dropped seven (`bufio`, `encoding/json`, `io`, `path/filepath`, `regexp`, `strconv`, `strings`) — exactly the set that traced uniquely to `tailJSONL`'s reader stack + `projectsDir`'s path composition + `matchSpinner`'s regex + `extractAssistantText`'s `strings.Builder`. The "cheap check is `go vet`" advice held: vet flagged each unused import on its own line, no archaeology required. Reuse posture: when planning the remaining four [#89](89.md) follow-ups, expect one-to-three import deletions per binary (the multi-turn / cancel / permission / ask-user spikes have less surface than spike-one-turn but more than spike-multiselect). The pattern is "delete the helper, run `go vet`, delete what vet flags" — no need to pre-compute the import diff.
- **The `projects-dir` log-line drop produced zero downstream churn — the e2e harness does not assert on per-binary startup log surfaces.** The spec flagged this as an "Open question" with an explicit cost ladder: keep it = one extra `logger.Printf` + restore the `path/filepath` import; drop it = match spike-long-prompt verbatim. The drop was the right call: the `jsonl=` line that survives contains the same path information (the `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` path's `Dir` IS the projects dir), and the e2e harness's spike-one-turn assertion is exclusively on the `SUCCESS: <text>` stdout line. Lesson: when a migration debates dropping a log line that's not asserted-on and not user-facing, the default is "drop." Bringing back an import just to preserve a redundant log line is the wrong cost trade. The architectural value of the log line — startup observability — is preserved by the surviving `session-id-resolved id=... jsonl=...` line.
- **`TailJSONL`'s silent-parse-warning behaviour is a quality-of-implementation regression in theory, a no-op in practice.** Pre-migration `tailJSONL` emitted `jsonl-parse-warning err=%v` for malformed JSON lines; library `TailJSONL` silently `continue`s on parseEntry-returns-false. The spec flagged this as acceptable because claude's JSONL writer is deterministic and malformed lines have never been observed in the wild. Three weeks of production drift later (#103 / #104 added typed accessors over `JSONLEntry`; neither surfaced a parse anomaly), the prediction holds. Lesson: a diagnostic-only log line whose underlying failure mode has zero observed instances is a fair drop during library extraction. If the failure mode ever surfaces, the right place to surface it is inside the library (one log line at the parse site, behind a `WatchdogOpts`-style `Logger` field) — not back in the consumer.
