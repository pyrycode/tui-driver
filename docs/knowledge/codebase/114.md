# #114 — spike-cleanup: migrate spike-ask-user + probe-first-prompt-hang off duplicated helpers

[Issue](https://github.com/pyrycode/tui-driver/issues/114) · [Spec](../../specs/architecture/114-spike-cleanup-ask-user-and-probe-first-prompt-hang.md) · Commit `e41c1b5` · Predecessors: [#9](9.md), [#58](58.md), [#59](59.md), [#60](60.md), [#71](71.md), [#87](87.md), [#89](89.md), [#97](97.md), [#103](103.md), [#112](112.md), [#116](116.md), [#117](117.md), [#118](118.md)

## Summary

Closes the spike-binary cleanup arc opened by [#112](112.md). The last two non-typing binaries — `cmd/spike-ask-user/main.go` and `cmd/probe-first-prompt-hang/main.go` — drop their local `projectsDir` / inline `filepath.Join` (path composition), `openSessionJSONL` (file-appearance poll), `tailJSONL` / `tailJSONLAll` (line-reader loop), `isEndTurn` (terminator predicate), and — in spike-ask-user only — the inline 1 Hz watchdog goroutine plus `spinnerRe` + `matchSpinner`. Substitutions are mechanical: `tuidriver.SessionJSONLPath`, `tuidriver.WaitForSessionJSONL` (wrapped in a `sessionFileWait`-bounded ctx), `tuidriver.TailJSONL`, `tuidriver.IsEndTurn`, and `tuidriver.RunWatchdog`. Two files in one commit: 70 insertions / 253 deletions; spike-ask-user shrinks by 124 lines (42 added, 166 removed), probe-first-prompt-hang shrinks by 109 lines (29 added, 138 removed). AC #1 + #2 mechanical greps return empty; `go build`, `go vet`, `go test -race`, and `make e2e` (including snapshot-drift) all clean. With this PR every spike + probe binary exercises the same library surface a future consumer will — the seven-spike `// copied from … — keep in sync until library extraction` attribution chain is fully retired.

Three #114-specific deltas relative to the [#117](117.md) / [#118](118.md) precedents are worth flagging.

First, **the probe-first-prompt-hang first-PTY-byte marker goroutine is NOT a watchdog and stays verbatim.** The ticket body's substitution table named it as one (lumped into "inline watchdog goroutine") but the architect's spec inverted that reading and the implementation followed: the goroutine has no `Tracker`, no `ParseSpinner`, no `CheckWatchdog`, and no wedge return path. It polls `rb.LastAppendAt()` at `statePollInterval` (50 ms), records the `first-pty-byte` marker on the first non-zero tick via `sync.Once`, and exits — pure instrumentation. Substituting `tuidriver.RunWatchdog` would (a) require constructing an unused `Tracker`, (b) introduce wedge-detection that ABORTS the probe on a slow-claude start which is exactly the failure mode the probe is designed to characterise, and (c) drop the `first-pty-byte` marker entirely (`RunWatchdog` doesn't record any). The architect's reasoning at `docs/specs/architecture/114-…md § probe-first-prompt-hang deltas item 1` makes the call explicitly; the PR body restates it for reviewers. This is the only non-mechanical interpretive call in the entire migration arc, and the answer is "the ticket's substitution table mislabelled a goroutine; the symmetric reading under AC #2's standing 'document the gap' instruction is to document the mismatch and not migrate."

Second, **probe-first-prompt-hang's tail goroutine is a single inlined consumer over `TailJSONL`, not a 1:1 helper swap.** Pre-migration `tailJSONLAll` did three things per line — write a timestamp-prefixed raw line to `jsonlLog`, surface `attachment.deferred_tools_delta.pendingMcpServers` as a `recordMarker` event, and invoke a caller-supplied `onEvent` for first-assistant / end-turn detection. Library `TailJSONL` only emits parsed `JSONLEntry` values; the three behaviours move into a single `for ev := range eventCh { … }` consumer inside `run()` (`main.go:233-263`). Per-entry sequencing matches the pre-migration shape: raw-line log first (`fmt.Fprintf(jsonlLog, "[+%9.3fs] %s\n", time.Since(startedAt).Seconds(), ev.RawLine)` — relying on the [#103](103.md) `RawLine` field added precisely so byte-faithful re-emitters can avoid `json.Marshal`'s key-order normalisation), then `attachment` filter for `deferred_tools_delta`, then `assistant` filter for first-assistant + end-turn. The `attachment` ladder's top-level key access is the only line that meaningfully changes shape — `ev.Raw["attachment"]` instead of the pre-migration `ev["attachment"]` (the entry is now a struct with a `Raw map[string]any` field, not a bare map). The nested type-assertion ladder past that point is byte-equivalent. `cancelCause(errors.New("end-turn reached"))` preserves the existing graceful-exit pathway (ctx cancel → main's `<-rootCtx.Done()` returns → summary prints).

Third, **spike-ask-user's answer keystroke stays as `ptmx.Write`, the spike-permission [#118](118.md) `sendKeystroke`-via-`Session.Write` migration is NOT mirrored here.** [#118](118.md) moved its single approve keystroke (`"1\r"`) through `Session.Write` because the migration was already renaming the helper (`sendKeystroke(session, approveKey)`); spike-ask-user's answer keystroke is one inline `ptmx.Write` at the end of `run()` (`main.go:257-259`) with no helper to rename. Migrating it would introduce an arbitrary helper and exceed the mechanical-cleanup scope; the trust-folder accept write at `main.go:156` (the other `ptmx.Write` call site) sets the precedent every sibling spike follows. Post-migration `grep -n 'ptmx\.Write' cmd/spike-ask-user/main.go` returns exactly two hits (trust-accept + answer keystroke), unchanged from pre-migration. The [#118](118.md) follow-up about a generic `Session.WriteKeystroke` / `Session.AcceptTrustFolder` primitive is still the right home for this if it ever lands; bundling it into per-spike cleanups stays out of scope.

The end-turn receive loop in spike-ask-user adopts the standard [#117](117.md) / [#118](118.md) shape: closed-channel guard (`if !ok { eventCh = nil; continue }`), assistant-only filter (`if ev.Type != "assistant" { continue }`), then `tuidriver.IsEndTurn(ev)` (`main.go:266-288`). The assistant filter re-establishes the pre-migration `tailJSONL`'s in-source filter; same architectural reason as the four preceding migrations — library `TailJSONL` emits every envelope type and the consumer takes on the type filter. `tuidriver.IsEndTurn` enforces the assistant guard internally as well, so the explicit filter is doubly safe but kept for shape parity with the spike-cancel / spike-permission receive sites. `ptyQuietLimit = 120 * time.Second` stays on the existing `NewTracker` call (`main.go:110-113`); the modal-quiescence rationale (`ptyQuietLimit`'s commentary at `main.go:53-58` — "AskUserQuestion modals render then claude goes QUIET waiting for user input") is preserved verbatim. `oscRe` (`main.go:70`) stays — used at `main.go:232` for OSC-sequence stripping in the modal snapshot, which library `tuidriver.StripANSI` doesn't cover (it strips CSI only). The `extractAskUserQuestion` and `hasAskUserModal` helpers (`main.go:297-325`) stay verbatim — spike-specific predicates with no library counterpart.

probe-first-prompt-hang's other constants and helpers: `statePollInterval` (50 ms) stays — drives the first-PTY-byte marker ticker; `sessionFileWait` (30 s, longer than the spike-one-turn shape — hangs can delay JSONL creation) stays as the `context.WithTimeout` argument; `wallTimeout` (3 min) and `hangThreshold` (10 s) stay — drive the probe's overall deadline and summary verdict; `promptText = "ready?\r"` stays sent verbatim via `ptmx.Write` (not `TypePrompt` — probe uses a short keystroke shape with a literal `\r` and explicitly does NOT want paste-detection-aware pacing); `timestampedWriter` (`main.go:322-334`) stays — out-of-scope PTY-mirror helper used by `tuidriver.Spawn`. spike-ask-user's deleted constants: `statePollInterval`, `jsonlTailInterval`, `sessionFilePoll`, `watchdogTick`; probe-first-prompt-hang's deleted constants: `jsonlTailInterval`, `sessionFilePoll`.

## Patterns established

- **First-PTY-byte instrumentation goroutines are NOT watchdogs and survive migration sweeps.** Pre-migration the probe-first-prompt-hang substitution table grouped its first-byte marker goroutine with "inline watchdog goroutine" (the [#89](89.md) sweep's headline target). Inspection showed the goroutine had none of the watchdog-defining surface: no `Tracker`, no `ParseSpinner` consumer, no `CheckWatchdog` call, no wedge return — it's a one-shot observation that records `first-pty-byte` and exits. The distinction matters because `tuidriver.RunWatchdog` and instrumentation goroutines have opposite design goals: `RunWatchdog` ABORTS on slow-claude conditions (PTY-quiet, spinner-frozen), instrumentation goroutines OBSERVE those conditions. Substituting one for the other in a probe whose entire purpose is observing slow conditions would defeat the probe. Audit rule for future cleanup sweeps: before classifying a goroutine as a watchdog, grep it for `Tracker` / `ParseSpinner` / `CheckWatchdog` / `cancelCause`-on-error-return — absent any of those, it's instrumentation and stays. Reuse posture: any future probe-shaped binary that polls `rb.LastAppendAt()` or `rb.QuietFor()` to record a marker (not to abort) follows this same shape.
- **Inlined per-entry consumer goroutine over `TailJSONL` when the consumer wants ≥2 per-entry behaviours and there's no library counterpart.** probe-first-prompt-hang's pre-migration `tailJSONLAll` carried three per-entry behaviours (raw-line log + deferred_tools_delta marker + onEvent callback) under one helper signature. Post-migration the helper goes away and the three behaviours live inline in a single `for ev := range eventCh` block. The alternative — chaining `TailJSONL` with three downstream goroutines, each filtering for its slice — would multiply goroutine count and require an internal fan-out broadcaster (not in the library). For consumer-side composition, inline-in-one-goroutine is the cheaper shape; the library's "emit every envelope type, consumer filters" posture (see [#59](59.md)) is what makes the inline filtering sequence trivially expressible. Reuse posture: any consumer whose pre-migration tailer wrapper carried multiple side effects in one helper should collapse them into one ranged-over consumer block, not split into N goroutines.

## Lessons learned

- **The ticket's substitution table can mislabel a goroutine; the spec audit is what catches it.** The ticket body listed "inline watchdog goroutine" as one of the things to migrate in probe-first-prompt-hang. Without an architect-side audit that reading would have produced a wrong implementation: either a `RunWatchdog` substitution that defeats the probe's purpose, or — worse — a "looks-like-a-watchdog" implementation that aborts on the first slow-claude tick during e2e runs and surfaces as flaky tests. The architect's spec caught it (`§ probe-first-prompt-hang deltas item 1`) and labelled it explicitly as a ticket-body mislabel. Lesson: when a cleanup ticket's substitution table targets a goroutine, verify the goroutine matches the named pattern's defining surface (here: `Tracker` + spinner consumer + wedge-error return). The ticket's column-A label is a hint, not a contract. Two minutes of inspection > two hours of investigating "why does the probe abort?" in CI. The spec's standing instruction "If `tailJSONLAll` exposes behavior that `tuidriver.TailJSONL` does not cover, document the gap in the PR description rather than reintroducing the helper" extends to the watchdog case under the same logic — document the mislabel, don't migrate.
- **Two behavioural deltas on raw-line logging are observable in principle and invisible in practice.** Pre-migration `tailJSONLAll` wrote EVERY line to `jsonlLog` before attempting to parse it — malformed-JSON lines and empty lines were logged then suppressed for marker extraction. Library `TailJSONL` silently drops malformed-JSON lines AND empty lines before the consumer sees them; post-migration those lines no longer appear in `jsonl.log`. Separately, `JSONLEntry.RawLine` is the line bytes WITHOUT the trailing `\r\n` (per [#103](103.md)'s `bytes.TrimRight`-and-`bytes.Clone` at parse time); the consumer formats `[+%9.3fs] %s\n` so byte-for-byte the result is one byte shorter than today only on lines that ended `\r\n` (the pre-migration code preserved the `\r`). For probe inspection purposes neither delta is visible — claude has never been observed to emit malformed JSON, the `\r` distinction matters to terminal-protocol analysers and not to the human reading `jsonl.log`. The ticket-body permission ("document the gap in the PR description rather than reintroducing the helper") explicitly authorises both drops. Lesson: when a library API is deliberately stricter than the local helper it replaces (here: parses-then-emits vs. emits-then-parses), the loss surface is "what gets dropped." Walk the dropped set explicitly and decide per-set whether the loss is acceptable; for an observational throwaway probe, almost always yes. For a production consumer wanting parse-error visibility, the answer would differ — a `TailJSONLRaw` library variant exposing parse failures would be the right addition. Out of scope for this slice, on file as a future ticket if the probe ever observes a real malformed line.
- **Two-files-in-one-commit was the right packaging for this slice.** [#112](112.md) bundled spike-one-turn + spike-multiselect; this ticket bundles spike-ask-user + probe-first-prompt-hang. The intermediate three tickets ([#116](116.md), [#117](117.md), [#118](118.md)) each migrated one binary because each had a non-trivial structural delta from its predecessor (multi-turn pointer-to-channel-slot, cancel's `logCancelEvent` Raw-map preservation, permission's two-`runSession` orchestrator). This ticket's two files share zero structural deltas — both are single-session, both are linear `run()` bodies, neither has the deferred-tailer constraint, and the only interpretive call (probe's first-byte goroutine) lives in one file. Bundling cost: one PR review, one commit, one e2e run instead of two. Lesson: per-ticket bundling for cleanup migrations should track structural distinctness, not file count. Two files that share zero deltas are cheaper as one ticket; one file with three deltas is cheaper as one ticket; the inflection point is "do reviewers need to context-switch between files?" — for this slice, no.
- **`make e2e` ran clean on the first build — the migration arc's steady-state expectation held for the fifth consecutive ticket.** Same pattern as [#112](112.md), [#116](116.md), [#117](117.md), [#118](118.md): library entrypoints are stable, mechanical substitutions don't change consumer semantics, the unfiltered-firehose behaviour change (`TailJSONL` emits every envelope type) is absorbed by consumer-side type filters re-established at receive sites, and snapshot-drift fixtures don't exercise the migrated binaries so there's no churn surface. Lesson: at the close of a five-ticket migration arc, "clean e2e on first build" is no longer newsworthy — it's the predicted outcome and observing it confirms the predicate (no library-side regressions during the arc, no migrated-binary regressions during the migration). The newsworthy outcome would have been drift; the absence is the steady-state signal that the library surface is right.
