# #261 — corpus-replay: per-cast result cache keyed by a detector-version hash

[Issue](https://github.com/pyrycode/tui-driver/issues/261) · [PR #280](https://github.com/pyrycode/tui-driver/pull/280) · Sibling of the corpus-replay tool family: harness [#227](https://github.com/pyrycode/tui-driver/issues/227), transition-edges [#247](247.md), parallelize [#260](260.md) · Code: `cmd/corpus-replay/cache.go` (new), `cmd/corpus-replay/cache_test.go` (new), `cmd/corpus-replay/main.go`, `cmd/corpus-replay/replayall_test.go`, `cmd/corpus-replay/README.md`

## Summary

A cast's replay result is a pure function of three inputs — the cast bytes (immutable per recording), the resolved sampling stride, and the detection code — so #260's parallelized full-corpus pass still recomputed every result identically on every repeat run. This ticket adds an on-by-default per-cast result cache: the routine case (a handful of new recordings, unchanged detectors) now costs seconds, while a full re-replay fires exactly when detection code changes.

The cache key is `sha256(version + stride + castName + contentHash)` (`resultCache.key`, `cache.go:118`), so any one of the four inputs changing produces a full miss for just that cast. `version` is a single sha256 folded over every `*.go` file's path+content under **both** `pkg/tuidriver` and `cmd/corpus-replay` (`versionHash`, `cache.go:39`), sorted by path for determinism — the architect spec deliberately widened this beyond the ticket's `pkg/tuidriver`-only Technical Notes because `cmd/corpus-replay` itself owns detection code (`contentAnchors`, `segmentOf`, `classify`), and keying on `pkg/tuidriver` alone would silently serve stale results after an edit there. `stride` folds in the *resolved* value (post `<1 → 1` clamp), so a stride-16 entry can never satisfy a stride-1 lookup — the safety property a future `-assert` gate (#259, forces stride to 1) needs, with zero reference to `-assert` anywhere in this code. `castName` + `contentHash` (streamed sha256 of the file, `hashCastContent`) fold in identity and immutability: a new cast is a new key (miss, everything else stays hit); a renamed-but-identical cast is also a new key (deliberate — name is part of identity via `tag` derivation).

`castResult` has unexported fields including three maps, so it round-trips through a tagged `cacheEntry` JSON mirror (`toCacheEntry`/`toResult`, `cache.go:158`) rather than being marshalled directly or having its fields exported (which would cascade through `main.go`/`report.go`). `report()` already sorts every map before printing, so JSON's sorted-key marshalling has no bearing on byte-identity.

`replayOrLoad` (`cache.go:224`) is a thin wrapper around the unmodified `replayCast`: `cache == nil` replays directly; otherwise a hit returns the cached result with **no** call to `replayCast` at all, and a miss replays then stores best-effort (a store error doesn't fail the cast — the fresh result is still returned, the entry just isn't persisted). `replayAll` (`main.go`) now takes a `*resultCache` and returns a `cacheStats{hits, misses}` alongside results — an errored/skipped cast counts as neither. One file per key (`<dir>/<key>.json`) means the #260 worker pool composes with zero new locking: distinct casts hash to distinct keys, so each cache file is touched by exactly one worker, either load-only or store-only, never both.

Two new flags: `-no-cache` (bypass entirely, never read/write) and `-cache-dir` (override the default `os.UserCacheDir()/corpus-replay` location). Cache-construction failure (bad source dir, uncreatable cache dir) degrades gracefully to `cache = nil` with a stderr warning — stdout stays byte-identical to a `-no-cache` run either way. The hit/miss summary line goes to stderr only, keeping stdout untouched.

## Patterns established

- **A result cache for a pure function over N inputs is a single content-addressed hash of all N inputs, one file per key, no index/manifest.** No mutex needed under a worker pool as long as workers own disjoint keys — the same "distinct paths, no shared state" shape #260 established for the worker pool itself, now applied one layer down at the cache-file level.
- **When a computation depends on code living in more than one source tree, the version hash must cover every tree that holds logic relevant to the result — not just the tree the ticket's prose names.** The ticket's Technical Notes pointed at `pkg/tuidriver` only; the architect spec caught that `cmd/corpus-replay` itself contributes detection logic (anchors, segmentation, classify) and widened the hash to cover both. Read the actual data flow, not just the ticket body, when scoping an invalidation key.
- **Over-invalidation is the safe default when a "which files matter" filter would require judgment.** `versionHash` hashes `*_test.go` files too rather than filtering them out — a test edit triggers a spurious full re-replay (cheap, self-correcting) rather than risking a filter that excludes a file that actually affects the result (silent staleness).
- **A resolved-value (not requested-value) key is how a future feature's correctness need gets satisfied without coupling to that feature.** Keying on the *resolved* stride (post-clamp) rather than the raw flag value means a not-yet-shipped `-assert` (#259) automatically gets a stride-1-only cache partition the day it lands, with this code never mentioning `-assert`.
- **Serialize via a tagged mirror struct, not by exporting the domain type's fields.** `castResult` stays unexported/internal to `main.go`/`report.go`; `cacheEntry` is the only type that knows about JSON tags, keeping the on-disk format decoupled from the in-memory type's field visibility.

## Lessons learned

- **Corrupt-or-absent cache entries must be the *same* code path (a miss), not a special-cased error branch.** `load` returns `(castResult{}, false)` on both "file doesn't exist" and "file exists but won't unmarshal" — a corrupt entry self-heals on the next run (re-replayed, overwritten) with no separate recovery logic.
- **Byte-identity across cold/warm/no-cache is the test that actually proves the cache is transparent**, not just that hits/misses count correctly. `TestReplayAll_ByteIdenticalColdWarmNoCache` captures `report()` stdout three ways (`-no-cache`, cold cache, warm cache) and diffs all three, plus asserts the cold run is all-miss and the warm run is all-hit — proving "every cast is a hit and no replay occurs" rather than assuming it from the hit count alone.
- **The stride-key interaction needed its own dedicated test, not incidental coverage.** `TestReplayAll_StrideKeyInteraction` warms the cache at stride 16, then re-runs at stride 1 over the same cache dir and asserts **all misses** — the one property a casual hit/miss smoke test would not have caught, since a naive key (name+content only) would have wrongly served the stride-16 result to the stride-1 lookup.
