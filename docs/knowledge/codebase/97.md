# #97 — spike-one-turn slow-path predicate: swap to PTY-quiescence

[Issue](https://github.com/pyrycode/tui-driver/issues/97) · [Spec](../../specs/architecture/97-spike-one-turn-pty-quiescence.md) · [PR #110](https://github.com/pyrycode/tui-driver/pull/110) · Code: `cmd/spike-one-turn/`

## Summary

`spike-one-turn`'s slow path wedged ~1/5 of runs against `claude 2.1.150` with `watchdog: spinner counter frozen at Ns for 31s`. Mechanism is the canonical four-incident wedge ([#11](11.md) / [#73](73.md) / [#70](70.md) / [#69](69.md)): `thinking-detected` fires, ~100 ms later `end-turn-detected` fires, then post-`end_turn` claude emits well under 4 KB so the stuck `✻ <verb> for Ns` glyph stays painted in the rolling buffer (`pkg/tuidriver/buffer.go:8-13`) indefinitely; `matchSpinner` keeps matching the same `for Ns`, `spinnerGone` never flips, and the 30 s `spinnerFreezeLimit` watchdog (`pkg/tuidriver/tracker.go:144`) trips. The fast path (4/5 runs) succeeded because the spinner regex never matched on `What is 2+2?` before `end_turn` arrived — `thinkingObserved` stayed false and the `gotEndTurn && (!thinkingObserved || spinnerGone)` disjunction short-circuited the moment `gotEndTurn` flipped. That fast-path pass was luck-of-the-prompt under the regex coverage gap, exactly what [#73's lessons-learned](73.md) anticipated ("Fixing the regex would expose spike-one-turn to the same buffer-residue class spike-multi-turn just escaped"). The shift from `claude 2.1.148` to `2.1.150` surfaced the wedge without any spike code change — the verb coverage shifted just enough that `Churned` now sometimes matches before `end_turn` arrives.

Fix is a one-binary predicate swap matching the proven shape from PR #74, [#70](70.md), and [#69](69.md). The slow-path predicate becomes `gotEndTurn ∧ bytes.Contains(StripANSI(rb.Snapshot()), tuidriver.IdleGlyph) ∧ rb.QuietFor() ≥ ptyQuietWindow` with `ptyQuietWindow = 1500 ms` — the same empirical window calibrated in [#11](11.md), reused at five sites now. The `thinkingObserved` / `thinkingVerb` / `spinnerGone` state and the probe-tick branch that drove them via `matchSpinner` on the rolling buffer are all deleted; the dormant `thinking-detected` / `spinner-gone` log lines go with them, matching PR #74's precedent (the PO note's "thinking-detected log can remain as instrumentation" was overridden in spec because the system-overview already notes the regex misses every observed verb in practice — keeping a dormant log just to log dead instrumentation isn't worth the local state it requires). The watchdog goroutine's `matchSpinner` call (`cmd/spike-one-turn/main.go:143`) stays unchanged — it feeds `tr.ObserveSpinner` + `tr.CheckWatchdog` and is the structural safety net for genuinely-wedged sessions (claude itself hanging indefinitely); the new loop predicate exits within ~1.5 s of `gotEndTurn` on the normal slow path, well before the 30 s `spinnerFreezeLimit`. No exported package symbols change; `pkg/tuidriver/IsIdle` is untouched. Net diff: 83 lines changed in one file, +54/−29.

Verified per AC: `bin/spike-one-turn -trust-folder=accept` on `claude 2.1.150` exits 0 in 5 consecutive trials covering both fast-path and slow-path execution. `spike-multi-turn` and `spike-cancel` continue to pass (no regression in sibling spikes). Safety property pinned by AC 2 (assistant text extracted only after `end_turn` observed AND TUI verifiably done emitting bytes) is preserved: the rationale comment block above the `check` closure (`cmd/spike-one-turn/main.go:218-245`) documents why the three conjuncts are independent and why `tuidriver.IsIdle` is deliberately not called — pattern-matches PR #74's rationale block as the AC required.

## Patterns established

- **PTY-quiescence is now a five-consumer pattern across four binaries.** Post-cancel readiness (`waitReappeared`, [#11](11.md)), multi-turn turn-complete (`runTurn`, [#73](73.md)), post-approve readiness (`runAutoRespond`, [#70](70.md)), post-cancel-recovery readiness (`runRecovery`, [#69](69.md)), and now single-turn turn-complete (`run`, this ticket). Five independent state transitions — cancel-then-redraw, end_turn-then-next-turn, approve-then-respond, end_turn-after-recovery, end_turn-then-extract — converged on `desired-event-observed ∧ bytes.Contains(StripANSI(snap), tuidriver.IdleGlyph) ∧ rb.QuietFor() ≥ 1500 ms`. This is the final spike binary that uses the predicate; four-binary coverage is the integration-pressure ceiling before library extraction lifts it. The library extraction (#58–#62) should now treat `ReadyForInput` (or whatever it lands as) as a top-priority primitive distinct from `IsIdle` — five consumer call sites in four binaries is decisive. See [system overview § Key signals](../architecture/system-overview.md).
- **The five-citation chain on `ptyQuietWindow` confirms the cross-binary calibration convention.** The constant's comment block in `cmd/spike-one-turn/main.go:53-56` cites the four sibling adoptions (`cmd/spike-cancel` empirical derivation; spike-multi-turn / spike-permission / spike-cancel adopters via [#73](73.md) / [#70](70.md) / [#11](11.md) / [#69](69.md)). No empirical re-derivation; no re-measurement run. The pattern established across [#73](73.md) ("Reuse calibrated empirical constants across binaries by citation, not by re-derivation") and [#70](70.md) ("Reuse empirical constants by citation across the spike suite — confirmed at three sites now") now holds at five sites. Post-extraction, the constant collapses into the library with one home; the citation chain's archaeological value (five consumers agreed on the same value before the library imposed it) survives the extraction.
- **Delete dormant instrumentation when porting a predicate; don't preserve it as polite courtesy.** PR #74 dropped the dormant slow-path log lines when porting spike-multi-turn's predicate; this ticket does the same for spike-one-turn (`thinking-detected verb=...` + `spinner-gone`). The PO note's suggestion to "keep thinking-detected as instrumentation" was correctly overridden in spec — keeping a log line whose underlying regex misses every observed verb in practice (system-overview line 92) means keeping local state (`thinkingObserved`, `thinkingVerb`, `spinnerGone`) whose only purpose is feeding the dead log. The predicate-port playbook is now: rewrite the closure, drop the constant, **delete the local state that the old predicate-shape required**, rewrite the rationale block. Don't carry forward state that the new shape doesn't read.

## Lessons learned

- **An "accidentally immune" sibling stays accidentally immune until it doesn't — and the deadline is set by upstream version drift.** [#73's lesson set](73.md) explicitly anticipated this exact failure ("Fixing the regex would expose spike-one-turn to the same buffer-residue class spike-multi-turn just escaped"). The actual trigger turned out to be slightly different — the regex wasn't fixed, but `claude 2.1.150` shifted the verb distribution enough that `Churned` now sometimes lands inside the regex's coverage on `What is 2+2?` before `end_turn` arrives. The structural takeaway holds either way: when a sibling binary is "unaffected" by a bug because of a coverage gap, the gap is a load-bearing assumption that upstream can quietly invalidate. The fix horizon was set by claude's verb choice, not by anything in this repo. Lesson sharpens [#73](73.md)'s "structurally immune vs accidentally immune" lesson: track which sibling binaries depend on coverage-gap luck, and treat upstream-version-drift surfacing the dependency as a "when" not "if." File a defensive ticket *when the gap is identified*, not *when it surfaces*.
- **Documented follow-ups in a per-ticket lessons section ARE the defensive ticket — they just don't auto-file.** [#73.md](73.md) closed with a "Follow-ups anticipated" bullet naming this exact wedge as anticipated work. The pipeline doesn't automate follow-up ticket creation from those lines, so the prediction sat in the docs for ~50 tickets until QA on PR #96 surfaced the wedge on `claude 2.1.150`. The cost was modest here (the diagnosis closed in one inspection step, the architect didn't have to re-derive anything, and the fix mirrored PR #74's diff shape verbatim) — but the gap between "we know this will break" and "we filed a ticket for it" is a structural one. Two options going forward: (a) when a per-ticket "Follow-ups anticipated" line names a specific binary + a specific failure mode, file the corresponding GitHub issue at the same time (cost: one extra `gh issue create` per documented follow-up; benefit: the ticket exists and can be picked up before the wedge surfaces); (b) accept the latency and treat surfaced follow-ups as a normal pipeline input. For tui-driver specifically, (b) is fine because the failure mode is benign (a watchdog trip in a spike binary is not a production incident) and the diagnosis-and-fix cost is low; for the broader pattern, when the predicted-failure cost is *high*, (a) is the discipline.
- **The PO ticket's "PRIMARY hypothesis" framing accelerates diagnosis even more when the predecessor proved the shape four times over.** Same lesson [#70](70.md) flagged after [#73](73.md). The ticket itself called out PR #74 as the reference fix; the technical-notes section sketched the predicate shape line-by-line; the architect's role on this one was confirming the shape (one paragraph) and writing the rationale block (which is mostly a citation chain). The cumulative effect of the four prior tickets in this lineage ([#11](11.md), [#73](73.md), [#70](70.md), [#69](69.md)) is that the architect-side decision surface for #97 was effectively empty — every architectural question had a precedent. Future tickets that mirror a four-times-proven pattern should expect a very thin architect step; the value the architect adds is verifying the shape transfers cleanly (citing the four predecessors as evidence) and writing the comment block that future readers will use to understand why the shape is right. The expensive architect work was [#73](73.md); ports are cheap.
- **"Same diff shape" is now a verifiable property across four binaries — and that property's existence is the strongest evidence yet that the library extraction is overdue.** spike-cancel's `waitReappeared` ([#11](11.md), then revised in [#69](69.md)), spike-multi-turn's `runTurn` ([#73](73.md)), spike-cancel's `runRecovery` ([#69](69.md)), spike-permission's `runAutoRespond` ([#70](70.md)), and now spike-one-turn's `run` (this ticket) all have functionally-identical `check` closures, functionally-identical `ptyQuietWindow` constants, and functionally-identical rationale blocks (cross-cited). The five call sites differ only in surrounding state (`preCancel`, `gotEndTurn`, none) and per-binary log-line conventions. This is the cleanest possible signal that a library primitive is wanted — five consumers, four binaries, one shape, no per-consumer variation in the predicate itself. The extraction work (#58–#62 and follow-ups) should treat this as a top-priority lift; further "fifth time porting the same shape" tickets are pure churn at this point. The PO ticket's note that "the library extraction work … is the right home for a `ReadyForInput`-shaped primitive" + AC 4's explicit "no `pkg/tuidriver/` changes" framing both confirm the discipline: don't lift in this ticket, but flag that the next architectural fix is the lift.
- **The "luck-of-the-prompt" pass on the fast path needs an explicit success criterion, not just "exits 0."** The AC required 5/5 passes covering both fast-path and slow-path execution. The post-fix run distribution naturally produces both (the spinner regex's verb coverage is still incomplete, so some runs go fast and some go slow), but a future hardening pass could close the regex's coverage gaps entirely — at which point the fast path disappears and *all* runs go through the new predicate. That's fine; the predicate is designed for both paths and the slow path was always the regressing case. Lesson: when ACs require "covers both paths," document which observation distinguishes them post-fix. Here the distinguisher is "did `end-turn-detected` fire with the rolling buffer still showing `✻ Verb for Ns`?" — visible from the log lines and the post-fix `check` closure's three-clause failure mode. The next time a "fast path / slow path" predicate is touched, the AC should name the observation, not just the exit code.
