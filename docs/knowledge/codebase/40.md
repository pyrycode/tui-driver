# #40 — CI: GitHub Actions workflow runs `make e2e` on push-to-main

[Issue](https://github.com/pyrycode/tui-driver/issues/40) · [Spec](../../specs/architecture/40-ci-e2e-workflow.md) · Code: `.github/workflows/e2e.yml`

## Summary

First GitHub Actions workflow in the repo. One YAML file (~70 lines) that wires `make e2e` as the deterministic backstop on the release branch. Triggers are `push` to `main` and `workflow_dispatch` only — explicitly NOT `pull_request`, because every run burns metered `ANTHROPIC_API_KEY` credits (CI runners cannot use a Max subscription). Two complementary cost controls land together: narrow trigger surface AND job-level `timeout-minutes: 20` so a hang cannot burn credits indefinitely. The 20-minute cap intentionally sits above the operator's `< 15min` p99 wall-time target, giving ~5min headroom before the hard kill — see the spec for why `timeout-minutes: 15` would be wrong (it would invert the relationship and kill healthy long-tail runs).

Steps in order: checkout → set up Go via `go-version-file: go.mod` (no hardcoded version string) → cache `~/.npm-global` keyed on `hashFiles('claude-version.lock')` → on cache miss, parse `version=` from the lock file via `awk -F= '/^version=/ {print $2; exit}' | tr -d '[:space:]'` and `npm install -g "@anthropic-ai/claude-code@${version}"` → write `$HOME/.npm-global/bin` to `$GITHUB_PATH` → `make e2e` → upload `e2e-report.json` and `/tmp/probe-first-prompt-hang-*` as artifacts on `if: always()` (30-day retention).

Three layers of correctness flow from the existing harness, NOT from this workflow:

- **`--strict-mcp-config` is NOT wired at the CI level.** The runner already injects `TUIDRIVER_STRICT_MCP_CONFIG=1` onto every spawned child (`cmd/e2e-runner/main.go:466`), which `EnsureClaudeEnv` translates into `--strict-mcp-config` on the spike's argv. CI sets nothing; `make e2e` is the only invocation. AC #2's last bullet ("each spike receives `--strict-mcp-config` (or the harness's equivalent CI flag)") is automatic — the workflow MUST NOT also set the env var at the job/step level, because future readers would misinterpret the redundancy as load-bearing.
- **`build-bin` is folded into `make e2e`.** AC #2 separates "build all spike + probe binaries" from "run `make e2e`" but they collapse into a single Makefile target because `build-bin` is a phony prerequisite of `e2e`. The workflow has one build/run step, not two.
- **Drift surfaces via the lock file, not via CI.** The `claude-version-lock` check ([#36](36.md)) runs inside `make e2e` and asserts version + pinned flags against the installed `claude`. CI's job is to invoke the harness on every push and archive the report — the in-process check decides what counts as drift.

Zero deviations from the spec. No code review NITs. Workflow file is the entirety of the production change; the e2e-harness feature doc's stale "Out of scope (today): GitHub Actions wiring" note is updated to reference the workflow.

## Patterns established

- **`hashFiles(<lock-file>)` as the cache-invalidation key for a pinned external tool.** `key: claude-${{ runner.os }}-${{ hashFiles('claude-version.lock') }}` hashes the lock file's content — any edit (version bump, flag add/remove, even a comment change) flips the key. Lock-file drift is the bug we're catching; missing the cache on every drift event is exactly correct, not a cost regression. Future CI integrations of other pinned binaries (a hypothetical pinned `node`, pinned `terraform`) should reuse the same hash-the-lock-file shape rather than maintain a parallel `cache-bump-counter` input. Trade-off: a maintainer who hand-fixes a typo in a comment line also invalidates the cache, which is fine — comment edits are rare and the alternative (parse the lock and hash only `version=`) trades simplicity for fragility.
- **Cache + cache-miss-only install + unconditional PATH propagation = three steps, not two.** The naive shape is "if cache miss: install + add to PATH; else: skip." That works on a cache miss but the PATH mutation never fires on a hit, leaving `claude` unavailable to `make e2e`. The correct shape splits PATH propagation into its own unguarded step: `echo "$HOME/.npm-global/bin" >> "$GITHUB_PATH"` runs on every job, while the `npm install -g` step is gated on `steps.cache-claude.outputs.cache-hit != 'true'`. Apply this anywhere a cached binary needs to survive cache hits.
- **Job-level `env:` over step-level for secrets.** `ANTHROPIC_API_KEY` is set exactly once at `jobs.e2e.env` and inherited into every step's subprocess tree. GitHub's auto-masking holds as long as the workflow references `${{ secrets.* }}` directly; copying the secret into a shell variable (`API_KEY=$ANTHROPIC_API_KEY`) or into an intermediate `env:` block elsewhere breaks masking on a subset of error paths. The job-level placement is the smallest-surface shape that still propagates.
- **`if: always()` on artifact uploads, paired with `if-no-files-found` per-artifact.** `e2e-report.json` uses `warn` (the runner is engineered to always emit the report; missing it is worth surfacing in the log). `/tmp/probe-first-prompt-hang-*` uses `ignore` (the probe may have no recordings on a clean run). The `always()` guard fires on cancellation too — including the 20-minute timeout kill — so even a hung run produces forensic artifacts. Pattern: pick `warn` when absence is itself an anomaly; pick `ignore` when absence is a healthy outcome.
- **`concurrency` group keyed on `github.ref` with `cancel-in-progress: false` for release-branch backstops.** Serialises runs so a back-to-back push pair doesn't trigger two parallel API-paid runs; `cancel-in-progress: false` preserves the first run's verdict per SHA rather than cancelling it. A cancelled run muddies the "did the gate pass on this SHA?" question and is the wrong shape for a deterministic backstop. Defensive shaping at zero YAML cost. Don't reach for `cancel-in-progress: true` on any workflow whose conclusion is meant to be per-commit truth.
- **Major-version action pins (`@v4`, `@v5`) for first-party `actions/*` actions, not SHA pins.** Trust model: `actions/checkout`, `actions/setup-go`, `actions/cache`, `actions/upload-artifact` are GitHub-stewarded. Major-version pinning is the documented best practice; SHA pinning would be stronger but adds renovation burden. Revisit if a future ticket adds third-party actions (`@some-org/*`) — those should be SHA-pinned.
- **`permissions: contents: read` at the job level shrinks the default `GITHUB_TOKEN` blast radius.** Default GHA token permissions are read/write across many scopes. This workflow only needs the checkout to read the repo — nothing writes back, no comments, no PR statuses beyond the inherent check-run. Apply this minimum-permissions shape to any workflow that doesn't actively need write scopes; the explicit declaration is one line and prevents a future step-injection bug from escalating.

## Lessons learned

- **AC text can describe what should happen at runtime, not what the workflow YAML must literally say.** AC #2's "each spike receives `--strict-mcp-config` (or the harness's equivalent CI flag)" sounded like a workflow-level requirement; in fact it's already satisfied at the runner layer ([#34](34.md), `EnsureClaudeEnv` + `TUIDRIVER_STRICT_MCP_CONFIG=1`). The spec's job is to translate "the AC says X" into "X is already true via Y, do nothing." Future tickets that touch the e2e harness from outside (CI, dispatcher integration, etc.) should read `cmd/e2e-runner/main.go` first to check what the runner already injects before adding env vars or flags at the caller's layer. Redundancy in this seam is harmless but misleads readers.
- **`build-bin` is a Makefile phony prerequisite; collapse "build" and "run" AC bullets into one `make e2e` step.** The ticket body lists "build all spike + probe binaries" and "run `make e2e`" as separate workflow steps. The cleanest workflow has neither as an explicit step — `make e2e` depends on `build-bin`, so a single `run: make e2e` does both. Splitting them into two `run:` lines would double the surface for errors and add zero observability. Read the Makefile before laying out CI steps.
- **`hashFiles()` is filesystem-side, not git-side — works for any file in the checkout, no special config.** Considered briefly whether the cache key needed to account for the commit SHA, the file's git history, or a separate explicit hash input. None of that. `hashFiles('claude-version.lock')` hashes the post-checkout file content; that's all CI cares about (the binary should match what the maintainer pinned in this commit's lock file). If a future cache key needs to incorporate a SHA or branch, prefer composing it into the `key:` string via `${{ github.sha }}` over reaching for a custom action.
- **`actions/upload-artifact@v4` accepts absolute paths and preserves basenames.** `/tmp/probe-first-prompt-hang-*` is an absolute path glob; the resulting artifact archive contains `probe-recordings/probe-first-prompt-hang-<tsTag>/...` (only the basename is preserved). This is the correct shape for forensic uploads — operators downloading the artifact don't see a meaningless leading `/tmp/` path. If a future artifact needs the full path retained, the `actions/upload-artifact` docs document an `include-hidden-files` and a `path` shape; default behaviour is fine here.
- **Workflow YAML has no test surface beyond actual execution.** No CI for the workflow file itself. Pre-merge validation is `actionlint .github/workflows/e2e.yml` (catches typos, invalid `uses:` references, expression-language mistakes — 5-second sanity check, not a hard gate) plus a `workflow_dispatch` test on the feature branch via the Actions UI. Post-merge validation is the first push-to-main run. Build the dispatch-test instinct: any new workflow should be exercised via the manual trigger on its own branch before merge, because YAML errors aren't caught by Go's compiler or `go vet`.
- **30-day artifact retention is a deliberate trim from the 90-day default.** Drift events get inspected within hours; >30 days of history rarely consulted. Storage is cheap but not free, and an over-large retention window inflates the Actions billing line on the org account without adding diagnostic value. The number is easy to revisit if a recurring failure mode wanted longer evidence trails.
