# #260 — corpus-replay: parallelize cast replay across cores

[Issue](https://github.com/pyrycode/tui-driver/issues/260) · [PR #271](https://github.com/pyrycode/tui-driver/pull/271) · Sibling of the corpus-replay tool family: harness [#227](https://github.com/pyrycode/tui-driver/issues/227), transition-edges [#247](247.md) · Code: `cmd/corpus-replay/main.go`, `cmd/corpus-replay/replayall_test.go`, `cmd/corpus-replay/README.md`

## Summary

A full-fidelity `cmd/corpus-replay` pass was single-threaded: one classify tick costs ~1.3ms and the corpus holds ~4.5M output events, extrapolating to ~100 minutes — too slow for the assert-mode gate to be routine. `replayCast` was already a pure function over `(path, stride)` with no shared mutable state, so the fix confines itself to `main()`'s replay loop: the sequential `for _, p := range paths { replayCast(p, *stride) }` loop is extracted into a new, independently-testable `replayAll(paths, stride, workers int, errOut io.Writer) []castResult`, and a `-workers N` flag (default `runtime.NumCPU()`, clamped to `>= 1`) drives it. No detector, buffer, or report logic changed.

`replayAll` is a streaming worker pool: a feeder goroutine streams `paths` into an unbuffered `jobs` channel and closes it; `workers` goroutines range over `jobs`, call `replayCast`, and send a `replayOutcome{path, res, err}` onto an unbuffered `out` channel; a closer goroutine `wg.Wait()`s then closes `out`; `replayAll` itself is the single reader of `out` — the sole writer of both `errOut` (skip lines) and the `results` slice, so no mutex is needed. Ownership of each `castResult` transfers from its worker to the collector at the moment of channel send, which is what makes `go test -race` pass without synchronization beyond the channels and `sync.WaitGroup`.

Casts complete in arbitrary order under the pool, but `report()`'s per-cast table and top-flappers tie-break walk the `results` slice in order, so `replayAll` re-sorts `results` by `r.name` (`sort.Slice`, non-stable — safe because `os.ReadDir` yields unique names within one directory, giving a strict total order) before returning. This restores exactly the pre-existing sequential (`-workers 1`) order, making stdout byte-identical across worker counts — the regression test (`TestReplayAll_ByteIdenticalAcrossWorkerCounts`) renders `-workers 1` and `-workers 8` through `report()` with `perCast=true` (the most order-sensitive section) and asserts the two buffers are byte-equal; its `workers=8` arm doubles as the `-race` exerciser.

Wall-clock (hand-run, synthetic corpus = `testdata` fixtures ×400 = 1600 casts, stdout discarded, 10-core machine): `-workers 1` 5.405s → `-workers 10` 1.478s, ~3.7×. The sub-linear ratio is the fixed per-cast open/parse overhead of the tiny synthetic fixtures dominating at this corpus size, not a pool inefficiency — see PR #271 body for the exact hand-run recipe (`testdata` duplicated into a `mktemp -d`, both worker counts timed with `>/dev/null`).

## Patterns established

- **Streaming worker pool with single-collector ownership transfer is the shape for parallelizing any "map independently-owned mutable state, then aggregate" loop in this codebase.** Feeder → unbuffered `jobs` → N workers → unbuffered `out` → one collector goroutine that is the sole writer of every shared destination (a results slice, an error stream). No mutex, because nothing is ever written by more than one goroutine at a time — each item's ownership is created by exactly one worker and handed off exactly once via the channel send. Reach for this over a `sync.Mutex`-guarded shared slice whenever the per-item work (like `replayCast`) is already a pure function with no cross-item state.
- **A parallelized loop's ordering guarantee is a sort, not a scheduling property.** Byte-identical output across worker counts does not come from the pool "happening to" preserve order — it comes from an explicit `sort.Slice` on the aggregated result before it reaches the order-sensitive consumer (`report()`). Any future parallelization of an ordered-output loop in this repo should budget for the same explicit re-sort rather than relying on channel/goroutine scheduling order.
- **Extract the loop body into a plain, `os`/`flag`-free function to make a `main()` change testable.** `replayAll(paths, stride, workers int, errOut io.Writer) []castResult` takes no dependency on `os.Args`/`os.Exit`/`os.Stderr` (errOut is injected), so tests can drive it directly with `io.Discard` or a `bytes.Buffer` and assert on the returned slice or the error stream — `main()` collapses to three calls (`castPaths` → `replayAll` → `report`).

## Lessons learned

- **The byte-identity guarantee rests entirely on the sort, not on the concurrency being correct.** A pool that's `-race`-clean and has no data races can still silently break AC3 if the final sort is dropped or scoped wrong — race-cleanliness and output-determinism are two separate properties that both need their own test. Verified by neutering the sort locally and re-running the byte-identical test 5× (fails every time with the sort removed, confirming the test isn't a false-positive green from small-corpus luck).
- **`go build ./cmd/corpus-replay` (no `-o`) drops a default-named `corpus-replay` binary at the repo root**, not inside `cmd/corpus-replay/`. Easy to `git add -A` by accident after a hand-run wall-clock measurement; remove it before staging.
- **Self-reference discipline (carried from #152/#154/#155/#227/#247) applies to the wall-clock measurement, not just to normal test runs.** The tool's source and `testdata` quote live detector anchors and the tool prints matched content, so the hand-run benchmark must redirect stdout to `/dev/null` rather than being displayed on a live `claude` screen.
