# #90 — picker parser: decouple from color-code encoding (structural anchor + parsed-RGB classification)

[Issue](https://github.com/pyrycode/tui-driver/issues/90) · [Spec](../../specs/architecture/90-picker-parser-decouple-color-encoding.md) · Supersedes [#85](https://github.com/pyrycode/tui-driver/issues/85) (closed wontfix) · Code: `pkg/tuidriver/picker.go`, `pkg/tuidriver/modal.go`, `pkg/tuidriver/picker_color.go` (new)

## Summary

The slash-picker row detector and `ParsePicker` highlight classifier both keyed on the indexed-color SGR shape `\x1b[38;5;(246|153)m/<letter>` (`pkg/tuidriver/picker.go:47-48` and `pkg/tuidriver/modal.go:80-81` pre-fix). claude 2.1.148+ ships truecolor SGRs (`\x1b[38;2;<r>;<g>;<b>m`) instead; indexed-color regex misses → `DetectModalClass` returns empty → `ParsePicker` returns nil → `spike-multiselect` logs `modal-class detected=` / `no-parser-for-modal-class class=`. #85 framed the fix as regex-widening (capture both shapes); the architect's own #85 technical-notes comment flagged the deeper smell ("classify by parsed triplet rather than by captured string-equality"). This ticket promotes that observation to the spec premise, mirroring the layered-volatility retirement #72 → #81 two days earlier.

Implementation splits the picker into two seams:

1. **Row finding** — `findPickerRows(snap) []pickerRow` in `pkg/tuidriver/picker.go`. Line-segments `StripOSC(snap)` on **both** `\n` and `\r`, then for each line tests `StripANSI(line)` against `pickerRowStartRe = ^[ \t\r]*/[a-zA-Z]`. No reference to color SGRs at all. Survives indexed → truecolor → hypothetical-third-encoding migrations because the underlying text is `/<letter>…` regardless of how claude paints it. The structural anchor also kills the historical `? for shortcuts · ← for agents` hint-bar false-positive (the welcome banner doesn't start its line with `/`).
2. **Highlight classification** — `pickerRowOpenColor(raw) (rgb, bool)` walks each row's raw bytes through a tiny SGR state machine (`parseForegroundSGR` in `pkg/tuidriver/picker_color.go`), capturing whatever foreground color was in effect when the leading `/` was painted. `rgbIsHighlighted(c)` matches against the package-private set `pickerHighlightedRGBs = [{175,215,255}, {177,185,249}]` — xterm-256 index 153 and the truecolor variant claude 2.1.150 emits. Unrecognised SGR encodings yield `colorSet=false`, which means "default/unknown" and falls back to "first row is highlighted" (the convention claude follows for filtered-mode default selection anyway).

`xterm256ToRGB` is ~10 LOC: a 16-entry literal for the system-and-bright region (the only values that aren't formulaic), arithmetic for the 6×6×6 color cube (`n = 16 + 36*r + 6*g + b`, components from `{0, 95, 135, 175, 215, 255}`), arithmetic for the grayscale ramp (`gray = 8 + 10*(n-232)`). No 256-entry literal.

`DetectModalClass` now classifies slash-picker via `len(findPickerRows(snap)) > 0`. The old "check picker first on RAW bytes because the anchor is an SGR" rationale is obsolete — the new anchor runs on stripped lines — but the check stays at the head of the switch because it's structurally more specific than any of the substring anchors. `slashPickerRowRe` is deleted; `pickerItemStartRe` is deleted; `pickerColorCodeRe` is widened to also match `\x1b[38;2;<r>;<g>;<b>m` and `\x1b[39m` (description reconstruction still strips colors, just now covers all three shapes); `pickerCsiCursorFwdRe` is widened from `\x1b[<N>C` to `\x1b[<N>[CG]` because claude 2.1.150's truecolor renderer uses cursor-horizontal-absolute (`G`) for inter-word spacing where the indexed-color era used cursor-forward (`C`). Both still collapse to a single space.

Public surface unchanged. `spike-multiselect` (the sole consumer) requires zero edits. Out of scope per the ticket: exposing parsed-color helpers to consumers, refactoring `mcp`/`agents` parsers (already structural), generalising the structural-anchor pattern to other modal classes.

This ticket landed via dispatcher max-turns salvage. The developer phase hit the per-task turn budget mid-flight; dispatcher auto-committed the working tree as `WIP: max_turns salvage for #90` (commit `2c05781`), and a human salvage triage (`c3a892d`) kept the core fix while reverting two scope-creep deltas: (a) a 3.2 MB compiled `e2e-snapshot-check` binary that leaked into the repo root (built locally without `-o bin/`; `/e2e-snapshot-check` added to `.gitignore` to close the leak), (b) changes to `cmd/e2e-runner/main.go` + `cmd/e2e-snapshot-check/main.go` that added the new fixture to the byte-compare snapshot-drift registry — perpetuating the byte-compare model that [#81](https://github.com/pyrycode/tui-driver/issues/81) is explicitly retiring. The new `picker-truecolor-snapshot.bin` is kept as **library regression coverage** (`TestDetectModalClassRealFixtures` + `TestParsePickerRealFixture` parametrise over both fixtures) but is **not** byte-compared by snapshot-drift. The pre-existing snapshot-drift e2e failure (tracked by [#81](https://github.com/pyrycode/tui-driver/issues/81)) is unchanged.

## Patterns established

- **Two-seam decoupling: structural anchor + parsed-RGB classifier.** This is the canonical shape for any parser that recognises rows in a stylised TUI region. The row-finder owns structural geometry (where the rows are); the classifier owns presentation (what color/highlight they have). Both are pure functions over a byte snapshot; the two seams compose with zero shared state (`findPickerRows → []pickerRow → classifier reads pickerRow.openColor`). Future renderer-encoding migrations touch ONE function: `parseForegroundSGR` (add a case) or `pickerHighlightedRGBs` (add an entry). The row anchor and the highlight predicate stay frozen. AC #5's hypothetical-third-encoding test (`TestParsePickerHypotheticalThirdEncoding`) is the executable proof — synthesise `\x1b[38;6;…` rows, watch them parse cleanly with rows[0].Highlighted=true via fallback. **Reuse posture:** when a parser keys on both structure and presentation, separate the seams in the implementation, not just in the doc-comments — the seam IS the test for "could this be re-coupled in a future patch?"
- **Multi-value highlight sets beat single constants when the renderer history has shipped two shades.** `pickerHighlightedRGBs` is a `[]rgb` of length 2 (indexed-153 → {175,215,255}; truecolor-2.1.150 → {177,185,249}), not a single constant. Same equality semantics, one-line cost to add a future shade. The architect's spec considered both shapes; the developer phase picked the set because the empirical evidence — the truecolor fixture's highlighted-row RGB ≠ xterm-256(153) — falsified the single-constant hypothesis at capture time. **Reuse posture:** when a presentation value is "the canonical one, modulo small renderer-version shifts," express it as a set, not a constant. The cost of `slices.Contains` is zero versus a const compare in this access pattern (per-row check, never in a tight loop), and the diff to extend it later is two lines (one new RGB literal + maybe a comment).
- **Empty-param-defaults-to-zero is an ECMA-48 contract, not a quirk.** `parseSGRParams` treats `\x1b[38;5;m` as `[38, 5, 0]` (palette index 0 = black). That's correct per the SGR spec, even though it looks like a malformed input. The test row (`picker_color_test.go:88-95`) documents the contract explicitly: "empty trailing param parses as 0 per SGR spec. Black is harmless because it's not in `pickerHighlightedRGBs`." **Reuse posture:** when implementing a tokeniser for a documented escape-sequence family, follow the family's defaulting rules verbatim. The rule looks like a quirk locally, but it's part of the long contract terminal authors rely on; deviating creates surprises that surface as parse-shape mismatches against future renderer outputs.
- **Line segmentation that splits on `\n` AND `\r` survives claude's render-time cursor mechanics.** The spec proposed `bytes.Split(snap, []byte{'\n'})`. The developer phase widened to "any of `\n` or `\r`" after finding that claude emits bare `\r` to overprint the prompt's `/ ` glyph with the picker rows (e.g. `\r/ \r/code-review`). Splitting only on `\n` left the post-CR content concatenated with the preceding overprinted prefix, breaking the row anchor. The wider separator is correct per terminal mechanics — `\r` is `CARRIAGE RETURN`, which by VT100 convention moves the cursor to column 0 and effectively starts a new logical line for content purposes. **Reuse posture:** when scanning TUI bytes for content-line boundaries, split on the union of CR / LF / CRLF; don't assume the producer normalises line endings.
- **Avoid 256-entry palette literals when the palette is mostly formulaic.** xterm-256 has exactly 16 historically-accidental values (the system-and-bright region) and 240 deterministically-computable ones (216 cube + 24 grayscale ramp). The implementation uses a 16-entry literal plus two arithmetic branches — total ~12 LOC. A 256-entry literal would be denser to write, harder to audit, and obscures the cube's structure. **Reuse posture:** before embedding a large literal, check whether the values are formulaic; if so, the formula is the right shape even when the literal would be smaller in keystrokes.

## Lessons learned

- **Dispatcher max-turns salvage is not free; the human triage cost is real.** The developer hit max_turns mid-flight; the dispatcher's safety-net auto-commit preserved 100% of the architectural fix (no work lost) but also swept up two scope-creep deltas — a 3.2 MB compiled binary in the repo root and changes that recoupled the new fixture to the snapshot-drift byte-compare model. The triage cost was ~15 minutes of `git diff` + revert work plus a `.gitignore` patch to close the binary-leak root cause. The salvage is **strictly better than losing the developer's work**, but the rate of "developer hit max_turns" runs warrants a separate look — every salvage requires a human reviewer to distinguish the architectural fix from incidentally-modified files. The structural prevention is the binary leak: `make build` should always go to `./bin/`, never to the repo root. Adding `/e2e-snapshot-check` to `.gitignore` is the local fix; the durable fix is for the developer-phase agent to never invoke `go build` without `-o bin/<name>`. **Generalisable lesson:** the safety-net commit-on-max-turns shape (auto-commit-everything when the agent runs out of turns) preserves work but transfers triage cost to the human. The cheapest defence against scope creep being preserved alongside the real fix is to keep the agent's diff narrow during the run, not after.
- **The "wontfix the noisy ticket, fresh framing in a new one" decision happened twice in the same week — that's a pattern, not a coincidence.** #72 → #81 (snapshot-drift coupled to raw bytes → parsed-shape comparison) closed 2026-05-22. #85 → #90 (picker coupled to color codes → structural anchor + parsed RGB) closed 2026-05-23. Same shape: an immediately-failing ticket framed the bug as a presentation-coupling regex widening, the architect's own technical notes named the deeper smell, the wider redesign was promoted into a fresh ticket and the noisy one wontfix'd. Two instances in one week is enough evidence to treat it as a standing diagnostic pattern: **when an assertion or parser keyed on a presentation detail breaks under a renderer-version bump, the right question is "what's the structural property the presentation was a proxy for?" rather than "what's the next presentation form to capture?"** The presentation form will shift again; the structural property won't (or if it does, the next change is also a presentation form, and the cycle resets). The cost of the wider redesign is roughly equal to two or three rounds of regex-widening, but the wider redesign caps the future maintenance at "add one case to the encoding-parsing helper" rather than "audit every captured-string-equality predicate in the file."
- **`/e2e-snapshot-check` byte-compare coverage and library regression coverage are different things.** The salvage triage initially looked like it should keep the new fixture wired to both: `TestDetectModalClassRealFixtures` + `TestParsePickerRealFixture` (library regression) AND `cmd/e2e-snapshot-check`'s registry (byte-compare against re-captures). The triage commit reverted the snapshot-drift registry change deliberately because #81's premise is that byte-compare is being retired in favour of parsed-shape comparison — adding the truecolor fixture to byte-compare would have perpetuated the model #81 is dismantling. The fixture stays as library regression evidence; the snapshot-drift e2e failure stays pre-existing and continues to be tracked by #81. **Generalisable lesson:** when a new fixture lands during a ticket that pre-dates a model retirement, route the fixture only to the surviving coverage paths. The temptation is to wire everything that already exists; the durable move is to wire only what's still load-bearing in the model that survives the retirement.
- **The first-item-per-fixture assertion has to vary per capture, not per parser semantics.** `TestParsePickerRealFixture` asserts `picker-snapshot.bin` opens with `/figma-use` and `picker-truecolor-snapshot.bin` opens with `/code-review`. The first command differs because claude's plugin set (and therefore the alphabetically-first skill) changes between captures, not because the parser is doing anything different. The test row carries an explicit comment ("First-command differs per capture because claude's plugin set … changes; the parser must report whichever row claude paints first") to keep future re-recorders from "fixing" the assertion to match. **Generalisable lesson:** when parametrising a regression test over multiple fixtures captured at different times, the per-fixture assertions need to be data-tagged with the capture context, or future re-recorders will read divergent assertions as parser-side mismatches and try to normalise them.
- **Spec-resolved open questions cost zero; spec-deferred ones cost a developer round.** The spec's three open questions (leading-glyph anchor vs slash-letter anchor, highlight RGB value(s), `cmd/e2e-snapshot-check` integration) were three actual decisions the developer phase had to make. The third one (the e2e-snapshot-check registry update) was the source of the scope-creep that triggered salvage. **The two questions that resolved cleanly (anchor choice, RGB set) consumed roughly one fixture-capture run; the question that resolved poorly (snapshot-drift registry) consumed the rest of the developer's turn budget and triggered the max_turns salvage.** Same lesson as [#60](60.md): open questions explicitly resolved in the spec cost zero; open questions deferred to the developer cost a round of code review at best, a max_turns salvage at worst. The mitigation isn't "resolve every question in the spec" — that's unrealistic when some questions require empirical fixture data the architect can't produce — but it is "name the questions that REQUIRE developer-phase empirical work versus the ones that are architect-deferrable, and resolve the latter category in the spec." The `cmd/e2e-snapshot-check` question was architect-deferrable in retrospect (the decision turns on whether #81 retires byte-compare, not on any new empirical signal); resolving it in the spec would have saved the salvage round.
