# #38 — `Session.Wait()` drains the PTY reader before returning

[Issue](https://github.com/pyrycode/tui-driver/issues/38) · [Spec](../../specs/architecture/38-wait-drains-reader.md) · Predecessor: [#34](34.md) (origin of the `t.Skip`)

## Summary

`Session.Wait()` now receives both `<-s.exited` and `<-s.readerDone` (in that order) before returning, tightening the public contract: any bytes the PTY reader goroutine wrote into the rolling `Buffer` or into `SpawnOpts.Mirror` before the subprocess exited are guaranteed visible to the caller once `Wait()` returns (happens-before via the `readerDone` channel close). Pre-#38, `Wait` only synchronised on subprocess exit — `cmd.Wait`'s observer goroutine closed `s.exited`, but the PTY reader could still be draining the final EIO/EOF chunks from `ptmx.Read` into `Buffer`/`Mirror`, so a naive consumer that called `Wait()` and then read `Buffer.Snapshot()` or `Mirror.String()` was racing the reader. `go test -race` flagged it on every run of `TestSpawnMirrorReceivesOutput`; #34 hid it under `t.Skip("blocked on #38 — …")` and a 50 ms paper-over `time.Sleep` in `TestSpawnAndBufferReceivesOutput` so #34's race gate could land, with the explicit follow-up landing here.

The change is three production lines in `pkg/tuidriver/session.go` (`session.go:244` adds `<-s.readerDone`; `session.go:232-241` rewrites the doc-comment from one paragraph to two, naming `Buffer` and `SpawnOpts.Mirror` explicitly as the synchronisation point) plus nine deletions in `pkg/tuidriver/session_test.go` (the `t.Skip` + paper-trail block from #34, plus both 50 ms sleeps from `TestSpawnAndBufferReceivesOutput` and `TestSpawnMirrorReceivesOutput`). No new fields, no new channels, no signature change, no `WaitReader()` companion (the ticket Technical Notes explicitly ruled out a parallel method — folding the synchronisation into `Wait` keeps the surface area smaller and matches what consumers naturally write). `Close`'s shutdown sequence (`session.go:258-273`) is unchanged — it already waited on `<-s.readerDone` after closing the PTY; this ticket exposes the same happens-before chain to `Wait` callers that `Close` callers always had.

Receive order matters and is fixed at `exited` then `readerDone`. Two reasons: (1) **causal order** — `ptmx.Read` only returns EOF after the child closes its end of the PTY, which happens when the child exits, so `exited` closes first in practice; (2) **`exitErr` read-ordering** — the `cmd.Wait` observer sets `s.exitErr` before `close(s.exited)`, so the existing read-after-channel-close guarantee for `s.exitErr` is preserved by waiting on `exited` first. The `<-s.readerDone` receive is panic-safe and instant on an already-closed channel (Go spec guarantee), so callers that invoke `Wait` long after the process exited see no latency regression.

## Patterns established

- **Public-API synchronisation point should expose the same happens-before chain the internal shutdown already uses.** `Close`'s flow (`session.go:258-273`) had been waiting on `<-s.readerDone` after closing the PTY since the library's first commit; the primitive existed, `Wait` simply was not using it. The right shape for an API-level race fix is to identify the already-correct internal synchronisation (here: `Close`'s reader-drain) and project it onto every public surface that could plausibly observe the same reader-side state. The change cost was one channel receive; the alternative (introducing `WaitReader()` or a new sync primitive) would have grown the surface area for the same guarantee. Reuse posture: when two public methods both terminate a session lifecycle, they should share the same happens-before chain for any goroutine-driven side effects. If one method drains and the other does not, the asymmetry is a footgun — the fix is to make them symmetric, not to document the difference.
- **Fold reader-synchronisation into the natural exit point rather than exposing a parallel method.** The original ticket considered `WaitReader()` as an alternative and explicitly ruled it out: consumers were using `Wait()` the way any consumer naturally would, and a separate method would split the "session is done" contract across two calls with no compelling reason. Reuse posture: when the question is "should the existing method's contract grow, or should we add a parallel method," prefer growing the existing method if the new behaviour is a strict happens-before tightening (no caller has to opt out, no caller breaks). Add a parallel method only when callers genuinely want both shapes — e.g. when one caller needs the fast-but-racy variant for a benchmark or a soft-shutdown path. No such caller existed here; the fast-but-racy `Wait` was the footgun, not a feature.
- **Docstring growth is part of the fix, not an afterthought.** The new `Wait` doc grew from one paragraph (exit semantics only) to two paragraphs that explicitly name `Buffer` and `SpawnOpts.Mirror` as the synchronisation target. The reader of the doc now learns "after Wait returns, both subprocess exit AND reader-side state are observable" — without that sentence, a future consumer reading the doc could plausibly assume the old behaviour and write the same footgun-y sleep-after-Wait code that motivated this ticket. Reuse posture: when the contract change is "this method now also synchronises on X," the godoc must name X explicitly — a generic "all internal state is visible" phrasing is too vague to be useful, and a behaviour-only fix (no doc growth) leaves the next reader to either re-discover the contract from the source or hit the original footgun.

## Lessons learned

- **`time.Sleep` in a test that exercises a synchronisation contract is almost always a contract bug, not a test bug.** Both `TestSpawnAndBufferReceivesOutput` and `TestSpawnMirrorReceivesOutput` had a `time.Sleep(50 * time.Millisecond)` after `s.Wait()` with comments explaining the PTY-drain timing; the sleeps worked most of the time and made the tests pass under plain `go test`. The race only became visible under `go test -race`, but the contract gap had been present from day one. The cheapest tell: if a test needs to sleep to observe a side effect of an API call, the API contract is incomplete — the API caller's natural code path would have the same gap, just without the sleep. Generalisable check: when reaching for `time.Sleep` in a test, ask "would any consumer of this API need to do the same thing?" If yes, the sleep is hiding a contract gap that belongs in the production code. If no (the sleep is genuinely test-rig-specific, e.g. waiting for a filesystem operation to settle), call that out in a comment.
- **Skip-with-paper-trail closes out cleanly when the paper trail is mechanical.** #34's `t.Skip("blocked on #38 — Mirror buffer race between reader goroutine and test read")` plus the four-line explanatory comment block was exactly the right shape: it surfaced the race without blocking the harness, named the follow-up ticket, and made the close-out a mechanical deletion. This ticket's developer phase deleted the skip and the comment block in one motion, removed the two sleeps, and the proof-of-fix was the same `go test -race` invocation #34's footnote pointed at. Reuse posture: when a ticket surfaces a pre-existing problem that is out of scope to fix in-band, file the follow-up ticket, then skip-with-paper-trail the test that would have caught it — naming the follow-up ticket in the skip message and adding a comment block that names the structural cause. The close-out is a mechanical revert plus the actual fix, no archaeology required. The "five years from now, why is this skipped?" failure mode is averted by the in-line ticket reference.
- **`go test -race` should be the default gate for any package that exposes concurrent state.** The race detector caught a contract gap that plain `go test` had hidden since the library's first commit. The pkg/tuidriver package's reader-goroutine architecture is a natural concurrent-state surface — `Buffer.Append` from the reader, `Buffer.Snapshot` from the consumer, plus optional `Mirror.Write` — and every test that exercises that surface should run under `-race` in CI. #34's `e2e-harness` foundation made `go test -race ./...` the harness's package-test gate, which is what surfaced #38 in the first place; the pattern earns its keep. Reuse posture: in any package that ships concurrent state on public types, default to `-race` in the package's primary CI invocation. The cost is ~2× wall-time on small packages; the benefit is catching contract gaps before they become consumer-side bug reports.
- **The "what if the reader is stuck forever" concern was correctly deferred.** The spec called it out and dispatched it: a stuck reader would already block `Close` today (which also does `<-s.readerDone`); with #38, it would also block `Wait`. Same blast radius, same failure signature — evidence-based fix selection says no new defence is justified without an observed failure. Adding a timeout or a select-with-fallback to `Wait` would have grown the API surface (a new timeout knob? a new error kind?) for a theoretical failure mode. Reuse posture: when extending a synchronisation contract, the right baseline question is "does the existing parallel path already accept this risk?" If yes, the extension inherits the same risk profile and no new defence is justified; if no, the asymmetry is the bug.
