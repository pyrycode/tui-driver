# #185 — spike-one-turn: relax `sessionFileWait` 10s → 30s for concurrent-suite load

[Issue](https://github.com/pyrycode/tui-driver/issues/185) · [Spec](../../specs/architecture/185-spike-one-turn-jsonl-wait-load-tolerance.md) · [PR #186](https://github.com/pyrycode/tui-driver/pull/186) · Code: `cmd/spike-one-turn/main.go`

## Summary

`spike-one-turn` was a **known intermittent flake** — not a regression — under `make e2e` on the pinned `claude 2.1.199`. It passes deterministically on standalone binary re-run (3/3) and passed the baseline in the same window, but reddened once during PR #184's `make e2e` (`fail`, 11090ms). Left unfixed, any future PR whose `make e2e` happened to catch it looked like a regression under a naïve single-run baseline comparison (green baseline, red PR) and got mis-routed to `needs-rework:developer`.

**Diagnosis (conclusive).** The failing deadline is `sessionFileWait = 10s` wrapping `WaitForSessionJSONL` (`main.go:172`). Interactive `claude --session-id` **defers JSONL creation until it processes the first input** (README finding #9), and that first-input work — session init + file open — is **local-process-bound**, so it slows under CPU/IO contention. Standalone the file opens in ~200 ms (README Runs 5/6: 202 ms, 304 ms); under concurrent-suite load it exceeded the 10 s bound, the deadline won the race, `WaitForSessionJSONL` returned wrapped `context.DeadlineExceeded`, `run()` returned the error and the binary `os.Exit(1)`'d → the runner recorded `fail` at ~11 s. The **~11 s fingerprint is decisive**: every *other* failure path is guarded by the 60 s `ptyQuietLimit` watchdog or the 60 s runner check-timeout and would surface as a 60 s `timeout`, not a `fail`. History corroborates — README Run 1 already died at this same wait's earlier 5 s value. Source of the load is *external* to a single `make e2e` (the e2e-runner runs checks serially): `PYRY_MAX_CONCURRENT=2` dispatch and/or overlapping baseline + PR `make e2e`, each a live `claude` competing for cores.

**Fix.** One production line: `sessionFileWait` 10s → **30s**, plus a rationale comment block. 30 s is 3× the observed ~10 s failure threshold, adopted by citation from the sister spike `cmd/probe-first-prompt-hang/main.go:41` (which already reasoned to 30 s for the same deferred-JSONL-creation reason — cited, not re-derived), and stays well inside the e2e-runner's 60 s `defaultCheckTimeout`, so a *genuinely* hung claude still surfaces via the 60 s watchdog / runner timeout — only the legitimate-but-slow case is newly tolerated. `pkg/tuidriver/jsonl.go` (`WaitForSessionJSONL`) was **not** touched — the library poll-until-exists is correct; only the caller's deadline was too tight. README got a Run 7 row, a new finding #10 (load-sensitivity of the deferred-JSONL window), and a two-angle repro recipe.

**Scope.** Only `spike-one-turn`. The five sibling spikes (`spike-multi-turn`, `spike-long-prompt`, `spike-ask-user`, `spike-cancel`, `spike-permission`) share the same latent `sessionFileWait = 10s` and the same deferred-JSONL window, but **none has been *observed* to flake** → left untouched per evidence-based fix selection; recorded as a follow-up (below). Not `security-sensitive` (harness/timing, doesn't touch the permission-gate detection path). Confirmed **not** the #173 surface: #173 inverts a *classification default* for unknown pre-first-prompt chrome; this is a harness *deadline* that is too tight for a legitimately-slower-under-load operation — a distinct fix shape, so no route-back to PO.

## Patterns established

- **Relax the deadline, don't retry — the load-tolerant fix for a poll-until-success wait whose underlying op is local-CPU-bound.** The operation *succeeds given enough wall-clock* (it is not failing on the merits), so a bounded retry would only mask the race. The deterministic move is to size the deadline to N× the observed failure threshold while keeping it inside the enclosing check budget, and to **adopt the value by citation from a sibling that already reasoned to it** rather than re-deriving. Direct sibling of the cross-repo precedent [pyrycode #584](https://github.com/pyrycode/pyrycode/issues/584) ("passes in isolation, flakes under full parallel load" poll-loop race — same shape, size-S fix). This is the sanctioned deterministic option over a blind retry per the ticket's Technical Notes.
- **A monotonic deadline change gives a *structural* refutation of a flaky baseline `comm`, stronger than sampling alone.** QA's naïve baseline diff flagged `spike-one-turn` pass→fail as a regression — the exact flaky-check trap that the project's baseline-hygiene discipline (defeat a flaky single-run signal with *more* deterministic sampling, not with reasoning) mandates overriding. Two independent lines killed it: (a) **structural monotonicity** — the only production change *raises* a poll-until-success deadline; no JSONL-appearance latency exists for which 10 s passes but 30 s fails, so the baseline-pass/PR-fail split is two different load draws, not a diff effect; and (b) **deterministic re-sampling** — 10/10 pass (5/5 standalone + 5/5 under 10-core CPU saturation). When the diff is a monotonic relaxation, (a) is available and is airtight in a way sampling can only approximate; reach for it first.
- **The precise diagnostic granularity is worth preserving — reject "drop the sub-deadline, ride the watchdog."** The alternative of running the JSONL wait under `rootCtx` (bounded only by the 60 s watchdog + check-timeout) was considered and rejected: it degrades the precise `open session jsonl: … did not appear: context deadline exceeded` message into a generic 60 s `timeout`. An explicit bounded deadline that errors *precisely* on genuine non-appearance is better hygiene than anchoring on liveness alone.

## Lessons learned

- **A single fixed deadline reduces a load-sensitive flake's *probability*, it doesn't eliminate its *tail*.** The fix's own target still hit the new 30 s bound **once** during QA's PR `make e2e` (`fail`, 30763 ms — the deferred-JSONL work exceeded even 30 s under that draw), yet deterministic re-sampling was 10/10 pass, including 5/5 under deliberate 10-core CPU saturation. This is expected, not a fix defect: the underlying operation's latency has an unbounded tail under unbounded contention, so no fixed clock guarantees 0 failures under *arbitrarily adversarial* artificial load. 30 s is 3× the *natural* ~10 s threshold and holds under representative make-e2e load; the once-observed 30 s fail was under QA's saturation harness, not a normal run. Code review passed the change as **safe by construction + probability-reduced** rather than proven-20/20, with a *non-blocking* SHOULD-FIX to record the actual post-fix run count/load before close. The honest framing: this makes the mis-route *rare*, and the escalation path (§ Follow-ups) exists if it recurs — it does not claim to make it impossible.
- **The mechanism-isolation repro deadline must sit below the standalone latency, not just "small."** The spec suggested shrinking `sessionFileWait` to ~1 s to prove the JSONL wait is the failure point; the developer found 1 s does **not** reliably reproduce, because standalone JSONL-open is ~200 ms — well under 1 s. The reliable value is `1 * time.Millisecond` (below the ~200 ms floor), which fails immediately after `prompt-written` with the exact PR #184 error string. When authoring a "shrink the deadline to force the failure" repro, calibrate the shrunk value against the operation's *observed* standalone latency, not against intuition.
- **`security-sensitive` gates on the label, not the blast radius — and the *absence* of the label is also a judgment.** PO deliberately did **not** label this `security-sensitive` (harness/timing, no touch to the permission-gate detection path), consistent with #173 itself being unlabeled. The code-review security gate was correctly skipped. The mirror of [#182's lesson](182.md) ("harmlessly conservative label is not a reason to skip the review"): a correctly-*withheld* label is what lets a truly-orthogonal change skip the gate without ceremony.

## Follow-ups anticipated

- **Sibling latent risk (deferred, not this ticket).** `spike-multi-turn`, `spike-long-prompt`, `spike-ask-user`, `spike-cancel`, `spike-permission` share `sessionFileWait = 10s` and the same deferred-JSONL window, so they carry the same latent load-sensitivity. None observed to flake → untouched per evidence-based selection. If a *second* spike reddens under the same signature, it earns its own ticket — or, once there is integration pressure from a second observed case, a follow-up that lifts a **shared load-tolerant default** (the natural home; today the constant is a distinct package-private local in each `package main`, zero coupling, so a blanket bump would fan out to 5+ files for no observed gain).
- **If 30 s proves insufficient at the 20/20 target** (the once-observed 30 s fail under QA saturation is the early signal to watch): the arch-doc contingency is to raise the e2e-runner per-check `Timeout` override for `spike-one-turn` **and** bump `sessionFileWait` further, keeping the internal deadline inside the (then-raised) check budget. The e2e-runner's 60 s `defaultCheckTimeout` was **not** touched here — no runner `timeout` has been *observed* for this spike (the failure is an internal `fail`), so a per-check override would be speculative defense against an unobserved mode.
