# #61 — library API: unified `Session.Events()` merging PTY + JSONL

[Issue](https://github.com/pyrycode/tui-driver/issues/61) · [Spec](../../specs/architecture/61-unified-events-channel.md) · [PR #94](https://github.com/pyrycode/tui-driver/pull/94) · Predecessors: [#59](59.md), [#60](60.md)

## Summary

Promoted the select-loop ceremony every spike binary has been writing — one ticker polling `Buffer.Snapshot` for PTY state, one tailer goroutine over the session JSONL, one `select` reconciling both in arrival order — into one library method: `(s *Session).Events(ctx, jsonlPath, startOffset) (<-chan Event, error)`. Internals are a single merge goroutine that owns the output channel (buffered cap 32, blocking on full — same shape as `TailJSONL`), a `time.NewTicker(DefaultPollInterval)` (50 ms) that calls `snapshot()` and a private `classify` helper to diff `(IsIdle, IsThinking, DetectModalClass)` against previous-tick values, and the existing `TailJSONL` channel as its JSONL source. The output `Event` carries a typed `EventKind` enum (six emitted kinds: `PtyIdle`, `PtyThinking`, `PtyModalShown`, `PtyModalHidden`, `JsonlEntry`, `JsonlEndOfTurn`), an `EventSource` tag (Pty / Jsonl) redundant-but-convenient for switch-on-source consumers, a wall-clock `Time` set by the merge loop (poll-tick for PTY events; channel-receive instant for JSONL events), a `Modal ModalClass` field populated only on `PtyModal*`, and an `Entry JSONLEntry` field populated only on `Jsonl*`. The synthetic `JsonlEndOfTurn` fires immediately after the underlying `JsonlEntry` whenever `IsEndTurn(e)` holds — both events carry the same entry, so consumers can switch on `Kind` without re-running the predicate. Two ordering rules the developer codified in the loop body: (1) on a modal class→class change the merge loop emits `Hidden(old)` before `Shown(new)` in the same tick; (2) idle/thinking emissions are **suppressed while a modal is active** (modal axis dominates) — a permission prompt renders with `❯` present and no spinner, so `IsIdle(snap)` would otherwise fire a false "ready for next prompt" signal during what is actually "claude is waiting on modal input." The merge loop starts transition-blind (prev state zero-valued); the first tick fires whichever rising edges hold against that, so a buffer already idle at subscription emits one `PtyIdle` immediately — documented as the "current state on subscribe" signal. Shutdown invariant: ctx cancellation or `jsonlCh` closure (the latter signals an unrecoverable `TailJSONL` I/O error mid-tail) drives the merge goroutine through one of three `select` arms, `defer close(out)` fires on every return path, and the maximum delay between ctx cancellation and output-channel close is bounded by one poll tick (50 ms). The package doc-comment in `tuidriver.go` gained the phrase "unified PTY+JSONL event subscription" in its in-scope sentence. **Existing primitives (`IsIdle`, `IsThinking`, `DetectModalClass`, `TailJSONL`, `IsEndTurn`, `AssistantText`) keep their shape and stay public** — `Events()` is purely additive; consumers that prefer to compose the streams themselves keep doing so. The four `cmd/spike-*/main.go` select-loop migrations and the cross-repo `pyry acp` migration to `Events()` are deliberately deferred to follow-ups (#62 + downstream).

## Patterns established

- **In-library multi-goroutine composition is now the streaming-API shape.** `Events` spawns a merge goroutine that itself consumes from `TailJSONL`'s goroutine — the first place in `pkg/tuidriver/` where one library goroutine reads from another library goroutine. The shape works because each goroutine has one owner and one exit signal: `TailJSONL`'s tailer exits on `ctx.Done()` or unrecoverable I/O (closes `jsonlCh`); the merge goroutine exits when either of its three `select` arms fires (`ctx.Done()`, `jsonlCh` closed observation via `ok := <-jsonlCh`, or backpressure-aware send observing `<-ctx.Done()` mid-emit). No mutexes added — the merge goroutine is `jsonlCh`'s sole reader, `out`'s sole writer, and `prevIdle`/`prevThinking`/`prevModal` are loop-local. Reuse posture: when a future library API needs to compose two streaming primitives, copy this layout — one merge goroutine, deferred close on the owned channel, three-arm select with backpressure-aware sends to the output. Do not add a `Handle` struct with `Stop()`/`Err()` methods; the channel-close + `ctx.Err()` pair already covers every shutdown signal a handle API would carry.
- **Polling against a snapshot function is the testable seam for buffer-derived state.** `mergeEvents` takes a `snapshot func() []byte` parameter (production caller passes `s.Buffer.Snapshot`); tests pass a `*testSnap` helper with `Set(b)` / `Snapshot()` methods to drive any byte-state the predicates need, including state transitions a real `*Buffer` can't easily reproduce (the rolling buffer is append-only; transitioning modal-class A→B by dropping A's anchor bytes requires the test source to drop bytes, which `*Buffer` does only by overflow-by-byte-count). The seam is internal — `Events`'s public signature still takes the `*Session` and reads `s.Buffer.Snapshot` itself — but the seam **exists** as a function parameter on `mergeEvents`, which is what makes the loop unit-testable without spawning a real PTY. Reuse posture: when a library function reads "rolling state" from a Session field, define the work loop as a private helper that takes the read closure as a parameter rather than the Session itself. The Session-method wrapper becomes a three-line "spawn goroutine over `s.X.Y`"; the unit tests target the helper.
- **`testSnap` is the canonical "controllable snapshot source" for any future merge-loop test.** Three properties make it the right primitive: (1) `Snapshot()` returns a copy under lock — matches `Buffer.Snapshot`'s contract so the merge loop literally can't tell the difference; (2) `Set(b)` replaces the bytes wholesale, supporting both grow and shrink (which `Buffer.Append` can't); (3) zero-value usable (`&testSnap{}` is a valid empty buffer). The 7 `TestMergeEvents_*` tests all use it via dependency injection. Reuse posture: any future test for a primitive that takes "snapshot of bytes" as input should use this helper rather than constructing a real `*Buffer` — the latter pulls in the rolling-buffer behaviour (capacity, append-overflow semantics) the test doesn't care about and **can't** drive transitions that require byte-removal.
- **Six-kind `EventKind` enum + `EventSource` tag is the right shape for typed-union output channels.** Each `EventKind` value is one named transition or arrival; the consumer's `switch ev.Kind` is exhaustive and gets a compile-time-detectable default arm via the explicit `EventKindUnknown` zero value (never emitted; same idiom as `ModalClassUnknown`). The `EventSource` tag is structurally redundant with `Kind` but materially useful — consumers that dispatch "all PTY events through path A, all JSONL events through path B" check `ev.Source` once instead of mapping six kinds to two paths. Per-kind payload fields (`Modal` for `PtyModal*`, `Entry` for `Jsonl*`) are sparse — both `PtyIdle` and `PtyThinking` carry no payload at all — and the doc-comment documents the population rule per-kind. The cost of the sparse fields is one zero-value `ModalClass` + one zero-value `JSONLEntry` per `PtyIdle`/`PtyThinking` event (≤16 bytes each per Go struct layout, dwarfed by the channel-send cost). The benefit is one flat `Event` struct instead of a sum-type-via-interface (which would force `switch ev.(type)` and a heap allocation per send). Reuse posture: for any future library streaming API that emits a small, fixed taxonomy of typed events, prefer a flat struct with a `Kind` enum + sparse payload fields over `interface{}` + type-switch on the consumer side. Allocation profile is friendlier and the consumer-side switch is easier to read.
- **"Filter moves up the stack" + "polling beats subscribing to `Buffer.Append`" are now both load-bearing across two library promotions.** `#59`'s `TailJSONL` emits every envelope type (filter moves up); this slice's `Events` polls `Buffer.Snapshot` at `DefaultPollInterval` instead of subscribing to per-`Append` notifications. Same reasoning shape both times: the spike-side narrow API (assistant-only filter, per-append notification) imposes design choices the library cannot anticipate downstream (cancellation markers need `user`-role; coalescing multi-`Append` ANSI redraws is per-consumer policy). The library promotes the wider primitive and pushes the narrower choice to consumers, paying a one-line filter cost or a 50 ms poll cadence — both empirically negligible. Reuse posture: when promoting a spike helper, default to the wider primitive (more envelopes, simpler internals) and resist the temptation to ship the spike's narrow filter or its push-based notification shape. The spike narrowed because it knew exactly which signal it wanted; the library can't.

## Lessons learned

- **Modal suppression updates `prev*` unconditionally, leaking the post-modal-close idle/thinking rising edge.** The merge loop's tail (`events.go:212-234`) updates `prevIdle = curIdle` and `prevThinking = curThinking` at every tick — including ticks where the idle/thinking emissions were suppressed because `curModal != ModalClassUnknown`. So while a Permission modal is active, `prevIdle` quietly tracks the underlying `IsIdle` classification (true throughout, because the modal renders with `❯` present — see [system-overview § Permission modal present](../architecture/system-overview.md) and `pkg/tuidriver/state.go:36-37`). When the modal then hides while claude is still idle, the tick computes `cur.idle=true && !prev.idle=true` → false → no `PtyIdle` fires after the `PtyModalHidden`. The consumer sees the modal go away and gets no "ready for next prompt" signal — exactly the ceremony the unified channel is supposed to eliminate. The code-review caught this on PR #94 ("[SHOULD FIX] modal-active suppression leaks an idle/thinking rising edge across modal close") and noted it as a spec-level gap, not a developer error — the spec explicitly says "Update `prev = cur`" with no exception for suppressed axes. `TestMergeEvents_ModalShowAndHide` masks the bug by transitioning Permission→MCP→idle (the MCP detour drops `❯` and resets `prevIdle` to false), so a Permission→idle test would catch the regression. The two fixes the reviewer flagged: (a) don't update `prevIdle`/`prevThinking` while a modal is active; (b) on `prevModal != Unknown && curModal == Unknown`, force-emit the current idle/thinking state. **Currently unfixed in `feature/61`** — review decision PASS-with-flag; a follow-up ticket will pick the fix shape (likely (a) — minimal and symmetric). Reuse posture: when suppressing emissions on one axis based on another axis's state, **either** suppress the `prev*` updates symmetrically **or** force-emit the suppressed axes on the suppressing-axis-clear transition. Updating `prev*` without emitting is the failure mode; one of those two compensations restores the contract.
- **A spec that pre-decides the open questions converts to a one-shot implementation — but per-axis edge interactions in a multi-axis state machine are exactly where the spec can still miss.** Same pattern that worked on #58, #59, #60 worked again on #61: the architect named every public symbol, every doc-comment paragraph, every test row, every considered-and-rejected alternative (handle struct? Buffer.Append subscription? configurable poll interval? msg_id grouping?). The developer's job collapsed to typing it in, no mid-implementation thrash, code-review PASS. **But the modal-suppression edge case slipped through both the spec and the developer** — the spec said "Update prev = cur" verbatim and the developer matched it verbatim, and the loop's behaviour against the documented test matrix is correct (no test in the AC scenario list catches it). The gap is between "the spec covers every scenario the AC names" (it does) and "the spec covers every scenario the API will encounter in practice" (it misses the Permission→idle path, which is a common real-world flow). Reuse posture: when a spec defines a state machine with two-or-more independent axes that interact via suppression rules, write down the "what happens at the suppressing-axis-clear transition" answer **for every suppressed axis** in the spec, not just "update prev". The cost in the spec is one paragraph; the cost in the field is a code-review finding plus a follow-up ticket.
- **`*Buffer` is not a sufficient test seam for state machines that consume snapshots — `testSnap` is.** Initial intuition would be to use the production `*Buffer` in tests (it's cheap, exercises real library code, no extra fixture). Empirically wrong: `*Buffer.Append` is append-only, so a test transitioning modal A → modal B has to either (a) overflow the 4 KB rolling buffer with junk before appending B's anchor bytes — fragile, noisy, hard to read; or (b) use a non-`*Buffer` snapshot source that supports `Set`-style replacement. The `testSnap{mu, b}` helper (24 lines) does (b) trivially; every `TestMergeEvents_*` uses it for `Set(bytes-without-A-anchor; bytes-with-B-anchor)` phase transitions. The investment is paid back in every test that needs a state transition `*Buffer`'s append-only semantics can't reproduce. Reuse posture: for any future test against a primitive whose input is "bytes the consumer can observe via snapshot," default to a `testSnap`-shaped helper rather than a real `*Buffer`. The test is shorter, the phases are clearer, and the test catches bugs `*Buffer.Append`'s overflow-driven semantics would mask.
- **A merge loop's `Time` field should be set by the merge loop, not the source — even when one of the sources (JSONL) carries its own timestamp.** The JSONL envelope has a per-line `timestamp` field; setting `Event.Time = entry.timestamp` for `JsonlEntry`/`JsonlEndOfTurn` would give consumers the wall-clock instant claude wrote the line. Rejected, for the same reason `Event.Time` is set in the merge loop for PTY events (where there's no per-byte timestamp): consistency across sources is more valuable than precision on one source. A consumer ordering events by `ev.Time` wants a monotonic single-clock reference, not a mix of "when claude wrote it" and "when the merge loop saw it." Consumers needing the JSONL timestamp specifically read it from `entry.Raw["timestamp"]` (one extra type-assert; both fields are present per `JSONLEntry`'s shape). The decision is documented in the `Event.Time` doc-comment so future-me doesn't relitigate. Reuse posture: when a merge primitive interleaves events from sources with different timestamp semantics, set the timestamp in the merge loop using the merge loop's clock. Per-source timestamps remain available on the payload field for consumers that want them; the loop's clock provides the single ordering reference.
