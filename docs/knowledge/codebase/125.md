# #125 — tuidriver: add `NewCastRecorder` library API (asciinema v2, from spec)

[Issue](https://github.com/pyrycode/tui-driver/issues/125) · [Spec](../../specs/architecture/125-castrecorder.md) · [PR #126](https://github.com/pyrycode/tui-driver/pull/126) · Commit `c2c4db6` · Feature doc: [cast-recorder](../features/cast-recorder.md)

## Summary

Adds `tuidriver.CastRecorder`, an `io.Writer` that mirrors a PTY byte stream to an [asciinema v2](https://docs.asciinema.org/manual/asciicast/v2/) `.cast` recording — a flight recorder for `claude` sessions. `WriteHeader()` emits the version-2 header line (`{"version":2,"width":<cols>,"height":<rows>}`); each `Write(p)` appends one `[elapsed, "o", string(p)]` event. The **elapsed clock starts lazily on the first `Write`**, so the first event is ≈ 0 regardless of the construction→header→first-byte gap. `*CastRecorder` satisfies `io.Writer` so it drops straight into [`SpawnOpts.Mirror`](../../../pkg/tuidriver/session.go) (`session.go:37-49`) — the passive mirror seam that previously only teed the TUI to `os.Stderr` for spike operators now has a library-provided recording consumer. One new file (`pkg/tuidriver/castrecorder.go`, ~115 lines incl. doc comments) plus its unit test; **no existing file changed.**

**Re-scoped from "promote from spike" to "from-spec build."** The original framing ("promote the existing `castRecorder` from `cmd/spike-record`, start from `spike-screen-recorder`") was dead: that spike (built 2026-05-30) was never committed or pushed and is unrecoverable — same loss as pyrycode#553. Re-verified on the primary clone: `spike-screen-recorder` was a bare alias for `main` (`317c210`), no commit in `--all` history touched `cmd/spike-record`/`cmd/analyze-cast`, and the `-S` pickaxe for `castRecorder`/`NewCastRecorder` was empty. The library API was therefore built directly on `main` from the spec, with no spike branch to start from and no `cmd/` consumers to update (they're gone — out of scope).

The full behavioural contract (wire format, lazy clock, data encoding, error handling, concurrency model) is documented in the [cast-recorder feature doc](../features/cast-recorder.md). This file records the implementation-specific decisions, patterns, and lessons.

## Patterns established

- **A spec's "highest-risk decision" callout is a routing instruction, not a suggestion — follow it rather than re-derive it.** The spec dedicated a whole section ("The one subtle decision: data-string encoding (resolved)") to a single choice: marshal `string(p)` with `encoding/json`, accept U+FFFD coercion of invalid UTF-8, and **do not hand-roll a byte-exact escaper**. The AC phrasing *"non-UTF8 escaped correctly"* + *"decodes back to the exact bytes of `p`"* is genuinely misreadable as "byte-exact for arbitrary binary," which would send a developer down a multi-turn rabbit hole building a custom escaper that (a) isn't required and (b) can't actually round-trip arbitrary bytes through standard JSON decode. The developer followed the resolution verbatim; the test asserts byte-for-byte round-trip only for **valid** UTF-8 (quotes, control/escape bytes, multibyte runes), and explicitly does **not** assert `[]byte{0xff}` survives. Reuse posture: when a spec flags a decision as "highest-risk / resolved / do X not Y," treat the AC as describing the *behaviour* and the spec section as the *contract* — the spec author already paid the cost of resolving the ambiguity. This is the encoding-side analogue of [#109](109.md)'s "the wire dictates field-tag spelling, the spec describes shape" — both are cases where the literal artifact (here the spec's resolution, there the captured `.bin`) overrides a plausible-but-wrong reading.
- **Lazy-init a clock on first use to decouple a recording's timeline from harness startup latency.** The elapsed origin is set on the first `Write` (`if r.start.IsZero() { r.start = time.Now() }`), not at construction or `WriteHeader`. This guarantees the first event's `elapsed ≈ 0` no matter how long setup took, so a replay tracks the session rather than the driver's boot time. The test proves it by sleeping 20 ms between `WriteHeader` and the first `Write` and asserting `elapsed < 0.01`. Reuse posture: any "time since the stream started" primitive should anchor its origin on the first datum, not on object creation — construction time is an implementation detail of the harness, not part of the recorded signal. The `start.IsZero()` sentinel (zero `time.Time` = "not yet started") is the idiomatic Go way to express this without a separate `started bool`.
- **A new consumer of an existing passive seam needs zero changes to the seam.** `SpawnOpts.Mirror io.Writer` already existed and was only ever fed `os.Stderr`. Because the seam was typed as the narrowest useful interface (`io.Writer`), adding a recorder was a pure additive change — no edit to `session.go`, no new option, no wiring. Reuse posture: when a seam is already an `io.Writer`/`io.Reader`, the cheapest way to add a capability is a new type that satisfies it, not a new field on the producer. The compile-time `var _ io.Writer = (*CastRecorder)(nil)` assertion makes the contract explicit and catches drift at build time.

## Lessons learned

- **The `spike-screen-recorder` spike was lost — the same uncommitted-local-branch loss as pyrycode#553 — and the ticket had to be re-scoped from "move + export" to "from-spec build."** The original body assumed a working `castRecorder` in `cmd/spike-record` on a `spike-screen-recorder` branch, built 2026-05-30. It was never committed or pushed; the branch was a bare alias for `main`. The re-scope was done up front (in the issue body, 2026-05-31) after re-verification on the primary clone (`git --all` history scan + `-S` pickaxe for the symbol names, both empty). Lesson: this is the **third** recorded instance of a local spike branch evaporating (see the auto-memory `verify-spike-branch-before-promote` — "local spike branches have been lost twice"; this is the third). The discipline that paid off: the re-scoper *verified the branch actually held the code before refining*, found it didn't, and converted the ticket to a from-spec build rather than chasing a phantom. Any future "promote from spike branch X" ticket must confirm X actually holds the code in this repo (`git log --all -S<symbol>`, `git log --all -- <path>`) before starting — a green pickaxe means the spike is gone and the ticket is really a from-spec build. The recurring root cause (spikes built but never pushed) is a process gap upstream of this pipeline; the in-pipeline mitigation is cheap pre-flight verification.
- **`make e2e` is not runnable in the non-interactive build environment, and that's fine for a pure library addition — the per-package `go test` gate is the relevant one.** `make e2e` spawns a live `claude` subscription session (the operator's integration gate), which needs an interactive terminal + operator config. For a library-only change with no `cmd/` consumer, the relevant gate is `go test ./...` over `pkg/tuidriver` (green: `ok github.com/pyrycode/tui-driver/pkg/tuidriver 5.685s`, plus race detector + `go vet` + `gofmt -l` + `go build ./...` all clean). The developer pasted the `ok` line per the AC and noted the `make e2e` limitation explicitly in the PR. Lesson: the AC's "`make e2e` / `make test`" is an *either/or* — for additive library code that touches no spike and no real-claude path, the unit gate is sufficient and the e2e gate is operator-run. Don't block a green library PR on an integration harness it doesn't exercise.
- **`snapshot-drift` was RED at code-review but is a pre-existing failure on `main` (`317c210`), not caused by this PR — classified out-of-scope via baseline comparison.** The QA gate ran `snapshot-drift` against `git merge-base HEAD origin/main` and confirmed it fails on both the baseline and the PR branch; the other 9 e2e checks were green on both. This matches the standing pattern (auto-memory `snapshot-drift-tracker-deferred`): snapshot-drift is a recurring renderer-volatility red on `main`, classified PASS via baseline comparison, current signature tracked as #127. Code review PASSED. Lesson: a RED CI gate on a docs/library PR is only blocking if the *baseline* is green — always diff against the merge-base before attributing a failure to the change under review.
