# #158 — add a general "unrecognized modal" axis to readiness

[Issue](https://github.com/pyrycode/tui-driver/issues/158) · [Spec](../../specs/architecture/158-unknown-modal-readiness-axis.md) · [PR #192](https://github.com/pyrycode/tui-driver/pull/192) · Commit `9d95061` · Size: XS · Security-sensitive (the axis reads attacker-influenceable rendered TUI bytes into consumer readiness state; spec carries a `## Security review` section, verdict PASS)

## Summary

`WaitReady` classified the first post-idle screen against a closed set of conditions — trust modal, MCP-failure banner, network-failure banner — so any startup dialog outside that set left `Readiness` clean and the consumer typed its first prompt straight into the dialog. `DetectModalClass` already recognises eight modal classes, but only the trust modal reached `Readiness` (as `TrustModal`); the other recognised classes (permission, ask-user-question, slash-picker, model-select, permissions-config, `/mcp`, agents) were invisible at readiness time.

This ticket adds one catch-all axis. `Readiness` gains an additive `UnknownModal bool`, and `WaitReady` sets it via a new unexported `isUnknownModal(snap)` that returns true for any `DetectModalClass` result other than `ModalClassUnknown` (the common no-modal idle screen) and `ModalClassTrustFolder` (already surfaced by `TrustModal`). Report-only: the library flags that a dialog the first prompt would land in is up, and the consumer owns abort-vs-continue. No change to `modal.go`; the classifier is consumed as-is.

## Patterns established

- **A "recognised-but-not-yet-surfaced" axis is the inverse of the no-match case, not equality with it.** The trap the spec calls out and the implementation avoids: `DetectModalClass` returns `ModalClassUnknown` for BOTH the common no-modal idle screen and a genuinely unrecognised dialog, so `class == ModalClassUnknown` would fire on nearly every clean readiness. The axis is instead "a class is positively detected AND it isn't one `Readiness` already surfaces" — `switch class { case ModalClassUnknown, ModalClassTrustFolder: return false; default: return true }`. Reuse posture: any future readiness axis derived from a classifier whose zero value doubles as "no signal" must exclude that zero value explicitly rather than key off it.
- **Detecting a genuinely novel dialog stays out of scope.** This axis rides on the existing recognised-class set. Distinguishing a truly unknown modal frame (one `DetectModalClass` returns `ModalClassUnknown` for, but that is a dialog rather than the empty idle screen) needs a forgery-resistant modal-frame-present signal that does not exist yet; it rides on the rendered-grid chain (#152). The field's godoc says so, so a later reader does not mistake this class-based axis for full novel-dialog detection.

## Lessons learned

- **Existing table rows cover the negative acceptance criteria for free — verify, don't rewrite.** After adding the field, the pre-existing `TestWaitReady` "clean idle" row (`want: Readiness{Idle: true}`) already asserts `UnknownModal == false` by zero value, covering "no false positive on the normal ready path"; the "trust modal at idle" row already asserts it stays false while `TrustModal` is true, covering "trust stays surfaced via `TrustModal`, not double-counted." Only the positive case needed a new row. Adding a struct field to a table-driven test that asserts full-struct equality is backward-safe: unspecified fields zero-value on both sides.
- **`ModalClassMCP` is deliberately NOT excluded.** `McpFailure` surfaces the "N MCP servers failed" status *banner* (`HasMcpFailureBanner`), a different thing from claude's interactive `/mcp` *modal* (`ModalClassMCP`). If the `/mcp` modal is genuinely up at idle, that is a dialog to flag, so `UnknownModal` is true for it. Only `ModalClassTrustFolder` is excluded, because only it is already carried by another `Readiness` field.
