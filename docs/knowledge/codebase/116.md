# #116 — spike-cleanup: migrate spike-multi-turn off duplicated helpers

[Issue](https://github.com/pyrycode/tui-driver/issues/116) · [Spec](../../specs/architecture/116-spike-multi-turn-migrate-off-duplicated-helpers.md) · [PR #117](https://github.com/pyrycode/tui-driver/pull/117) · Predecessors: [#58](58.md), [#59](59.md), [#60](60.md), [#73](73.md), [#87](87.md), [#89](89.md), [#112](112.md)

## Summary

Closes the third of the four [#89](89.md)/[#112](112.md) spike-migration follow-ups. `cmd/spike-multi-turn/main.go` drops `projectsDir`, `openSessionJSONL`, `tailJSONL`, `isEndTurn`, `typePrompt`, `spinnerRe` + `matchSpinner`, the inline 1 Hz watchdog goroutine, and the wg-driven tailer in favour of the corresponding `pkg/tuidriver/` primitives (`SessionJSONLPath` + `WaitForSessionJSONL`, `TailJSONL`, `IsEndTurn`, `Session.TypePrompt`, `RunWatchdog` + `ParseSpinner`). The session-scoped event channel becomes `<-chan tuidriver.JSONLEntry`; `extractByMsgID` and `msgIDOf` stay in-file but switch to struct-field access. Net diff: 326 lines down (85 added, 241 removed) in a single file. AC #1's mechanical grep returns empty; `go vet`, `go test -race`, and `make e2e` all pass; the three snapshot-drift fixtures match. Mirrors [#112](112.md)'s spike-one-turn shape closely (closer than spike-long-prompt because both keep the PTY-quiescence termination predicate).

Two shape choices deserve calling out. First, **the `runTurn` `eventCh` parameter is `*<-chan tuidriver.JSONLEntry`, not `<-chan tuidriver.JSONLEntry`** — pointer-to-channel-slot. The reason is the multi-turn-specific deferred-tailer constraint from [#9](9.md)'s finding #9: interactive `claude --session-id` does not create the JSONL file until the first input arrives, so the tailer can't be started in `main` before turn 1's prompt-write. Turn 1's `postPromptHook` populates the session-scoped slot after the prompt is typed; turns 2+ pass a nil hook and reuse the slot. The pointer indirection is what lets the hook's `eventCh = ch` assignment in `main`'s closure scope become visible to the post-hook receive loop inside `runTurn` without restructuring `main` into a "phase 1 = first turn (inline), phase 2 = loop" two-block shape. Pre-hook drain inside `runTurn` therefore gates on `*eventChRef != nil` so turn 1's drain is a no-op (`cmd/spike-multi-turn/main.go:283-292`); the receive loop dereferences once post-hook (line 332) and then runs the normal channel-close-sentinel `case ev, ok := <-eventCh:` + `if !ok { eventCh = nil; continue }` (`main.go:388-396`, mirror [#112](112.md)). Second, **`msgIDOf` carries an `ev.Message == nil` guard** — load-bearing because library `TailJSONL` emits every JSONL envelope type (assistant, user, attachment, file-history-snapshot, …) and only assistant/user carry a `Message`. The pre-migration local `tailJSONL` filtered to `type=="assistant"` only, so the guard wasn't needed; the library is deliberately type-agnostic so the consumer takes on the nil-check. `extractByMsgID`'s `msgIDOf(ev) != targetID` short-circuits when `Message` is nil (returns ""), so the existing extraction loop body doesn't need its own guard.

`resolveSession` shrinks to `(sessionID, err)` mirror of spike-long-prompt / spike-one-turn — caller composes `home, _ := os.UserHomeDir(); cwd, _ := os.Getwd(); jsonlPath := tuidriver.SessionJSONLPath(home, cwd, sessionID)` directly (`main.go:118-126`). The legacy `projects-dir path=...` startup log line is dropped (same call as [#112](112.md) — `session-id-resolved id=... jsonl=...` carries the same path; the e2e harness asserts only on `SUCCESS: <text>` stdout). PTY-quiescence termination predicate (the three-clause `gotEndTurn ∧ bytes.Contains(stripped, tuidriver.IdleGlyph) ∧ rb.QuietFor() >= ptyQuietWindow` at `main.go:372-381` and the ~60 lines of [#73](73.md) rationale at lines 49-61 and 336-362) preserved verbatim per architect's load-bearing flag.

Two follow-ups from [#89](89.md)'s list remain after this PR: `spike-cancel`, `spike-permission`. (`spike-ask-user` was completed earlier — [#87](87.md) already landed for it and the watchdog/spinner half was the [#112](112.md) shape.) Both remaining are the same mechanical template as the spike-multiselect half of [#112](112.md) plus the [#87](87.md) `TypePrompt` migration. Neither needs the pointer-to-channel pattern from this ticket — they don't have the deferred-tailer constraint (spike-cancel and spike-permission both operate within a single turn, so the JSONL exists by the time the tail loop runs).

## Patterns established

- **Pointer-to-channel-slot for hook-populated session-scoped channels.** When a tail channel can't exist at consumer setup time — because the file it tails is created by a side effect of a later operation (here: turn 1's prompt-write triggers claude to create the session JSONL) — the consumer can sidestep restructuring the caller into "phase 1 = inline, phase 2 = loop" by passing `*<-chan T` instead of `<-chan T` to the per-iteration function. The first iteration's hook populates the slot via the caller's closure; subsequent iterations see the populated channel. Per-iteration code gates the pre-hook drain on `*eventChRef != nil` (turn 1: no-op) and dereferences once post-hook into a local `eventCh` for the receive-loop. Reuse posture: any spike-shaped binary whose tailer depends on a side effect of the first input (think `claude --session-id` deferred file creation, or any TUI whose log-file path is announced only after handshake) wants this pattern over the alternatives (forwarder goroutine that proxies a never-receives chan; restructure `main` into two phases). The pointer is cheap; the alternatives ripple. This is genuinely multi-turn-specific — spike-one-turn / spike-long-prompt open the JSONL on a known-existing path and can create the channel in `main` before `runTurn`, so this pattern doesn't apply there.
- **`msgIDOf`-style helpers need a nil-guard on `ev.Message` when consuming `tuidriver.TailJSONL`.** `TailJSONL` emits every JSONL envelope type, not just `assistant` and `user` — file-history-snapshot, attachment, system, and future envelopes show up too, and only assistant/user carry a populated `Message` pointer. Consumers that pull msg_id (or any other Message-resident field) from arbitrary entries must `if ev.Message == nil { return "" }` first. The pre-extraction shape filtered to `type=="assistant"` inside `tailJSONL`, so consumers never saw non-message envelopes and never needed the guard. The library deliberately doesn't filter — it's the consumer's job to ignore the kinds they don't care about, which makes mixed consumers (assistant text + attachment metadata, say) cheap. Reuse posture: any consumer porting a `map[string]any`-typed local tailer onto `TailJSONL` needs to audit every site that reads `ev.Message.*` and add the nil-guard. `go vet` does NOT catch this — the field access on a nil pointer panics at runtime. The fix is one line, but missing it crashes the binary on the first non-message envelope, which (luckily) is rare enough that smoke tests can pass and the bug surfaces in production.

## Lessons learned

- **The spec's "IsEndTurn is strictly stricter than the local `isEndTurn`" prediction held; the two predicates were behaviourally equivalent for this spike's prompts.** Pre-migration, the local `isEndTurn` returned true for any entry whose `message.stop_reason == "end_turn"`, regardless of type. Library `tuidriver.IsEndTurn` additionally requires `e.Type == "assistant"` AND `AssistantText(e) != ""` (i.e. the assistant message has at least one non-empty text block). The spec flagged the divergence with a behavioural note: for this spike's prompts 1-5 (every final assistant message carries text — every prompt asks for a worded reply or summary), the two predicates fire on the same lines. `make e2e` confirms — all 5 prompts emit `SUCCESS: <text>` and exit 0. The stricter predicate is the safer default going forward; it rejects pathological future-claude `end_turn`-without-text deltas that would slip past the local version. Lesson: when a library predicate is strictly stricter than the consumer's local predicate, the migration is safe iff the consumer's input domain is a subset of the stricter predicate's accept set. Confirm that subset relation in the spec (the architect did) and the migration is mechanical; skip that confirmation and the migration is a behaviour change disguised as a refactor. Note this is the inverse direction from the usual `tuidriver.IsIdle` migration concern (where the library is sometimes stricter in ways that wedge against transient buffer residue, see [#97](97.md) / [#73](73.md)); the direction matters when judging whether "stricter" is safe.
- **`TailJSONL` emitting all envelope types (not just assistant-filtered) was a memory non-event in practice.** The spec called out that `runTurn`'s `events` slice would now accumulate user(tool_result), attachment, file-history-snapshot, and other entry types in addition to assistant deltas. For prompt 2's `list the files in /tmp` (Bash tool) and prompts 4-5 (parallel Read tool probes), this means tool_result entries land in the slice and are filtered out by `extractByMsgID` (different msg_id) and `IsEndTurn` (non-assistant). The slice grew by maybe 20-30 entries per turn vs. the assistant-only pre-migration shape. `make e2e` runtime for spike-multi-turn was unchanged (~45 s wall — all five turns); the GC didn't notice. Lesson: when a library API is deliberately unfiltered ("emit everything; consumer filters"), pre-migration filtered-at-source consumers tend to over-estimate the memory/CPU cost of the unfiltered firehose. Real spike-shaped workloads carry tens to hundreds of entries per turn, not millions. The unfilteredness is a feature — it lets multi-axis consumers (assistant text + attachment-list + token-usage histogram, say) compose against one channel — and the cost is in the noise. Premature filtering inside the library would have been a bad trade.
- **Vestigial `sync.WaitGroup` in `main` was left in place per template-parity** (spec § Concurrency model). Pre-migration `main` declared `var wg sync.WaitGroup` with two `wg.Add(1)` calls (watchdog + tailer); after the migration there's only one (the `RunWatchdog` wrapper at `main.go:170-177`), and there's still no `wg.Wait()` anywhere in the file. The watchdog goroutine is lifecycled by `rootCtx` cancellation, not by WaitGroup synchronisation. [#112](112.md)'s spike-one-turn migration noted the same vestige and deleted the WaitGroup entirely. This ticket's architect explicitly chose template-parity over deletion ("removing it here is out of scope for this cleanup"), so it stays. The asymmetry between spike-one-turn (WaitGroup deleted) and spike-multi-turn (WaitGroup retained) is visible but harmless. Lesson: scope discipline in mechanical migrations cuts both ways — when the [#112](112.md) author dropped the WaitGroup as part of an in-scope deletion sweep, that was right; when this ticket's architect chose to leave it for a future sweep, that was also right. The judgment call is "is this deletion mechanical-equivalent or does it require thinking?" The WaitGroup deletion requires confirming nothing depends on it, which is one extra check per binary; bundling it into a cleanup-focused ticket is fine, deferring it to a tidy-pass ticket is also fine. What's NOT fine is "delete it because spike-one-turn did" without the confirmation step.
- **Import-list deletions matched the [#87](87.md) / [#112](112.md) prediction:** six unique imports dropped (`bufio`, `encoding/json`, `io`, `path/filepath`, `regexp`, `strconv`) — exactly the union of `tailJSONL`'s reader stack, `projectsDir`'s path composition, and `matchSpinner`'s regex. `strings` stays (used by `extractByMsgID`'s `strings.Builder`). `bytes` stays (used by `runTurn`'s predicate for `bytes.Contains(stripped, tuidriver.IdleGlyph)`). `sync` stays (the vestigial WaitGroup). `go vet` flagged each unused import on its own line — no archaeology required, same as [#112](112.md)'s experience.
