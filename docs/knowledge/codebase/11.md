# #11 — spike: cancellation mid-response (ESC keystroke, JSONL signaling, recovery)

[Issue](https://github.com/pyrycode/tui-driver/issues/11) · [Spec](../../specs/architecture/11-spike-cancel.md) · Code: `cmd/spike-cancel/`

## Summary

Third spike binary in the repo: `cmd/spike-cancel/main.go` (~1060 LOC) plus `cmd/spike-cancel/README.md` (~610 lines of empirical log). Drives three sequential probes against a single PTY-attached `claude --session-id <uuid> --permission-mode bypassPermissions` process: Probe 1 cancels mid-thinking (monad-essay prompt), Probe 2 cancels mid-tool-use (`recursively list all files under /tmp`), and Probe 3 verifies the same session is recoverable with `say hello`. Reuses spike #9's primitives verbatim under attribution comments (`rollingBuffer`, `tracker`, `isIdle`, `tailJSONL`, `resolveSession`, `extractByMsgID`, `typePrompt`, etc.) and adds: `runProbe`/`runCancel`/`runRecovery`/`waitForKickoff`/`waitReappeared`/`logCancelEvent`, `sendCancel` (single bulk-write of the keystroke), `clearInputLine` (Ctrl-U), `hasSpinnerGlyph`/`isToolUse` predicates, `parseCancelKeystroke` + `-cancel-keystroke` flag, and a new `rollingBuffer.quietFor()` PTY-quiescence primitive.

Five empirical answers (one per open question this spike was filed to resolve):

1. **Cancel keystroke is ESC (`0x1b`), single byte, no `\r`.** Double-ESC and Ctrl-C also work; ESC is preferred because it matches the on-screen `esc to interrupt` hint and is the simplest single-byte representation. Library default should be ESC; alternatives are nice-to-have for debugging.
2. **Cancellation is signaled in the JSONL via `user(text "[Request interrupted by user]")` — NOT via a new `stop_reason` value or envelope type.** The cancelled assistant message keeps its pre-cancel `stop_reason` (e.g. `tool_use`); no `stop_reason=canceled`/`null`/`max_tokens` ever surfaces. The marker lands AFTER any in-flight `tool_result` events. The current assistant-only tailer filter drops this marker — consumers needing JSONL-side cancel acknowledgment must widen the filter or rely on PTY-side detection (see [JSONL layout § Cancellation signal](../architecture/jsonl-layout.md)).
3. **Cancel propagation is fast (~100 ms thinking, ~600–1200 ms tool-use).** End-to-end `cancel-sent → ❯-reappeared` measures ~1.6 s (thinking) / ~2.1–2.7 s (tool-use), but most of that is the 1500 ms `ptyQuietWindow` debounce. The 30 s post-cancel watchdog from the AC is mostly headroom.
4. **Tool subprocesses are NOT killed by ESC.** Probe 2's `ls /tmp` Bash subprocess ran to completion and emitted its `tool_result` BEFORE the interruption marker. No orphan subprocesses (`pgrep -lf '^ls '` returns nothing post-exit), but that's because `ls /tmp` is fast — the cancel doesn't kill in-flight tools, the tools just happen to finish first. Implication for `pyry acp`: an ACP `session/cancel` issued during tool execution can NOT abort the running tool; consumers must surface this honestly.
5. **The session is fully recoverable post-cancel.** Probe 3's `say hello` lands a fresh `msg_id` (not derived from cancelled probes), normal `stop_reason=end_turn`, coherent response (`"Hello."` / `"Hello!"`) — same wall time (~2.1–2.7 s) as a spike-#9 turn-1 baseline. The `[Request interrupted by user]` marker acts as a hard turn boundary; claude does not try to continue the cancelled essay or tool listing.

Two implementation deviations from the architect's spec, both forced by behavior the spec's open questions explicitly flagged:

- **PTY-quiescence predicate replaces the spec's spinner-glyph-absence predicate.** The spec specified `❯-reappeared` as "`hasSpinnerGlyph` becomes false AND `isIdle` true AND both hold continuously for `idleStableWindow`," with open question #4 flagging this might not work if the spinner glyph sat stale in the rolling buffer. Empirically it doesn't work — post-cancel claude emits ~1.4 KB of redraw + title-bar updates, which doesn't roll the spinner glyph out of the 4096-byte rolling buffer; the glyph stays painted indefinitely. Replaced with `isIdle(rb.snapshot()) AND rb.quietFor() >= ptyQuietWindow` (1500 ms). Detects "claude has finished settling" directly instead of via a proxy that depends on buffer churn.
- **`Ctrl-U` (0x15) clear-line keystroke before every probe's `typePrompt`.** Post-cancel, claude restores the previously-submitted prompt as the drafted input. Without an explicit clear, Probe 2's prompt got concatenated with Probe 1's residue in run 4 (`"…monadsrecursively list all files…"` visible in the JSONL `user` record) and the wait condition timed out. The fix is idempotent on an empty input (Probe 1's case after session boot).

Three runs (5, 6, 7) all green with `-cancel-keystroke esc`: `SUCCESS: Hello.` / `Hello!` from Probe 3 in ~12.7–13.2 s total. Additional runs with `double-esc` and `ctrl-c` confirm both alternatives also produce green; double-ESC is ~1 s slower on Probe 1 (likely because claude treats the second `\x1b` as a separate keystroke and emits another redraw burst that delays the PTY-quiescence predicate).

## Patterns established

- **PTY-quiescence as a post-cancel readiness predicate.** `rb.quietFor()` reports time since the last byte was appended to the rolling buffer (`lastAppendAt` is bumped inside `append`). "Recovery is complete when the PTY has been silent for ≥1500 ms AND `❯` is visible" is what `pkg/tuidriver/` will likely use post-extraction — it's the right predicate for "claude has finished settling" generally, not only post-cancel. The spinner-glyph-absence predicate the spec called for is unsound for any post-cancel state that doesn't churn the rolling buffer (and likely for other settle scenarios too). The library should expose quiescence as a first-class primitive.
- **Per-probe wait conditions distinguish "claude has started something to cancel."** `isIdle()` is satisfied continuously even during processing (spike #9 finding #7), so it can't serve as a "claude is busy" signal. Probe 1 (thinking) polls for the `✻` glyph in the rolling buffer via `hasSpinnerGlyph`; Probe 2 (tool-use) accumulates assistant events until one carries `stop_reason=tool_use` and then sleeps 200 ms for the tool subprocess to actually begin. Future cancel-driven flows in the library should pair the cancel API with a "has claude actually started" predicate appropriate to the trigger.
- **Cancel keystroke is single-byte, single-write, no inter-byte delay, no `\r`.** Unlike prompt submission (`typePrompt` uses 10 ms/byte + 50 ms pause + `\r`), the cancel keystroke is `pty.Write([]byte{0x1b})` — one syscall, one byte. The inter-byte-delay reasoning that drove `typePrompt` does not apply because there's no `\r` for claude's input handler to swallow mid-redraw. The library should expose cancel as a separate API from prompt-write; they have structurally different write semantics.
- **`Ctrl-U` clear-line before every prompt, not only after a cancel.** Claude's post-cancel state restores the cancelled prompt as drafted input. Defensively clearing the input line before every prompt write is idempotent on an empty input box and eliminates a class of "prompt got concatenated" bugs the post-spike API would otherwise have to special-case based on prior-state-was-cancel. The library should make this a default-on behavior of the prompt-write path, not a separate cancel-cleanup API.
- **Three-probe binary, one process, one `--session-id`, one JSONL file.** Same "session-scoped, multi-action" shape spike #9 established for multi-turn. Future cancel-driven flows (in the library or follow-up spikes) should keep the same "spawn once, drive many actions, shut down once" structure — it's the only way to validate cross-action state (here: recovery after cancel) against real session behavior.

## Lessons learned

- **The spec's open questions are the highest-value reads.** The spec flagged FOUR things the architect couldn't decide pre-spike (predicate soundness, wait-condition timeout, recovery-limit headroom, post-cancel input state). Two of them (predicate, input state) turned into implementation deviations; one (timeout) was fine as specified; one (recovery limit) turned out to be mostly headroom. Whenever the spec hands open questions to the dev, those are the spots where the spec couldn't pre-decide and the dev should expect to write code that may not match the prescription. Read those sections first; they're not edge cases, they're the spike's deliverable.
- **Buffer-size math eventually catches up with proxy predicates.** The `hasSpinnerGlyph false AND isIdle true` predicate is a proxy for "claude is no longer painting the spinner." It works iff the rolling buffer churns past the stale glyph before the predicate is checked. The rolling buffer is 4 KB; post-cancel claude emits ~1.4 KB of redraw and then stops. The math was already against the predicate before the spike started — but it was only obvious in retrospect. When the structural quantity you care about ("claude has stopped writing") is reachable directly (`rb.quietFor()`), reach for it instead of a proxy. The library should default to direct primitives where they exist; proxies introduce buffer-size dependencies that nothing else in the code expresses.
- **Claude's input box is stateful across cancels.** This is a hidden state machine that ACP `session/prompt` calls cannot ignore. The visible symptom is "the next prompt's JSONL `user` record contains text from the prior cancelled prompt." There's no error, no log line, no JSONL warning — the concatenated prompt just runs as if it were what the user wanted. Diagnosis took an entire run (run 4) before the JSONL inspection caught the concatenation. Lesson: when a wait condition fails after a state transition that worked in isolation, dump the JSONL `user` record before assuming the wait condition is the bug.
- **Cancellation is signaled via `user(text)`, not `assistant.stop_reason`.** This contradicted all three pre-spike candidates (partial assistant with `stop_reason=null`, new `stop_reason=canceled`, brand-new envelope type). The actual shape is: cancelled message keeps its pre-cancel `stop_reason`, and a separate `user`-role event with `[{type:"text", text:"[Request interrupted by user]"}]` lands afterward. The implication for the library is structural: the assistant-only tailer filter from spike #9 silently drops the cancel marker. Either the filter needs widening or the library needs a separate "user-system-message" channel. The spec's prediction that the JSONL would surface cancellation via `stop_reason` was wrong; the actual signal lives in a place the existing parser doesn't look.
- **Cancel does not kill tools — it lets them finish.** Probe 2's `ls /tmp` ran to completion before the cancellation marker landed. The two-line conclusion: (a) for fast tools this is invisible to consumers; (b) for slow tools (hypothetical `sleep 60`) this means `session/cancel` returns "cancelled" while the model's last tool subprocess keeps running until it would have finished anyway. ACP consumers must surface this honestly. A library API like `Cancel()` can't promise tool termination; it can only promise "no more tokens from claude." Tool subprocess management is downstream of claude itself and out of `pkg/tuidriver/`'s scope.
- **JSONL line count varies across runs (unlike spike #9's identical-27).** Spike #9 saw deterministic 27-line runs. This spike sees 22 / 25 / 22 across three runs — variance is in `attachment` envelope counts (3–5 per prompt) and the presence/absence of mid-stream `last-prompt` / `ai-title` envelopes after cancelled probes. Sample size 3, but the variance is real. The headline data (which `assistant` lines exist, their `stop_reason`, their content blocks) IS deterministic. Lesson: the "test harness can assert envelope shape for fixed prompts" claim from spike #9 was over-optimistic; the deterministic level is content shape, not envelope counts. Envelope-count assertions will be flaky.
- **The spec's `preCancelHadSpinner` parameter became dead code, and that's fine.** The original predicate design needed to know whether the spinner glyph was visible pre-cancel to pick between two predicate variants. The PTY-quiescence predicate doesn't need that information — quiescence is the same signal regardless of pre-cancel state. The parameter is still wired through `waitReappeared` for snapshot/audit purposes (the README documents what was observed) but doesn't drive the predicate. When a design's parameter becomes unused after an implementation pivot, leave it as a one-line `_ = paramName` with a comment rather than deleting it; the alternative is forgetting a piece of state worth observing.
- **`-cancel-keystroke` flag earns its keep as a debugging tool, not as a runtime knob.** All three values (`esc`, `double-esc`, `ctrl-c`) produced green runs once the predicate and input-clear fixes were in. The flag's purpose was empirical iteration — "if ESC doesn't work, try X." That purpose was served (it was the iteration mechanism for runs 1–3 before the predicate fix). Post-spike, the library should default to ESC and not expose the alternatives unless a consumer asks for them; the keystroke choice is not a meaningful product knob.
