# #33 — code-review agent invokes `make e2e` during PR review for library code changes

[Issue](https://github.com/pyrycode/tui-driver/issues/33) · [Spec](../../specs/architecture/33-code-review-e2e-gate.md) · Functional change lives in `pyrycode/tui-driver-agents` (sibling repo)

## Summary

Cross-repo ticket. The only artifact in **this** repo is the spec at `docs/specs/architecture/33-code-review-e2e-gate.md`; the functional change — three edits to `tui-driver-agents/code-review/CLAUDE.md` — lands in the sibling agents repo via a separate PR (opened by the developer agent, reviewed manually by Juhana). The two PRs are coupled by GitHub's cross-repo `Closes pyrycode/tui-driver#33` keyword in the agents-repo PR body; merge order is independent because the agents-repo prompt change has no runtime effect on tui-driver until the next code-review run.

The change adds a third coverage layer for the e2e harness, sitting between two existing layers:

- **Push-to-main workflow ([#40](40.md))** — deterministic backstop on the release branch; fires AFTER merge.
- **Code-review gate (this ticket)** — pre-merge, stochastic; the code-review agent runs `make e2e` against the PR's worktree when the diff matches a path-prefix INCLUDE list (`pkg/tuidriver/`, `cmd/spike-*/`, `cmd/probe-*/`, `cmd/e2e-runner/`, `cmd/e2e-snapshot-check/`, `Makefile`, `claude-version.lock`).
- **Developer-local runs** — discretionary; not required by any prompt.

The two automated layers are redundant on purpose per the agents-repo CLAUDE.md "Belt-and-Suspenders Means Different Fabric" rule: the workflow is the deterministic check that decides whether `main` is healthy; the gate is the pre-merge visibility check that catches breakage on the PR rather than on `main`. Trading determinism for earliness is the explicit shape — a flaky gate is acceptable because the workflow remains the load-bearing verdict.

The gate's failure-mode distinguisher is deterministic and reads only three signals: the `make e2e` exit code, the presence and parseability of `e2e-report.json`, and the `status` field on each entry in `.checks[]`. Exit 0 is **green** (no callout). Exit ≠ 0 with a valid report containing at least one `status ∈ {"fail","timeout"}` entry is **red** — posted via `gh pr review --request-changes`, with `❌ e2e harness FAILED` at the top of the comment, the failing check names extracted via `jq`, a 5-line stdout/stderr tail, and `needs-rework:developer` added to the issue. Exit ≠ 0 with a missing or unparseable report is **infra failure** — posted via `gh pr review --comment` (NOT `--request-changes`), no label change from the gate; the per-diff review's verdict decides PASS/FAIL independently.

Three security-shaped details land inside the prompt:
- **Token redaction before the tail is composed.** Before the `tail -n 5` extraction, the captured combined stdout/stderr is filtered through a `sed -E` pipeline that redacts `sk-ant-…`, `ghp_…`, `ghs_…`, `ANTHROPIC_API_KEY=…`, and `GITHUB_TOKEN=…` shapes. Threat model: `pyrycode/tui-driver` is a public repo, so the comment body is public; a malicious spike that emits `ANTHROPIC_API_KEY=<value>` to stderr would otherwise leak the credential into a public artifact.
- **Bounded comment body.** `tail -n 5` post-redaction caps the harness-section of the comment at 5 lines; the line-by-line review is already bounded by the existing "Findings" template. A pathological 64 KiB-wide stderr line cannot blow past the GitHub 65,536-char comment-body cap.
- **No env-scrubbing on the `make e2e` invocation.** Deliberately. `make e2e` needs `ANTHROPIC_API_KEY` to function; the redaction-before-tail step is the compensating control for env leakage via stderr.

The spec deliberately does NOT touch this repo's source — no Go code, no `Makefile` change, no workflow change, no feature-doc edit. The PO body's existing reference at `e2e-harness.md § "CI integration"` ("PR-time coverage is a separate concern: the code-review agent runs the harness selectively elsewhere") was already the in-repo pointer to this gate and stays as-is. Architect, developer, dispatcher, and PO/documentation prompts are all out of scope.

## Patterns established

- **Cross-repo ticket shape: spec-in-this-repo, functional-change-in-sibling-repo.** This is the first ticket in tui-driver where the functional artifact lives entirely outside the repo. The shape that worked: (a) the architect spec calls out the cross-repo boundary explicitly in its own `## Cross-repo boundary` section near the top of the spec, naming both absolute paths (`/Users/juhanailmoniemi/Workspace/Projects/tui-driver-agents/...`) and the consequence that the dispatcher's auto-commit safety net only sees the worktree; (b) the developer commits only the spec to the tui-driver worktree (which the dispatcher's empty-branch guard accepts because `commitsAhead != 0` from the architect's spec commit), and uses `git -C <sibling-repo>` for all staging/commit/push/PR-open against the agents repo; (c) the agents-repo PR title and body use cross-repo `Closes pyrycode/tui-driver#33` so GitHub auto-closes the tui-driver issue when the agents-repo PR merges. Reuse for any future ticket whose payload lives in `tui-driver-agents`, `agent-dispatcher`, or any other sibling pyrycode repo. The key invariant: the tui-driver branch must still have at least one commit (the spec) to satisfy the dispatcher's empty-branch guard; without it the pipeline blocks.
- **Path-prefix INCLUDE list, not exclude.** Path filters that gate expensive operations bias toward false negatives over false positives. New files at unfamiliar paths default to "no run" rather than "run" — a missed run is recovered by the next layer (here, the push-to-main workflow at [#40](40.md)); a spurious run wastes metered API credits with no signal. The shape: a single anchored alternation regex (`^(pkg/tuidriver/|cmd/spike-|cmd/probe-|cmd/e2e-runner/|cmd/e2e-snapshot-check/|Makefile$|claude-version\.lock$)`) consumed by `grep -qE` against `gh pr diff <PR> --name-only`. Note the `$` anchor on bare filenames (`Makefile$`, `claude-version\.lock$`) but not on prefix dirs (`pkg/tuidriver/`) — the trailing slash on a prefix already prevents `pkg/tuidriver-extra/` from matching, and the `$` on a bare filename prevents `Makefile.in` from matching. Reuse anywhere a path filter gates an expensive operation.
- **Failure-mode distinguisher: read three signals, never just one.** A binary "exit code" rule conflates "the harness ran and reported a real failure" with "the harness couldn't run at all." The distinguisher used here reads three signals (exit code + report presence + report `.checks[]` content) and routes them differently: report-with-failures → `--request-changes` + label (the developer can act on it); no-report-or-empty-checks → `--comment` only (the human reviewer decides what to do because the gate has no verdict to offer). The corollary: keep the deterministic-classification rule simple enough that a `jq` one-liner extracts the failing check names. Reuse for any gate that wraps a multi-check harness — the rule generalizes (exit + machine-readable artifact + array of per-check statuses).
- **Token-redaction before output capture is mirrored to a public channel.** Any agent step that copies subprocess output into a public PR comment must run a redaction filter first, even when the project's threat model assumes trusted agents. The shape: a `sed -E` pipeline with explicit token-prefix patterns (`sk-ant-…`, `ghp_…`, `ghs_…`) and explicit env-var-assignment patterns (`ANTHROPIC_API_KEY=…`, `GITHUB_TOKEN=…`), applied **before** the `tail`/`head`/`grep` that selects the public excerpt. Belt: the trusted-agents assumption holds today. Suspenders: the redaction makes credential exfiltration structurally hard even if the trust model erodes. Reuse for any future gate that mirrors subprocess output to GitHub comments, Slack messages, or any other public-or-semi-public channel.
- **Three-layered coverage stacking: deterministic backstop + stochastic earlier layer.** The combination of [#40](40.md) (workflow, post-merge) + this ticket (code-review gate, pre-merge) is an instance of the agents-repo CLAUDE.md rule "Belt-and-Suspenders Means Different Fabric": when adding redundant coverage, the two layers must differ in their failure modes. The workflow is deterministic (GitHub Actions, fixed runner, fixed YAML); the gate is stochastic (a Claude agent reads a prompt and decides whether to run). Replacing the workflow with the gate would be wrong (a stochastic check cannot be a deterministic backstop). Adding the gate on top of the workflow is right (the gate catches things earlier; the workflow remains the load-bearing verdict). Reuse this framing for any future "should we add another check?" question — the new check must add a different failure mode, not just another instance of the same one.

## Lessons learned

- **The dispatcher's empty-branch guard is satisfied by the architect's spec commit alone.** A cross-repo ticket where the developer makes zero commits to the tui-driver worktree (because the functional payload lives in the sibling repo) initially looks like it would trigger `shouldFlagEmptyBranch`. It does not — the guard reads `commitsAhead`, which is non-zero from the architect's spec commit regardless of which agent produced the commits. The spec called this out explicitly with a `dispatcher/src/blockers.ts` reference; documenting the invariant here so future cross-repo tickets don't waste cycles second-guessing whether they need a no-op commit in the worktree. The spec commit IS the worktree's contribution.
- **`pyrycode/tui-driver` is a public repo and the gate's tail output is mirrored to a public comment.** This is the single most consequential property that shaped the spec's security-review section. It changes the threat model from "what does the dispatcher see?" (internal) to "what does the public see when the comment lands on the PR?" (external). A doc edit that mirrors any subprocess output to a public-repo PR comment must walk the [Tokens, secrets, credentials] checkbox before the prompt ships; the existing push-to-main workflow has the same exposure surface but does NOT redact (a follow-up could close that gap). Future tickets that touch the code-review prompt's output-capture shape — or any other agent prompt that posts comments to a public repo — should re-walk this checkbox; the public-repo property is sticky and easy to forget.
- **The path-filter command's deterministic-on-fresh-checkout property comes from `gh pr diff`, not from `git diff`.** `git diff $BASE...HEAD` requires the local checkout to have fetched both refs and resolved the merge-base correctly; in a fresh agent worktree that's not guaranteed. `gh pr diff <N> --name-only` fetches the file list from the GitHub API, which is deterministic by construction (the API returns the canonical PR diff regardless of local git state). The PO body's "must be deterministic on a fresh checkout" constraint reads like a style preference but is actually load-bearing — pick the GitHub-API source over the local-git source whenever the gate runs in an environment where local state is unreliable. Same shape applies anywhere an agent needs "what files did this PR touch?" from a freshly-cloned worktree.
- **Wall-budget mismatch (10-minute `make e2e` inside a ~50-turn agent budget) is acceptable as long as the failure mode is "burns one turn", not "blocks the pipeline".** The spec's open-questions section notes that a hung `make e2e` consumes the full 10-minute wall budget and burns one of the agent's turns. The alternative — adding a `-wall 5m` override inside the gate — risks classifying healthy-but-slow runs as infra failures. The decision shape: defer the override until the failure mode is observed in practice (per CLAUDE.md "Evidence-Based Fix Selection"); the cost of a single burned turn is bounded and recoverable. Reuse for any "should we add a tighter timeout?" decision — if the looser timeout's worst case is bounded, defer until evidence accumulates.
- **Two separate PRs (one per repo) is the natural shape; don't try to bundle them.** Initial impulse for a cross-repo ticket is to find a way to merge both changes "atomically" — but GitHub has no cross-repo atomic merge, and the spec explicitly accepts the asymmetry: the tui-driver PR is doc-only (auto-merged after passing this very pipeline) and the agents-repo PR is reviewed manually by Juhana. Merge order doesn't matter for correctness because the agents-repo prompt change has no runtime effect on tui-driver until the next code-review run; the cross-repo `Closes` keyword in the agents-repo PR body handles the issue-close cleanly. Reuse for any cross-repo split where one side is doc-only and the other is reviewer-gated.
