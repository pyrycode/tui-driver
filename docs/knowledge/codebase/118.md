# #118 — spike-cleanup: migrate spike-permission off duplicated helpers

[Issue](https://github.com/pyrycode/tui-driver/issues/118) · [Spec](../../specs/architecture/118-spike-permission-migrate-off-duplicated-helpers.md) · Commit `590cb32` · Predecessors: [#11](11.md), [#58](58.md), [#59](59.md), [#60](60.md), [#70](70.md), [#87](87.md), [#89](89.md), [#112](112.md), [#116](116.md), [#117](117.md)

## Summary

Closes the spike-binary cleanup arc opened by [#112](112.md) and continued through [#116](116.md) / [#117](117.md). `cmd/spike-permission/main.go` drops `projectsDir`, `openSessionJSONL`, `tailJSONL`, `isEndTurn`, `typePrompt`, `clearInputLine`, `spinnerRe` + `matchSpinner`, and the inline 1 Hz watchdog goroutine in favour of `tuidriver.SessionJSONLPath` + `WaitForSessionJSONL`, `TailJSONL`, `IsEndTurn`, `Session.TypePrompt`, `Session.ClearInputLine`, and `RunWatchdog`. The session-scoped event channel becomes `<-chan tuidriver.JSONLEntry`, populated lazily inside `openTailerHook` via [#117](117.md)'s pointer-to-channel-slot pattern. `sendKeystroke` now routes Probe 2's approve keystroke through `Session.Write` instead of the bare `*os.File`. In-file helpers `logObservationEvent`, `isToolUse`, `extractByMsgID`, and `msgIDOf` shift from `map[string]any` to struct-field access on `tuidriver.JSONLEntry`; `logObservationEvent` keeps its three-way `<missing>` / `<nil>` / string discrimination on `stop_reason` by reading through `ev.Message.Raw`. Single-file diff: 381 lines down (115 added, 266 removed). AC #1's mechanical grep returns empty; `grep -c 'ptmx\.Write'` returns exactly 1 (the trust-folder accept write); `go vet`, `go test -race`, `go build`, and `make e2e` (including snapshot-drift) all clean. With this PR five of the six remaining inline-watchdog copies from the [#89](89.md) sweep are migrated; only `cmd/spike-ask-user/main.go` remains.

Three spike-permission-specific deltas relative to the [#117](117.md) precedent are worth flagging.

First, **the two-`runSession` orchestrator** (Session A + Session B, three probes total) is preserved verbatim per AC #5. Each `runSession` invocation owns its own `var eventCh <-chan tuidriver.JSONLEntry` slot, its own `openTailerHook` closure, its own `sync.Once`, and its own tracker / claude subprocess / watchdog goroutine / JSONL tail goroutine. Session A runs Probe 1 (`runObserve`) then returns — its `defer cancelCause` fires, the watchdog returns, the tail goroutine closes the channel, `session.Close()` SIGTERMs claude A — then Session B runs with a fresh stack for Probes 2 (`runAutoRespond`) and 3 (`runEscalate`). Three probe-runners instead of [#117](117.md)'s unified `runProbe`; each gets the same parameter cascade (`session *tuidriver.Session`, `eventChRef *<-chan tuidriver.JSONLEntry`). `runEscalate` is the third runner shape and the only one without a `postPromptHook` parameter — by the time it runs, Probe 2's `runAutoRespond` has already populated the slot, so its dereference (`eventCh := *eventChRef` at `cmd/spike-permission/main.go:756`) is non-nil at entry. The pre-probe drain (`main.go:760-766`) doesn't need the `*eventChRef != nil` guard [#117](117.md) added because of this ordering invariant.

Second, **`sendKeystroke` migrates to `Session.Write` (Probe 2's approve keystroke path).** [#117](117.md)'s `sendCancel` was the structural twin; spike-permission's `sendKeystroke` is the 1:1 mirror — direct signature swap from `*os.File` to `*tuidriver.Session`, body becomes `session.Write(keystroke)` (`main.go:1002-1004`). The comment about why the keystroke is a single bulk write (small payload, no per-byte pacing needed unlike `TypePrompt`) and why it doesn't go through `TypePrompt` (no terminating `\r`, no paste-detection desired) is preserved verbatim at `main.go:998-1001`. With this change, only one `ptmx.Write` call remains in the file: the trust-folder accept at `main.go:414` (`ptmx.Write([]byte("1\r"))`), deliberately untouched and matching every sibling spike's shape. The ticket originally mentioned an "escalate keystroke" migration site — inspection confirmed `runEscalate` never sends a keystroke (it just observes the modal stays open and reports), so that AC bullet was a false alarm; no second migration site exists under that label.

Third, **`logObservationEvent` preserves the three-way `<missing>` / `<nil>` / string discrimination on `stop_reason`** by reading through `ev.Message.Raw["stop_reason"]` rather than the typed `EntryMessage.StopReason` field. Same architectural reason [#117](117.md)'s `logCancelEvent` flagged: the typed accessor collapses absent key / JSON null value / empty-string value into one empty Go string, but Probe 1's observation-window log line is a README-finding surface and the README documents the three cases distinctly (`<missing>` = field absent; `<nil>` = JSON null; otherwise the literal stop_reason string). The explicit three-arm switch on `raw, present := rawMap["stop_reason"]` at `main.go:1041-1050` keeps the distinction live. Nil-Message guard matches sibling helpers' posture (`msgIDOf` at `main.go:1099-1104`, `isToolUse` at `main.go:1065-1070`) — callers gate on `ev.Type == "assistant"` upstream so `ev.Message` is in practice always non-nil here, but the defensive guard is one extra line per helper and aligns the four helpers stylistically.

`runAutoRespond`'s post-approve readiness predicate (`gotEndTurn ∧ bytes.Contains(stripped, tuidriver.IdleGlyph) ∧ rb.QuietFor() >= ptyQuietWindow` at `main.go:680-695`) and the multi-paragraph commentary documenting why it bypasses `tuidriver.IsIdle`'s spinner-absent half (the empirical 1500 ms `ptyQuietWindow` constant at `main.go:84-107`, the [#70](70.md) wedge incident, the cross-spike sibling references) are preserved verbatim per AC #4 — load-bearing [#70](70.md) design. The only type change inside the predicate body is `events []map[string]any` → `events []tuidriver.JSONLEntry`. The trust-folder accept write at `main.go:414` is the single remaining `ptmx` reach-through, matching the sibling spikes; the local `ptmx := session.PTY` binding at `main.go:381` exists solely for that one call site. `resolveSession` shrinks to `(sessionID, err)` mirror of the [#116](116.md) / [#117](117.md) shape — caller (here: `run()`) composes `home`/`cwd` once and derives each session's JSONL path inline via `tuidriver.SessionJSONLPath(home, cwd, sessionID)`. The legacy `projects-dir path=...` startup log line is dropped (matches [#116](116.md) / [#117](117.md) — the e2e harness only asserts on `SUCCESS:` stdout). Sole stylistic deviation worth noting: the `session-id-resolved id=... jsonl=... tag=b` log line for Session B (pre-migration at line 332) is dropped in the migrated form — the equivalent line for Session A stays at `main.go:307`, and Session B's path is logged via `session-jsonl-opened` once the hook fires. This is a minor information-density reduction not flagged in the spec; the e2e harness doesn't depend on either line.

## Patterns established

- **Closed-channel guard + assistant-only filter pattern at three receive sites in one binary.** [#117](117.md)'s `waitReappeared` established the pattern at one site (`if !ok { eventCh = nil; continue }` followed by `if ev.Type != "assistant" { continue }`); spike-permission now applies it at three: `runObserve`'s observation-window loop (`main.go:558-566`), `runAutoRespond`'s post-approve receive case (`main.go:702-709`), and — implicitly via the drain-only shape — `runEscalate`'s pre-probe drain (`main.go:760-766` which has no consumer-side effect so needs no filter). The pattern's reuse posture: when a binary has multiple receive sites against the same `<-chan tuidriver.JSONLEntry`, audit each one for whether downstream consumers (helpers, log-format strings, accumulator slices) carry an assistant-type assumption baked in. `runObserve`'s downstream is `logObservationEvent` whose format string includes `type=assistant` literally → needs the filter. `runAutoRespond`'s downstream is the `events` accumulator + `modalCleared` flag + `tuidriver.IsEndTurn` check; the `modalCleared` flag is documented (per the pre-migration comment block at `main.go:633-640`) as "first JSONL `assistant` event after keystroke-sent" (finding #15 from spike #11), so the filter is required to preserve that semantics — otherwise the first non-assistant entry library `TailJSONL` emits (user/attachment/permission-mode) would flip the flag wrongly. `runEscalate` only drains, no downstream → no filter. The same audit shape applies to any future binary porting more than one receive site off pre-migration assistant-filtered tailers.
- **`sendKeystroke`-style single-bulk-write keystroke senders take `*tuidriver.Session` and call `session.Write`, not `*os.File` and `ptmx.Write`.** With this ticket, two binaries (spike-cancel via `sendCancel`, spike-permission via `sendKeystroke`) follow the pattern. The differentiator from `Session.TypePrompt` is intentional: `TypePrompt` paces bytes individually (10 ms inter-byte delay) + appends a terminating `\r` + invokes paste-detection-aware buffering; `Session.Write` is a raw passthrough for short multi-byte keystrokes (`"1\r"`, `"y\r"`, `"\r"`, `"\x1b[B\r"`) where paste-detection would actively misbehave. Reuse posture: any spike-shaped binary sending a permission/cancel/numeric-selection keystroke through the PTY should route through `Session.Write`, not bare `session.PTY.Write` and not `TypePrompt`. The trust-folder `1\r` write is a known exception that all four spikes still reach through `ptmx` for — a future tidy ticket could lift that into a `Session.AcceptTrustFolder()` primitive (or just a generic `Session.WriteKeystroke`) but bundling it into per-spike cleanups has so far been out of scope.

## Lessons learned

- **The two-`runSession` orchestrator shape generalised the pointer-to-channel-slot pattern from one channel-per-binary to one channel-per-session-scope cleanly.** Spike-cancel had one `eventCh` slot in `main`; spike-multi-turn had one in `main`; spike-permission has two distinct slots, one per `runSession` invocation, each with its own `openTailerHook` closure and `sync.Once`. The architect's spec was specific that each call has its own slot in `runSession`'s frame (not a shared slot in `run`'s frame), and the implementation followed that — the closure captures the per-invocation `eventCh` variable correctly. The risk was capturing the wrong variable (Session A's hook closing over Session B's slot or vice versa, which would compile but deadlock at runtime); the per-invocation `var eventCh <-chan tuidriver.JSONLEntry` declaration at `main.go:439` inside `runSession`'s body makes the lexical scope unambiguous. Lesson: when generalising a hook-populated-slot pattern across multiple session scopes, declare the slot inside the session-scope function (not the caller) so the closure capture is per-invocation by construction. The alternative — shared slot in the caller, reset between invocations — works but invites lifetime bugs.
- **The "escalate keystroke" line in the ticket's substitution table was a false alarm; inspection of `runEscalate` confirmed no keystroke is ever sent.** The ticket's "Library replacements available today" table listed "raw approve/escalate keystroke" as migrating to `Session.PTY.Write` (or equivalent). Reading `runEscalate`'s body showed it only types a follow-up prompt (`session.TypePrompt(prompt)` at `main.go:773`) then observes the modal stays open — no keystroke send anywhere. The migration is single-site (`runAutoRespond`'s `sendKeystroke(session, approveKey)` at `main.go:624`), not two-site. Lesson: when a ticket's substitution table mentions a migration site name (here: "escalate keystroke") that isn't backed by a literal code reference, verify the call site exists before planning the migration. The architect's spec caught this — `§ sendKeystroke signature change` noted "inspection confirms `runEscalate` does NOT send any keystroke today (just observes the modal stays open), so there is no second migration site under that label" — but a less thorough spec could have missed it and the implementer would have spent time looking for a call that doesn't exist. The audit cost is one grep (`grep -n 'ptmx\.Write\|sendKeystroke' cmd/spike-permission/main.go`); cheap insurance against a phantom migration site.
- **`make e2e` ran clean on the first build — three probes (observe / auto-respond / escalate) across two sessions all hit `SUCCESS:` and snapshot-drift was unchanged.** Same pattern as [#116](116.md) and [#117](117.md): the unfiltered firehose behaviour change (library `TailJSONL` emits all envelope types vs. the pre-migration assistant-only filter) didn't surface as snapshot drift because the `picker` / `mcp` / `agents` snapshots in `pkg/tuidriver/testdata/` exercise other spike binaries. The three consumer-side filters re-establishing pre-migration semantics (`runObserve` gating before `logObservationEvent`, `runAutoRespond` gating before `events`+`modalCleared`, `runEscalate` not needing one because drain has no side effect) were correct on the first pass. The `events` slice in `runAutoRespond` grew by maybe 5-10 entries per probe vs. the pre-migration shape; the readiness predicate fired on the same wall-clock as before and the probe duration was within historical variance. Lesson: at this point in the migration arc (three binaries done with the same architectural shape — [#116](116.md), [#117](117.md), and now [#118](118.md)) the e2e-on-first-build outcome stops being newsworthy and starts being a sanity check. The "noteworthy" result would be drift; absence of drift is the expected steady state for mechanical migrations against an unchanged library surface. Same posture spike-multi-turn observed.
- **The `tag=b` session-id-resolved log line drop is a minor information-density regression worth flagging for the spike-ask-user follow-up.** Pre-migration, `run()` logged both Session A's and Session B's `session-id-resolved id=... jsonl=... tag={a,b}` lines immediately after each `newSessionID` call. The migrated form keeps the `tag=a` line (`main.go:307`) but drops the `tag=b` line because Session B's `jsonlB` is composed via `tuidriver.SessionJSONLPath` right after `resolveSession` and the architect's spec didn't explicitly preserve the log emit. The information is recoverable from the subsequent `session-jsonl-opened path=... tag=b` line emitted inside `openTailerHook` (`main.go:451`), but the recovery is async (hook fires after Probe 2's prompt-write, not at session-resolution time). Lesson: when a `run()` body has N near-identical log emits at session-resolution boundaries, the migration to the shrunken `resolveSession` signature should add the missing emit back at each call site for parity. Spike-ask-user's follow-up should preserve any analogous emits; this one is harmless but visibly asymmetric in the migrated file (A: emit, B: skip).
