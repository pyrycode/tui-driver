# #7 — fix(spike): deterministic `--session-id` for JSONL discovery

[Issue](https://github.com/pyrycode/tui-driver/issues/7) · [Spec](../../specs/architecture/7-deterministic-session-id.md) · Code: `cmd/spike-one-turn/main.go`

## Summary

Replaced the `newestJSONL`-by-mtime discovery heuristic with a deterministic session-ID-driven path. The spike now generates a UUIDv4 (or accepts one via `-session-id <uuid>`) before spawn, logs `session-id-resolved id=<uuid> jsonl=<path>`, and spawns `claude --session-id <uuid>`. The JSONL filename is then known up-front: `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl`. `openSessionJSONL` is rewritten as a `os.Stat` poll on that exact path with a 10 s timeout; pre-existing stale `.jsonl` files in the cwd are structurally invisible. `newestJSONL` and the `errNoSessionJSONL` sentinel are deleted.

One empirical surprise discovered during implementation inverted the spec's call ordering. Under `--session-id`, interactive claude defers JSONL creation until first input — the file does not exist at `idle-detected`. The spike now polls **after** `prompt-written` and tails from offset 0; the parser filter (assistant-with-message only) silently skips the startup envelopes claude writes when it begins processing input. Runs 5 (generated UUID) and 6 (operator-supplied UUID) both produce the spike's first end-to-end `SUCCESS: 4` in ~2–3 s total wall time, closing the loop on the original spike ticket #1.

Dep added: `github.com/google/uuid` (~4 KB; standard choice; aligns with the eventual `pkg/tuidriver/` consumer API where `pyry acp` will want a typed `uuid.UUID` correlation field).

## Patterns established

- **Dictate identifiers when the tool allows; only fall back to discover.** Pinning `claude --session-id <uuid>` eliminates the discovery race entirely — no directory scan, no mtime heuristic, no `fsnotify`. The hierarchy for "find the active file" is now codified in finding #9: (1) dictate the identifier via a tool flag; (2) snapshot-then-diff; (3) newest-by-mtime + retry (only safe when no stale data is plausible). Always check the tool's flags for option (1) before reaching for (2) or (3).
- **Library-API seed: generate-by-default, accept-override.** The `-session-id` flag is the spike-level prototype of an `Options.SessionID uuid.UUID` field on the post-spike `pkg/tuidriver/` API. Empty = generate; non-empty = use as-is (after validation). Consumers like `pyry acp` will populate the field to correlate library-driven sessions with their own ticket/dispatch IDs. The flag/option shape and the `google/uuid` dep choice are deliberately the same here and there.
- **Operator-tail hook fires *before* spawn.** `session-id-resolved id=<uuid> jsonl=<path>` is logged immediately after `resolveSession` returns and **before** `pty.Start`. The path is therefore knowable to an external operator who wants to `tail -f` the JSONL or run `claude --resume <id>` from another shell during the run.
- **`flag.ExitOnError` + explicit exit-2 on UUID validation.** Bad `-session-id` values are printed via `fmt.Fprintf(os.Stderr, ...)` then `flag.Usage()` + `os.Exit(2)` — single coherent error message, no double-print, no claude process ever started.

## Lessons learned

- **`claude --session-id` defers JSONL creation until first input.** Plain `claude` writes `permission-mode` and `file-history-snapshot` into the JSONL during its boot sequence (ticket #3 finding #1). `claude --session-id <uuid>` does **not** — `os.Stat(jsonlPath)` fails with `IsNotExist` at the moment `❯` first renders. The file appears only after the spike writes the prompt and claude begins processing it. Confirmed by the ~200 ms gap between `prompt-written` and `session-jsonl-opened` in Runs 5 and 6 (polling cadence is 100 ms, so the true gap is in [102, 304] ms — small but consistent and the sign is unambiguous). The architect's original spec assumed the opposite ordering (poll after `idle-detected`, before `prompt-written`); that ordering would have wedged in `openSessionJSONL` for 10 s and timed out. Whether the deferral is intentional or a v2.1.143 implementation accident is unknown; either way the spike must accommodate it. **Implementation consequence:** `openSessionJSONL` is invoked after `prompt-written`, and the JSONL tailer seeks to offset 0 (file is brand new) — the existing parser filter handles the startup envelopes the same way it handles them on the non-`--session-id` path.
- **Newest-by-mtime fails twice over here, not once.** The #3 retry covered a fresh-cwd race ("the directory was just created, give it a moment"). It did NOT cover the failure mode that emerged in Run 4: with stale `.jsonl` files already accumulated in the cwd, `max(ModTime)` returns *the wrong existing file* the instant after `idle-detected`, with no observable error. The mtime heuristic's "claude is touching its log right now" premise was already shaky in #3 (race-window thin) and false in #4 (the new file's mtime was ~7 s in the future at the call instant). The deterministic-path model has neither failure mode — the only way `os.Stat(jsonlPath)` succeeds is if that exact path exists, and claude controls that path via the flag.
- **The spec's "snapshot-then-diff" fallback was never needed.** The architect's spec listed snapshot-then-diff as the fallback in case `claude --session-id` exhibited surprising behavior (rejected our UUID, wrote elsewhere, fragmented on missing dir). Empirically it does none of those things — the supplied UUID becomes the filename verbatim, the file appears under the deterministic path, and the missing parent dir is created by claude during startup. The only surprise was the deferral above, which is orthogonal to the discovery mechanism. Recording this here so a future reader doesn't pre-emptively invest in the fallback path.
- **`google/uuid` over hand-rolled is the right call for a library API seed.** Operator policy in earlier spike tickets leaned toward dep minimalism (no `fsnotify`; polling is fine). The architect chose `google/uuid` anyway because the seed must align with the eventual library, where consumers will want a typed `uuid.UUID` field. Confirmed sound: ~4 KB binary growth, zero behavioural surprises, `uuid.Parse` accepts hyphenated and non-hyphenated forms and re-emits the canonical lowercase-hyphenated shape that matches claude's filename convention exactly.
- **Spinner regex still doesn't match in Run 5/6** (`✻ Brewing…` — ellipsis form, no `for Ns` counter). The fast path established in #4 absorbs this without wedging; `thinking-detected` and `spinner-gone` are skipped on every successful run so far. Finding #8 is still open; a fix would unblock the slow-path log lines without affecting end-to-end success.
