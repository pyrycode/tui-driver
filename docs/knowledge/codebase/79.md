# #79 — Makefile: force per-binary rebuild via `FORCE` prereq

[Issue](https://github.com/pyrycode/tui-driver/issues/79) · [Spec](../../specs/architecture/79-makefile-binary-staleness.md) · [PR #84](https://github.com/pyrycode/tui-driver/pull/84) · Code: `Makefile`

## Summary

`make e2e` silently ran stale binaries when source changed. The pattern rule `$(BIN_DIR)/%:` had no prerequisites, so `make` saw `bin/<name>` exists and short-circuited before invoking `go build` — even though `go build`'s own cache would have rebuilt correctly if called. Discovered during #69 work: a timeout bump in `cmd/e2e-runner/main.go` was committed, `make e2e` re-run, and the old behavior surfaced — `make clean-bin && make e2e` was the only way to pick the change up. Cost ~1 minute of "did the commit not land?" confusion per occurrence; the same trap waits for every future iterative edit on `cmd/<name>/` or `pkg/tuidriver/`.

Fix is three lines in `Makefile` (`Makefile:33`, `Makefile:37`): append `FORCE` as a prerequisite of the existing pattern rule, and add a recipe-less `FORCE:` target. `FORCE` is treated as always-out-of-date (no prerequisites, no recipe), so any rule that lists it as a prereq has its recipe re-run on every invocation. The pattern rule still matches `bin/<name>` via implicit-rule search (the *target* is not phony), but the recipe always fires; `go build` then handles incremental rebuilds via its own cache, which tracks transitive Go deps across `pkg/` correctly. No `.PHONY` edit, no per-binary boilerplate, no `find`-based source enumeration. Steady-state no-op cost ≈ 480 ms across all 10 binaries (cache hits inside `go build`), versus the previous false-zero of "did nothing, but also wasn't supposed to."

This was architect rework #4. The first three iterations all anchored on `.PHONY: $(BIN_PATHS)` in various shapes; the developer phase empirically falsified them against GNU Make 3.81 on macOS. See *Lessons learned* below.

## Patterns established

- **`FORCE:` as the canonical way to force a Make pattern rule to always run.** Two-line cost (the target line gets ` FORCE` appended; a recipe-less `FORCE:` rule lives elsewhere in the file). Works in concert with `go build`'s cache so the "always invoke" doesn't mean "always rebuild from scratch." Idiomatic in Go and Linux-kernel Makefiles; do not `.PHONY: FORCE` — it works in practice but breaks parity with prior art and confuses future readers about which mechanism is doing the work. If a future Makefile addition needs the same "always invoke the recipe, let downstream tooling do incremental work" property, list `FORCE` as a prereq — don't reinvent.

## Lessons learned

- **`.PHONY` does not force pattern-rule recipes to run.** GNU Make skips implicit and pattern-rule search for phony targets (manual § 4.6, § 10.5). To force a pattern rule to always re-run, list a recipe-less always-out-of-date target (`FORCE`) as a prerequisite of the pattern, not as the target's phony designation. **`FORCE` ≠ `.PHONY`.** Empirically: on this Makefile against GNU Make 3.81, `.PHONY: $(BIN_PATHS)` causes `make build-bin` to report *"Nothing to be done"* from a clean tree and produce zero binaries — the recipe simply never fires. The trap is that the two mechanisms *sound* equivalent ("treat this target as never-up-to-date") but operate at different layers of Make's rule-matching: `.PHONY` is a target-level designation that suppresses implicit-rule matching; `FORCE` is a real prerequisite that the pattern rule can still match against.
- **"Functionally equivalent" claims about Make mechanisms need empirical confirmation, not desk-checking.** The previous spec's *Alternatives considered* section claimed `FORCE` was "functionally equivalent to `.PHONY`" — exactly the falsified claim. The rework was triggered not by reading the GNU Make manual harder but by the developer phase actually running `make build-bin` from a clean tree and watching zero binaries appear. Make's rule-matching is non-obvious; the cheapest verification is `make clean-bin && make build-bin && ls bin/` — seconds of wall time, decisive signal. For future Makefile changes (or any change to a tool whose semantics depend on implicit search/match logic), the spec-side smoke test should be "would this fail loudly enough that the developer phase couldn't miss it?" — and if the answer is "only if they happen to run from a clean tree," add `make clean-bin` to the testing strategy explicitly. The current spec does this (testing step 6).
- **An "obvious" one-line Makefile fix took 4 architect iterations because the problem looked simpler than it was.** The recurring failure mode wasn't sloppiness — it was that `.PHONY` and `FORCE` solve adjacent-looking problems with different mechanisms, and the GNU Make manual's phrasing ("phony targets do not name actual files that could be remade") reads like "phony makes them always remake" until you notice the *"could be remade"* clause — Make is saying it skips the pattern-rule search entirely because there's no file to remake from. Generalizable lesson: when a "trivial" change re-spawns a ticket multiple times, the cost-effective move is to stop iterating on the design and start running the actual command on the actual tool — every rework on #79 collapsed to a 3-line file change, but the *correct* 3 lines required Make-side empirical evidence the desk-check kept missing.
- **The previous bug's workaround (`make clean-bin && make e2e`) hid the real failure mode for as long as people used it.** This trap existed for the entire pre-#79 lifetime of the Makefile because the workaround is what everyone reaches for when "I edited and the change didn't appear" — it's faster to type `make clean-bin && make e2e` than to investigate why the rebuild didn't happen. The discovery moment was a `commit → rebuild → same failure` loop where the commit *had* landed, the source *was* correct, and the workaround was the obvious next step. Lesson for future developer-experience traps: when a workaround exists and is cheap, the underlying bug accumulates years of latent surface area. The fix-it-properly trigger should be "I noticed I'm reaching for a workaround," not "the workaround stopped working."
