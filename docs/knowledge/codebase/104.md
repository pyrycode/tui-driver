# #104 — library API: typed `AssistantUsage` helper for assistant JSONL entries

[Issue](https://github.com/pyrycode/tui-driver/issues/104) · [Spec](../../specs/architecture/104-jsonl-assistant-usage.md) · Sibling predecessors: [#60](60.md), [#103](103.md) · Split from #101

## Summary

Added a typed sibling to `IsEndTurn` / `AssistantText` for the per-assistant-entry `message.usage` block: a new exported `Usage` struct (four `int` counters — `InputTokens`, `OutputTokens`, `CacheCreationInputTokens`, `CacheReadInputTokens`) and a new exported `AssistantUsage(e JSONLEntry) *Usage` free function (`pkg/tuidriver/jsonl.go:339-388`). The motivating consumer is pyrycode's `internal/agentrun/streamjson/emitter.go:188-192`, which aggregates these four counters per assistant entry; before this slice every such consumer hand-walked `Message.Raw["usage"]` and `float64`→`int` each counter themselves.

The function reads `e.Message.Raw["usage"]`, asserts `map[string]any`, then reads each of the four wire keys (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`) via `float64` type assertion + `int` conversion through an inline `intField` closure that zero-values on missing or non-numeric keys (`pkg/tuidriver/jsonl.go:378-381`). Returns `nil` if `e.Type != "assistant"`, `e.Message == nil`, or `Raw["usage"]` is absent / not a `map[string]any`; otherwise returns a non-nil `*Usage`. This distinguishes "usage block absent" (`nil`) from "usage block present, all counters zero" (`&Usage{}`) — the AC's required presence-distinction. The pointer-return mechanism was chosen over `(Usage, bool)` to parallel pyrycode's existing `*jsonl.UsageBlock` pattern; both shapes satisfy the AC, the pointer reads slightly cleaner at the call site.

Pure additive — no change to `parseEntry`, `tailJSONLLoop`, `TailJSONL`, or any of the typed `JSONLEntry` / `EntryMessage` / `ContentBlock` struct shapes. The four counters are intentionally **only** what `Usage` carries: `service_tier`, cache TTL breakdowns, and any other usage siblings claude may emit remain reachable through `e.Message.Raw["usage"]` directly. YAGNI until a consumer surfaces the need.

Tests added in `pkg/tuidriver/jsonl_test.go:710-800` (one new test, `TestAssistantUsage`, no edits to existing tests): nine table-driven scenarios covering all four AC scenarios plus three guard cases — all four counters populated; usage map present but counter keys omitted (asserts non-nil `&Usage{}` for the "present-but-zero ≠ absent" distinction); non-numeric counter value (`"input_tokens": "lots"` — that one counter zeroed, others populated); no `usage` key in `Message.Raw`; `Raw[usage]` of wrong shape as string; `Raw[usage]` of wrong shape as number; `nil` Message; `type=user` envelope with a usage map present (must short-circuit to `nil`); zero-value `JSONLEntry{}`. Uses a tiny `assistantEntryWithUsage(v any) JSONLEntry` helper appended next to the existing `textBlock` / `blockWithRaw` builders to construct the test entries inline — distinct from those because usage lives on `Message.Raw["usage"]`, not on a `ContentBlock`. Each case asserts via `reflect.DeepEqual` over `*Usage` (handles the nil-vs-non-nil comparison uniformly with the field-by-field comparison).

## Patterns established

- **`(Usage, bool)` vs `*Usage` for "present-but-zero ≠ absent" comes out the same on the AC, but the pointer wins on call-site ergonomics.** The AC required a way to distinguish absent from all-zero; the spec considered both shapes and picked the pointer because (a) pyrycode's existing `jsonl.UsageBlock` already uses the pointer-return shape, so the cross-repo consumer's existing `if usage != nil { ... }` migrates verbatim, and (b) the pointer eliminates the awkward `(_, ok) := AssistantUsage(e); if !ok { ... }` two-name-binding shape that consumers using only the presence-bit would write. The cost is one allocation per non-nil return (Go's escape analysis lifts it to the heap because the result outlives the function); the benefit is the caller doesn't write `_` to discard the value-half when they only want the presence-bit. Reuse posture: for accessors over an optional sub-object whose zero value is a legitimate wire state, prefer `*T` over `(T, bool)` — the call site reads cleaner and the heap allocation is dwarfed by the JSON parse that produced the input.
- **The four-counter walk is hand-written, not `json.Unmarshal` into the struct, for the same reason `AssistantText` is.** The spec named this call out explicitly: `Message.Raw["usage"]` is already a `map[string]any` (parsed once by `parseEntry`'s `json.Unmarshal`), and a second `json.Marshal(usage) → json.Unmarshal(into &Usage)` round-trip would be both slower and structurally distant from how `AssistantText` reads `c.Raw["text"]`. The hand-written walk is four assertions + four conversions, fits in a six-line closure, and inherits `AssistantText`'s zero-value-on-mismatch posture (`n, _ := usage[key].(float64); return int(n)` — same idiom as `text, _ := c.Raw["text"].(string)`). Reuse posture: when a helper walks a sub-object that's already in a `map[string]any`, do the hand-walk; reserve `json.Unmarshal` for the boundary where bytes first cross into Go types (i.e. for `parseEntry`, not for accessors over `Raw`).
- **Field-counter accessors zero on mismatch silently — they do not surface "this counter was malformed" upward.** The non-numeric-counter test row (`"input_tokens": "lots"`) asserts the function returns a non-nil `*Usage` with that counter set to `0` and the other three populated — not `nil`, not an error, not a warning. This matches `AssistantText`'s posture: malformed input contributes nothing observable, the function returns a valid result derived from the well-formed parts. The alternative (return `nil` if any counter is malformed; or carry a second `bool ok` per counter) was considered and rejected — wire-trust + zero-value-on-mismatch is the prevailing idiom across the package's `Raw`-walking accessors, and consumers who care about counter validity can sanity-check after the fact (e.g. `if u.InputTokens < 0 { warn }`). Reuse posture: stay consistent with the surrounding zero-value-on-mismatch style for any new `Raw`-walking accessor; don't introduce an error-channel for one field-counter accessor when its three sibling accessors don't have one.

## Lessons learned

- **The `assistantEntryWithUsage` test-helper appends to the existing builder set; it doesn't replace `textBlock` / `blockWithRaw`.** The spec called out that the existing builders are content-block-shaped (they live inside `Message.Content`), but the usage block lives on `Message.Raw["usage"]` — distinct slot, distinct constructor needed. The implementation added one small builder (`assistantEntryWithUsage(v any) JSONLEntry`) that constructs `JSONLEntry{Type: "assistant", Message: &EntryMessage{Raw: map[string]any{"usage": v}}}` when `v != nil`, or with no `"usage"` key when `v == nil` — captures both the present-with-shape and absent-key cases through one parameter. The `v any` typing lets the same builder construct the wrong-shape rows (`"not-a-map"` string, `float64(42)` number) without a second variant. Reuse posture: when a new helper tests a slot adjacent to existing builders' slots, write a third tiny builder rather than overloading an existing one — three single-purpose builders read more clearly than one polymorphic builder, and the cost is two extra lines.
- **Nine test rows for a four-counter accessor is the right exhaustiveness floor.** The AC named four scenarios; the spec named eight; the implementation landed nine (added the second wrong-shape row — `Raw[usage]` as a number — alongside the string-typed one, to pin the `(map[string]any).(...)` assertion's behaviour across both common JSON-decoded primitives). The cost is two lines per row in the table; the benefit is that any future refactor that swaps the assertion idiom (e.g. to `switch v := raw.(type) { case map[string]any: ... }`) immediately fails on whichever wrong-shape case it accidentally allows through. The two wrong-shape rows are belt-and-suspenders against a class of refactor that doesn't exist yet — and the spec called it out as worth pinning because the wire format is outside the library's control. Reuse posture: when an accessor's type-assertion against a `map[string]any` slot is the load-bearing guard, exercise it against at least two distinct non-map JSON primitive types in tests; the second row pins the shape against accidental widening.
- **XS-sized library-promotion slices continue to land in one round when the spec pre-decides the architect-level calls — same pattern from #58 → #59 → #60 → #61 → #87 → #89 → #100 → #103, now #104.** The architect named the struct's name (`Usage`), the struct's field names + types (the four `int` counters, in that order — matching pyrycode's existing `jsonl.UsageBlock`), the function's signature (`func AssistantUsage(e JSONLEntry) *Usage`), the placement (immediately after `AssistantText` at `jsonl.go:337`), the doc-comment paragraphs (verbatim), the wire-key → field mapping (hand-walk, not `json.Unmarshal`), the presence-mechanism (pointer return, not `(Usage, bool)`, with the pyrycode-parallel reasoning), the zero-on-mismatch posture, the test-scenario matrix (eight rows, the developer added a ninth wrong-shape variant), the assertion style (`reflect.DeepEqual` over `*Usage`). Developer's job was typing it in; no mid-implementation thrash, no PR-time back-and-forth. Reuse posture: the per-ticket evidence has now accumulated across eight slices that XS additive-field tickets land one-round under this spec-quality posture — the pattern is generalisable enough that "architect names every decision in the spec" should be the default for XS/S-sized library promotions, not the exception.
