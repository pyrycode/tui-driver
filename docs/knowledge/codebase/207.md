# #207 — Encode the cwd per UTF-16 code unit to match `claude`

[Issue](https://github.com/pyrycode/tui-driver/issues/207) · [Spec](../../specs/architecture/207-encode-cwd-per-utf16.md) · [PR #211](https://github.com/pyrycode/tui-driver/pull/211) · Split from [#166](https://github.com/pyrycode/tui-driver/issues/166) · Unblocked by [#206](https://github.com/pyrycode/tui-driver/issues/206) · Architecture: [JSONL layout](../architecture/jsonl-layout.md)

## Summary

Flipped `tuidriver.EncodeCwd` (`pkg/tuidriver/cwd.go`) from a per-UTF-8-**byte** hyphen map to a per-UTF-16-**code-unit** one, matching the ground truth [#206](206.md) recorded against real `claude` **2.1.199** (2026-07-06): `claude` encodes the projects-dir name with JS `.replace(/[^a-zA-Z0-9]/g,'-')` semantics — one hyphen per UTF-16 code unit. The loop now ranges by rune and, for each non-`[a-zA-Z0-9]` rune, emits `len(utf16.Encode([]rune{r}))` hyphens: a BMP rune (`ö` U+00F6, `é` U+00E9) → **1**, an astral rune (`😀` U+1F600, a surrogate pair) → **2**. So `Työ😀 → Ty---`, where the old per-byte loop produced `Ty------`. The change mirrors `cmd/probe-cwd-encoding`'s `perUTF16` reference transform shape (a deliberately independent second copy — see below). Signature, the `canonicalisePath` prefix, the no-error nonexistent-path fallback, and the `b.Grow(len(cwd))` hint are all unchanged; only the character→hyphen mapping moved. This closes a **latent** bug: `SessionJSONLPath` / `WaitForSessionJSONL` ([#58](58.md)) route through `EncodeCwd`, so for **any** cwd containing a multi-byte char they computed a projects-dir `claude` never writes → the JSONL wait timed out against a real non-ASCII working directory. Defect was invisible for the whole life of the function because every prior derivation ([#47](47.md), [#57](57.md)) and every unit case exercised only ASCII specials. Also folds in #206's deferred deterministic safety net: a new `cmd/probe-cwd-encoding/main_test.go` table test pins the probe's `perByte` / `perRune` / `perUTF16` / `deriveRule` reference transforms to the golden, giving `make check` teeth alongside the fix rather than reopening #206. Three files: `cwd.go` + `cwd_test.go` (per-UTF-16 rule + fixtures), new `probe-cwd-encoding/main_test.go` (claude-free reference-transform table test).

## Patterns established

- **Per-UTF-16-code-unit encoding idiom in Go: ASCII fast path + `utf16.Encode` hyphen count.** The rule is not "per rune" — for BMP chars per-rune and per-UTF-16 agree, but they diverge on astral chars (per-rune emits 1 hyphen, per-UTF-16 emits 2). The correct shape is `for _, r := range s { if r < 128 && isASCIIAlnum(byte(r)) { b.WriteByte(byte(r)); continue }; for range utf16.Encode([]rune{r}) { b.WriteByte('-') } }`. The `r < 128` guard before `isASCIIAlnum(byte(r))` is load-bearing: without it a multi-byte rune whose low byte happens to land in `[a-zA-Z0-9]` would wrongly pass through. Ranging a Go string yields runes and decodes invalid UTF-8 to `utf8.RuneError` (1 byte consumed, non-alnum → 1 hyphen), so no explicit bad-UTF-8 guard is needed — at least as sensible as the old per-byte behaviour. Reuse posture: any transform claiming to match JS `/[^…]/g` string semantics must count UTF-16 code units, not runes or bytes.
- **`EncodeCwd` and the probe's `perUTF16` are two deliberately-independent copies — a documented DRY exception.** `cmd/probe-cwd-encoding` is the verification rig for `EncodeCwd`; [#206](206.md) established that a rig must discover ground truth by a path that does **not** run through the artifact it verifies. Importing `EncodeCwd` into the probe (or extracting a shared helper) would collapse that independence and blind the rig to a future divergence. Both copies stay; this ticket reaffirmed the exception by **not** deduplicating them. Reuse posture: when a verification harness and the code it checks implement the same rule, keeping two copies is correct, not a smell.
- **One discriminating astral fixture stands in for three separate rule-checks.** The leaf `Työ😀` fans out per-byte (`Ty------`), per-UTF-16 (`Ty---`) and per-rune (`Ty--`) into three distinct outputs in a single observation (`ö` = 2 bytes / 1 unit / 1 rune; `😀` = 4 bytes / 2 units / 1 rune) — inherited from #206 and reused here as both the `cwd_test.go` unit case (a naive per-*rune* implementation yields `Ty--` and must fail it) and the `main_test.go` reference-transform rows. Reuse posture: to pin a transform against N candidate rules, engineer one input that separates all N rather than N narrower fixtures.
- **A test helper that re-implements the production loop is renamed and re-bodied in lockstep with it.** `cwd_test.go`'s `byteTransform` (flagged "Keep in sync with EncodeCwd's loop") computes expected outputs for `TestEncodeCwd_RealpathHappyPath` / `_NonexistentPath` from canonicalised paths without hardcoding them. It was renamed to `utf16Transform`, its body and doc-comment rewritten to the per-UTF-16 rule, and its two call sites updated together — otherwise those tests would compute stale expected values. (Both exercise ASCII-only temp paths, so their outputs are unchanged, but the helper must stay honest to the rule it mirrors.)

## Lessons learned

- **A test that pins a transform's output computed *by* that transform proves nothing.** The pre-#207 `café → caf--` unit case ([#47](47.md)) was the byte loop describing its own 2-byte-per-char output — a self-referential golden, never observed from `claude`. It "passed" for the function's entire life while the function was wrong for every non-ASCII cwd. #206 broke the loop by observing real `claude` independently; #207 replaced the self-referential case with the observed golden (`café → caf-`, `Työ😀 → Ty---`). Lesson: a golden must come from an external observation, not from the artifact under test. (Same shape as the `spike-gated-fix-split` rule — a "self-descriptive test pin" whose expected value is computed by the code under test is not evidence; flipping it needs a real observation.)
- **A byte-level string transform is only as verified as its most exotic tested input.** The per-byte bug survived #47 (derivation), #57 (canonicalisation), and #58 (the `SessionJSONLPath` wrapper) — three tickets, a full test suite — because none exercised a multi-byte character. The multi-byte axis was simply never in a fixture. Lesson: when a transform's contract spans a character-set space (bytes vs code units vs runes), a fixture must land in each distinct region, or the untested region hides a latent defect indefinitely.
- **The deterministic `make check` safety net shipped with the fix it guards, not as a follow-up.** #206's code-review flagged the pure claude-free reference transforms (`perByte`/`perRune`/`perUTF16`/`deriveRule`) as SHOULD-FIX-untested; rather than reopen #206, that table test was folded into #207 (per [206.md § Follow-ups](206.md)). The safety net (deterministic, claude-free) and the behavioural fix land in the same PR, so `make check` gains teeth in lockstep with the change — belt-and-suspenders of different fabric (a deterministic test guarding a code fix), and no dropped-owner window between fix and net.

## Cross-repo note (consumer already routes through this encoder)

The ticket body and [#58](58.md) describe pyrycode's `agentrun.EncodeProjectDir` as a **separate copy** carrying the same per-byte bug, out of scope here. Per the pyrycode knowledge base that framing is now stale: **pyrycode#501** made `agentrun.EncodeProjectDir` delegate to `tuidriver.EncodeCwd`, and **pyrycode#508** deleted the wrapper entirely (dropping a redundant `EvalSymlinks` from the JSONL hot path, since #57's `canonicalisePath` already resolves symlinks). The consumer no longer maintains an independent copy — it routes through this function — so the #207 fix propagates downstream on the consumer's next tui-driver bump; no separate per-byte fix is needed in pyrycode. (The pyrycode#633 divergence map recorded the historical split; that split is now closed at source.)
