# #247 — corpus-replay: report per-detector transition-edge counts

[Issue](https://github.com/pyrycode/tui-driver/issues/247) · Related: [#259](https://github.com/pyrycode/tui-driver/issues/259) (assert mode, future gate consumer) · Code: `cmd/corpus-replay/main.go`, `cmd/corpus-replay/report.go`, `cmd/corpus-replay/main_test.go`, `cmd/corpus-replay/report_test.go`, `cmd/corpus-replay/README.md`

## Summary

`cmd/corpus-replay` previously recorded only whether each detector fired *at least once* per cast (`castResult.fired`). The 2026-07-07 detection review needed transition counts to see two real defects — a permission modal flapping shown/hidden six times in one recording, and the busy axis flipping hundreds of times per run — and had to hand-build a throwaway probe to get them. This ticket makes flapping a first-class, standard-report signal: `castResult` gains `edges map[string]int`, incremented whenever a detector key's membership in the active-key set flips between two consecutive *sampled* ticks (`cur △ prev`, `prev` starting empty per cast). A key that fires once and stays registers exactly one edge (its first appearance); a flapping key climbs past 1. The duplicate final classify (`replayCast`'s unconditional last-frame check) re-renders the same frame, so it lands `cur == prev` and adds no spurious edge.

Both classify sites (`main.go`'s in-loop stride check and the final-frame check) now go through one method, `(*castResult).classify(snap, prev) map[string]bool`, replacing the old free function `applyDetectors`. `classify` calls the new `activeKeys(snap)` (the extracted, side-effect-free membership computation `applyDetectors` used to mutate in place), ORs the result into `r.fired` (preserving the existing monotonic-fires semantics byte-for-byte), folds the symmetric difference into `r.edges`, and returns `cur` as the next tick's `prev`.

Two architect decisions shape the keying: **(1)** the busy/idle axis is counted — `idle`/`thinking` are excluded from the false-positive-suspects section (a healthy run is idle) but are valid flapping axes, so edges include every key `activeKeys` returns, no exclusion. **(2)** edges key on the existing `modal:<class>` space, not a single collapsed `modal` key — this preserves per-class attribution (permission vs. trust) and means a direct class→class transition with no idle in between registers an edge on both classes, which is the correct "both unstable" signal.

`report.go` gained one additive section (after anchor-in-content, before the `-per-cast` block): a per-key edge-totals table (same bucket columns as the fires table, plus a trailing `total`), and a top-flappers list broken out per `(segment, tag)` bucket — the `(cast, key, count)` triples with `count > 1`, sorted descending, capped at `topFlappersN = 5` per bucket with the cap stated in the sub-header. All prior sections and the `-per-cast` line format are unchanged (verified by the pre-existing `TestReplayCast_RealTrustDialogFires` / `TestReplayCast_ForgedHeaderAndRetiredTokenSuppressed` tests, left untouched).

Tests use two new synthetic `testdata/*.cast` fixtures reusing `sample-ok.cast`'s proven trust-folder modal content, each frame opening with `\x1b[2J\x1b[H` so vt10x fully repaints and the modal's presence/absence is deterministic per frame: `flap-err.cast` (idle → trust modal → thinking spinner → trust modal, asserting `edges["modal:trust-folder"] > 1` and `edges["idle"] > 1`) and `stable-ok.cast` (trust modal present every sampled frame, asserting `edges["modal:trust-folder"] == 1`). A report-level smoke test confirms the new section renders (header, top-flappers sub-header, the flapping cast's name, the flapping key).

Report-only, no new flags, no exit-code change — not security-sensitive (a forged edge count routes nothing; see [[corpus-replay-tool-ticket-family]]). Added the deferred "transition edges" bullet to `README.md`'s "What it reports" list per the spec's open question (nice-to-have, explicitly left to the doc phase).

## Patterns established

- **Active-key-set diff for flap detection.** Any future "did this boolean/enum flip too often" signal over a per-tick classification loop can reuse the shape: maintain `prev` (a `map[string]bool` snapshot of active keys, starting empty), compute `cur` each tick, increment a counter for every key in `cur △ prev`, then `prev = cur`. First appearance always counts exactly 1; only genuine toggling climbs past it. This generalizes past corpus-replay to any pattern-matching loop over a rolling buffer.
- **Duplicate/idempotent re-classification is free under a set-diff, not under a raw counter.** A naive "increment on every fire" counter would double-count the unconditional final-frame reclassify in `replayCast`. Diffing against the previous *set* rather than incrementing on presence makes a repeated identical classification a no-op automatically — worth reaching for a diff-based counter instead of a presence-based one whenever a call site might reclassify the same state twice.
- **Report table growth stays additive by construction when the new field lives inside the existing per-result struct.** `report()`'s signature didn't change — `edges` rides inside `castResult` like `fired`/`anchors` already do, so every existing section (false-positive-suspects, anchor-in-content, `-per-cast`) needed zero edits to stay byte-identical. Adding a report dimension to this tool means adding a `castResult` field + one new aggregation block, not touching existing ones.

## Lessons learned

- **A spec's "open question" deferred to the doc phase is a real to-do, not decoration.** The spec explicitly scoped the developer's worktree to code+tests+spec and named the README "transition edges" bullet as the doc phase's job. Checked for and applied here — worth scanning a ticket's spec for an explicit doc-phase handoff before treating "nothing changed in docs/" as complete.
- **No new feature doc was warranted for this ticket.** `cmd/corpus-replay` already has a maintained `README.md` describing its report semantics; #247 extends an existing report dimension rather than introducing a new subsystem, so the per-ticket file + the README bullet is the right documentation footprint (mirrors #245's agents-arm retirement, which also skipped a standalone feature doc for the same reason — a change to an existing tool's behavior, not a new one).
