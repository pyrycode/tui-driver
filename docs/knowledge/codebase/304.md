# #304 — mid-response API-error (partial-output) detector → payload-free `EventKindPtyMidResponseError*`

[Issue](https://github.com/pyrycode/tui-driver/issues/304) · [Spec](../../specs/architecture/304-mid-response-error-event.md) · [PR #306](https://github.com/pyrycode/tui-driver/pull/306) · Predecessor: [#100](100.md) · Split from #297 (sibling: #303, blocked-by #303 — merged)

## Summary

Added a fourth region-scoped status-banner detector, `pkg/tuidriver/midresponse.go`, alongside `network.go` (#220), `mcp_banner.go`, and `apiretry.go` (#303): `HasMidResponseError(snap []byte) bool` reports whether claude's mid-response partial-output error line (`API Error: Connection closed mid-response. The response above may be incomplete.`) is present in the bottom `bannerRegionRows` window. This is the **payload-free sibling of #303**, not a copy of it — the spec's framing was "this is network-failure (#220), not api-retry (#303)": the event kind is the whole signal, there is no counter, no `Parse*` function, no struct.

The anchor is the single distinctive token `Connection closed mid-response` — never the bare `API Error:` prefix, which the out-of-scope 401 auth line (`API Error: 401 …`, owned by the dispatcher's own 401 retry) shares. Disjointness from all three neighbouring `API Error:`-prefixed lines (401 auth, #220 network, #303 retry) is cross-tested in both directions in `midresponse_test.go`.

`Session.Events` / `ScreenEvents` gain two new payload-free `EventKind` constants slotted right after `EventKindPtyApiRetryHidden`: `EventKindPtyMidResponseErrorShown` / `Hidden`. `classify` grows one `ptyState` field (`midResponseError bool`, set from `hasMidResponseErrorGrid(g)`) and `mergeEvents` gets one new emission block with the exact two-branch boolean-flip shape of the #100 network-failure block (rising edge → `Shown`, falling edge → `Hidden`) — no third count-change branch, since that was #303's payload wrinkle and doesn't apply here. `Event` gains **no new field**. Independent of the modal/idle/thinking axes, like the other three banner kinds.

Implementation matched the architect's spec (13c5bc4) exactly — zero deviation. Code review passed with no findings (verified the mid-iota `EventKind` insert is safe: nothing serializes `EventKind` by integer).

## Patterns established

- **Payload-free banner is the default shape; payload-carrying (#303) is the exception.** When adding a fourth banner-style PTY axis, the base template is the #100 two-branch boolean flip (`network.go` / `mergeEvents`'s network block), not #303's three-branch payload variant. Reach for the payload variant only when the axis genuinely carries a value that changes while the condition persists (a counter, in #303's case) — otherwise the two-branch shape is correct and simpler.
- **Shared-prefix disjointness table.** With four `API Error:`/`API error`-prefixed status lines now live in the codebase (401 auth — out of scope, #220 network, #303 retry, #304 mid-response), each anchored on a token absent from the other three, cross-testing pairwise disjointness (as `apiretry_test.go` and `midresponse_test.go` both do) is the standing discipline for any fifth line that might share the prefix.

## Lessons learned

None beyond what #303 already logged (the shared-suffix/shared-prefix disjointness risk) — this ticket rode #303's settled `events.go` plumbing with no new wrinkles, per the spec's explicit "subtract every payload element from #303's spec" framing.
