# #100 — library API: `Session.Events` emits MCP-failure and network-failure transitions

[Issue](https://github.com/pyrycode/tui-driver/issues/100) · [Spec](../../specs/architecture/100-mcp-network-failure-events.md) · [PR #102](https://github.com/pyrycode/tui-driver/pull/102) · Predecessors: [#61](61.md), [#62](62.md)

## Summary

Extended the unified `Session.Events` channel (#61) with two new boolean axes — the `HasMcpFailureBanner` status-line predicate (`pkg/tuidriver/mcp_banner.go`) and the `HasNetworkFailure` anchor-list predicate (`pkg/tuidriver/network.go`) — so consumers monitoring those failures no longer need a parallel `Buffer.Snapshot` poll loop alongside the merge channel. Four new `EventKind` constants slot into the existing PTY-side iota block between `EventKindPtyModalHidden` and `EventKindJsonlEntry`: `EventKindPtyMcpFailureShown` / `EventKindPtyMcpFailureHidden` / `EventKindPtyNetworkFailureShown` / `EventKindPtyNetworkFailureHidden`. All four are payload-free (`Source = EventSourcePty`, `Time` set by the merge loop, no `Modal`/`Entry` fields — the kind itself is the signal; consumers wanting the failure count call `FailedMcpCount(snap)` directly). The merge loop emits Shown on a false→true tick edge and Hidden on a true→false tick edge against the previous `ptyState`, mirroring the modal show/hide convention for switch-statement parity.

The new axes fire **independently of modal state**, diverging deliberately from the existing modal-suppression rule that gates idle/thinking. The banners are condition events ("this string is in the status area right now"), not state events — `HasMcpFailureBanner` is just as true with a modal open or the spinner running as it is at idle, and consumers want the signal regardless of dominant-axis state. Suppressing the MCP-failure event because the `/mcp` modal happened to be open would defeat the use case (it's exactly when the user is looking at MCP UI that they want to know about MCP failures). The divergence is the one non-obvious design call, called out in spec § "Why banner events fire independently of modal state" and mirrored in the source via a one-line "Banner axes are independent of modal state" comment over the new emission block.

Internal refactor: `classify` widens from `(idle, thinking, modal)` 3-tuple to a private `ptyState` struct (`idle, thinking, modal, mcpFailure, networkFailure`), and `mergeEvents`'s three `prevIdle / prevThinking / prevModal` locals collapse to a single `var prev ptyState`. The 3-tuple was at the point where any 5-return Go function reads poorly, and the struct refactor was the spec-recommended shape. Both call sites updated; the struct stays unexported (the open-question on whether to surface it as a public state-snapshot accessor was resolved "no — a future ticket can add a curated public type if/when that need arises"). Maximum events emitted per tick rises from 3 to 5; output channel remains buffered at 32 with the same backpressure-aware `send` helper, no shape change.

Tests added in `pkg/tuidriver/events_test.go` (additive, no edits to existing tests): `TestMergeEvents_McpFailureBannerTransitions` and `TestMergeEvents_NetworkFailureTransitions` exercise the AC's four-phase clean → appear → clear → re-appear edges (the network test's phase 4 uses an ANSI-wrapped `\x1b[31mFailedToOpenSocket\x1b[0m` reappearance to exercise the StripANSI path through the predicate). `TestMergeEvents_BannerCoexistsWithIdleAndModal` exercises the modal-independence contract: phase 1 drives the idle glyph + MCP banner in one snapshot and asserts BOTH `EventKindPtyIdle` and `EventKindPtyMcpFailureShown` arrive in the same tick (collected into a `map[EventKind]bool` because internal emission order is not contract); phase 2 flips the modal on with the banner unchanged and asserts only `EventKindPtyModalShown(Permission)` fires with no spurious `McpFailureHidden`; phase 3 clears the banner while the modal stays up and asserts the lone `McpFailureHidden`. All seven existing `TestMergeEvents_*` cases plus `TestEvents_TailJSONLErrorBubbles` continue to pass unchanged — the `classify` struct rewrite is observably equivalent on the existing axes.

Code review (PR #102): PASS with no findings. The known modal-suppression `prev*`-update leak (the lessons-learned item from [#61](61.md) — idle/thinking rising edge across modal close suppressed because `prev.idle` updates unconditionally) is deliberately preserved unchanged; this slice doesn't touch suppression semantics and isn't the place to fix it.

The motivating cross-repo consumer is pyrycode's `ptyrunner` migration to `Session.Events`, which lands separately on the pyrycode side. Without these event kinds, ptyrunner would have kept its own banner-poll loop in parallel with the merge channel — defeating the point of the unified API.

## Patterns established

- **Condition events vs state events — independent axes opt out of modal suppression.** The existing modal-suppression rule (idle/thinking suppressed while a modal is active) was correct precisely because idle/thinking are **state** classifications of the dominant UI axis: `IsIdle` returning `true` during a permission prompt is technically correct (the `❯` glyph IS still drawn under the modal) but semantically wrong as a "ready for next prompt" signal. The two banner predicates are **condition** classifications of an independent UI region (the lower status area) — `HasMcpFailureBanner` returning `true` while a modal is open is both technically and semantically correct, because the banner literally is in the status area while the modal sits above it. The merge loop's new emission block correspondingly runs unconditionally on every tick, not gated on `cur.modal`. Reuse posture: when adding a new boolean axis to the merge loop, ask first whether it classifies the same UI region as modal/idle/thinking (a competing **state** — apply modal suppression for switch-statement parity) or a different UI region (an independent **condition** — fire whenever the boolean flips, no suppression). The predicate's own doc-comment is the giveaway: `mcp_banner.go:14-16` and `network.go:18-22` both explicitly document independence from `DetectModalClass`. A future "DNS failure" or "rate limit" banner predicate will follow the same independence pattern.
- **Single-struct internal classification beats a widening return tuple.** The pre-#100 `classify(snap) (idle, thinking, modal)` 3-tuple was at the right size; widening to 5 returns would have read poorly in Go (large positional return lists conflate axes — readers can't tell which `bool` is which at the call site) and obscured the next-axis-addition cost. Converting `classify` to return a private `ptyState` struct made the call-site read self-documenting (`cur.mcpFailure` vs `cur.networkFailure` is unambiguous; positional `mcpFailure, networkFailure` is not) and reduced `mergeEvents`'s previous-state bookkeeping from three named locals to one (`var prev ptyState`). The struct is deliberately unexported because today's only consumer is the merge loop; a future ticket that wants a public state-snapshot accessor on `*Session` will land its own curated exported type with a public name and documentation. Reuse posture: when an internal classifier function gains a third or fourth return value, convert it to a private struct in the same file rather than letting the tuple widen. The conversion is a 1-callsite refactor inside an unexported function — cheap. The next addition is then a single struct-field append, with no positional reshuffle of existing code.
- **Boolean axes use a two-branch if/else-if for mutual exclusion, not two independent if statements.** The new emission blocks pair Shown and Hidden as `if cur.X && !prev.X { … } else if !cur.X && prev.X { … }` — the `else if` is load-bearing for clarity (a boolean transition has at most one edge per tick, never both) even though the predicate conjunction would make two independent ifs functionally equivalent. The modal Shown/Hidden block from #61 uses a different shape (separate if blocks for Hidden(old) and Shown(new), because a class→class change DOES emit both in one tick); the new boolean axes deliberately don't copy that shape because the modal axis has more than two states and the banner axes have exactly two. Reuse posture: when adding a new boolean rising/falling-edge emitter, structure as `if rising { … } else if falling { … }`; the mutual-exclusion shape makes the "at most one event per tick on this axis" invariant local-readable. Multi-state axes (modal, future N-state classifiers) keep the modal pattern of independent Hidden-then-Shown blocks.
- **AC-driven test fixtures inherit predicate-test vocabulary verbatim.** The new `TestMergeEvents_McpFailureBannerTransitions` and `TestMergeEvents_NetworkFailureTransitions` reuse the exact byte literals from `mcp_banner_test.go` and `network_test.go` (`"1 MCP server failed · /mcp"`, `"2 MCP servers failed"`, `"FailedToOpenSocket"`, the `\x1b[31m…\x1b[0m` ANSI-wrapped form). This is deliberate: the merge-loop tests are end-to-end-shaped through the predicates, not the predicates themselves, so reusing the predicate-test vocabulary keeps the two test suites in lockstep (a future predicate-vocabulary change updates both call sites). Reuse posture: when writing merge-loop tests for any new axis whose predicate is itself unit-tested, copy the fixture byte literals from the predicate test rather than inventing new ones. The merge-loop test is exercising the integration (predicate → ptyState → edge detection → event), not the predicate's matching surface.
- **Multi-event-per-tick assertions collect into a set, not a sequence.** `TestMergeEvents_BannerCoexistsWithIdleAndModal` phase 1 expects both `EventKindPtyIdle` and `EventKindPtyMcpFailureShown` to arrive on the same tick, but the spec deliberately under-specifies cross-axis ordering ("internal emission order is informational, not contract"). The test collects both kinds into `map[EventKind]bool` and asserts membership, not order. This is the right shape: ordering between independent axes is an implementation detail of which `if` block runs first inside the ticker arm; tests that assert order would lock in a contract the spec explicitly refuses to make. Reuse posture: any future merge-loop test that asserts on multiple events from one tick should collect into a set (`map[EventKind]bool`) and assert membership. The two-kinds-from-one-tick case is the canonical pattern; the same shape extends to three or more kinds. Reserve sequence assertions for within-one-axis ordering (modal Hidden-before-Shown on a class→class change — that IS contract).

## Lessons learned

- **The spec-pre-decided-everything pattern (#58 → #100) continues to work for additive XS slices.** Same playbook as #58/#59/#60/#61/#87/#89: the architect named every new public symbol, every doc-comment paragraph, every test phase, every considered-and-rejected alternative (carrying the failure count? unified banner kind? per-axis configurability?). The developer's job was typing it in; no mid-implementation thrash, code-review PASS no findings. The pattern continues to hold for additive slices that don't touch the existing state-machine semantics. The lesson that surfaced in #61 — "specs can miss multi-axis edge interactions even when they cover every named scenario" — did not recur here because this slice's two new axes are deliberately **non-interactive** with the existing axes (no suppression, no shared `prev*` bookkeeping). The structural independence is what made the spec tractable to pre-decide. Reuse posture: additive boolean axes that are by-construction independent of existing axes can be specced exhaustively in one pass. The risk only re-emerges if a future axis interacts with modal/idle/thinking suppression — for those, write down the cross-axis behaviour explicitly in the spec, per the #61 lesson.
- **The `else if` in the new emission block is a readability nudge, not a correctness fence.** A predicate transition is by definition either rising OR falling on a given tick, never both, so `if rising { … }; if falling { … }` would behave identically to the implemented `if rising { … } else if falling { … }`. The `else if` shape was chosen to make the mutual exclusion local-readable — a reader doesn't have to think about the impossibility of both branches firing, the syntax encodes it. Cost: one extra keyword per block. Benefit: one less invariant a future reader has to verify by inspection. Reuse posture: for boolean rising/falling-edge emitters, the `else if` is the right default. The alternative `if-if` is acceptable but quietly assumes the reader knows the predicate's tick-edge invariant; the `else if` lifts that into the syntax.
- **`reflect.DeepEqual`-equivalent struct passing is what made the `classify` refactor a 1-call-site change.** `mergeEvents` calls `classify` exactly once per tick and stores the result in a local; the struct rewrite turned three named locals (`curIdle`, `curThinking`, `curModal`) into one (`cur`) and three previous-state locals into one (`prev`). Net diff in `mergeEvents`: ~10 lines changed in existing code (the `prev.X` / `cur.X` field-access updates) + ~25 lines added for the two new emission blocks. The refactor was small enough to ride along with the feature in the same PR; if `classify` had had multiple callers or if the merge loop had stored the individual booleans in non-co-located places, the refactor would have been larger than the feature and deserved its own slice. Reuse posture: when widening an internal classifier from a tuple to a struct, audit the call-site count before bundling the refactor with the feature. One caller → bundle is fine; N callers → refactor first, feature second (or refactor in a separate PR landed before the feature slice).
- **PR #102's "PASS no findings" reflects the spec's investment, not the diff's smallness.** The diff IS small (147 lines of `events.go` changed, 166 lines of test added), but the absence of findings tracks to the spec's exhaustiveness more than the line count. The reviewer's checklist matches the spec section headers ("Four new constants slotted between …", "classify refactored to return ptyState struct", "New emission block runs after the existing modal/idle blocks, unconditionally on every tick — correctly diverges from the modal-suppression rule", "Doc-comment updates per spec § …"). When the spec pre-specifies the implementation shape paragraph by paragraph, the code review collapses to verifying conformance, not auditing for unspecified judgment calls. Reuse posture: for additive slices where the architect can name every change in advance, treat spec-section exhaustiveness as the leading code-review-cost lever. Specs that say "do X" + reviewers that check "X done?" produce fast clean reviews. Specs that say "design something for the X-shaped need" + reviewers that audit the design produce slower reviews regardless of diff size.
