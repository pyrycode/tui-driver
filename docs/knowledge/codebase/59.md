# #59 — library API: JSONL file tail with parsed-entry channel

[Issue](https://github.com/pyrycode/tui-driver/issues/59) · [Spec](../../specs/architecture/59-jsonl-tail-entry-channel.md) · [PR #86](https://github.com/pyrycode/tui-driver/pull/86)

## Summary

Promoted the tail-loop primitive — open at offset, `bufio.Reader.ReadBytes('\n')`, accumulate partial bytes across short reads, JSON-decode each completed line, emit on a buffered channel, EOF-sleep one tick then retry — from the seven in-tree `tailJSONL` open-codes (every `cmd/spike-*` plus `cmd/probe-first-prompt-hang/tailJSONLAll`) into `pkg/tuidriver/` as `TailJSONL(ctx, path, startOffset) (<-chan JSONLEntry, error)`. The function is additive to `jsonl.go` (which #58 introduced precisely to carve thematic space for "future related primitives e.g. tail helpers"); no new files, no new constructor, no handle struct. The library version differs from the spike loop in exactly two behaviour ways: (1) it emits **every** parsed envelope, not just `type == "assistant" + message is map` — filtering moves up the stack because cancellation markers are `user`-role, `attachment` markers are `attachment`-type, and `user(tool_result)` interleavings are interesting to some consumers; (2) parse errors are silently dropped instead of `logger.Printf`'d because the library has no logger to call into. The typed shape on the channel is `JSONLEntry{Type, Message *EntryMessage, Raw map[string]any}`; `EntryMessage` carries `ID`, `StopReason`, and `Content []ContentBlock`; `ContentBlock` carries `Type` and a `Raw` map. Every typed field is populated best-effort via zero-value-on-mismatch type assertions — missing or type-mismatched JSON yields zero values, and the entry is still emitted; consumers requiring presence-vs-absence semantics check `_, ok := e.Raw["message"]` directly. The package doc-comment scope sentence was extended in two places (in-scope gained "tail-with-parsed-entries"; out-of-scope was widened from "JSONL parsing" to "JSONL semantic interpretation (end-of-turn detection, msg_id grouping, content extraction)") — codifies that the library owns the loop + typed shape and consumers own the semantics on top. **Migrating the seven in-tree spike/probe `tailJSONL`s and pyrycode's `agentrun` consumers is deliberately out of scope for this slice**; the new API is additive, the spike-side code keeps working, and the closing-at-source effect lands when consumers migrate.

## Patterns established

- **`pkg/tuidriver/` library-promotion shape now spans three function kinds: pure helper (`SessionJSONLPath`), context-driven waiter (`WaitForSessionJSONL`), and goroutine-owned streamer (`TailJSONL`).** All three live in `jsonl.go` and compose at the call site without a struct to carry shared state (`p := SessionJSONLPath(...); err := WaitForSessionJSONL(ctx, p); ch, err := TailJSONL(ctx, p, 0)`). The streamer shape pairs a synchronous open/seek (programmer-error path — returns `(nil, err)` immediately, no retry) with a goroutine that owns the file handle, the partial-byte accumulator, and the bufio reader, closing both the channel and the file on every exit path via stacked `defer`s. Three exit triggers: `ctx.Err() != nil` at loop top (cheap pre-I/O guard), `<-ctx.Done()` in the EOF-sleep `select` (the common shutdown path), and `<-ctx.Done()` in the send `select` (backpressure-aware send). The maximum delay between ctx cancellation and channel close is one poll tick (`DefaultPollInterval`, 50 ms). Reuse posture: when promoting a "polling loop with cross-read state" shape from the spikes, prefer a free function returning a receive-only channel over a struct with `Start()`/`Stop()`/`Err()` methods — the channel + ctx pair already covers every shutdown signal a struct API would carry, and the spike call sites already structure the work this way.
- **Typed-shape-plus-`Raw`-map is the right trade-off for envelopes whose full schema the library does not want to commit to.** `JSONLEntry` exposes named fields for the four hot paths every consumer reaches for (`Type`, `Message.ID`, `Message.StopReason`, `Message.Content[].Type`) and a `Raw map[string]any` for everything else (envelope-specific fields like `attachment` / `sessionId` / future additions; per-block fields like `text` / `input` / `name` / `tool_use_id`). This deliberately does NOT commit the library to a type-tagged union over claude's content-block schema (which would otherwise force a library bump every time claude adds a block kind). The cost is one extra `Raw["…"].(…)` type assertion at consumer sites that need a non-typed field; the spike's `extractByMsgID` already does this shape with raw maps, so consumers lose zero ergonomics and gain compile-time hits on the four hot paths. Reuse posture: when defining a public type for a parsed external schema, expose only the fields with stable upstream contracts as typed and preserve the rest as `Raw map[string]any`. The line between the two is "would a schema change here force a library version bump?" — if yes, leave it in `Raw`.
- **"Filter moves up the stack" is the default when promoting a spike helper to the library.** The spike-one-turn `tailJSONL` filters to `type == "assistant"` with a `message` map; the library `TailJSONL` emits everything. The decision is structural: the spike knew exactly which signal it wanted (`assistant`'s final-answer `text`); the library cannot know, because three different downstream needs flow through the same channel — cancellation marker detection (`user`-role), attachment / deferred-tools-delta markers (`attachment`-type), and the assistant's final-answer text (the spike's original case). Empirically the move costs the assistant-only consumer one line (`if e.Type != "assistant" || e.Message == nil { continue }`) — a line they were going to write anyway against the typed shape — and unlocks two filter variants the library cannot anticipate. Reuse posture: when promoting a shape that the spike intentionally narrowed, default to widening at the library boundary and pushing the narrow case into consumer code. The narrow filter is one line; the narrow API is a deprecation hazard.
- **Buffered channel + `select { case ch <- v: case <-ctx.Done(): return }` is the canonical send shape for a library-owned streaming goroutine.** Capacity 32 (matches the spike-side observed-stable size that survived all six observed tickets without buffer-overflow). The `select` lets the goroutine cooperate with ctx cancellation even when the consumer is lagging — without it, the goroutine would block on `ch <- entry` forever after cancellation, leaking the goroutine and the file handle. The buffer absorbs short-lived bursts; the `select` covers the case where the consumer fell behind permanently. **Do NOT expose the capacity as an option** until a real consumer surfaces a real backpressure problem — 32 is the value six spikes converged on, and the only knob that has paid for itself in this codebase is `DefaultPollInterval`. Reuse posture: for any future library streamer with bounded backpressure tolerance, copy this shape — cap 32, no exposed knob, the `select`-with-ctx pattern on every channel send.

## Lessons learned

- **A spec that pre-decides the open questions converts to a one-shot implementation.** The architect's spec for #59 named every public symbol's signature verbatim, gave the full doc-comment text for `TailJSONL`, included a behaviour-contract sketch for the goroutine loop (down to the `partial = partial[:0]` reset and the order of the two `defer`s), enumerated the test matrix with one paragraph per test, and explicitly considered-and-rejected the three big alternative-design questions (return a handle? log parse errors? expose the buffer capacity?). The developer's job collapsed to typing it in — no mid-implementation design questions, no PR-time back-and-forth on the public surface. The pattern that worked on #58 worked again here unchanged: when the spec names signatures + error shapes + test matrix + considered-alternatives verbatim, S-sized library promotions land in one round of code review. Open questions that the spec leaves unresolved produce mid-implementation thrash; open questions that the spec explicitly defers ("hardcoded at 32; expose as an Option only if a consumer surfaces real backpressure") save the same conversation from happening at review time.
- **"Append-after-EOF" tests benefit from `time.Sleep(150 * time.Millisecond)` between phases (3× the 50 ms poll interval).** The pattern from `TestWaitForSessionJSONL_FileAppearsPartwayThrough` carries straight across to the tail tests: write a phase, sleep 150 ms (one poll tick is 50 ms; 3× provides CI margin), append the next phase, assert the channel value. The `mustReceive` helper (fail-fast 500 ms timeout on a receive) bounds total test runtime if a tail goroutine deadlocks — without it, a stuck goroutine hangs until `go test`'s default 10-minute timeout. The `mustAppend` helper centralises the `O_APPEND|O_WRONLY` open + write pattern so individual tests don't repeat the boilerplate. Reuse posture: any future test in this package that interacts with a tailing goroutine should copy `mustReceive` / `mustAppend` / the 150 ms inter-phase sleep idiom directly. The trio is reliable enough that the seven `TestTailJSONL_*` cases land green on first try.
- **Stacked `defer` order matters when both the file and the channel are owned by the goroutine.** `defer close(ch)` then `defer f.Close()` (declared in that order) fires `f.Close()` first, then `close(ch)`. Either order is correct here — the channel and file are independent resources — but the convention "close the output last so consumers see the channel close after any in-flight side effects have completed" is worth preserving across future library streamers. The current code declares `defer close(ch)` before `defer f.Close()`, which gives the reverse: `f.Close()` fires first, then `close(ch)`. Both orders are observably equivalent for this function (the consumer cannot observe a file close), but the chosen order has a subtle property — it means any `f.Close()` panic surfaces before the consumer sees the channel close, which is the right end-of-life ordering for a library that promises "channel close means goroutine exit". Document this in the doc-comment if the convention needs to be load-bearing in a future streamer.
