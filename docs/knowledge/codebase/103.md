# #103 — library API: `JSONLEntry.RawLine` exposes verbatim source-line bytes

[Issue](https://github.com/pyrycode/tui-driver/issues/103) · [Spec](../../specs/architecture/103-jsonlentry-rawline.md) · Predecessors: [#59](59.md), [#60](60.md) · Split from #101

## Summary

Added a fourth field — `RawLine []byte` — to `JSONLEntry` (`pkg/tuidriver/jsonl.go:108-113`) so consumers that re-emit claude's per-session JSONL byte-for-byte (the motivating case: pyrycode's `internal/agentrun/streamjson/emitter.go:195`, which does `append([]byte(nil), ev.RawLine...)`) can get fidelity that `json.Marshal(e.Raw)` structurally cannot provide. Go's encoder sorts map keys alphabetically and normalises whitespace; `Raw` round-tripped through `encoding/json` does not preserve either. `RawLine` is the trimmed source bytes the tail goroutine read — byte-identical to what `parseEntry` consumed, modulo the trailing `\r\n` (or `\n`) strip already in place. Pyrycode's byte-equivalence test (pyrycode #506) pins this contract on the consumer side; this slice is its library-side prerequisite.

Implementation is one line of behaviour change inside `parseEntry` (`pkg/tuidriver/jsonl.go:240`): `entry := JSONLEntry{Raw: raw, RawLine: bytes.Clone(line)}`. The `bytes.Clone` is **mandatory, not defensive ornamentation** — `line` is the result of `bytes.TrimRight(partial, "\r\n")` in `tailJSONLLoop`, which shares backing memory with `partial`, and the next iteration's `partial = append(partial, chunk...)` may grow the slice in place and clobber the bytes a previously-emitted entry's `RawLine` would otherwise still point at. A naked `RawLine: line` would race the next read. The copy lives inside `parseEntry` rather than in `tailJSONLLoop` so the byte-ownership concern stays localised to the parser; the loop continues to own only the rolling buffer.

`tailJSONLLoop` itself is unchanged. `TailJSONL`'s public signature, channel cap, poll cadence, and EOF-sleep loop are unchanged. `defaultJSONLTailBuffer = 32` is unchanged — the per-entry allocation (sized to the line length, dwarfed by the JSON parse it sits next to) doesn't move backpressure characteristics meaningfully. The library doc-comment for `JSONLEntry` gained two paragraphs (`pkg/tuidriver/jsonl.go:96-107`) distinguishing `RawLine` from `Raw` and pinning the trimming-rule contract: populated for every entry the channel emits, owned by the entry, the library will not mutate it post-send; nil is allowed for entries callers synthesise directly (test fixtures), but on the `TailJSONL` channel `RawLine` is never nil.

Tests added in `pkg/tuidriver/jsonl_test.go:265-320` (one new test, `TestTailJSONL_RawLineByteFidelity`, no edits to existing tests): four scenario lines exercise the realistic worst cases for re-marshal drift — mixed-order keys (`{"z":1,"a":2,"m":3}` — Go's encoder sorts; the canonical drift source), multi-byte UTF-8 (Japanese characters + emoji), JSON-escaped `\n` / `\t` inside a string value (escape must stay escaped, not become a literal byte), and a long base64-looking value with `+`/`/`/`=` (stand-in for tool_use input payloads). Each scenario asserts `bytes.Equal(ev.RawLine, []byte(want))`. A second phase in the same test appends a fifth line, drains it, then re-asserts the original four `entries[i].RawLine` values — pinning the defensive-copy contract: if a future refactor "optimises" the `bytes.Clone` away, the rolling-buffer reuse would clobber earlier `RawLine`s between iterations and this phase would fail. Code review (PR for #103): the diff is 18 production-source lines + 59 test lines.

## Patterns established

- **Slice-aliasing fields in public types need an explicit "library will not mutate it after emission" doc-comment.** The contract `JSONLEntry.RawLine`'s doc carries — "owned by the entry; the library will not mutate it after emission" — is the right shape for any future field that exposes bytes a streaming goroutine read into a rolling buffer. Without that sentence, a careful consumer would assume the worst (must copy on receive) and waste an allocation; without the underlying `bytes.Clone` at the emit site, a careless consumer would discover the alias the hard way when their stored `RawLine` mutates under them seconds later. The doc-comment commits the library to the property; the `bytes.Clone` enforces it. Reuse posture: any future tuidriver public type that exposes a `[]byte` field sourced from a rolling buffer should pair the same two pieces — a one-line "owned by the entry, will not mutate after emission" guarantee in the doc, and an unconditional copy at the emit site to back it. The TailJSONL→parseEntry boundary is the canonical example.
- **Typed shape + `Raw` map + `RawLine` bytes are three orthogonal access patterns for the same line, not redundant copies.** `Type` / `Message` are the typed view for the four hot fields every consumer reaches for (cheap, compile-time-checked, zero allocation beyond the parse itself). `Raw` is the parsed map for envelope-specific or future-schema fields outside the typed view (one allocation per envelope, already paid by `json.Unmarshal`). `RawLine` is the verbatim bytes for consumers that need byte-fidelity (one extra allocation per entry, sized to the line). The three serve genuinely different needs — `Raw` cannot substitute for `RawLine` because `encoding/json` normalises key order and whitespace on re-marshal, and `RawLine` cannot substitute for `Raw` because re-parsing on every field access is expensive. Reuse posture: when a parsed-shape API needs to support both "give me this field" and "give me the original bytes" access modes, expose both rather than picking one and forcing consumers through a workaround. The cost is one extra `[]byte` field and one copy per entry; the benefit is removing the entire "marshal-drift" failure class from the consumer's plate.
- **`bytes.Clone` reads more intentionally than `append([]byte(nil), src...)` for "I am copying this because of aliasing, not because of appending".** Both produce the same allocation; both are stdlib (the former since Go 1.20). The spec called out the choice between them ("`bytes.Clone` is stdlib since Go 1.20 — already used in this codebase? if not, `append([]byte(nil), line...)` is the equivalent idiom") and the implementation chose `bytes.Clone` with a two-line comment naming the aliasing reason: "bytes.Clone is mandatory — line aliases tailJSONLLoop's rolling `partial` buffer, which the next iteration's append may clobber." The named function spells the intent at the call site; the `append(nil, …)` form requires the reader to recognise the idiom. Reuse posture: prefer `bytes.Clone(src)` over `append([]byte(nil), src...)` when the copy exists for aliasing-safety reasons; reserve the `append` form for cases where the surrounding code is already building up a slice via `append` and the `(nil, src...)` shape is the natural local idiom.

## Lessons learned

- **The "is RawLine populated on synthesised entries?" question is worth answering in the doc-comment, not the test matrix.** The `JSONLEntry` doc explicitly carves out the synthesised-entry case ("RawLine may be nil: its presence is the TailJSONL contract, not a struct invariant"), and the test suite does not exercise it — `parseEntry` is unexported, and every public-API path through `TailJSONL` produces a non-nil `RawLine`. The alternative (assert `RawLine != nil` as a struct invariant, populate something defensible in synthesis paths) would have either forced every test fixture to carry a `RawLine: []byte("…")` literal or pushed an empty `[]byte{}` allocation into the struct's zero value. Both are worse than the doc-only carve-out, which costs one paragraph and matches the existing precedent — `Message` is also non-nil only for envelopes that carry a `message` object, not on every `JSONLEntry`. Reuse posture: when a new field's "always populated" property is a streaming-contract guarantee rather than a struct invariant, say so in the doc and rely on the streaming entry point to enforce it, rather than threading the invariant through every constructor path.
- **One-test-with-two-phases beats two separate tests when the second phase is a pin-down for the first.** `TestTailJSONL_RawLineByteFidelity` runs the four scenario-line round-trips, then in the same test appends one more line and re-asserts the original four `RawLine` values. The spec offered a sibling-test option ("or a sibling test if it grows"), the implementation kept it in one. Two reasons. First, the second phase is meaningless without the first having populated `entries[i]` — a sibling test would have to either duplicate the four-scenario setup or share a helper that the first test also calls; either is more code than the inline `mustAppend` + `mustReceive` + re-loop. Second, the second phase's failure mode is "the contract the first phase established silently breaks under later activity" — bundling them keeps the reader's mental model of "what is being tested" connected to the actual assertion that proves it. Reuse posture: when a test has a "now prove the property still holds after X happens" follow-on, prefer inline phases over sibling tests; reach for a sibling test only when the second phase's setup diverges enough that sharing is awkward.
- **XS-sized library-promotion slices continue to land in one round when the spec pre-decides the architect-level calls.** Same pattern as #58 → #59 → #60 → #61 → #87 → #89 → #100 and now #103: the architect named the field's type (`[]byte`, not `json.RawMessage`, with the reasoning), the field's name (`RawLine`, distinct from `Raw`), the field's placement in the struct (end, after `Raw`, for adjacency), the doc-comment paragraphs (verbatim), the call-site idiom (`bytes.Clone` vs `append(nil, …)`), and the test matrix (four scenarios + one pin-down phase). The developer's job was typing it in; no mid-implementation thrash, no PR-time back-and-forth on shape. The cost-per-decision pattern remains: architect-level calls cost an architect-pass; developer-time thrash costs an architect-pass plus a developer-pass plus a review-pass. Reuse posture: for XS additive-field tickets, the architect should default to pre-deciding every named call (type, name, placement, doc-comment text, call-site idiom, test scenarios) rather than leaving them as "developer's call" — the deferred decisions cost the same amount of thinking either way, and pre-decided ones cost it once.
