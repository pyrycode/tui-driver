# #253 — `repro-permission-flake`: reproduce + diagnose spike-permission's load flake (slice A)

[Issue](https://github.com/pyrycode/tui-driver/issues/253) · [Spec](../../specs/architecture/253-repro-permission-flake.md) · Split from [#250](https://github.com/pyrycode/tui-driver/issues/250) · Slice A of the spike-from-implement split of #253 (architect override, 2026-07-09) · Code: `cmd/repro-permission-flake/`

## Summary

Adds `cmd/repro-permission-flake`, a hand-run `TOOLS`-category diagnostic (sibling of `corpus-replay`) that reproduces and diagnoses `spike-permission`'s **"modal not detected within 30s"** load flake — observed once under full-suite `make e2e` on PR #249 (`fail`, 31830ms), but 3/3 green on direct standalone re-run. That "passes alone, reddens under load" signature matches [#185](185.md)'s `spike-one-turn` flake, but the 30s wall here is `spike-permission`'s own **internal** `modalDetectLimit` (`cmd/spike-permission/main.go:115`), hit **pre-clear** in Probe 1 before any `OBSERVED:` line prints — distinct from the closed #180 (a deterministic *post*-clear 60s hang) and not covered by #180's `^OBSERVED` de-gate.

This is **slice A only — it fixes nothing.** It treats `./bin/spike-permission` as a black box, drives it in concurrent waves (`-concurrency` × `-waves`) mirroring #185's load model, timestamps each instance's stderr/stdout with harness-owned elapsed-ms, and classifies each capture with two pure functions:

- `classifyCapture` (`classify.go`) — parses the timestamped lines into an `instanceOutcome{outcome, modalSeenAtMs, stageTimeline, maxByteGapMs}`. `outcome` is `pass` (stdout has `^OBSERVED`), `flake` (stderr has `modal not detected within`), or `other`. `modalSeenAtMs` is the earliest elapsed-ms any of `spike-permission`'s three `modalLiteralTexts` anchors (`main.go:150-168`, hand-copied here as `modalAnchors`) appears in the `tuidriver.StripANSIString`-ed PTY stream — the (c)-discriminator.
- `diagnose` (`classify.go`) — applies the spec's decision table to a flake's `instanceOutcome`: `modalSeenAtMs < deadline` → **(c) detection-bug**, unambiguous (rationale below); otherwise the byte-gap profile (`maxByteGapMs` vs `steadyGapMs`/`burstGapMs` thresholds) splits **(a) contention** / **(b) pty-starvation** / **ambiguous**, all three routing to the same non-security-sensitive fix.

**Why (c) is unambiguous.** `spike-permission`'s stderr mirror and its rolling detection buffer are fed by the *same* reader goroutine, so an anchor drained before the 30s deadline proves the bytes were both rendered and available to `hasModal` in time — a timeout despite that is a detector defect, not a slow render. This is the fork that decides slice B's branch (consolidate into #185 vs. a distinct `pkg/tuidriver` fix) and its security posture (only (c) is `security-sensitive`, audited against #242's forgery threat model).

Output is a durable per-run artifact (`wave<w>-inst<i>.log` captures + a `summary` readout naming the root-cause tally and the shared-vs-#185 mapping), not just stdout — the deliverable PO authors slice B against. Enrolled in `Makefile` `TOOLS` + a `make repro-permission-flake` phony target (flags surfaced as `CONCURRENCY=`/`WAVES=`/`CPU_BURN=`); deliberately **not** in `PROBES` or `cmd/e2e-runner` `buildChecks` — enrolling it would spawn `P×W` live `claude` instances on every `make e2e`.

**Not security-sensitive** (confirmed): slice A builds instrumentation *around* the prebuilt spike binary and observes timing; it changes no modal-detection logic in `pkg/tuidriver` and no modal-answer path. The precautionary posture attaches to slice B *iff* the live diagnosis is root-cause (c).

## Patterns established

- **Black-box repro harness over the observation-rig binary, not a README recipe.** #185's fix was a single constant, so its repro stayed shell-instructions in a README. Here the fix branch *and* its security posture both fork on the diagnosis, so a reusable, instrumented, artifact-producing harness earns its own `cmd/` binary — the same rig gets re-run to validate slice B against the #185 bar (≥20 consecutive load runs). "Every instance is both load and subject" (concurrent `spike-permission` copies competing for cores) reproduces `PYRY_MAX_CONCURRENT=2` contention directly rather than simulating it.
- **Harness-owned timestamps, not the subject's own log flags.** The capture goroutine prefixes every drained line with its own monotonic elapsed-ms (`lineWriter` in `main.go`), giving one consistent clock across `spike-permission`'s stage lines and raw PTY bytes regardless of that binary's logging config — the same "external, independent-of-the-thing-being-measured" posture as [#206](206.md)'s `discoverProjectsDir` avoiding `EncodeCwd`.
- **The one unambiguous signal decides the fork; don't force separability where none exists.** (a) vs (b) are honestly reported as `load-induced-ab-ambiguous` when the byte-gap profile doesn't clearly separate them from a black-box capture — both route to the same non-security-sensitive fix, so the ambiguity is harmless. Only (c) needs a clean verdict, and the mirror==buffer single-reader guarantee gives it one. Resist over-engineering a grey-box (a)/(b) split into slice A; that's an explicit out-of-scope follow-up if PO ever needs it.
- **Reproducing the flake is success, not failure.** Exit 0 whenever the wave plan completes and the artifact writes — including the run that reproduces the timeout — mirroring [#206](206.md)'s "green on observation, red only on no-observation" rig semantics.

## Lessons learned

- **The developer commit message claims more test coverage than the diff carries.** `e72e7b3`'s message says the "concurrent capture path" is "race-tested against a fake spike," but `cmd/repro-permission-flake/classify_test.go` (the only test file in the diff) exercises only the pure `classifyCapture`/`diagnose`/`parseCaptureLine`/`sharedWith185` functions against committed `testdata/*.capture` fixtures — there is no test that spawns a fake `spike-permission` binary and drives `runWave`/`runInstance` under `-race`. This matches the architecture spec's actual Testing-strategy section (pure-function table tests only; the concurrent orchestration in `main.go` is exercised by `go vet`/build plus the operator's live run, not a fake-binary unit test) — so the *shipped* deliverable is correct and matches spec, but the commit message overstates what's under test. Worth a habit check on future diagnostic-rig tickets: verify a commit message's testing claim against the actual diff before trusting it, the same discipline [#206](206.md)'s lesson applied to a spec's convention claim.
