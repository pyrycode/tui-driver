# #9 — spike: multi-turn interactive `claude` (tool-use, slow-thinking, msg_id-grouped extraction)

[Issue](https://github.com/pyrycode/tui-driver/issues/9) · [Spec](../../specs/architecture/9-spike-multi-turn.md) · Code: `cmd/spike-multi-turn/`

## Summary

Second spike binary in the repo: `cmd/spike-multi-turn/main.go` (~740 LOC) plus `cmd/spike-multi-turn/README.md` (~495 lines of empirical log). Drives three sequential interactive `claude` turns end-to-end against a single PTY-attached process: `say hello` (baseline text), `list the files in /tmp` (Bash tool use), and `think carefully and compute 1+2+3+...+100, showing your reasoning` (slow thinking + multi-block message). Reuses spike-one-turn's primitives verbatim under attribution comments (`rollingBuffer`, `tracker`, `isIdle`, `tailJSONL`, `resolveSession`, `openSessionJSONL`, `matchSpinner`, `waitUntil`, etc.) and adds four new ideas: a `runTurn` per-turn driver, an `extractByMsgID` content extractor that groups assistant events by `message.id`, a `typePrompt` char-by-char PTY writer, and a 250 ms `idleStableWindow` debounce on the turn-complete predicate.

Empirical centerpiece: turn 3 emits **two assistant JSONL lines with the same `msg_id`, both tagged `stop_reason=end_turn`**, carrying different content-block types (`thinking` and `text`). Spike-one-turn's "concatenate text from one record" would have read the first line, found no `text` block, and returned empty. The new extractor walks every event whose `message.id == latestEndTurnMsgID` and concatenates `type=="text"` blocks in JSONL order — correctly producing the user-visible answer. This validates the ticket's findings 1 (one Anthropic message ⇒ N JSONL lines) and 3 (`stop_reason` is on every delta) against real data.

Turn 2 produced a simpler tool-use shape than the pre-spike probe predicted: two assistant lines with *different* msg_ids (`msg_011JC…` carrying a single `tool_use` block with `stop_reason=tool_use`, then `msg_01YEr…` carrying the final `text` block with `stop_reason=end_turn`) interleaved with one `user(tool_result)` event. The msg_id grouping rule handles this correctly because it keys on the latest `end_turn` msg_id — tool_use msg_ids are inert noise to the extractor. The heavier "5 lines under one msg_id" shape the pre-spike vault note predicted was not observed for a single-call task; both shapes route through the same extraction code.

Three implementation deviations from the architect's spec, all forced by behavior the spec couldn't have known:

- **`--permission-mode bypassPermissions`** is required for turn 2. The default permission mode renders a modal ("1. Yes / 2. Yes, allow reading from tmp/ from this project") and blocks on a keystroke choice — modal handling is out of scope per the ticket, so the spike sidesteps the modal by passing `--permission-mode bypassPermissions` at spawn. Not safe as a default for the eventual library; consumers must own the trust-model choice per session.
- **Char-by-char `typePrompt` with a 10 ms inter-byte delay** is required for turn 3 to submit. Bulk-writing `prompt+"\r"` works for turns 1 and 2 but the input handler swallows `\r` if it arrives mid-redraw after a tool-use turn's wind-down. The fix is empirical (not source-confirmed): write each byte separately with a brief delay, pause 50 ms before the final `\r`. Library will likely need this configurable.
- **250 ms `idleStableWindow` debounce** on the turn-complete predicate. The spec's `gotEndTurn ∧ isIdle(rb)` fires the moment both hold; in practice a transient idle observation while the TUI is mid-redraw could trip it before the input area has actually settled. The fix is to require `isIdle` continuously true for ≥250 ms after `gotEndTurn`. Belt-and-suspenders padding once `typePrompt` exists (typing already takes ~700 ms for a 64-char prompt) but the predicate's shape is structurally correct.

Three runs (5, 6, 7) all green: `SUCCESS:` × 3 each, ~16–21 s total wall time. JSONL line count is identical (27 lines per run) across all three runs and the envelope sequence around the assistant messages is identical too — variance is purely in `content[].text` length within the assistant lines. No new envelope types observed beyond spike-one-turn's catalog; `queue-operation` (predicted by the pre-spike probe) did not appear, possibly correlated with `bypassPermissions` suppressing the permission-prompt path. `last-prompt` fires 2× per multi-turn run (after turn 2 and turn 3) — different rate from spike-one-turn's per-turn pattern; one data point, not conclusive.

## Patterns established

- **`runTurn(turn, prompt, …, postPromptHook)` shape.** A linear per-turn driver that the orchestrator calls in a `for` loop. Turn 1 carries a `postPromptHook` that opens the JSONL and starts the tailer goroutine (the file doesn't exist until claude processes the first input — same `--session-id` deferral spike-one-turn ticket #7 already documented); turns 2+ pass `nil`. The driver's contract is "assume idle on entry; leave the TUI back at idle on exit" — the orchestrator therefore doesn't re-run `waitUntil(... isIdle ...)` between turns. This is the shape the library's eventual public API will grow from.
- **Residual-event drain at turn start.** Before accumulating events for turn N, `runTurn` non-blocking-drains `eventCh` to discard any delta lines for turn N-1's msg_id that the prior turn left buffered after its `end_turn` was observed. Without the drain, the `gotEndTurn && isIdle` predicate could fire spuriously at the start of the new turn. The drain is cheap (single non-blocking select loop) and structurally necessary because the events channel is session-scoped, not turn-scoped — there's only one tailer goroutine for the whole session.
- **msg_id grouping = correct content extraction rule for multi-block messages.** The rule is: at end of turn N, identify the `msg_id` of the **latest** assistant line with `stop_reason=end_turn`; collect every assistant event whose `.message.id == that_id`; walk their `content[]` in JSONL arrival order; concatenate blocks with `type == "text"`. Skips `thinking` and `tool_use` blocks. Replaces spike-one-turn's `extractAssistantText` (which assumed one record per message). The post-spike library MUST implement this rule, not the single-record shortcut.
- **Turn-complete = JSONL `end_turn` AND PTY idle stable** (conjunction). `end_turn` says "model done speaking"; `isIdle` says "TUI ready to accept input." Both must hold before the next prompt is safe to write. The `idleStableWindow` debounce protects against transient idle observations during TUI redraws. Whether the `isIdle` half is a real gate or just a heartbeat depends on whether the spinner regex matches (it currently never does — spike-one-turn finding #8 still open) — see [system overview](../architecture/system-overview.md) and [#1's notes](1.md) for the conjunction's structural correctness regardless.
- **Copy-paste-with-attribution between spikes is fine until library extraction.** Both spike binaries duplicate ~600 LOC of helpers under `// copied from cmd/spike-one-turn/main.go — keep in sync until library extraction` comments. The comments are the index for which symbols the library will pick up; the duplication is intentional and deletes itself when `pkg/tuidriver/` lands.
- **Char-by-char PTY writes for prompt submission.** `typePrompt` writes the prompt body one byte at a time with a 10 ms delay between bytes, pauses 50 ms, then writes `\r`. Required between turns 2 and 3 specifically; turn 1 (after session boot) and turn 2 (after a simple-text turn 1) both work with bulk writes, but a bulk write after a tool-use wind-down does not. The library should default to char-by-char and expose the inter-byte delay as a per-session option.

## Lessons learned

- **The default `--permission-mode` is incompatible with unattended tool use.** The architect's spec said claude would invoke the Bash tool "under the hood, via the interactive permission-mode default." In practice, the default renders a modal that blocks on a keystroke. The spec couldn't have known this — modal-trigger behavior wasn't probed pre-spike — but the fix is small (`--permission-mode bypassPermissions` at spawn) and the implication for the library is large: permission-mode is a per-session option the consumer must own. The library cannot pick a default that's safe for arbitrary callers.
- **Bulk-writing `prompt+"\r"` between turns races with the prior turn's wind-down redraw.** The wedge mode is silent and visually misleading: the prompt body appears in the input box, the `\r` is in the same write, but the input handler never recognises it as submit. There's no error, no log line, no JSONL event — just the 60 s inactivity watchdog tripping a minute later. The wind-down redraw is much heavier after a tool-use turn (spinner collapse + permissions footer redraw + MCP status line redraw + ai-title/last-prompt envelope writes) than after a simple-text turn, which is why turns 1 and 2 succeed and turn 3 wedges. Char-by-char typing was the empirical fix; the architectural lesson is that the library will need a "TUI quiescence" model for the input write path, not just for the read path.
- **msg_id is the right grouping key, not arrival order or content-block index.** Three plausible-but-wrong rules for content extraction surfaced during analysis: "first end_turn line" (spike-one-turn's implicit rule — wrong for turn 3), "latest end_turn line" (would have worked for turn 3 but only by luck of arrival order, not by anything structural), "concatenate every `text` block in every `end_turn` line" (wrong if a turn ever emits multiple distinct messages with end_turn — not observed but plausible). The correct rule is the one the spec specified: target the latest end_turn line's `msg_id`, then group by `message.id == that_id`. The rule is robust to the spike's three actual shapes (turn 1: 1 line, 1 block; turn 2: 2 lines, different msg_ids, only one is end_turn; turn 3: 2 lines, same msg_id, both end_turn) and to a pathological "model emits multiple end_turn messages within a turn" case if it ever appears.
- **The spec contradicts the ticket body on the inter-turn idle wait — and the spec is right.** The ticket implies each turn re-checks `isIdle` before writing the next prompt. The spec specified `runTurn` to leave the TUI at idle on exit, so the orchestrator doesn't re-wait. Empirically the spec's shape is correct: spike-one-turn's `❯-reappeared` already establishes idle, and re-waiting would be a no-op on the fast path or a hang on a TUI that's about to redraw. Same lesson as #1 and #7: when the spec explicitly overrides the ticket body, trust the spec.
- **The `idleStableWindow` debounce is mostly load-bearing in theory, not in practice.** Once `typePrompt` shipped, the 250 ms debounce became redundant — the natural inter-turn pause is dominated by the typing latency (~700 ms for a 64-char prompt), and turning the debounce up to 1500 ms changed nothing. It's kept at 250 ms because the cost is negligible and the predicate's `isIdle` half is the structurally correct gate; if finding #8 ever gets fixed and `isIdle` becomes a tight signal, the debounce becomes a useful real debounce instead of defensive padding. Worth noting: the wedge that drove the debounce's introduction was actually surprise 2 (bulk-write race), not a predicate-timing race — diagnostic effort was misdirected for several runs before the underlying cause surfaced.
- **Spinner regex still misses, and the verb set is larger than spike-one-turn observed.** This spike added `Cooked for 5s`, `Churned for `, `Baked for 11s`/`5s`/`3s`, `Sautéed for 5s` (unicode in verb), and `Crunched for 4s` to the captured set. None matched the regex — same CSI-cursor-forward cause as spike-one-turn finding #8. Finding #8 is unchanged; the library's slow-path log lines remain dormant until it's fixed. Useful side data for whoever picks up the regex ticket: the verb set is open-ended and the verbs themselves may carry unicode.
- **JSONL line count is remarkably consistent across runs.** All 3 green runs produced exactly 27 JSONL lines with the same envelope sequence around the assistant messages. Variance is purely in the `text` content lengths. Sample size 3, not a guarantee — but suggestive that the per-turn envelope shape is deterministic given the same probe prompts. The library's test harness should be able to assert envelope shape for fixed prompts.
- **`last-prompt` fires per *multi-turn continuation*, not per turn.** Spike-one-turn observed `last-prompt` once per single-turn session; spike-multi-turn observes it twice per 3-turn run (after turns 2 and 3 — turn 1 has none). Suggests the event correlates with "this is not the first turn" rather than firing unconditionally per turn. Single multi-turn data point — not enough to be sure, but worth recording.
