# #70 — spike-permission post-approve predicate: swap to PTY-quiescence

[Issue](https://github.com/pyrycode/tui-driver/issues/70) · [Spec](../../specs/architecture/70-spike-permission-pty-quiescence.md) · Code: `cmd/spike-permission/`

## Summary

`spike-permission` wedged every run against `claude 2.1.148` (~54 s wall, watchdog-shaped) because `runAutoRespond`'s post-approve readiness predicate — `gotEndTurn ∧ tuidriver.IsIdle ∧ stable 250 ms` (`cmd/spike-permission/main.go:655-672` pre-fix) — was the verbatim pre-#74 spike-multi-turn predicate, copy-pasted into spike-permission's Probe 2 path. The wedge is mechanically identical to #73: claude paints a `✻ Verb for Ns` spinner glyph during tool execution; after Probe 2 approves Bash, claude streams the final assistant text, flips `stop_reason=end_turn`, then emits a small redraw + title-bar updates and falls silent — well under the 4 KB rolling-buffer cap (`pkg/tuidriver/buffer.go:8-13`). The stale `✻` glyph stays in the buffer; `IsIdle`'s spinner-absent half (`pkg/tuidriver/state.go:38-44`) stays false forever; the session watchdog (`ptyQuietLimit = 30 s` / `spinnerFreezeLimit = 30 s`) trips. The ~54 s runtime cleanly decomposes into Probe 1 (~15-20 s observe) + Session B startup (~5-10 s) + Probe 2 wedge (~30 s watchdog). Hidden until recently — the `claude-version-lock` short-circuit at `cmd/e2e-runner/main.go:181-183` masked it through every `claude` version drift; once the short-circuit came out (#64), the failure surfaced every `make e2e` run.

Fix is a one-binary predicate swap matching the proven shape from PR #74 (spike-multi-turn) and `cmd/spike-cancel/main.go:513-568` (the original `waitReappeared` PTY-quiescence consumer). The `check` closure becomes `gotEndTurn ∧ bytes.Contains(StripANSI(rb.Snapshot()), tuidriver.IdleGlyph) ∧ rb.QuietFor() ≥ ptyQuietWindow` with `ptyQuietWindow = 1500 ms` — the same empirical window spike-cancel calibrated (`cmd/spike-cancel/main.go:82-91`), reused by citation rather than re-derivation. `idleStableWindow` and `idleSince` are deleted; the compile-time anchor for the removed constant comes out of the bottom-of-file `var ( _ = … )` block. No exported package symbols change; `pkg/tuidriver/IsIdle` is untouched. Every other consumer in the binary keeps current behaviour — `runObserve` (Probe 1) and `runEscalate` (Probe 3) never used this predicate, and the session-level watchdog runs at 30 s scale (vs the predicate's 1.5 s scale), different scales for different purposes.

The diagnosis lived in code inspection, not measurement: three rival hypotheses from the ticket (marker change, keystroke regression, tool-specific auto-approve drift) all fall out by inspection of the existing log signals. `gotEndTurn` does flip true (the modal cleared and the tool ran; otherwise the watchdog would fire from a different state); the JSONL contract for `stop_reason=end_turn` is intact across spikes on the same runner host; `1\r` is the shared `sendKeystroke` path that's healthy in spike-cancel's recovery cycles. The wedge is post-`end_turn`, on the readiness predicate. Same architect-side path #73 took.

## Patterns established

- **PTY-quiescence is now a three-consumer pattern.** Post-cancel readiness (spike-cancel `waitReappeared`, #11), multi-turn turn-complete (spike-multi-turn `runTurn` since #73), and post-approve readiness (spike-permission `runAutoRespond` since #70). Three independent state transitions — cancel-then-recover, end_turn-then-next-turn, approve-then-respond — converged on the same predicate against the same `claude` failure mode. The shape that lasted across all three: `desired-event-observed ∧ ❯-present ∧ rb.QuietFor() ≥ 1500 ms`. The library extraction (#58–#62) now has decisive integration pressure — three call sites is the minimum where "lift this primitive" becomes structurally obvious; the public API needs a "ReadyForInput" / "PTY-quiet" predicate distinct from `IsIdle` (which keeps its spinner-absent half for callers that want it). See [system overview § Key signals](../architecture/system-overview.md).
- **Reuse empirical constants by citation across the spike suite — confirmed at three sites now.** `ptyQuietWindow = 1500 ms` appears in `spike-cancel/main.go:82-91` (with the empirical derivation block), `spike-multi-turn/main.go:59-71` (citing spike-cancel), and now `spike-permission/main.go:99-114` (citing both). Each constant declaration is paired with a comment block naming (a) the empirical derivation site, (b) the proven sibling(s) using the same value, and (c) the 4 KB rolling-buffer constraint that motivates quiescence. This is the convention to keep until the library extraction lifts the constant. The citation-chain shape stays useful post-extraction too — it documents why three binaries agreed on the same value before the library imposed it.
- **Predicate ports between spikes are one-binary, no-package-change refactors.** #70 followed #73's playbook to the byte: touch one binary; rewrite one closure; drop one constant; remove one compile-time anchor; rewrite the rationale comment block; cite the proven siblings. No new exported package symbols; no edits to `pkg/tuidriver/` (or its forthcoming shape); no edits to other spike binaries. This shape is the right default for any future "same failure mode, fourth consumer" — the integration pressure for an extraction is the count of consumer call sites, not the count of binaries that depend on a new helper. Resist the temptation to lift early; let the consumer set settle, then extract once.

## Lessons learned

- **A copy-paste between spike binaries copies the bug too.** `runAutoRespond`'s wedging predicate was the verbatim pre-#74 spike-multi-turn predicate — spike-permission inherited the bug at copy-paste time, then sat behind the version-lock short-circuit for weeks. #73's fix had no chance of propagating because the spikes share helpers via `// copied from` attribution comments, not via a shared package. The `// keep in sync until library extraction` convention works for adding a feature ("port this regex") but silently fails for fixing a bug ("port this predicate swap") — there's no mechanism that flags "this attribution-block-copied function diverged from the source after the source was fixed." Three options going forward: (a) grep for sibling attribution comments when fixing a copied function and propagate the fix as a single-PR fan-out (this ticket's shape, in retrospect); (b) accelerate the library extraction so the source-of-truth lives in one place; (c) leave it alone and treat each "wait, this is the same wedge in spike-X" ticket as the cost of the deliberate-duplication policy. The pyrycode pipeline naturally produces (a) when the diagnoses surface separately — but the cost is one ticket per binary instead of one ticket fixing them all together. For tui-driver specifically the next-ticket pressure is small (only three binaries use the predicate; spike-permission was the last); for the broader pattern it's worth flagging in the extraction's API-design notes.
- **The version-lock short-circuit masked a structural bug, not a flaky one.** The instinct when removing a short-circuit is to expect new "flakes" — environmental drift, version skew, race conditions. The actual surfaced failure was the same predicate wedge that already existed; the short-circuit was hiding deterministic breakage. Lesson: when a long-standing CI check is short-circuited under "the environment doesn't match the lock," assume some checks behind the short-circuit are deterministically broken too, not just version-sensitive. After-the-fact diagnosis is cheap (file an issue when the check fails first time); the active discipline is **removing version-lock short-circuits eagerly** rather than leaving them in place "just to be safe."
- **The ticket's "PRIMARY hypothesis" matters when the failure shape is recognised.** The ticket itself flagged #74 as the primary hypothesis and asked the architect to evaluate it first — and that's what saved time. The architect-side decision surface was empty: predicate shape (copied from spike-multi-turn), window length (copied from spike-cancel), migration path (one binary, one closure, one constant). Compare to the alternative path where the architect would have spawned a parallel investigation across all three hypotheses; the diagnosis-by-inspection in the spec ("`gotEndTurn` does flip true, so the modal cleared and the tool ran, so it's not a keystroke regression; the JSONL contract is intact across other spikes on the same runner, so it's not a marker change; …") was load-bearing for closing the alternatives without empirical work. **Ticket authors who recognise the failure shape should call it out as the primary hypothesis**; spec authors should rule out the rivals by inspection before reaching for empirical measurement.
- **The 4 KB rolling buffer cap is now a confirmed three-incident root cause.** Three independent wedges (#11, #73, #70) all trace to the same upstream limit at `pkg/tuidriver/buffer.go:8-13`: 4096 bytes is small enough that claude's "small redraw then quiesce" patterns leave stuck glyphs in the buffer indefinitely. PTY-quiescence has now sidestepped the problem three times; "discover a new wedge, swap to quiescence, move on" is sustainable but every consumer that asks "is glyph X absent from the buffer?" still inherits the buffer-size dependency. The library extraction has to decide: lift the cap, make churn behaviour explicit in the consumer API ("this predicate is buffer-size-dependent; this one is not"), or formally deprecate glyph-absence-on-buffer as a primitive and ship quiescence-only readiness predicates. Three incidents is enough evidence to make the deprecation case, but it's an API-design decision that belongs in the extraction tickets, not in another spike-binary patch.
- **Five-minute fixes that lasted two months are worth examining as a class.** The bug in `runAutoRespond` predates `claude 2.1.148` — the wedge mechanism (rolling-buffer residue) doesn't depend on a recent claude version; spike-permission has plausibly been broken since #13 landed but was masked end-to-end until #64 removed the short-circuit. That's two months of false-green on the e2e harness for this one check, dressed up as "version skew." Without changing the policy ("eagerly remove version-lock short-circuits"), the harness can grow more checks like this whenever a check happens to copy a predicate from a sibling. One actionable defence: when a spike adopts a sibling spike's helper or predicate under a `// copied from` attribution comment, the bug-fix grep in #73's lesson set should also produce a checklist of "binaries that inherited this code; verify each on the next harness run." That checklist gives the diagnose-and-fix tickets (#69-#72 in this set) a structural reason to land in batch rather than independently.
