# #60 — library API: end-of-turn discriminator and assistant-text helper

[Issue](https://github.com/pyrycode/tui-driver/issues/60) · [Spec](../../specs/architecture/60-end-of-turn-discriminator-and-assistant-text.md) · Predecessor: [#59](59.md)

## Summary

Promoted the two per-entry JSONL semantic helpers — `IsEndTurn` and `AssistantText` — out of the seven in-tree spike binaries (`cmd/spike-{one-turn,multi-turn,cancel,permission,ask-user,long-prompt}/main.go` plus `cmd/probe-first-prompt-hang/main.go`) into `pkg/tuidriver/jsonl.go`. Both are free functions over the typed `JSONLEntry` shape that #59 introduced; no new types, no new files. `AssistantText(e JSONLEntry) string` walks `e.Message.Content`, skips non-`text` blocks, reads each block's `Raw["text"]` via zero-value-on-mismatch type assertion, skips empty strings, and returns the in-arrival-order concatenation. `IsEndTurn(e JSONLEntry) bool` composes on top: requires `e.Type == "assistant"`, `e.Message != nil`, `e.Message.StopReason == "end_turn"`, AND `AssistantText(e) != ""`. The text-non-empty half is the **scope delta from the spike helpers** — the seven spike `isEndTurn`s checked only `stop_reason`, which returns `true` for the `thinking`-only or `tool_use`-only per-block delta lines that also carry `stop_reason=end_turn` (a single Anthropic message serialises as one JSONL line per content block, and every delta line carries `stop_reason`; the text content is what disambiguates the user-visible-reply line from the noise lines). Both functions are total over `JSONLEntry` — including the zero value, including `Message == nil`, including blocks with non-string/missing `Raw["text"]` — and never panic. The package doc-comment in `tuidriver.go` was tightened in two phrases: in-scope gained "per-entry assistant-text / end-of-turn helpers"; out-of-scope was rephrased from "JSONL semantic interpretation (end-of-turn detection, msg_id grouping, content extraction)" to "JSONL semantic interpretation across lines (msg_id grouping, cross-line content aggregation, cancellation-marker detection)" — codifies that per-entry semantics are now in-library and only cross-line aggregation remains a consumer concern. **Migrating the seven in-tree spike/probe sites and pyrycode's `agentrun` consumer to call `tuidriver.IsEndTurn` / `tuidriver.AssistantText` is deliberately out of scope for this slice**; the new API is purely additive, and the closing-at-source effect lands when consumers migrate.

## Patterns established

- **Per-entry primitives compose; cross-line aggregation does not (deliberately).** This ticket lands the per-entry shape (`IsEndTurn(e)` / `AssistantText(e)`) and defers `extractByMsgID` (the multi-line aggregation that walks every assistant event with a given `message.id` and concatenates their text blocks across lines). The decision was structural: per-entry helpers compose at the stream boundary (`for e := range ch { if IsEndTurn(e) { ... } }`), have no internal state, and are pure over their input type. Cross-line aggregation needs state (which `msg_id` is currently "active", how to bound memory on long turns, replay semantics on resume) and has design tradeoffs that vary per consumer. The library promotes a primitive only when its shape is stable across all consumers; aggregation isn't, so it stays consumer-side until a real consumer surfaces a concrete shape worth standardising. Reuse posture: when a spike helper has both a per-entry form (cheap, stateless, total over its input) and a cross-line form (stateful, branching design choices), promote the per-entry form first and leave the cross-line form to the consumer until a second consumer asks for the same shape.
- **`AssistantText` is a building block, not a wrapper around `IsEndTurn`.** The spec considered a combined `EndOfTurn(e) (bool, string)` shape that returns the discriminator and the extracted text together; the implementation rejected it. Two reasons. First, `AssistantText` is independently useful on non-end-turn assistant lines — logging mid-stream content, observing partial outputs during a long turn, post-cancel reconstruction — and bundling it into the discriminator would force every "give me the text" caller to first ask "is this end-turn?" and discard the bool. Second, the spike code already shows the two-function call shape (`if isEndTurn(ev) { assistantText = extractAssistantText(ev) }`) — promoting two functions mirrors what consumers already write. The cost of computing the text twice (once inside `IsEndTurn`, once after by the caller) is exactly zero in practice: entries have ≤10 blocks, the consumer caches, the lookup is a few map indexes plus a string append. Reuse posture: when one helper logically depends on another, prefer two separately-callable functions over one composite return — the dependent helper remains independently useful, and the composite call is one line in the consumer.
- **`e.Type == "assistant"` AND `e.Message == nil` are two distinct guards, both worth writing.** The AC required both "non-assistant entry types → false" and "malformed/empty entry → false, no panic". The type check is the cleanest way to satisfy the first; the nil check is the cleanest way to satisfy the second. Both happen in practice: claude's `system` / `permission-mode` / `file-history-snapshot` envelopes don't carry a `message` object, so they hit both guards; a future envelope variant might carry `message` with shapes the parser doesn't recognise, in which case the type check is the load-bearing one. Defensive cost is two if-statements; safety is a future-envelope-kind that happens to carry `stop_reason` for an unrelated reason never producing a false positive. Reuse posture: when a function is total over a tagged-union input shape, check both the tag and the nullable payload — even if one of the two is "redundant" against today's data, neither is free of meaning, and the cost is two compares per call.
- **Empty-string guard inside the content walk pre-empts a malformed-block class.** `AssistantText`'s loop body reads `text, _ := c.Raw["text"].(string)` and then skips if `text == ""`. The `_` zero-values on missing or non-string `"text"` fields (the spec's idiom from `parseEntry`'s zero-value-on-mismatch assertions); the explicit empty-string skip removes a second source of zero-length contributions (a malformed `{"type":"text","text":null}` block that does decode to a `nil` string would otherwise call `b.WriteString("")` for no observable effect). Cost is one branch; benefit is one less malformed-input class that produces "function ran successfully but emitted nothing observable". Reuse posture: in any walk that accumulates strings via zero-value-on-mismatch assertions, skip-empty on the asserted value as well as on the type mismatch — the two cases collapse to the same intent ("contributing nothing") at the same trivial cost.

## Lessons learned

- **Tests against pure functions don't need file I/O, JSON parsing, or goroutines — synthesise `JSONLEntry` struct literals directly.** The 21 test rows (11 for `IsEndTurn`, 10 for `AssistantText`) all build `JSONLEntry{Type: "assistant", Message: &EntryMessage{...}, Content: []ContentBlock{...}}` as struct literals via two tiny helpers (`textBlock(s)` and `blockWithRaw(kind, raw)`). Routing through `parseEntry` would add coupling to the parse layer that the helpers don't share — and the parse layer has its own tests. The struct-literal approach is faster (no temp files, no `time.Sleep`), more direct (the test inputs match the code's inputs byte-for-byte), and surfaces parse-layer drift as a separate failure rather than entangling it with the per-shape contract. Reuse posture: when promoting a helper that takes a public typed shape, synthesise that shape directly in tests; do not route through the parser unless the test is specifically about parser behaviour.
- **Spec quality continues to dominate ticket size.** This is the third ticket in a row (#58, #59, #60) where the architect named every public symbol, every doc-comment paragraph, every test row, and explicitly considered-and-rejected the alternative-design questions — and the developer's job collapsed to typing it in with no mid-implementation thrash. For #60 specifically, the spec resolved the four most expensive open questions before the developer started: (1) two functions vs `(bool, string)` (two, with explicit reasoning); (2) free functions vs methods on `JSONLEntry` (free, to match the existing `pkg/tuidriver` idiom); (3) call `AssistantText` from `IsEndTurn` vs duplicate the walk (call it, single source of truth wins over a ≤10-block early-exit micro-optimisation); (4) explicit `e.Type == "assistant"` guard even though non-assistant envelopes don't carry `stop_reason` (yes, future-envelope-safety). All four answers landed in the spec as one-paragraph justifications, none re-surfaced during implementation, none surfaced at code review. Pattern that worked on #58 and #59 worked again on #60: when the spec names signatures + error shapes + test matrix + considered-alternatives verbatim, XS/S-sized library promotions land in one round. **Open questions left for the developer cost a round of code review; open questions explicitly deferred in the spec cost zero.**
