The 6-day-old open question (vault `📋 Projects/2026-05-16 - tui-driver/Open Questions § spike-ask-user JSONL-never-appears with --strict-mcp-config (2026-05-18, possibly resolved — re-verify)`) is now resolved. The human syncs the vault doc from AC4's closing comment on #109 — agent doesn't touch the vault. Whether the resolution came from [#77](https://github.com/pyrycode/tui-driver/pull/77)'s byte-by-byte prompt submit (per [#71](71.md)) or from claude version drift (2.1.144 → 2.1.150) is undetermined and out of scope; the green-path AC routes to library extraction and explicitly punts mechanism analysis.

**AC2 — `pkg/tuidriver/ask_user.go` lifts the JSONL `AskUserQuestion` tool_use shape.** Three exported types (`AskUserQuestion`, `AskUserQuestionItem`, `AskUserQuestionOption`) plus one public function `ParseAskUserQuestion(snap []byte) *AskUserQuestion`. Mirrors [`ParsePicker`](../../../pkg/tuidriver/picker.go) shape exactly: doc-comment-first public parser, parsed-shape struct, nil-on-no-parse posture, two-test file (`TestParseAskUserQuestionReturnsNilOnNon` table of nine non-match cases + `TestParseAskUserQuestionRealFixture` structural assertions). The parser is pure (`[]byte → *AskUserQuestion`, no goroutines, no I/O, no shared state) and reuses [#60](60.md)'s `parseEntry` so envelope/message/content decoding stays single-sourced — `parseEntry` had one prior caller (`tailJSONLLoop`); this is the second. The existing `ModalClassAskUserQuestion` PTY-side detector ([#13](13.md)/`pkg/tuidriver/modal.go`) is reused as-is; no new `ModalClass` constant is added.

`MultiSelect`'s JSON tag is `multiSelect` (camelCase), matching the captured wire shape — not the snake_case `multi_select` the architect's spec sketched. The deviation was a spec typo against empirical capture and is documented in the PR body. The fixture `.json` sidecar reflects camelCase, and a `bytes.Contains(snap, []byte("\"multiSelect\""))` sanity guard inside `TestParseAskUserQuestionRealFixture` makes future re-records that silently swap field names trip loudly.

Fixture pair follows the post-[#81](81.md) parsed-shape comparison model used by `picker-snapshot.{bin,json}`: `testdata/ask-user-question-snapshot.bin` is the raw 1976-byte assistant envelope captured from AC1 run 2 (no trailing newline, `bytes.Clone`'d at parse time per [#103](103.md)'s `RawLine` convention); `testdata/ask-user-question-snapshot.json` is `json.MarshalIndent`'d parser output as the human-readable expectation, not deep-equal'd against. Picker's sidecar is used the same way — committed for review, not asserted.

`cmd/spike-ask-user/main.go`'s local `extractAskUserQuestion` (the literal source for this extraction, at `main.go:297-312` post-[#114](114.md)) stays as-is; the ticket scope is library extraction, not spike migration. A follow-up to migrate the spike onto `tuidriver.ParseAskUserQuestion` is the natural successor (closes the spike-ask-user library-surface adoption loop — the spike's prompt-write and tail-side migrations already landed via [#87](87.md) and [#114](114.md) respectively).

## Patterns established

- **The spec's wire-shape sketch is a hint, not a contract — verify against the captured `.bin` before committing the struct tags.** The architect spec sketched `json:"multi_select"` for `AskUserQuestion.MultiSelect`; the empirical JSONL wire emits camelCase `multiSelect`. The developer matched the wire (not the spec) and noted the deviation in the PR body. A tag mismatch with the wire would have made `json.Unmarshal(snap, &AskUserQuestion{})` silently produce `MultiSelect: false` regardless of the wire value, breaking the very behaviour the test asserts. Reuse posture: any future `Parse*` lift from a captured `.bin` fixture should read the field names off the fixture bytes (or off the live wire), never off the spec — the spec describes shape and behaviour, the wire dictates field-tag spelling. The reviewer's `codegraph` confirmation that `parseEntry` had exactly one prior caller is the analogous discipline for the JSON-decode side: verify what's already there before sketching the second caller.
- **Re-record sanity guard is a `bytes.Contains` on the wire-shape substrings inside the fixture test.** `TestParseAskUserQuestionRealFixture` asserts the captured `.bin` literally contains `"name":"AskUserQuestion"` and `"multiSelect"` before running the parser. The cost is two lines; the payoff is that a future fixture re-record that silently swaps `multiSelect` → `multi_select` (or `AskUserQuestion` → `askUserQuestion`) fails with a meaningful "fixture missing camelCase multiSelect field marker" instead of a confusing "Questions[0].MultiSelect = false, want true." This is the parsed-shape-fixture analogue of [#81](81.md)'s "exact-equal across the entire parsed struct; no field whitelist" — both guard against the silent-drift failure mode. Reuse posture: any new `Parse*` test reading a captured `.bin` should `bytes.Contains` the load-bearing wire substrings up front. The substrings are the wire-shape contract the parser depends on; codifying them in the test makes the contract visible to fixture-re-record maintainers.
- **Re-verification of stale "broken" failure modes is cheap and unblocks downstream work.** AC1 was three smoke runs from `mktemp -d` — XS work, no code change. The reward was unblocking a library extraction (AC2) that had been gated on a 6-day-old open question and would have otherwise required mechanism investigation. Reuse posture: when an open question of the form "X is broken, possibly resolved by Y, re-verify" sits for more than a few days and Y has landed, structure the next ticket as `if re-verify-clean: do downstream work; else: file investigation`. The cost ceiling is XS, the routing is mechanical, and the green path delivers a real shipped artifact instead of just an updated open-questions doc.

## Lessons learned

- **The 2026-05-18 `--strict-mcp-config` JSONL-never-appears block is no longer reproducible against claude 2.1.150 (3/3 green from fresh cwd).** The mechanism that resolved it is unknown — both [#77](https://github.com/pyrycode/tui-driver/pull/77) (byte-by-byte prompt submit per [#71](71.md), which changes prompt submission shape) and the claude 2.1.144 → 2.1.150 version drift are plausible contributors. The ticket explicitly declared mechanism analysis out of scope (red-path AC3's "Mechanism investigation belongs in the new ticket, not here"); on the green path the question dissolves rather than getting answered. Lesson: when a failure mode goes silent across a multi-week gap with multiple plausible upstream changes, the right move is to (a) record the silence with enough provenance that a future regression is recognisable (claude version pinned in PR body; reproducible repro command captured in the spec), and (b) move on. The post-extraction smoke runs become the regression detector — if `make e2e` ever starts surfacing the original fingerprint, the chain back through #109 → #77 + claude 2.1.150 is documented and discoverable.
- **The architect's spec contained a small wire-shape typo that the developer caught at implementation time, not at spec review.** The spec sketched `MultiSelect bool \`json:"multi_select"\`` (snake_case); the captured wire emits camelCase `multiSelect`. The developer ran the parser against the captured `.bin`, observed the mismatch, fixed it in the struct tag, regenerated the sidecar `.json`, and noted the deviation in the PR body — clean handoff, no escalation needed. The reviewer flagged the deviation as a "notable positive deviation" rather than a defect. Lesson: spec-time wire-shape sketches that are not literally copy-pasted from a real capture are typo-prone (snake_case is the dominant Go-side convention, so the spec author defaulted to it without checking). For parsers lifted from a `.bin` fixture, the literal field names in the fixture are the contract; the spec describes shape and posture. The next architect spec for a wire-shape lift should either include the fixture excerpt verbatim or explicitly defer field-name spelling to the developer; either eliminates this class of typo.
- **The `len(items) == 0` after-iteration branch in `ParseAskUserQuestion` is dead-letter logic — the empty-wire-array case returns earlier via `len(rawQuestions) == 0`.** The reviewer flagged this as a NIT: covering it would need a `"questions":[1,2,3]` (non-object questions) test case to trip the after-iteration branch. The branch is correct defensive code, but the test suite as shipped does not exercise it; a fixture with malformed non-object `questions[]` elements would close the gap. Out of scope for this ticket (low-risk, the branch returns `nil` either way), tracked in the Follow-ups section. Lesson: when defensive branches collapse to the same `nil` return as an earlier short-circuit, the coverage gap is invisible to a fixture-driven test suite — the table cases assert reachable behaviour, not unreachable defensive paths. Future `Parse*` tests should explicitly include a "malformed inner element" case to close the dead-letter gap, even when the production behaviour is the same `nil` return.
