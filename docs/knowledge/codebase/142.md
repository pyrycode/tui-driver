# #142 — `ParseToolResult` JSONL extractor

[Issue](https://github.com/pyrycode/tui-driver/issues/142) · [Spec](../../specs/architecture/142-parse-tool-result.md) · [PR #144](https://github.com/pyrycode/tui-driver/pull/144) · Commit `f0b52b6` · Sibling: [#140](140.md) · Predecessors: [#60](60.md), [#81](81.md), [#103](103.md), [#109](109.md)

**Part of pyrycode#596** (Phase 2 structured streaming); enables the daemon bridge core (pyrycode#608) to emit `ToolUpdate` events from JSONL — the robust source — rather than the screen-scraped PTY spinner, which is dead at claude 2.1.158 (see [CLAUDE.md spinner caveat](../../../CLAUDE.md)). This is the `tool_result` half (→ `ToolUpdate`) of the original #140; the `tool_use` half (→ `ToolStart`) shipped as the independent sibling [#140](140.md). Neither blocked the other.

## Summary

One new file, `pkg/tuidriver/tool_result.go`: the exported type `ToolResult{ToolUseID string; IsError bool; Content any}` and the function `ParseToolResult(snap []byte) *ToolResult`. It is the **third member of the `Parse<Tool>` family** after [`ParseAskUserQuestion`](109.md) and [`ParseToolUse`](140.md) — takes the bytes of one JSONL envelope, walks `message.content[]` for the first `tool_result` block, and projects its `tool_use_id` / `is_error` / `content` off `ContentBlock.Raw` into the typed value. Reuses [#60](60.md)'s `parseEntry` so envelope/message/content decoding stays single-sourced — `parseEntry` now has four callers (`tailJSONLLoop`, `ParseAskUserQuestion`, `ParseToolUse`, `ParseToolResult`). Pure function: no I/O, no goroutines, no shared state; safe for concurrent use and on a nil/zero-value `snap`.

It diverges from both prior family members in **exactly one structural way: the envelope gate is `entry.Type == "user"`, not `"assistant"`.** `tool_result` blocks ride **user**-role envelopes — the observed sequence is `assistant(tool_use) → user(tool_result)`, and the assistant-only tailer filter drops them ([jsonl-layout § Tool-use shapes](../architecture/jsonl-layout.md)). No decoder change was needed: `parseEntry` already populates `Type` and `Message` for `user` envelopes (its `raw["message"]` decode is envelope-agnostic — it fires for any envelope carrying a `message` object), so the `user`-gate works against the existing decoder with the gate string as the only change.

Like `ParseToolUse`, **the match gate is `type == "tool_result"` alone — not field-gated.** A `tool_result` block with a missing/non-string `tool_use_id`, missing/non-bool `is_error`, or missing `content` still returns a **non-nil** `*ToolResult` with those fields at their zero values (`""`/`false`/`nil`, never a panic — the `AssistantText`/`AssistantUsage` zero-value-on-mismatch posture). The presence of `type:"tool_result"` is the entire match signal. The doc comment flags this explicitly so a future "consistency" pass doesn't re-converge it onto `ParseAskUserQuestion`'s payload gate.

`Content` is typed **`any`, deliberately**, because the wire shape is a union: `content` arrives either as a string (the common `Bash`/`Read` result) **or** as an array of content blocks (`[{"type":"text","text":"…"}]`, the Anthropic structured shape). It is read with a plain map index (`c.Raw["content"]`, **no type assertion** — there is nothing to assert against a union, and an absent key already yields `nil`) so whichever arrived is preserved "exactly as found on the wire": a string projects to `string`, an array to `[]any`, an absent key to `nil`. This generalises `ParseToolUse.Input map[string]any`'s generic-preservation choice from a single shape to a type union. `ToolUseID` is the join key the bridge uses to correlate a `ToolUpdate` back to its `ToolStart`.

Signature is `snap []byte` for the same reasons as #140 (read its [§ Signature decision](140.md)): family consistency, the AC's "malformed JSON → nil" case which only a `[]byte`-arg function calling `parseEntry` itself can honour, and `parseEntry` reuse. The bridge loop stays uniform: `ParseToolUse(e.RawLine)` for `assistant` lines, `ParseToolResult(e.RawLine)` for `user` lines ([#103](103.md)'s verbatim line bytes).

Fixture pair follows the post-[#81](81.md) parsed-shape model. `testdata/tool-result-snapshot.bin` is the **`user(tool_result)` reply to #140's `tool-use-snapshot.bin` Bash call** — it reuses that fixture's `tool_use_id` `toolu_01BashListTmpExampleAAAAAA`, so the two fixtures read as one observed `assistant(tool_use) → user(tool_result)` exchange. It carries **string** `content` (the common Bash result arm); the array-content arm is exercised by the inline test table. `testdata/tool-result-snapshot.json` is the human-readable parsed-shape sidecar (committed for review, not deep-equal'd). Hand-crafted from the documented wire shape, version-stamped `2.1.158` with placeholder ids, same sanctioned-synthetic posture as #140.

Pipeline ran clean: RED→GREEN tests, code-review PASS. Not `security-sensitive` — pure projection of a local claude-written JSONL file, no execution, never-panics; the network/trust boundary lives downstream in the bridge consumer (pyrycode#608).

## Patterns established

- **A family member can diverge from its siblings on the *envelope gate*, not just the block type — and that divergence reuses the existing decoder for free.** #140's lesson was "a divergence must be named in the doc comment." #142 adds: when the divergence is the envelope kind (`user` vs `assistant`), check whether the shared decoder already supports it before touching it. `parseEntry`'s `raw["message"]` decode was envelope-agnostic from the start, so the `user`-gate cost exactly one string literal — no `parseMessage`/`parseContentBlock` change. The reusable check: before adding an envelope variant to a `Parse<Tool>`, confirm `parseEntry` already populates `Type`/`Message` for it (it does for every envelope carrying a `message` object — `assistant` *and* `user`); if so, the gate string is the only edit.
- **Project a wire field whose type is a union as `any`, with no type assertion.** When a field arrives as either a scalar or a composite (here `content`: string | array-of-blocks), a typed field (`string`) silently drops one arm — lossy, violates "exactly as found on the wire." `any` read by plain map index preserves whichever arrived (string→`string`, array→`[]any`, absent→`nil`) at zero cost; the consumer type-switches on it exactly as it would have on the wire. **No type assertion** is the tell: a union has nothing to assert against, and a missing key already yields the `nil` zero value without one. This generalises `ParseToolUse.Input`'s generic-map choice (one shape) to a true type union, and is preferred over a typed string field (lossy) or `json.RawMessage` (forces a re-decode of bytes `parseEntry` already decoded — `Raw["content"]` is already a live `any`, not bytes).
- **A request/reply fixture pair should share its join key so the two files read as one exchange.** `tool-result-snapshot.bin` reuses `tool-use-snapshot.bin`'s `tool_use_id`, so a reader opening both sees one coherent `assistant(tool_use) → user(tool_result)` conversation rather than two unrelated synthetic lines. When a new fixture is the reply to an existing one, thread the correlating id through rather than minting a fresh value.

## Lessons learned

- **The cancel-marker test case is load-bearing — it proves the gate is the content-type walk, not the envelope alone.** The `user(text "[Request interrupted by user]")` cancellation marker ([jsonl-layout § Cancellation signal](../architecture/jsonl-layout.md)) is *also* a `user` envelope. A naive "gate on `user`, return non-nil" implementation would wrongly match it. The `c.Type != "tool_result"` skip is what rejects it (the marker carries a `text` block, no `tool_result` block → `nil`). The no-match test table includes this case explicitly, alongside its mirror image — an **assistant envelope carrying a well-formed `tool_result` block** must *also* return `nil`, asserting the `user`-gate from the other side. The two cases pin the gate as `user`-envelope ∧ `tool_result`-block, neither half sufficient alone.
- **No new ADR, no new feature doc, no system-overview change.** Like [#109](109.md) and [#140](140.md), this is a JSONL-side per-entry projection following the already-decided `Parse<Tool>` convention (documented in [jsonl-layout § Tool-use shapes](../architecture/jsonl-layout.md), where the family now lists three members) — no cross-cutting decision of ADR weight, no PTY signal change. The `Parse<Tool>` family lives in the architecture's JSONL-layout doc, not a per-helper feature page.
