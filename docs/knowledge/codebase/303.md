# #303 — live API-error retry detector → `EventKindPtyApiRetry*` carrying attempt N/M

[Issue](https://github.com/pyrycode/tui-driver/issues/303) · [Spec](../../specs/architecture/303-api-retry-event-payload.md) · [PR #305](https://github.com/pyrycode/tui-driver/pull/305) · Predecessor: [#100](100.md) · Split from #297 (sibling: #304, blocked-by this ticket)

## Summary

Added a third region-scoped status-banner detector, `pkg/tuidriver/apiretry.go`, alongside `network.go` (#220) and `mcp_banner.go`: `HasApiRetry(snap []byte) bool` and `ParseApiRetry(snap []byte) (ApiRetryAttempt, bool)` report claude's live API-error retry status row (`✻ API error · Retrying in Ns · attempt N/M`) in the bottom `bannerRegionRows` window and parse its `attempt N/M` counter into `ApiRetryAttempt{Current, Total int}`. The anchor is a two-token structural match (`API error` … `Retrying in`) rather than the full literal, chosen so it stays disjoint from #220's network-unreachable line — which shares the identical `· Retrying in Ns · attempt N/M` retry suffix but reads `Unable to connect to API`, not `API error`. Both directions of that disjointness are locked in `apiretry_test.go` (`HasApiRetry` false on the real network-failure line; `HasNetworkFailure` false on the api-error line).

`Session.Events` / `ScreenEvents` gain two new `EventKind` constants slotted into the PTY group right after `EventKindPtyNetworkFailureHidden`: `EventKindPtyApiRetryShown` and `EventKindPtyApiRetryHidden`. This is the **first payload-carrying PTY event** — `Event` gains a `Retry ApiRetryAttempt` field, populated only on these two kinds (every prior PTY event was payload-free; the kind alone was the signal). `classify` grows two `ptyState` fields (`apiRetry bool`, `apiRetryAttempt ApiRetryAttempt`) set from one shared `apiRetryInRegion(g)` grid scan, and `mergeEvents` gets one new emission block with three mutually-exclusive branches: rising edge (`Shown`), count-change-while-present (`Shown` again — the one divergence from the #100 boolean-banner shape, since the consumer needs to watch the count climb 3/10 → 4/10), and falling edge (`Hidden`, carrying the last-known attempt). Like the #100 banners, the axis is independent of modal/idle/thinking state (fires even with a modal open or the spinner running).

Implementation matched the architect's spec (fee7112) exactly — zero deviation. Code review passed with no findings.

## Patterns established

- **Payload-carrying event shape.** `Event.Retry ApiRetryAttempt` is the first non-empty payload field on a PTY-sourced event (JSONL-sourced events already carried `Entry`/`Err`). The precedent for a future payload-carrying PTY axis: add one field to `Event`, document it in the "Field population by Kind" block as populated only on the new kind(s), and keep every other kind's field zero-valued — no variant/union type, no breaking change (every `Event{...}` construction is field-named).
- **Re-emit-on-change for a persisting condition with a mutable payload.** The existing #100 banner shape (`if rising {...} else if falling {...}`) doesn't fit an axis whose payload can change while the boolean stays true. #303's fix: a third branch, `cur.X && prev.X && cur.payload != prev.payload`, sitting between the rising and falling branches, still mutually exclusive with them per tick (a boolean can't rise/fall and stay-with-changed-payload on the same tick). Reuse posture: any future payload-carrying condition axis that needs "watch the value climb" should copy this three-branch shape rather than inventing a separate polling API.
- **Row-scoped secondary parse to avoid cross-line scraping.** The `attempt N/M` counter regex is applied to the *matched row itself*, not the whole `bannerRegionRows` region — otherwise, on a screen where both #220's network line and a stale api-error line happened to coexist in the region, the counter regex could scrape the wrong line's count. Any future banner detector with a sub-parse (a second regex extracting structured data from within an already-anchored row) should bind the sub-parse to the matched row string, not re-scan the region.

## Lessons learned

- **A shared retry suffix between two detectors is a real double-fire risk, not a hypothetical one.** The committed `network-failure-snapshot.bin` fixture (#220, real 2.1.199 capture) already renders `· Retrying in 1s · attempt 1/10` as part of its `Unable to connect to API` line — the exact suffix shape this ticket's line also uses. Discriminating on the token that's absent from the other line (`API error` vs `Unable to connect to API`) rather than on the shared suffix is what keeps them disjoint. Any future status-line detector should check existing committed fixtures for shared substructure before picking an anchor, not just design the anchor in isolation.
