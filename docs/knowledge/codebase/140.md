# #140 — `ParseToolUse` JSONL extractor

[Issue](https://github.com/pyrycode/tui-driver/issues/140) · [Spec](../../specs/architecture/140-parse-tool-use.md) · [PR #143](https://github.com/pyrycode/tui-driver/pull/143) · Commit `ea6e4e8` · Predecessors: [#60](60.md), [#81](81.md), [#103](103.md), [#109](109.md)

**Part of pyrycode#596** (Phase 2 structured streaming); enables the daemon bridge core (pyrycode#608) to emit `ToolStart` events from JSONL — the robust source — rather than the screen-scraped PTY spinner, which is dead at claude 2.1.158 (see [CLAUDE.md spinner caveat](../../../CLAUDE.md)). This is the `tool_use` half (→ `ToolStart`); the `tool_result` half (→ `ToolUpdate`) is the independent sibling ticket, neither blocking the other.

## Summary

One new file, `pkg/tuidriver/tool_use.go`: the exported type `ToolUse{ID, Name string; Input map[string]any}` and the function `ParseToolUse(snap []byte) *ToolUse`. It is the **second member of the `Parse<Tool>` family** after [`ParseAskUserQuestion`](109.md) — takes the bytes of one JSONL assistant envelope, walks `message.content[]` for the first `tool_use` block, and projects its `id` / `name` / `input` off `ContentBlock.Raw` into the typed value. Reuses [#60](60.md)'s `parseEntry` so envelope/message/content decoding stays single-sourced — `parseEntry` now has three callers (`tailJSONLLoop`, `ParseAskUserQuestion`, `ParseToolUse`). Pure function: no I/O, no goroutines, no shared state; safe for concurrent use and on a nil/zero-value `snap`.

It differs from `ParseAskUserQuestion` in exactly one way: **the match gate is `type == "tool_use"` alone — not name-gated, not payload-gated.** `ParseAskUserQuestion` matches only blocks named `AskUserQuestion` and returns `nil` when its `input.questions` is absent/empty; `ParseToolUse` matches *any* `tool_use` block and returns a **non-nil** `*ToolUse` even when `name`/`id`/`input` are missing or type-mismatched (those fall to `""`/`""`/`nil`, never panic — the `AssistantText`/`AssistantUsage` zero-value-on-mismatch posture). The presence of `type:"tool_use"` is the entire match signal; field absences are zero values, not no-match.

Signature is `snap []byte` (not per-entry `JSONLEntry` like `AssistantText`), the architect's delegated choice. Rationale: family consistency (the `Parse<Tool>` family is `[]byte`-native, the per-entry discriminators are a different family); the AC lists "malformed JSON" as a no-match case, which only a `[]byte`-arg function calling `parseEntry` itself can honour (a `JSONLEntry`-arg function never sees malformed JSON — `parseEntry` already dropped it upstream); and `parseEntry` reuse keeps decoding single-sourced. The bridge consumer holds `JSONLEntry` from `TailJSONL` and calls `ParseToolUse(e.RawLine)` ([#103](103.md)'s verbatim line bytes) — one `json.Unmarshal` per line at interactive-conversation rate, not a throughput hot path.

Fixture pair follows the post-[#81](81.md) parsed-shape model and the [#109](109.md) `ask-user-question-snapshot.{bin,json}` convention: `testdata/tool-use-snapshot.bin` is one raw assistant envelope carrying a `Bash` `tool_use` block (a non-`AskUserQuestion` tool, to prove name-agnostic projection); `testdata/tool-use-snapshot.json` is the human-readable parsed-shape sidecar (committed for review, not deep-equal'd). The `.bin` was **hand-crafted** from the documented wire shape ([jsonl-layout § Tool-use shapes](../architecture/jsonl-layout.md)) rather than live-captured — the architect blessed both, and the test's structural assertions (substring guards + field presence) don't depend on a real session's exact values. It is version-stamped `2.1.158` and uses obvious placeholder ids (`msg_01ToolUseBashExample…`, `toolu_01BashListTmpExample…`) so no future reader mistakes it for a real capture.

Pipeline ran clean: RED→GREEN tests, code-review PASS. Not `security-sensitive` — pure projection of a local claude-written JSONL file, no execution, never-panics; the network/trust boundary lives downstream in the bridge consumer (pyrycode#608), not in this extractor.

## Patterns established

- **A family member that deliberately diverges from its sibling must say so in its doc comment, or a future "consistency" pass will re-converge it.** `ParseToolUse` is intentionally *not* gated on any field's presence where its sibling `ParseAskUserQuestion` gates on `input.questions`. The risk is a future reader "fixing" the missing gate to match the sibling, silently breaking the `ToolStart`-from-any-tool contract. The mitigation is one sentence in the `ParseToolUse` doc comment: *"the presence of type:'tool_use' alone is the match signal, NOT any field's presence… do not 'fix' it into a gate."* When two functions in a family look almost identical but one omits a guard on purpose, the omission is invisible — name it at the divergence point. (Inverse of [#109](109.md)'s lesson, where the `len(items)==0` gate *was* the right thing for the name-gated parser.)
- **Hand-crafted fixtures are a sanctioned alternative to live capture when the test asserts structure, not values — but mark them as synthetic.** The `.bin` carries a `2.1.158` version stamp (so a future reader knows the wire era) and `…ExampleAAAAAA` placeholder ids (so nobody treats it as a recorded session). The substring guards (`"type":"tool_use"`, `"name":"Bash"`, `"id":`) and field-presence assertions hold regardless of whether the line was recorded or authored. Reuse posture: any `Parse<Tool>` fixture whose test is structural can be hand-crafted from the documented wire shape; stamp the version and use unmistakably-fake identifiers.
- **`parseEntry` is the single-sourced envelope decoder for the whole per-tool family.** Each new `Parse<Tool>` is another `parseEntry` caller, not a fresh `json.Unmarshal` of the envelope. Three callers now; the malformed-JSON / non-assistant / nil-message no-match gate is identical across all of them because it's literally `parseEntry`'s `ok=false` plus the `entry.Type != "assistant" || entry.Message == nil` check. Future per-tool extractors copy this skeleton.

## Lessons learned

- **The substring guard tightened from the spec's `"name":` to `"name":"Bash"` — a positive deviation worth keeping.** The spec sketched guarding the fixture on `"name":`; the developer guarded on `"name":"Bash"`. The tighter marker proves name-agnostic projection more concretely (a non-`AskUserQuestion` tool is what the `ToolStart` use case needs) and trips loudly if a future re-record swaps the tool. Same discipline as [#109](109.md)'s `multiSelect` guard — codify the load-bearing wire substrings in the fixture test so silent drift fails meaningfully.
- **The `input` field needs no re-decode — `Raw["input"]` is already `map[string]any`.** `parseEntry` decodes the content block's nested objects into `map[string]any`, so `tu.Input, _ = c.Raw["input"].(map[string]any)` is a single type assertion, not a second `json.Unmarshal`. This preserves the input "exactly as found on the wire" generically (the input shape varies per tool: `Bash`→`command`, `Read`→`file_path`) without a typed-per-tool union. The fixture's two-key input (`command` + `description`) round-trips intact, confirming the generic-map projection.
- **No new ADR, no new feature doc, no system-overview change.** Like [#109](109.md), this is a JSONL-side per-entry projection — it follows the already-decided `Parse<Tool>` convention (documented in [jsonl-layout § Tool-use shapes](../architecture/jsonl-layout.md)) and introduces no cross-cutting decision of ADR weight. The `Parse<Tool>` family lives in the architecture's JSONL-layout doc, not a per-helper feature page (consistent with `ParseAskUserQuestion`). No PTY signal changed, so `system-overview.md` is untouched.
