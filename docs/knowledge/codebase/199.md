# #199 — Spike: number-select modal commit semantics under two queued modals

[Issue](https://github.com/pyrycode/tui-driver/issues/199) · [Spec](../../specs/architecture/199-spike-queued-modal-commit-semantics.md) · [PR #201](https://github.com/pyrycode/tui-driver/pull/201) · Commits `b3f03ba` (harness) → `2631a3d` (msg_id fix) → `3a358ed` (untrack build artifact) · Size: S · **Not** security-sensitive (observation-only spike over already-shipped APIs; no new grant path — the keystroke-sequencing change and its security review land in the sibling fix [#200](https://github.com/pyrycode/tui-driver/issues/200)) · Split from [#165](https://github.com/pyrycode/tui-driver/issues/165)

## Summary

`Answer("1")` commits a permission modal by writing the two bytes `1\r` in one atomic PTY write (`keys.go:44-54`). The open safety question, split from #165 and blocking the fix #200: **when two permission modals queue (B behind A), does the trailing `\r` reach the freshly-surfaced B and auto-accept its highlighted default — a grant nobody issued?** The answer turns on one empirically-undetermined fact — if the *digit alone* commits A, the `\r` is a redundant, dangerous byte that can leak onto B (#200 must reorder/drop it); if claude requires *digit-then-`\r`*, `1\r` is atomic-and-safe (#200 collapses to a regression test). Spike #13 established `1\r` and that a bare `\r` commits the default, but [deliberately never drove two queued modals](13.md). This spike closes that gap.

It ships a new observation binary `cmd/spike-queued-modals/` — no new `pkg/tuidriver/` surface, a composition-and-observation harness over shipped primitives (`Spawn`, `TypePrompt`, `Answer`, `AnswerModal`, `DetectModalClass`, `ParseModalContent`, `TailJSONL`). One session, one probe: type a prompt engineered to induce two parallel tool calls (Bash + Read) in one assistant turn → wait for permission modal A → answer A via the exact sealed `Answer("1")` under test → observe B's fate (a distinct-signature permission modal surviving = B survived; a tool executing that the spike never approved = B's default was auto-consumed by the leaked `\r`) → feed the accumulated observation into a pure classifier that emits one of three findings.

This is a **live-claude observation spike**: the empirical answer only surfaces on the operator/CI `make e2e` path, never in the developer's claude-free `make check` gate (the reason it is its own ticket ahead of the fix). The developer ships the harness + the deterministic classifier (unit-tested under `make check`) + a README skeleton whose **Empirical log** carries an `Empirical result: TBD` placeholder. An operator runs `make e2e`, reads the `OBSERVED:` line, and transcribes the finding into the README — **that recorded finding is the sole input that scopes #200, and it is still TBD** (see Follow-ups).

## Patterns established

- **Split a stochastic live observation from its deterministic interpretation — belt-and-suspenders of different fabric.** The live measurement (did claude queue two modals? did B survive?) is inherently stochastic and can only run under `make e2e`; its *interpretation* is factored into a pure `classify(observation) finding` with a table test that runs claude-free under `make check`. This gives `make check` real teeth on the only logic that can run without claude, and structurally prevents a live run from smuggling a wrong conclusion past review. Reuse posture: any spike whose conclusion is an epistemic judgment over a noisy live signal should isolate that judgment in a pure, unit-tested function rather than inline it in the driver loop.
- **Asymmetric guard rail toward the safe direction.** The classifier only yields `safe-atomic-digit-cr` when a distinct modal B was *directly observed* surviving A's `1\r`. A single-modal run — which cannot distinguish "trailing `\r` is safe" from "the setup failed to queue a second modal" — can never be reported as safe; it is `inconclusive-no-queuing`. The dangerous direction keys off `toolsExecuted > modalsAnswered` (a tool ran that the spike never approved), which catches the auto-grant regardless of *which* option the leaked `\r` accepted. When a spike's false-negative and false-positive costs differ, bias the classifier so the cheap-but-wrong reading is unreachable.
- **Parallel-tool-use is a per-`msg_id` computation, never per-JSONL-entry.** claude serialises one assistant message as N JSONL lines — one content block per line — all sharing one `msg_id` ([jsonl-layout.md § "One Anthropic message ⇒ N JSONL lines"](../architecture/jsonl-layout.md)). Genuinely parallel tool calls therefore arrive as separate single-block entries, so counting `tool_use` blocks *within* an entry never reaches 2. `analyzeToolUse` sums `tool_use` blocks grouped by `msg_id` across retained assistant entries — the established cross-entry pattern (`spike-multi-turn`'s `extractByMsgID`) — and flags parallel once any single `msg_id` reaches ≥2. Any future consumer counting content blocks per assistant turn must group by `msg_id` first.
- **A diagnostic screen-diff may read the tool-influenceable `Label`; the production grant path may not.** To tell same-class modal B apart from A, `modalSignature` fingerprints `ParseModalContent`'s `Title` + option `Label`s (their Bash-vs-Read command/path text differs; the "Do you want to proceed?" `Prompt` is identical across both, so `Prompt` alone can't discriminate). Reading `Label` is safe here because the signature only routes a *screen comparison*, never a grant — unlike the production answer path, which #146/#147 pin to `ModalOption.Index` precisely because `Label` is prompt-/tool-influenceable. The Index-only rule is a property of the grant route, not of every read of a modal's labels.
- **Answer the modal-under-test through the raw sealed path, not `AnswerModal`, when a same-class successor is expected.** `AnswerModal`'s dismissal confirm reads `DetectModalClass`, which still reports `permission` when same-class B surfaces — so it returns a confounded "still present" error even though A committed ([answer.go / #147](147.md)). The spike therefore answers A with `Answer("1")` (the exact `1\r` under test) and does its own B-vs-A observation, then answers B via `AnswerModal` where no successor is expected and the class-level confirm is sound — exercising the production surface exactly where its check is valid.

## Lessons learned

- **A measurement gate can be silently *unsatisfiable* — the first code-review FAIL.** The initial `parallelToolUse` counted `tool_use` blocks within a single JSONL entry and only fired when that per-entry count reached ≥2. But per the msg_id-grouping rule above, that count *never* reaches 2 for genuinely parallel calls, so `parallelToolUse` was stuck `false` and `classify` was pinned at `inconclusive-no-queuing` regardless of what claude actually did — even in a true `safe` run. The spike could never report the behaviour it directly observes. The fix (`2631a3d`) replaced the per-entry counter with the msg_id-grouped `analyzeToolUse` and added `TestAnalyzeToolUse` with the exact regression row (two parallel calls as separate lines sharing one `msg_id` → `parallel=true`) — a case the old per-entry `TestClassify` structurally could not cover. Lesson: when a classifier has a precondition gate, unit-test that the gate can be *satisfied* by a realistic input, not only that it classifies correctly once satisfied — a gate that never fires makes every downstream branch dead code and the whole spike inert.
- **Compiled binaries land in the worktree — gitignore the spike name, don't commit it — the second code-review FAIL.** A 4.5 MB compiled `spike-queued-modals` Mach-O binary was tracked in git at the repo root (the `make`/`go build` output collides with the package directory name). Fixed (`3a358ed`) by adding `/spike-queued-modals` to `.gitignore` (matching the existing lines for every other spike) and `git rm --cached`-ing the artifact. Lesson: the `.gitignore` entry is part of "wire a new spike," not an afterthought — every `cmd/spike-*` needs its root-level `/spike-*` ignore line added in the same change as the `SPIKES` and `e2e-runner` wiring.
- **The `dangerous` verdict has a documented false-positive to cross-check before trusting.** `dangerous` keys off `toolsExecuted > modalsAnswered`, which a *third*, independently auto-approved tool in the same turn could inflate without any `\r` leak. The README's Empirical log calls this out: before scoping #200 off a `dangerous` finding, confirm `distinct_tools` matches the two tools the prompt requested and inspect the `modalB` snapshot — both raw fields ride the `OBSERVED:` line. The classifier stays simple; the caveat lives in the operator-facing log rather than in extra code.

## Follow-ups

- **The empirical finding is TBD.** No commit-semantics answer exists yet — the harness ships, but the live `make e2e` run that produces the `OBSERVED:` line has not been recorded. An operator must run `make e2e` (post-merge), read the finding, and transcribe it into `cmd/spike-queued-modals/README.md`'s **Empirical log**. **#200 is blocked on that recorded finding** and must not be scoped until it lands.
- **Does the default prompt reliably induce parallel (not sequential) tool use on the pinned claude version?** Unknown until the first `make e2e`. If claude issues the two calls sequentially, `parallelToolUse` is false and the run is honestly `inconclusive` — prompt-tuning is then a follow-up, not a faked result. The classifier already distinguishes the two, so this is not a blocker.
- **e2e Check timeout (120 s) is an estimate** — ~3–6× the expected ~20–40 s wall (two approvals + two fast tool executions + settle windows). Tune from the first live run's observed wall time (same posture as spike-cancel #69 / spike-multi-turn #111 timeout tuning).
- **Two NITs waived at PASS**, neither blocking: the documented `dangerous` false-positive (handled in the README, above), and a `sync.WaitGroup` without a `Wait()` that matches the established spike-ask-user template.
