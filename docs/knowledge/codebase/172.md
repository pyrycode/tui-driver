# #172 — Screen short prompts for any C0 control byte, not just newline

[Issue](https://github.com/pyrycode/tui-driver/issues/172) · [Spec](../../specs/architecture/172-screen-short-prompts-for-control-bytes.md) · [PR #216](https://github.com/pyrycode/tui-driver/pull/216) · Commit `51ca7eb` (spec `7bc811c`) · Touches [`deliver.go`](../../../pkg/tuidriver/deliver.go) + [`deliver_test.go`](../../../pkg/tuidriver/deliver_test.go) · Origin: Cross-Repo Code Review 2026-07-03 · `security-sensitive`, security-review verdict **PASS**

**XS security-hardening fix at the prompt-delivery seam.** One production edit site (a pure predicate), a new unexported helper, four table-test rows. No exported symbol, signature, config knob, or write-seam changed.

## Summary

`shouldTypePrompt` (`deliver.go`) selects the raw byte-by-byte `TypePrompt` seam for prompts that are `<= typePromptMaxLen` (256) **and** contain no `\n`. `TypePrompt` writes every prompt byte to the PTY **verbatim**, then a separate `\r` commit. The `\n` exclusion existed only because a multi-line prompt must paste — but `\n` was the *only* control byte screened, so a short single-line prompt carrying `\r` (0x0D, read as Enter → commits the turn early) or ESC (0x1B, steers claude's TUI — interrupt, dismiss/navigate a modal) reached the PTY unscreened through the seam the library advertises as "safe." The consumer's prompt content is an explicit trust boundary (pyrycode spec #749, `mapPromptContent` → `WriteUserTurn`, opaque downstream, never re-parsed), so control-byte screening belongs here at the delivery seam.

The fix generalises the newline check to the **whole C0 range**. A new pure helper `hasControlByte(text string) bool` reports whether `text` contains any byte `< 0x20` (a plain byte-index loop); `shouldTypePrompt` becomes `len(text) <= typePromptMaxLen && !hasControlByte(text)` and the `strings.Contains(text, "\n")` clause (plus the now-unused `strings` import) is deleted. Disqualified prompts need **no new routing code** — `deliverPrompt`'s existing `else` branch already selects `WritePrompt` (bracketed paste) whenever `shouldTypePrompt` returns `false`, so flipping the predicate is the entire behavioural change. The paste path embeds the body verbatim inside `\x1b[200~ … \x1b[201~`, so claude treats an embedded `\r`/ESC/`\t` as literal pasted text rather than a commit or a TUI command (already backed by `TestBracketedPasteWrapping`'s "embedded CR survives unchanged inside body" case, `session_test.go`). The route-to-paste choice and its rationale are recorded in the `shouldTypePrompt` doc comment (satisfies the review's "decision documented in a code comment" requirement).

## Why the whole C0 range (not just `\r` + ESC)

- **Zero marginal cost.** Screening `< 0x20` is one comparison — the same cost as screening two named bytes — and **subsumes** the existing `\n` (0x0A) check. Belt-and-suspenders against an undiscovered steering byte. This is the "screen the whole range for safety, set documented" branch the AC explicitly permits, under Evidence-Based Fix Selection (only `\r`/ESC are *demonstrated* turn-steerers, but widening costs nothing).
- **No false positives on real content.** Space is 0x20, so every printable ASCII byte is `>= 0x20`; no byte of a multi-byte UTF-8 rune is ever `< 0x80` (lead `>= 0xC0`, continuation `>= 0x80`), so a byte scan for `< 0x20` never trips on Unicode — rune- and byte-iteration are equivalent here. The only borderline-legitimate C0 byte is `\t`; a tab in a short single-line prompt is unusual and routing it to paste (which preserves it verbatim) is lossless.
- **DEL (0x7F) deliberately excluded** — keeps the predicate a single `< 0x20` comparison, and DEL is neither C0 nor a demonstrated steering byte. Widening to include it later is a one-token change.

## Why route-to-paste, not reject/sanitise

The disqualified prompt takes the **existing** non-typed path — one strategy, no new code. Rejecting would drop turns whose content legitimately contains a control byte; sanitising would silently mutate user content. Both are heavier and change observable behaviour. More importantly, either would be **asymmetric** — hardening only the short-prompt path while the long/multi-line path (a *larger*, more attacker-influenceable payload) keeps pasting the same bytes. Uniform route-to-paste is the coherent, minimal choice: after this change a short control-byte-bearing prompt behaves identically to a long or multi-line one — one code path, consistent, lossless, and it never drops a legitimate turn.

## Patterns established

- **The newline check was always a special case of "a control byte disqualifies the typed path."** This ticket names the general rule and screens the whole C0 range against it. Any future predicate that gates the raw `TypePrompt` seam should reason in terms of that rule, not re-enumerate individual bytes.
- **Tighten the pure predicate; let the existing else-branch route.** The entire behavioural change is a flip inside the pure `shouldTypePrompt` predicate — `deliverPrompt`'s method-selection `if/else` already routes a `false` result to `WritePrompt`, so no new routing, write-seam, or error path was needed. When a delivery-path change can be expressed as "disqualify from the typed path," prefer flipping the predicate over adding a guard on the write seam.
- **Byte scan, not rune scan, for C0 classification.** `hasControlByte` iterates bytes because any byte `< 0x20` is always a standalone single-byte rune in UTF-8 — the byte-oriented idiom matches `TypePrompt`'s own style and is provably equivalent to `strings.IndexFunc(text, func(r rune) bool { return r < 0x20 })`. The helper is total over the empty string (returns `false`).

## Lessons learned

- **Route-to-paste is a strict improvement for control bytes, but not a *complete* close for ESC — and that's acceptable here.** The paste path neutralises a bare `\r`/`\t` as literal text (unit-tested), but a body containing the exact paste-*close* sequence `\x1b[201~` can break out of the bracketed paste early, after which trailing bytes are interpreted by the TUI (see memory `paste-path-neutralises-r-not-esc`). This means routing an ESC-bearing short prompt to paste brings it to **parity** with long prompts (from "every byte reaches the PTY verbatim" to "only the exact `\x1b[201~` sequence can escape") rather than fully closing the ESC vector. That residual is **pre-existing for every long/multi-line prompt** delivered via `WritePrompt` today — this ticket neither introduces nor widens it. Fixing it means hardening `bracketedPaste` uniformly for *all* prompt lengths, which would be a separate follow-up; forcing it into this XS ticket would have produced an *asymmetric* fix (short prompts hardened, the larger long-prompt payload left open) — incoherent, and the security review classified it OUT OF SCOPE for exactly that reason.
- **The claimed trust boundary is single and the change tightens it.** `opts.Prompt` is untrusted attacker-influenceable data and `shouldTypePrompt` is the single point deciding how those bytes reach the PTY. Before the change the raw `TypePrompt` seam passed arbitrary control bytes through verbatim; after it, only control-byte-free prompts take that seam. No new error/log surface — route-to-paste refuses nothing, so no prompt content is ever echoed into an error message.

## Deferred / follow-ups

- **Paste-close-injection residual (recommend PO file it).** Harden `bracketedPaste` (`session.go`) against a body containing the literal `\x1b[201~`, uniformly for all prompt lengths, so a paste body can no longer break out of the bracketed paste early. Pre-existing, not introduced by #172; a natural next item from the same Cross-Repo Code Review 2026-07-03. Do **not** fold it into a short-prompt-only fix (that would be the asymmetric shape above).
