# #296 — slash-picker block co-signal rejects single-row bottom-region forgeries

## Summary

`isSlashPickerWithGrid` (`pkg/tuidriver/picker.go`) required only a *single* bottom-region `/`-row (`gridHasPickerRow`, ≥1) plus picker-highlight chrome — #237's region scope killed transcript-body forgeries, but a residual class survived **inside** the bottom `pickerRegionRows` window: a wrapped shell-output continuation beginning `/Users`, `/Workspace`, `/dev`, `/gradlew`, or claude's own footer tip wrapping to `/btw …`. corpus-replay (#227) measured `slash-picker` firing in 4/4 production-`ok` runs with a flapping signature — the tool's own spurious-modal marker. Since the consumer (`pyry agent-run`) is headless, every one of those fires was a false positive that suppressed turn-end.

The fix binds the row half to picker *shape*, not just location: a new `pickerRowBlockMin = 2` constant and `gridHasPickerRowBlock` require a **block** of ≥2 bottom-region `/`-rows (counted non-contiguously via new `gridPickerRowCount`, reusing the existing `pickerRowStartRe` — no new regex). `gridHasPickerRow` is retained, re-expressed as `gridPickerRowCount(g) >= 1`, purely as the weak signal non-vacuity tests assert against. `isSlashPickerWithGrid`'s signature is unchanged, so `isSlashPicker` and `detectModalClassWithGrid` fan out zero callers. `snapHasPickerHighlight` (chrome) and `findPickerRows`/`ParsePicker` are untouched.

This consciously **drops single-match filtered-picker detection**: one command row is structurally identical to a single-row forgery, so no threshold separates them. Safe because headless agent runs never surface a real picker at all — every slash-picker fire in that context was already a false positive.

## Patterns established

- Continues the #242/#244 "shape-over-literal co-signal" posture, applied here to a detector's *location* signal rather than its *chrome* signal: #244 found `snapHasPickerHighlight` too weak because the highlight shade is general-purpose (paths/links), and moved `mcp`/`permissions-config` to row-opening-color chrome. #296 shows that move doesn't generalize to slash-picker's forgery: a wrapped path *legitimately* opens its line in the highlight shade, so `snapHasRowOpeningHighlight` would not have rejected it. The real discriminator was the **row-count half**, not chrome — worth checking which half of a two-signal AND is actually weak before reaching for the sibling's fix shape.
- Threshold-based structural gates: pick the number that directly encodes the real/forged distinction (2 = "list vs single line"), not a padded margin — 3 would additionally drop genuine two-match pickers to defend an unobserved coincidence (evidence-based fix selection, no wider than the observed failure).
- Non-contiguous counting over the region window survives real-picker rows interleaving with wrapped description continuations (`picker-snapshot.bin` itself has one); a contiguity requirement would have been fragile against the very fixture proving the fix works.

## Lessons learned

- Six existing single-`/`-row synthetic positives (in `anchor_forgery_test.go`, `picker_test.go`, `modal_test.go`) flip verdict under a ≥2 gate — the architecture doc's "positive-control tension" flagged this at design time from a fixture read, not discovered mid-implementation. Two of the `modal_test.go` cases were repurposed as the explicit pin of the conscious drop (renamed, `want` flipped to `ModalClassUnknown`) rather than deleted, keeping the behavior change visible in the test file itself.
- Measuring the real fixtures' row counts (`picker-snapshot.bin` = 5, `picker-truecolor-snapshot.bin` = 6, one wrapped-description row breaking picker-snapshot's block) before picking the threshold is what let 2-vs-3 get resolved by evidence instead of debate.
