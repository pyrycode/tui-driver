# #48 — e2e harness: `--model` / `--effort` override env-var seam

[Issue](https://github.com/pyrycode/tui-driver/issues/48) · [PR #55](https://github.com/pyrycode/tui-driver/pull/55) · [Spec](../../specs/architecture/48-e2e-model-effort-override.md) · Feature doc: [e2e harness](../features/e2e-harness.md)

## Summary

Extends `EnsureClaudeEnv` (`pkg/tuidriver/pty.go`) with two new exported env-var constants — `ClaudeModelEnv` (`TUIDRIVER_CLAUDE_MODEL`) and `ClaudeEffortEnv` (`TUIDRIVER_CLAUDE_EFFORT`) — that mirror the existing `StrictMcpConfigEnv` opt-in. When set to a non-empty value the library appends `--model <value>` and/or `--effort <value>` to `cmd.Args` (idempotent — caller-supplied flag wins); unset / empty is a no-op (preserves the operator's interactive Claude default, the Max-subscription path). The `Makefile`'s `e2e:` recipe surfaces them as `make e2e MODEL=haiku EFFORT=low`, inlined per-recipe via `$(if $(VAR),…)` so `build-bin`'s `go build` never inherits the override. The runner (`cmd/e2e-runner/main.go`) is unchanged — `cmd.Env = append(os.Environ(), …)` already carries Make-exported vars through to every spike+probe child, so propagation is shell → Make → runner → spike with zero per-binary plumbing. `claude-version.lock` gains `flag=--model` and `flag=--effort` so future claude drift on either flag short-circuits the harness before spikes run. Lands the mechanism CI consumes via #32 to cap metered-API spend ~18–90× below the default Opus + high pairing.

## Patterns established

- **Env-var seam through `EnsureClaudeEnv` is the canonical place for claude-side argv mutations.** The strict-mcp opt-in set this contract; this ticket cemented it as a precedent rather than a one-off. Decision rule: any future "harness-wide claude flag" that must propagate to every spike+probe rides the seam too. Per-spike `flag.Parse` plumbing would touch ~10 files and defeat the "library owns claude-side argv" invariant; the seam is ~30 LOC across one production .go file regardless of how many spikes exist. New env vars go alongside `StrictMcpConfigEnv` / `ClaudeModelEnv` / `ClaudeEffortEnv` in `pkg/tuidriver/pty.go`, exported (consumer-discoverable) with a doc comment that names the contract (non-empty vs `"1"` semantics, idempotence, default behaviour when unset).

- **Copy-and-adapt is clearer than abstraction at N=3.** Each env-var block in `EnsureClaudeEnv` is a ~10-line copy of the previous one with the env var, flag name, and value-vs-bool check swapped. The spec explicitly declined to introduce a helper. Rationale: the differences between blocks (empty-string vs `== "1"`, append one arg vs two) are exactly the kind of subtle wire-shape distinctions a helper would obscure. Revisit if N grows to 5 or 6; for now, the 1:1 visual parallel is the documentation.

- **Makefile env vars MUST be inline-scoped on the recipe, never `export`-ed.** `MODEL=` / `EFFORT=` are declared at file scope with `?=` but applied to the `e2e:` recipe via `$(if $(VAR),VAR=$(VAR))` inline prefixes. The `?=` lets `make e2e MODEL=haiku` override the default empty value cleanly; the inline-`$(if …)` ensures empty values omit the env-var assignment entirely (rather than setting an empty value that downstream code must defensively check) AND scopes the override to the single recipe that needs it. `export` in a Makefile leaks to every recipe — including `build-bin`'s `go build` — which is wrong even though Go ignores these specific vars; the precedent matters for the next override that DOES affect builds.

- **`claude-version.lock` pins flag names, not value sets.** `flag=--model` and `flag=--effort` pin the *existence* of the flags as a load-bearing assumption of the harness. Pinning specific values (`value=haiku`, `value=low`) was explicitly declined: the value set (`low/medium/high/xhigh/max` today) is plausibly stable but not load-bearing, and committing to lock-file edits whenever Anthropic adds a new effort level adds toil without proportionate signal. Revisit only if a value-set drift bites in practice. The same principle: pin the *contract surface the library depends on*, not every detail the library could in theory observe.

- **9-test mirror per new env-var block.** Tests at `pkg/tuidriver/pty_test.go` follow the 4-scenario template per env var: (1) unset/empty leaves args alone, (2) set appends exactly one flag+value, (3) caller-pre-seeded flag wins (no double-append, original value preserved), (4) co-existence with strict-mcp (no inter-block interaction). Add a single cross-pair test asserting all env vars set together produce exactly one append each (no duplication, no cross-talk). Total: 4 + 4 + 1 = 9 tests per pair of new env-var blocks. Reuse the existing `t.Setenv` + `contains(args, …)` helper pattern verbatim; no new test infrastructure needed.

## Lessons learned

- **The e2e harness gate's red verdict on this PR was infrastructural, not a regression.** The harness short-circuited on `claude-version-lock` because the operator's local `claude` is 2.1.145 while `claude-version.lock` pins 2.1.144 (the deliberate revert in `0a33c82` per #47). Identical failure shape on `main`'s HEAD. None of this PR's spike-touching code paths exercised the harness end-to-end during the gate. The pattern was the same one #47 documented: version-lock edits are their own coordinated ticket (fixture re-record sweep + lock bump in the same change-set); they MUST NOT be bumped as a side-effect of unrelated PRs. Re-affirmed on this branch — the developer agent correctly declined the reviewer's "bump the lock" suggestion. First CI run on `MODEL=haiku EFFORT=low` (whenever #32 lands and the operator separately resolves the lock drift) will be the actual end-to-end verification of this ticket's mechanism.

- **The idempotence scan only detects the space-separated flag form.** Code review surfaced this nit: `for _, a := range cmd.Args { if a == claudeModelFlag … }` matches `--model` followed by `<value>` as two argv entries, but a hypothetical caller that pre-seeded `cmd.Args` with the combined form `--model=sonnet` would slip past the scan and have `--model haiku` appended after it, producing two `--model` occurrences on claude's command line. No caller in this repo today uses the combined form, and the strict-mcp block has the same theoretical shape — so consistency wins for now. Revisit if any future caller starts using `=`-form claude flags; the fix is a `strings.HasPrefix(a, claudeModelFlag+"=") || a == claudeModelFlag` check. Flagged here so future-us doesn't re-discover.

- **`os.Environ()` already carries Make-exported vars; no runner-side plumbing needed.** The spec deliberately left `cmd/e2e-runner/main.go` untouched. `cmd.Env = append(os.Environ(), "TUIDRIVER_STRICT_MCP_CONFIG=1")` (line 497) already inherits whatever Make exports onto its own process, so any `TUIDRIVER_CLAUDE_MODEL=…` set on the `make e2e` invocation flows transparently to every spike+probe child without an explicit pass-through. Adding a runner-side `os.Getenv` + flag would be redundant surface area and risk drift between "what Make sets" and "what the runner injects." Pattern: when extending an existing `os.Environ()`-based env-seed, additional shell-level env vars hitch a ride for free — don't add code to "forward" them.

- **`make e2e` does NOT auto-export `MODEL`/`EFFORT` to `build-bin`.** Inline `$(if $(MODEL),TUIDRIVER_CLAUDE_MODEL=$(MODEL))` is per-recipe scoping. If you ever switch to `export MODEL` or `e2e: TUIDRIVER_CLAUDE_MODEL=$(MODEL)` (Make target-specific variables), the override would also be in scope when `build-bin`'s prerequisite recipe runs `go build`. Go ignores these specific env vars so the leak is harmless today, but the inline scoping is the design choice that documents intent at the recipe boundary. Don't refactor it.
