# #35 — e2e: snapshot-drift check vs `pkg/tuidriver/testdata/*-snapshot.bin`

[Issue](https://github.com/pyrycode/tui-driver/issues/35) · [Spec](../../specs/architecture/35-snapshot-drift.md) · Code: `cmd/e2e-snapshot-check/`, `cmd/e2e-runner/`, `Makefile`

## Summary

Adds the third e2e check kind — `snapshot` — to the harness landed in [#34](34.md). The new `cmd/e2e-snapshot-check/main.go` (~130 LOC) is a thin orchestrator that re-derives each of `pkg/tuidriver/testdata/{picker,mcp,agents}-snapshot.bin` by invoking the existing `spike-multiselect` binary three times (one per fixture) via its `-trigger` / `-settle` flag surface, scrapes the `/tmp/spike-multiselect-bytes-<ns>.bin` dump path from spike-multiselect's stderr, byte-compares the dump to the committed fixture with `bytes.Equal`, and emits one `SNAPSHOT <name> match|diff` line per fixture to stdout. Exits `0` iff every fixture matched; `1` on any diff or capture failure. The binary is **read-only** by construction — it calls `os.ReadFile` on the committed fixtures and never writes them. Re-recording stays a manual maintainer workflow via spike-multiselect directly.

Three changes to `cmd/e2e-runner/main.go`:

- New `Check.OnComplete` callback field — fires regardless of status, after `OnFailure` if both are populated. The probe's `OnFailure` stays fail-only (its `recording_dir` must not leak into pass entries per [#34](34.md)'s path-scrubbing rule); the new field is the additive extension that lets snapshot-drift emit its per-fixture `snapshots[]` list on pass AND fail (AC bullet 3).
- New `snapshot-drift` entry in `buildChecks()` with `Binary: "e2e-snapshot-check"`, `Timeout: 180s`, no `SuccessMarker` (exit code is authoritative, same shape as the probe), and `OnComplete: parseSnapshotResults`.
- New `parseSnapshotResults` callback — one regex (`^SNAPSHOT (picker|mcp|agents) (match|diff)$`) over buffered stdout produces the `snapshots: [{file, result}, ...]` slice. Returns nil when the check binary crashed before printing any line, so the report entry omits the field rather than embedding an empty list.

`Makefile` gets one new variable (`CHECKERS := e2e-snapshot-check`) appended to `ALL_BINS`. The existing pattern rule `$(BIN_DIR)/%: ; go build -o $@ ./cmd/$*` handles the new binary uniformly — no rule changes.

`cmd/e2e-runner/main_test.go` is new — five table-driven cases pin the `parseSnapshotResults` wire format (all-match, mixed match+diff, empty stdout, noisy stdout with interspersed SNAPSHOT lines, partial output from a timeout mid-run).

No deviations from the spec. Zero library changes (`pkg/tuidriver` untouched). No new exported types. The runner still does not import `pkg/tuidriver`.

## Patterns established

- **Additive `OnComplete` over reshaping `OnFailure`.** When the existing fail-only callback needed a pass-too sibling, the right move was adding a second optional field — not converting the existing one. The probe's `recording_dir` semantics (path appears only on fail per #34's path-scrubbing rule) depend on `OnFailure` staying fail-gated; an additive extension preserves that invariant and gives the new check what it needs in ~10 LOC inside `runCheck`. Future cross-status post-processing should reach for `OnComplete`; future fail-only post-processing keeps using `OnFailure`. Precedence is unambiguous (`OnFailure` first, then `OnComplete`) even though no current check populates both.
- **Stdout-line protocol over JSON between check binary and runner.** `e2e-snapshot-check` emits one `SNAPSHOT <name> match|diff` line per fixture; the runner parses with one regex. Cheaper than a JSON envelope, robust to log noise (the regex anchors to `^...$`), and parseable by humans inspecting raw stdout. Same shape as the probe's `outDir=` line and the spike `SUCCESS:` / `OBSERVED:` markers — the runner stays a pattern matcher over subprocess stdout/stderr, not a structured-IPC consumer. Future check kinds should follow this convention.
- **Compose existing capture binaries rather than duplicate PTY plumbing.** spike-multiselect already does the exact capture work (idle → trust-folder → trigger → settle → snapshot → dump file); the snapshot check is a 130-line orchestrator that shells out to it three times with different flags. Zero spike-multiselect changes. The general rule for new e2e checks: if an existing spike or probe already performs the capture/observation step, wrap it via `exec.CommandContext` rather than re-implementing PTY/claude code paths in the new check binary.
- **`io.MultiWriter(&buf, os.Stderr)` for child stderr.** The check binary mirrors spike-multiselect's stderr to both its own buffer (for log-line scraping) and the host stderr (so operators see capture progress live). Same idiom the runner uses for spike stderr; reuse it whenever an orchestrator binary needs to both observe and surface a child's stderr.
- **`status="snapshot"` `Kind` is informational, exactly like `spike`/`probe`.** The new kind doesn't get its own `runCheck` branch — every check kind still goes through the same body. `Kind` is documentation, not behaviour switching. This is the third confirmation of [#34](34.md)'s leaf-shape pattern: a fourth check kind would slot in identically (one struct entry, one `Kind` string for documentation).
- **180s timeout for the snapshot-drift check** picked as `3 × claude-spawn (~10–20s) + /mcp settle (5s) + margin`. Per-fixture wall budget inside the check is 60s (`-spike-timeout`), so individual hangs surface inside the aggregate budget. Override pattern is the same as every other check: `-timeout snapshot-drift=DUR`, auto-registered via `tos.known` populated from `buildChecks()`.

## Lessons learned

- **`spike-multiselect`'s stderr log says `picker-snapshot path=` regardless of trigger.** Spec called this out at L4 of the design but it's worth re-stating: the log-line label is hardcoded `picker-snapshot` in `cmd/spike-multiselect/main.go:235`, so a single regex `picker-snapshot path=(\S+)` works for the picker, mcp, AND agents triggers. Counterintuitive but stable; the scraping code lives in one place. If a future spike grows fixture-type-specific labels, the check binary needs per-fixture regexes.
- **First-run mcp drift was the predicted outcome and the maintainer pre-decided to absorb it.** The spec's Open Question 1 flagged that `mcp-snapshot.bin` was captured pre-#34 without `--strict-mcp-config`, so the very first `make e2e` run with this check enabled would diff the mcp fixture. That's not a check bug; it's the check working. Re-recording with `TUIDRIVER_STRICT_MCP_CONFIG=1 ./bin/spike-multiselect -trust-folder=accept -trigger="$(printf '/mcp\r')" -settle=5s` and `cp /tmp/spike-multiselect-bytes-<latest>.bin pkg/tuidriver/testdata/mcp-snapshot.bin` is a separate maintainer step; explicitly out-of-scope for the ticket. Future "harness now sees a new env state" deltas should follow the same shape: ship the check, accept the first-run drift, re-record as a follow-up commit.
- **`OnComplete` ordering: `OnFailure` first, then `OnComplete`.** The map-merge in `runCheck` lets `OnComplete` keys overwrite `OnFailure` keys — won't happen in practice (no check populates the same key from both callbacks) but the precedence is part of the contract. Stick with `OnFailure`-first if a future check needs both callbacks; flipping the order would surprise readers and the probe's `recording_dir` would become overridable by a later `OnComplete` if anyone ever added one.
- **Treat capture failures as a `diff` for that fixture, not a hard crash.** When spike-multiselect exits non-zero, the dump file is missing, or the stderr log lacks the expected line, the check emits `SNAPSHOT <name> diff` + a `drift in <path>: <err>` stderr line and continues to the next fixture. The aggregate exit code summarises. This keeps the report's `snapshots[]` always 3-entries-long on the green path and degrades gracefully on partial failures — the operator can see exactly which fixtures got captured and which didn't. The temptation was to `log.Fatal` on capture failures; the implemented behaviour is strictly more useful in CI.
- **Unit test the regex callback, not the orchestrator binary.** `parseSnapshotResults` is ~12 lines and pure; 5 table-driven cases pin every wire-format edge (all-match, mixed, empty, noisy, partial). The check binary itself stays an integration shim — its behaviour is covered by the `make e2e` integration test and the forced-failure smoke test (corrupt a fixture, re-run, verify `status: "fail"` and the right `snapshots[]` entries). Same testing shape every future check kind should adopt: pure parsers get unit tests, orchestrators get integration coverage.
