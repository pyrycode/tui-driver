# #41 — docs: `ANTHROPIC_API_KEY` rotation + `--strict-mcp-config` rationale

[Issue](https://github.com/pyrycode/tui-driver/issues/41) · [Spec](../../specs/architecture/41-e2e-ci-doc-rotation-and-strict-mcp-rationale.md) · Doc: `docs/knowledge/features/e2e-harness.md`

## Summary

Documentation-only edit to `docs/knowledge/features/e2e-harness.md` (the only file touched). Two narrowly-scoped operational additions land together because they share the same audience (a maintainer with the workflow file open and a "what do I do now?" question) and the same reference target (`.github/workflows/e2e.yml`):

- **§ "Authentication" rewrite.** The pre-#41 paragraph deferred rotation to "ticket #41". Replaced that self-referential sentence with an owning-account pointer (placeholder — see Lessons learned) and two inline numbered procedures: routine rotation (validate the new key on a green run *before* revoking the old) and in-flight revocation (revoke first to stop the bleeding, then cancel the run, then rotate). The two procedures invert which step comes first because the failure mode is different: routine rotation optimises for not stranding a half-rotated secret; in-flight revocation optimises for stopping ongoing credit burn even if it costs one cancelled run.
- **§ "Headless / CI plumbing" addition.** New paragraph explaining *why* the e2e harness uses `--strict-mcp-config` (operator-machine determinism — without it, host-level MCP config bleeds into `make e2e` and produces flaky first-prompt timing) and explicitly reconciling that against the May 18 walk-back (which targeted pyry acp where MCP is user-facing; the e2e/CI context has no user-facing MCP feature, so the harness using the flag for scoped internal determinism is consistent with the walk-back, not a contradiction).

Both additions cross-reference `.github/workflows/e2e.yml` so a reader landing on the doc can navigate to the actual job. No behaviour change — the workflow, the runner, and `EnsureClaudeEnv` are untouched.

The redundancy paragraph at § "CI integration" ("**`--strict-mcp-config` is NOT set at the CI layer.**") was deliberately left intact. It explains *where* the flag is not set; the new paragraph explains *why* the flag is used at all. Two complementary statements, not a duplication.

## Patterns established

- **Reconcile-against-prior-decision paragraphs.** When in-repo documentation makes a choice that *looks* inconsistent with a recent decision recorded elsewhere (in this case the May 18 walk-back), the doc must surface and refute the contradiction inline, not assume the reader will reconstruct the reconciliation from project history. Format: state the choice, state the prior decision, state why the scope differs. Skipping the reconciliation makes the doc read as self-contradictory next to other guidance and erodes trust. Reuse this shape any time a feature doc adopts a posture that a casual reader might flag as out of step with a documented anti-pattern.
- **Pair routine + emergency procedures with inverted "what to do first" ordering.** Both are listed under one bold-lead with two sub-leads (`*Routine rotation*` / `*If a key is leaked while a workflow run is in flight*`) inside a single Authentication block. The two procedures share four of the same atomic steps (log in, generate key, update secret, validate) but order them differently because their failure modes diverge — routine optimises for "never break a green pipeline", emergency optimises for "stop the bleeding". Documenting both side-by-side under one heading makes the ordering contrast load-bearing rather than incidental. Reuse for any rotation, deploy-key, webhook-secret, or signing-key procedure.
- **Cross-reference the consumer file from operational docs, not just the producer file.** The new content references `.github/workflows/e2e.yml` from inside `e2e-harness.md` even though e2e-harness.md is the more general doc. A reader who lands on the feature doc with a workflow question should be one click from the actual YAML; demanding they grep is friction without benefit.

## Lessons learned

- **Placeholders can ship if the doc convention surfaces them clearly.** The owning Anthropic Console account name was unknown to the architect AND the developer (it's a fact in Juhana's head, not in the repo). The spec explicitly opted for `<the maintainer's Anthropic Console account — Juhana to fill in before merge or in a follow-up doc PR>` rather than letting the developer guess or omit the sentence. This is the right default for any doc edit that needs a real-world fact only the maintainer holds: write the sentence around the placeholder so a follow-up PR is a one-token edit, not a structural rewrite. The placeholder is visible to any human grepping for `<` or `Juhana to fill`. Future doc tickets with similar "I don't know this fact" gaps should reuse this shape rather than blocking on a clarifying question.
- **§ "Authentication" stayed a bold-lead paragraph rather than getting promoted to `###`.** All other paragraphs under § "CI integration" (Cost controls, Cache shape, Artifacts, Exit code, Concurrency) are bold-lead-with-content. Promoting just Authentication to a `###` subsection mid-`##` would visually mis-rank the surrounding paragraphs and create the impression that Authentication is structurally more important than the others. The spec called this constraint out explicitly; it's worth surfacing because the temptation to "just add a heading" when a paragraph grows by 15 lines is real, and the symmetry of surrounding paragraphs is a real signal that should override the impulse.
- **The walk-back reconciliation paragraph is the canonical record.** The May 18 walk-back lives in the vault session log and (downstream) in `🔄 Areas/Assistant Docs/instruction-design.md`. Neither is in the repo. The new paragraph in `e2e-harness.md` is now the only in-repo record of why CI uses `--strict-mcp-config` while the library walked back recommending it as a user-facing default. If the walk-back posture ever changes, this paragraph is what needs editing — there is no second copy.
- **Doc-only tickets benefit from explicit "what NOT to touch" lists in the spec.** The architect's "What this spec deliberately does NOT touch" section called out the workflow file, the runner, `EnsureClaudeEnv`, the existing redundancy paragraph, and every other subsection by name. The developer made zero unintended edits as a result. Future doc tickets that extend an existing doc should mirror this — the negative list is cheap to write and prevents scope creep into adjacent sections that "feel related" but aren't in the ticket.
