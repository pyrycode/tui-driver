# #57 — `EncodeCwd`: canonicalise via realpath before encoding

[Issue](https://github.com/pyrycode/tui-driver/issues/57) · [Spec](../../specs/architecture/57-encode-cwd-canonicalise.md) · [PR #63](https://github.com/pyrycode/tui-driver/pull/63)

## Summary

`tuidriver.EncodeCwd` was a pure byte-transform that honoured the casing and symlink shape of the input. When a process started under a non-canonical path (default case-insensitive APFS reached as `WorkSpace` vs the on-disk `Workspace`, or via a symlink such as `/tmp` → `/private/tmp`), the encoded output did not match the directory `claude` writes to under `~/.claude/projects/`, and every `--session-id`-pinning spike's deterministic JSONL path pointed nowhere — symptom: the 10 s `os.Stat` poll tripping with `session JSONL did not appear`. Closed at source: `EncodeCwd` now resolves its input to the on-disk canonical form before applying the unchanged byte transform. The exported signature stays `func(string) string` — every canonicalisation failure (non-existent path, permission denied, fcntl error) falls back to encoding the input as-passed, so test contexts that pass logical paths keep getting a usable result. Canonicalisation is split by build tag: `cwd_darwin.go` uses `os.Open` + `fcntl(F_GETPATH)` via stdlib `syscall` (the kernel-blessed mechanism, what `os.Getwd` uses internally, no global-state mutation); `cwd_other.go` uses `filepath.EvalSymlinks` (sufficient on case-sensitive Linux defaults — a differently-cased lookup returns `ENOENT` and the fallback fires vacuously). No new module dependencies. No consumer-side edits — every call site (`cmd/spike-*/main.go`, `cmd/probe-first-prompt-hang/main.go`) continues to work unchanged because the contract change is behaviour-compatible at the call site.

## Patterns established

- **Platform-specific filesystem semantics belong behind a build-tag-split internal helper, not behind a runtime `runtime.GOOS` switch.** `pkg/tuidriver/cwd_darwin.go` (`//go:build darwin`) and `pkg/tuidriver/cwd_other.go` (`//go:build !darwin`) both expose the same unexported `canonicalisePath(string) (string, bool)` signature; the public `EncodeCwd` in `cwd.go` is platform-agnostic and calls the helper without knowing which file it resolves to. Rationale: each platform variant compiles with only the imports and constants it needs (`syscall.SYS_FCNTL` / `syscall.F_GETPATH` / `unsafe.Pointer` on darwin; `path/filepath` on others), there is no dead branch at runtime, and a future `cwd_windows.go` using `GetFinalPathNameByHandleW` would slot in without touching the call sites. Reuse this shape for any future tui-driver feature whose correctness depends on platform-specific kernel APIs.
- **`F_GETPATH` via stdlib `syscall` over `golang.org/x/sys/unix` when the goal is a single, ABI-stable constant.** `go.mod` has zero `golang.org/x/*` deps and adding one for one constant (`F_GETPATH = 50` on darwin) is not worth the supply-chain surface. The cost is `syscall.Syscall(syscall.SYS_FCNTL, fd, F_GETPATH, uintptr(unsafe.Pointer(&buf[0])))` with a single `unsafe.Pointer` line, contained to one platform file (`cwd_darwin.go`). The `syscall` package is frozen but darwin's `F_GETPATH` constants reflect a stable kernel ABI, so freeze status is not a risk here. Reuse posture: prefer stdlib `syscall` for one-syscall platform helpers; only reach for `golang.org/x/sys/unix` when the API surface is wide enough that the dep cost amortises.
- **Total-function contract preserved across a behaviour change via in-function fallback.** The pre-#57 contract was `EncodeCwd(string) string` with no error path; the post-#57 contract is the same. Every new failure mode (FS doesn't exist, EACCES, fcntl error) collapses into "fallback to encoding the input as-passed." No call site needed to learn about the new failure surface; no consumer had to grow an `if err != nil` branch. This is the "behaviour-compatible at the call site" property that let every spike and probe continue to work without edits. Reuse posture for tui-driver: when adding filesystem or syscall behaviour behind an existing pure-function API, prefer in-function fallback over growing the signature unless the failure is one a caller must distinguish from success.
- **Test helpers may legitimately duplicate production logic when keeping them aligned has lower cost than coupling them.** `cwd_test.go`'s `byteTransform` re-implements the post-canonicalisation byte loop from `EncodeCwd` so tests can compute expected outputs from a canonicalised path without invoking `EncodeCwd` itself (which would tautologically pass). The duplication is flagged by a one-line "Keep in sync with EncodeCwd's loop in cwd.go" comment. Future maintainers who change the byte transform must touch both. Acceptable here because the loop is 8 lines and the alternative (export the loop, or factor a sub-function whose only consumer is the test) would couple the test to production internals.

## Lessons learned

- **`filepath.EvalSymlinks` does NOT canonicalise case on macOS.** Empirically (verified 2026-05-21 during refinement): `mkdir /tmp/Foo; filepath.EvalSymlinks("/tmp/foo")` returns the lower-case input unchanged on a default case-insensitive APFS volume — no symlink to resolve, so EvalSymlinks reports success and leaves the casing as-passed. This was the central spec-time gotcha: an obvious "just use EvalSymlinks" first cut would have shipped a fix that passed `TestEncodeCwd_SymlinkResolution` and `TestEncodeCwd_NonexistentPath` but silently failed `TestEncodeCwd_CaseCanonicalisation` on every macOS developer machine and every macOS CI runner — the exact bug the ticket exists to close. Mechanisms that DO canonicalise case on darwin: `os.Chdir(p) + os.Getwd()` (mutates global state, library-unsafe — ruled out by the ticket), `os.Open + fcntl(F_GETPATH)` (chosen), and component-wise `os.ReadDir` walk (portable but ~30 LOC with more edge cases than `F_GETPATH`'s ~15). Generalises beyond #57: when stdlib `path/filepath` claims to "evaluate" or "resolve" a path, read its godoc carefully on case-folding — the abstraction stops at symlinks.
- **`filepath.EvalSymlinks("")` returns `(".", nil)` on POSIX, not an error.** Caused a silent platform divergence missed in local darwin testing: `os.Open("")` errored out on darwin and hit the fallback (encoding `""` → `""`); `filepath.EvalSymlinks("")` resolved `""` to `"."` (because `filepath.Clean("") == "."`), reported success, and `EncodeCwd("")` canonicalised to `"."` then byte-transformed to `"-"` on Linux. Surfaced only as a Linux-CI test failure on `TestEncodeCwd/empty` after the darwin-passing implementation was pushed. Fix in `cwd_other.go`: explicit `if p == "" { return "", false }` guard before the `EvalSymlinks` call, mirroring darwin's natural rejection. Reusable lesson: when two platform implementations of the same contract have different natural error surfaces for edge inputs (empty string, root, `.`, `..`), normalise the rejection explicitly at the top of the variant whose stdlib accepts what the other rejects — don't trust matched behaviour across platforms unless you've tested it on both.
- **Mid-PR `claude-version.lock` bumps remain out of scope, no matter how convenient.** During PR #63, the e2e claude-version-lock gate failed because the reviewer's machine had claude 2.1.145 while the lock pinned 2.1.144. A "convenience" commit bumped the lock to unblock the gate (70d9fc0) and was reverted in 56d947f when the next commit-review pass caught it. Same lesson as ticket [#47](47.md) — version-lock edits are their own ticket and must coincide with a fixture re-record sweep across every consumer (`spike-multi-turn`, `spike-cancel`, `spike-permission`, `spike-ask-user`, `snapshot-drift` for picker/mcp/agents). Adding a feature does NOT justify a lock bump on the same PR. The reaffirmation matters because the convenience pressure is real (a red CI gate blocking a green-otherwise PR feels like it deserves a quick tactical bump) — the discipline is to revert the bump and accept the temporarily-red gate until the proper lock-bump ticket lands.
- **Supersedes [codebase/47.md](47.md) § Lessons learned bullet 4** (the `tuidriver.EncodeCwd` casing-faithful triage entry). That entry remains as a historical record of the gotcha and the operator workaround (`cd "$(pwd -P)"`) at the time of #47; the gotcha itself is closed by this ticket. The "Not a defect" framing in 47's entry was wrong in retrospect — it was a latent defect whose blast radius (every `--session-id`-pinning consumer) was misjudged because the spike's manual triage workaround was cheap. The lesson generalises: an operator-visible workaround in a spike README is a signal worth re-examining as a library defect, not a sufficient closure.
