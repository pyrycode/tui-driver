# #71 — spike-ask-user: byte-by-byte prompt submit to survive claude 2.1.148 paste-detection

[Issue](https://github.com/pyrycode/tui-driver/issues/71) · [Spec](../../specs/architecture/71-spike-ask-user-fix.md) · [PR #77](https://github.com/pyrycode/tui-driver/pull/77) · Code: `cmd/spike-ask-user/`

## Summary

`spike-ask-user` failed every `make e2e` run against `claude 2.1.148` with a distinctive ~11.6 s fail-fast — far too short for any modal-wait (60 s) or PTY-quiet (120 s) watchdog. Reproducing the spike standalone and matching the stderr signature against the spec's diagnostic flow landed on Branch A — `session JSONL did not appear at … within 10s`. The 10 s `sessionFileWait` (`cmd/spike-ask-user/main.go:55-76`) plus a few seconds of claude startup + idle-wait reconciles the 11.6 s wall-clock exactly. Root cause: the spike submitted its prompt with a single `ptmx.Write([]byte(prompt + "\r"))` (`cmd/spike-ask-user/main.go:192` pre-fix), and against claude 2.1.148 the 170-byte prompt body trips claude's auto-paste-detection heuristic — the trailing `\r` is absorbed as a literal newline inside the pasted block instead of as the submit keystroke. The prompt body appears in the input box, but is never submitted; claude never starts the turn; the session JSONL never materialises; the 10 s `os.Stat` poll trips with `session JSONL did not appear`. This is the **exact failure mode** already documented in [#9 lesson "Bulk-writing `prompt+"\r"` between turns races with the prior turn's wind-down redraw"](9.md) — but with a twist: spike-multi-turn observed it on inter-turn submission after a tool-use wind-down, while spike-ask-user reproduces it on the **first and only** prompt of the session against the long-enough default prompt. The trigger isn't post-tool-wind-down specifically; it's "long prompt body + claude 2.1.148 paste-detection," which generalises.

Fix is a one-binary swap to the established char-by-char convention: replace the single bulk `ptmx.Write` with a `clearInputLine(ptmx)` → `typePrompt(ptmx, prompt)` sequence, copied verbatim from `cmd/spike-cancel/main.go:700-790` under a `// Copied from cmd/spike-cancel/main.go — keep in sync until library extraction` attribution comment. `typePrompt` writes the prompt body one byte at a time with a 10 ms inter-byte delay, pauses 50 ms, then writes `\r` separately so the input handler can recognise it as submit rather than as part of a pasted block. `clearInputLine` sends `Ctrl-U` (`0x15`) first to clear any drafted text in the input box (idempotent on empty input; matches the convention all three sibling spikes use). One new constant `clearLineSettle = 50 * time.Millisecond` for the post-Ctrl-U pause. No exported package symbols change; the runner, the lockfile, and every other spike binary are untouched.

The fix landed inside Branch A's first sub-case (timeout was the binding constraint, but the binding wasn't the *duration* — it was the *fact that `\r` never reached claude*). The architect's diagnostic flow ruled out the modal-wait branch (B), the trust-handling branch (C), and the post-answer branch (D) by the fail-fast runtime alone; the spec's "single binary at risk" bound held. No `t.Skip`, no removal, no `sessionFileWait` bump, no sibling-spike edits, no `pkg/tuidriver/` changes.

Verified per AC: `./bin/spike-ask-user -trust-folder=accept` exits 0 with `OBSERVED: AskUserQuestion question + options structure logged; …` in ~11.2 s standalone; `make e2e` reports `spike-ask-user → pass` in 12.2 s; `claude-version-lock` still passes; the three other pre-existing e2e failures (`spike-cancel`, `spike-long-prompt`, `snapshot-drift`) are unchanged and explicitly out of scope per the ticket.

## Patterns established

- **The char-by-char `typePrompt` convention is mandatory for any spike submitting a non-trivial prompt — confirmed at four sites now.** Originally introduced in spike-multi-turn ([#9](9.md)) as a fix for inter-turn wind-down races, the convention now has four consumers: `cmd/spike-multi-turn/main.go:469-498` (source), `cmd/spike-cancel/main.go:756-790` (copy), `cmd/spike-permission/main.go:1068-1090` (copy), and `cmd/spike-ask-user/main.go:438-468` (this ticket's copy). The trigger generalises beyond "post-tool-wind-down": **any prompt body long enough to trip claude 2.1.148's auto-paste-detection heuristic will swallow a co-resident `\r`.** spike-one-turn's `"What is 2+2?"` and spike-multiselect's `/`-triggered slash-command inputs are short enough to escape this; everything else needs `typePrompt`. The library extraction (#58–#62) should make char-by-char the default prompt-submission shape, expose the inter-byte delay as a per-session option, and document the failure mode in package doc — three independent re-derivations is enough evidence to bake it in.
- **Reuse the helper-pair by citation, mirror the attribution-comment shape exactly.** `clearInputLine` + `typePrompt` move together as a pair; the attribution comment on the copy ALWAYS names the immediate source sibling, NOT the original (`spike-ask-user` cites spike-cancel, which cites spike-multi-turn — a chain, not a star). This keeps the deduplication burden cheap when the library extraction lands (the chain collapses to one import) and surfaces sibling-drift bugs the same way [#70's lesson](70.md) flagged: when fixing the source helper, grep for sibling attribution comments and propagate. Three options for handling the next divergence (per #70's lesson set): single-PR fan-out, accelerate the library extraction, or accept the cost.
- **Diagnostic flow ranking by fail-fast wall-clock is a real signal, not just colour.** The spec's primary contribution to this fix was the wall-clock decomposition: 11.6 s ≈ claude startup (~1–2 s) + idle-wait (~0.5 s) + `sessionFileWait = 10 s`, which cleanly fingered Branch A and ruled out B/C/D before any code was read. Future "spike X fails fast against a new claude version" diagnoses should start by enumerating every named timeout constant in the spike binary and matching the observed runtime against their sum. If the runtime can be cleanly decomposed into known constants plus startup, the binding constraint is the named timeout — not a race, not a modal-detection issue, not a keystroke regression.

## Lessons learned

- **A documented lesson doesn't propagate retroactively to spikes that predate it.** `spike-ask-user/main.go` was committed before [#9's "bulk-write race" finding](9.md) landed, so it never inherited the convention. Subsequent spikes (`spike-cancel`, `spike-permission`) adopted `typePrompt` because they were written *after* the finding — but no one swept back through earlier binaries to retrofit. The version-lock short-circuit ([#64](64.md) removed) hid the resulting brokenness for weeks. **Same general lesson as [#70](70.md):** the `// copied from … — keep in sync until library extraction` convention is great at propagating features forward and great at propagating bug fixes forward, but useless at retrofitting earlier code that predates a finding. One actionable defence: when a new convention is established in a per-ticket doc, the *next* ticket should sweep prior binaries for non-adoption. This sweep didn't happen for #9; it cost ~3 tickets (the 4 currently-failing checks plus the version-lock short-circuit that hid them) to surface.
- **The architect's prior on "the 11.6 s reading is load-bearing" was correct, and the spec's branch enumeration was the right shape.** The spec gave four branches keyed off literal stderr substrings; the developer's first action (reproduce and capture stderr) settled the branch on the first run. Compare this to the alternative — an architect spec that hand-waves "investigate" without enumerating the failure-shape decision tree, which would have multiplied diagnostic effort by 4× across branches. The shape generalises: when the failure has a quantitative signal (wall-clock, exit code, marker count), the architect should decompose it into the spike's named constants and use the decomposition to enumerate fix branches. The developer's evidence is then a single match against one branch's signature, not an open-ended investigation. (Counterpoint: this only works when the spike has well-named constants and a small set of error returns. Spikes without that shape — e.g. `probe-first-prompt-hang` — won't decompose this cleanly; the diagnostic flow has to fall back to instrumentation runs.)
- **"Removal authorised in last-resort branch" wasn't load-bearing here, but the carve-out shape is valuable as a forcing function.** The spec authorised removal of the check if AskUserQuestion couldn't be reliably triggered in claude 2.1.148. In practice the fix lived two layers below the prompt layer (keystroke transport, not prompt content or modal triggering), so removal was never on the table. But knowing removal was available kept the diagnostic honest: there's no slow drift toward `t.Skip`-equivalents when "remove the check entirely" is the explicit fallback. The pattern: authorise removal when (and only when) the fix shape is bounded by ticket size, and let the diagnostic surface decide whether to take it. Removal stays small (~30 LOC + a Makefile edit) and is auditable; `t.Skip`-equivalents grow in the dark.
- **claude 2.1.148's paste-detection heuristic is a new behavioural surface for the harness to defend against.** spike-multi-turn's #9 finding framed the wedge as "input handler swallows `\r` after wind-down redraw" — a stateful, transient phenomenon tied to a specific intra-session moment. This ticket's evidence is broader: the bug fires on the **first prompt of a fresh session** against a long-enough body. The mechanism is almost certainly paste-detection (the prompt body + `\r` arrives in a single `write(2)` and claude classifies the whole thing as pasted content, with `\r` becoming literal data instead of a submit). This generalises:
  - Any new spike that types a prompt should use `typePrompt` by default.
  - The "long enough to trigger paste-detection" threshold is empirical and version-dependent — the safe default is char-by-char regardless of length, since the 10 ms inter-byte delay is dominated by claude's own first-prompt latency anyway.
  - When `pkg/tuidriver/` lands a `Session.WritePrompt` (which already exists per [#47](47.md)'s `spike-long-prompt`), the bracketed-paste path it ships is **deliberately the paste path** — it writes `\x1b[200~ prompt \x1b[201~ \r` so claude knows it's a paste and doesn't have to heuristic-detect. That contract is the right architectural answer; the spike binaries' `typePrompt` is the workaround for spikes that haven't migrated to the library yet.
- **Six fast diagnostic runs are cheap and short-circuit speculation.** The spec ranks four diagnostic branches; on each new claude version a fresh round of "the marker pattern shifted" / "the modal text changed" / "the keystroke contract drifted" speculation will come up. The empirical short-circuit is: reproduce, capture stderr, match against the four branches' literal substrings — under 30 minutes from "I see the failure" to "I have the branch." Resist the temptation to speculate beyond what the evidence supports; the diagnostic flow exists precisely so that speculation is bounded by the spike's actual error returns.
