## Summary

Mirrors [#116](116.md)'s spike-multi-turn cleanup for `cmd/spike-cancel/main.go`. Drops `projectsDir`, `openSessionJSONL`, `tailJSONL`, `isEndTurn`, `typePrompt`, `clearInputLine`, `spinnerRe`/`matchSpinner`, and the inline 1 Hz watchdog goroutine in favour of `tuidriver.SessionJSONLPath` + `WaitForSessionJSONL`, `TailJSONL`, `IsEndTurn`, `Session.TypePrompt`, `Session.ClearInputLine`, and `RunWatchdog`. The session-scoped event channel becomes `<-chan tuidriver.JSONLEntry`, populated inside probe 1's `postPromptHook` via the same pointer-to-channel-slot pattern [#116](116.md) established. In-file helpers `isToolUse`, `msgIDOf`, `extractByMsgID`, and `logCancelEvent` stay but switch from `map[string]any` to struct-field access on `tuidriver.JSONLEntry`. Single-file diff: 393 lines down (126 added, 267 removed). AC #1's mechanical greps return empty; `go vet`, `go test -race`, `go build`, and `make e2e` (10/10 checks including snapshot-drift) all clean. PR closes the fifth of the seven spike-binary migrations from the [#89](89.md) / [#87](87.md) sweeps; two follow-ups remain (`spike-permission`, `spike-ask-user`).

Three spike-cancel-specific deltas relative to the [#116](116.md) precedent are worth flagging.

First, **`clearInputLine` migrates to `Session.ClearInputLine` (the new piece [#87](87.md) shipped that [#116](116.md) didn't exercise — spike-multi-turn never had a `clearInputLine` body to drop because its prompts never re-enter a fouled input box).** The `clearLineSettle` constant goes with it (library-owned via `tuidriver.ClearLineSettle`). One direct method substitution at `runProbe` `cmd/spike-cancel/main.go:355`; the empirical "after a cancelled probe, claude restores the previously submitted prompt as drafted input" rationale block at lines 348-354 is preserved verbatim (that's the reason for `ClearInputLine` existing as a separate primitive at all — see [#11](11.md) finding 6).

Second, **`logCancelEvent` must read `stop_reason` through `ev.Message.Raw["stop_reason"]`, not the typed `EntryMessage.StopReason` field.** The README's three-way `<missing>` / `<nil>` / string discrimination of `stop_reason` is the load-bearing finding from spike #11 (it's how the README documents that cancelled assistant messages keep their pre-cancel `stop_reason` rather than getting a new cancel sentinel) and the typed accessor collapses all three cases — absent key, JSON null value, empty-string value — into the same empty Go string. The substitution table in the spec called this out and the implementation honours it via the explicit three-arm switch on `raw, present := rawMap["stop_reason"]`. Same nil-guard posture as `msgIDOf` even though callers gate on `ev.Type == "assistant"` upstream so `ev.Message` is in practice always non-nil here; the defensive guard matches sibling helpers and costs nothing.

Third, **`waitReappeared` gains an explicit `if ev.Type != "assistant" { continue }` filter at `main.go:573` to preserve the pre-migration `logCancelEvent`-only-sees-assistants behaviour.** The pre-migration local `tailJSONL` filtered to assistant-only before send; library `TailJSONL` deliberately doesn't filter (every envelope type emitted — see [#59](59.md)), so the consumer-side filter has to be re-established at the receive site to keep the existing `probe=%d jsonl-cancel-event type=assistant ...` log line shape. Same architectural reason as [#116](116.md)'s `msgIDOf` nil-guard — the library-side unfiltering pushes type filtering into the consumer, which is fine but mandatory to audit at every receive site that has a type-shaped assumption.

The two PTY-quiescence predicate blocks in `waitReappeared` (`main.go:545-551`) and `runRecovery` (`main.go:671-680`) are preserved verbatim per AC #4 — load-bearing [#69](69.md) design, both bypass `tuidriver.IsIdle`'s spinner-absent half via `bytes.Contains(stripped, tuidriver.IdleGlyph)` directly, and both share the same `ptyQuietWindow = 1500 * time.Millisecond` (constant + 10-line commentary at `main.go:73-82` preserved verbatim as well). `sendCancel` reaches through `session.Write` instead of `*os.File` (one-line body change at `main.go:728-731`); the rationale comment about why the cancel keystroke does NOT go through `TypePrompt` is preserved verbatim. The trust-folder accept write at `main.go:251` (`ptmx.Write([]byte("1\r"))`) is deliberately untouched and matches the sibling spikes' shape — out-of-scope for this slice. `resolveSession` shrinks to `(sessionID, err)`; the legacy `projects-dir path=...` startup log line is dropped (matches [#116](116.md) / [#112](112.md) — the e2e harness only asserts on `SUCCESS: ...` stdout).

## Patterns established

- **`logCancelEvent`-style helpers that distinguish absent vs. null vs. empty-string MUST read through `ev.Message.Raw[key]`, not the typed field.** `EntryMessage`'s typed fields are parsed zero-value-on-mismatch — for strings, that means JSON null, missing key, and empty string all collapse to `""`. If the consumer needs to preserve the three-way discrimination (because the README documents what claude emits, or a downstream tool branches on the difference, or the field is a versioning marker where presence-as-null is the signal), the consumer has to walk `Raw` directly. Reuse posture: rare but specific — most call sites only care whether `stop_reason == "end_turn"` and the typed field is fine. The rule is "if the spec for your call site uses `<missing>` / `<nil>` / `<value>` as three distinct log/branch outcomes, use Raw; otherwise use the typed field." The library could in principle expose a typed three-way accessor (`StopReasonPresence() (string, presence)`) but the use case is narrow enough that direct `Raw` access is the cleaner trade — wrapping every `map[string]any` peek in a typed helper is what the [#60](60.md) / [#104](104.md) primitives already do for the common cases. (Same pattern applies to any other Anthropic-API field where "absent" and "null" are semantically distinct.)
- **`waitReappeared`-style receive-loop sites that previously assumed filtered-at-source emit need an explicit `ev.Type == "assistant" { continue }` (or the equivalent type filter) after migration.** Generalisation of [#116](116.md)'s `msgIDOf` nil-guard pattern: pre-migration local `tailJSONL` filtered the channel to `type=="assistant"` before send; library `TailJSONL` doesn't. Any receive-loop body that downstream-calls a helper which assumes assistant-only input (here: `logCancelEvent`'s "type=assistant" log line embedded in the format string) needs to re-enforce the filter at the consumer site. The fix is one line; missing it would emit `probe=N jsonl-cancel-event type=assistant stop_reason=<missing> msg_id=` lines for non-assistant envelopes (user, attachment, system, …) which would surface as a README finding regression. `go vet` does NOT catch this — both shapes typecheck. Audit-checklist item for any future `map[string]any` → `JSONLEntry` migration: grep for log-format strings or accumulator-helper names that have an envelope-type assumption baked into them, gate them at the consumer site.

## Lessons learned

- **The spec's two-line `logCancelEvent` rewrite was the only place in this migration where the typed `JSONLEntry` accessor is NOT the right answer.** Every other adapted helper (`isToolUse`, `msgIDOf`, `extractByMsgID`) is a clean win for the typed field — shorter, no `map[string]any` cast, nil-guarded once via `msgIDOf`. `logCancelEvent` is the exception because the README's three-way `stop_reason` discrimination predates the typed-field design and bakes in a presence/null/value distinction that the typed field deliberately erases (zero-value-on-mismatch is the correct posture for 99% of consumers — claude flickering between absent and null in patch releases shouldn't be observable to most callers). The spec called this out explicitly with the substitution table arm pointing to § Helpers staying in-file; without that guidance the migration would have silently regressed the README finding (`<nil>` and `<missing>` would both have become empty strings indistinguishable from a literal `""`). Lesson: when migrating a `map[string]any` helper onto a typed library accessor, audit every helper for "does this need the typed-accessor's normalisation, or does it depend on the raw-map's preserved distinctions?" The architect's spec did this audit upfront; future migrations should follow the same pattern. If the consumer doesn't need the distinction, use the typed field; if it does, walk `Raw` directly and accept the boilerplate.
- **Vestigial `sync.WaitGroup` retained per template-parity, same as [#116](116.md).** Pre-migration `main` declared `var wg sync.WaitGroup` with two `wg.Add(1)` blocks (watchdog + inline tailer); the tailer block is deleted entirely (library `TailJSONL` owns its goroutine + lifecycle), and the watchdog block is replaced (one `wg.Add(1)` + `defer wg.Done()` wrapping `tuidriver.RunWatchdog`). Post-migration `main` still has one `wg.Add(1)` for the watchdog (`main.go:227-234`) and no `wg.Wait()` anywhere. The watchdog goroutine is lifecycled by `rootCtx` cancellation, not by WaitGroup synchronisation. [#112](112.md)'s spike-one-turn migration deleted the WaitGroup entirely; [#116](116.md) and now this ticket retain it for template parity. The asymmetry between spike-one-turn (deleted) and spike-multi-turn / spike-cancel (retained) is visible but harmless — same "scope discipline cuts both ways" reasoning [#116](116.md)'s lessons captured. A future tidy-pass ticket can sweep all four binaries to the same posture; bundling it into this cleanup-focused slice was correctly out of scope.
- **`make e2e` ran clean on the first build — five probes (cancel-thinking, cancel-tool-use, three recovery shapes) all hit `SUCCESS:` and the snapshot-drift check passed without churn.** The unfiltered firehose behaviour change (library `TailJSONL` emits all envelope types vs. the pre-migration assistant-only filter) didn't surface as snapshot drift because the `picker` / `mcp` / `agents` snapshots live in `pkg/tuidriver/testdata/` and exercise other spike binaries — same reason [#116](116.md)'s e2e ran clean. Spike-cancel's only e2e success criterion is the `SUCCESS:` marker on stdout per probe; the wider-channel behaviour of `waitReappeared` (it now sees user / attachment / system events too and filters them at the receive site) and `runRecovery` (its `events` slice accumulates more entries than pre-migration but `extractByMsgID`'s msg_id filter + `IsEndTurn`'s type filter strip them out) are both validated end-to-end by the SUCCESS marker firing. The spec's prediction that the memory cost would be negligible held — five probes × a single recovery turn each, the events slice grew by maybe 10-20 entries per probe vs. the assistant-only pre-migration shape, GC didn't notice. Lesson: when a library deliberately under-filters (emit all, consumer filters), the consumer-side cost in real workloads is in the noise even for stateful accumulators — the architecture pays off because mixed consumers compose cheaply.
- **The "two PTY-quiescence predicates instead of one" delta from the [#116](116.md) precedent was the migration's smallest risk surface, not its largest.** Spike-multi-turn had one verbatim predicate (`runTurn.check`); spike-cancel has two (`waitReappeared.stable` + `runRecovery.check`). AC #4 explicitly called them out as load-bearing and the spec said "bodies preserved verbatim." Both bodies are five lines each (`gotEndTurn` half + `IdleGlyph` half + `QuietFor` half) and trivially identifiable as byte-equivalent diffs; the risk of touching them by accident during the migration was near-zero. The real risk surface (and where this ticket spent its review attention) was the `logCancelEvent` rewrite and the three closed-channel-handling sites in the receive loops — those are where a wrong choice would compile cleanly and break in production. Lesson: when a spec flags multiple "load-bearing, preserve verbatim" predicates, the count matters less than the diff surface — five-line predicate preserved twice is structurally easier than one rewrite that has to thread three distinct invariants. Architects writing migration specs can lean on this when scoping: "two verbatim copies of an identical block" is cheaper than "one block whose body has to be re-derived."
