# #146 — `ParseModalContent` screen-side modal extractor + serializer

[Issue](https://github.com/pyrycode/tui-driver/issues/146) · [Spec](../../specs/architecture/146-parse-permission-trust-modal.md) · [PR #148](https://github.com/pyrycode/tui-driver/pull/148) · Commit `dba8401` · Predecessors: [#13](13.md), [#90](90.md), [#109](109.md), [#100](100.md)

**Phase 3 foundation of pyrycode#597 (substrate seal / mobile-remote-head).** Permission and trust-folder prompts have **zero JSONL footprint** — they exist only on the rendered PTY screen ([jsonl-layout § Permission modals](../architecture/jsonl-layout.md)). The substrate seal makes tui-driver the sole owner of claude's screen knowledge, so the daemon must receive a modal as a **neutral typed value**, never by reading screen text. This ticket adds the *structured extraction* (title / prompt / ordered options / default → a struct) on top of the already-shipped *classification* (`DetectModalClass` / `ModalClass`, [#13](13.md)/[#100](100.md)); it re-introduces no class detection and owns no permission *decision* (that lives in the pyrycode children). The next tui-driver child (safe modal-answer: choice → keystroke + re-read confirmation) builds on the `ModalContent` struct.

## Summary

One new file, `pkg/tuidriver/permission.go`, plus its test and two fixtures — purely additive, no existing file touched, no exported symbol changed. It adds:

- `ModalContent{Class ModalClass; Title, Prompt string; Options []ModalOption; Default int}` — the neutral push shape. The **JSON tags ARE the serializer** (`class`/`title`/`prompt`/`options`/`default`), same convention as `AskUserQuestion` / `Agent` ([#109](109.md)); the consumer calls `encoding/json.Marshal(modal)` — there is no wrapper `Marshal*` method.
- `ModalOption{Index int; Label string}` (`index`/`label`). `Index` is claude's rendered 1-based number; `Label` is advisory display text with the `N.` prefix and ❯ marker stripped.
- `ParseModalContent(snap []byte) *ModalContent` — the **screen-sourced sibling of `ParsePicker`**, NOT of the JSONL `Parse<Tool>` extractors ([#140](140.md)/[#142](142.md)): modals never reach `Events()`. It calls `DetectModalClass`, returns `nil` unless the class is `permission` or `trust-folder`, `Render`s the snapshot, dispatches to a per-class branch, and returns `nil` when zero option rows parse (no half-struct — `ParseAskUserQuestion`'s "nil if it would be empty" posture).

Shared mechanics across both classes: an unexported `modalOptionRe = ^(❯\s*)?(\d+)\.\s*(.+)$` (the `N.` prefix and ❯ fall outside the label capture, so the label is clean by construction); `extractOptions` scans every line for option rows in render order and sets `Default` to the ❯-marked row's index (`0` = none); `Render(snap, 0, 0)` (not `StripANSI`) is mandatory so claude's `\x1b[1C` cursor-forwards expand back to spaces (`"2. Yes, allow…"`, not `"2.Yes,allow…"`); `modalLines` runs the `ParseAgentList`/`ParseMcpStatus` normalization prelude (split → collapse space runs → trim). Per-class only: **permission** takes `Title` = first non-empty/non-option line after the last `─{20,}` separator preceding the prompt, `Prompt` = the line carrying `anchorPermissionSpaced`/`anchorPermissionStripped` (reused from `modal.go`); **trust-folder** splits the `Quick safety check:` header on the first `:` into `Title` / `Prompt`.

Pipeline ran clean: RED→GREEN, code-review PASS, `make check` green. Carried the `security-sensitive` label; the architect's security review verdict was **PASS** (see spec § Security review) — the one trust boundary (claude's prompt-/tool-influenceable screen → struct → JSON → daemon → phone) is mitigated structurally, see Patterns below.

## Patterns established

- **`Index` is the security-relevant selector; `Label` is advisory and non-authoritative.** The modal *content* is prompt-/tool-influenceable — a hostile prompt can make claude render an arbitrary option label. The mitigation is structural, not a sanitizer: the downstream answer child routes on `Answer(strconv.Itoa(opt.Index))`, and `Index` is the rendered number claude itself paints, so a spoofed label can mislead a *human* but cannot change which grant a given keystroke applies. The `ModalOption` doc-comment states this at the type, exactly where a future caller would otherwise drift into parsing the label. This is the screen-side analogue of [#140](140.md)'s "name the deliberate divergence in the doc comment" — here the load-bearing fact is *which field is authoritative*, and it has to live on the struct or it is invisible.
- **The extractor is class-generic, named for the value not the class.** Named `ParseModalContent` → `*ModalContent` (the package's `Parse<Thing>` → `*<Thing>` convention: `ParseAgentList`, `ParseMcpStatus`, `ParseAskUserQuestion`), **not** the ticket's tentative `ParsePermissionModal`. It handles `permission` AND `trust-folder` today through one `Class ModalClass` field, so the epic's later classes (destructive / plan-confirm) extend by adding a `switch` arm, not a new exported function. Reusing the shipped `ModalClass` enum as the struct's class field is what makes that a natural extension rather than a parallel taxonomy.
- **Structured extraction is the library-side successor to the spike's raw-text scrape.** Spike #13's `extractModalText` (in `cmd/spike-permission`) joined the modal region into one `\n`-delimited *string*; `ParseModalContent` projects the same screen region into a *typed struct* with stable fields. The classification anchors are reused verbatim; the extraction is what's new. See [system-overview § Structured modal content](../architecture/system-overview.md).
- **`Render` (vt10x), not `StripANSI`, for any screen-side option extraction.** `StripANSI` collapses `\x1b[1C` cursor-forwards to nothing (`"1. Yes"` → `"1.Yes"`, `"Do you want to proceed"` → `"Doyouwanttoproceed"`); `Render` repaints them as real spaces. `DetectModalClass` can use the stripped form (it only substring-matches anchors), but the moment you read *option text* you must `Render`. Same prelude already used by `ParseAgentList` / `ParseMcpStatus`.

## Lessons learned

- **A space-stripped anchor reused from `modal.go` silently fails against `Render` output — the two paths normalize differently.** `DetectModalClass` matches anchors against `StripOSC(StripANSI(snap))`, where inter-word spaces are eaten, so its trust anchor is `anchorTrustFolder = "Quicksafetycheck"`. The extractor matches against `Render` output, where spaces are restored, so `"Quicksafetycheck"` does **not** appear — the header reads `"Quick safety check"`. The fix was a new unexported `anchorTrustHeaderSpaced = []byte("Quick safety check")` for the Render-side match (the permission anchors already ship in both spaced and stripped forms, so they were reusable as-is). Takeaway: when you reuse a classification anchor for *extraction*, check which normalization (`StripANSI` vs `Render`) it was authored against — a stripped anchor and a rendered line are different byte sequences for the same screen text.
- **Separator-anchored title extraction degrades to an empty title, never a wrong one, on the un-fixtured layout.** The permission `Title` is the first content line after the last `─{20,}` separator before the prompt. The Read permission modal (spec Open Question 2) is inline-packed — separator + header + action + question on one line — and structurally different from the Bash render. Requiring the separator means the Read layout yields an *empty* title rather than a confidently-wrong one; the parser never panics and the option rows still extract. Hardening the Read variant is deferred until it is fixtured (evidence-based fix selection) — building it now would defend an unobserved shape.
- **The trust-folder fixture is constructed, not captured, so the assertions are scoped accordingly.** No raw trust-modal snapshot survives (the spikes pre-mark the workdir trusted or send `1\r` via `AcceptTrust`). `trust-folder-snapshot.bin` is reconstructed from the known anchor + `AcceptTrust`'s `"Yes, I trust this folder"` contract + documented wording. The test asserts option-1, the option count (`>= 2`), and `Default == 1` — **not** an option-2 literal (its wording is unconfirmed). Follow-up on file: replace it with a live capture against a fresh untrusted cwd and tighten the assertions. (The permission fixture, by contrast, is a faithful transcription of real captured bytes from `cmd/spike-permission/README.md`.)
- **Action-detail lines are deliberately not captured — a security hardening, not an omission.** The permission modal's command lines (`ls /tmp`, `List files in /tmp`) are not among the named fields (class/title/prompt/options/default), so a full Bash command line — which could echo a secret — never reaches the push shape. `Title` is the generic header (`"Bash command"`), not the command; option labels carry only the coarse resource scope claude already shows the user (`tmp/`). If the daemon later needs the command detail as a distinct field, that is an additive struct extension in a follow-up.
- **No new feature doc, no new ADR.** Like the `Parse<Tool>` siblings ([#109](109.md)/[#140](140.md)/[#142](142.md)), this is a screen-side parser following an already-decided convention — it lives in `system-overview.md` (the screen-side parsers' home, beside the existing modal bullets), not a per-helper feature page. The Index/Label trust boundary is a substrate-seal *pattern* (captured above), not an ADR-weight decision; the remote-permission security model and ADR 025 live in pyrycode.
