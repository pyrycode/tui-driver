# #36 — e2e: claude-version-lock check + `claude-version.lock`

[Issue](https://github.com/pyrycode/tui-driver/issues/36) · [Spec](../../specs/architecture/36-claude-version-lock.md) · [PR](https://github.com/pyrycode/tui-driver/pull/44) · Code: `cmd/e2e-runner/`, `claude-version.lock`

## Summary

Adds the fourth check kind — `version-lock` — to the e2e harness from [#34](34.md). Differs from `spike`/`probe`/`snapshot` in one structural way: it's the first **in-process** check. Goal: catch claude upstream churn (version bumps that rename/remove flags) before the slow spikes accumulate 5 minutes of wall time confused about why they're failing.

Three things land:

- **`claude-version.lock` at the repo root** (8 lines, plain `key=value` + `#` comments). Initial content pins `version=2.1.144` and two `flag=` entries (`--session-id`, `--permission-mode bypassPermissions`) — the empirical contract the library has with `claude`. Hand-edit during a claude upgrade; the maintainer-facing runbook for that lives at docs ticket #37.
- **`Check.Run` field on the existing struct in `cmd/e2e-runner/main.go`.** When non-nil, `runCheck` calls `Run(ctx)` and returns its `(status, extra)` directly — `Binary`/`Args`/`SuccessMarker`/`OnFailure`/`OnComplete` are all ignored on this path. Five-line branch at the top of `runCheck`; the subprocess path stays untouched. The runner's "intentionally a leaf, not a framework" shape from #34 holds — one new optional field, parallel to the existing optional callbacks, no interface or registry.
- **`claude-version-lock` slotted first in `buildChecks()`.** Its `Run` closure is built in `main` before `buildChecks` is called so it can capture `claudeVersion` (populated later by `captureClaudeVersion`) by-reference and the `-lock` flag value. Parses the lock file, parses the leading token out of the captured `claude --version` output via `parseClaudeVersion`, asserts strict equality, then runs `claude --help` once and `strings.Contains` each flag string from the lock file. `extra` always carries `installed_version`, `expected_version`, `missing_flags` (empty list on pass) so the schema is uniform.

The runner also gains a one-line **short-circuit**: when `claude-version-lock` returns non-pass, the existing wall-budget arm at the top of the for-loop widens by one clause (`if parentCtx.Err() != nil || skipRest`), and every subsequent check is appended with `status="timeout"` and `duration_ms=0`. No new status value, no new top-level Report field — the surrounding `claude-version-lock` fail entry disambiguates "drift short-circuit" from "wall budget exhausted."

Test surface: two new pure helpers (`parseClaudeVersion`, `parseLockFile`) get table-driven coverage in `cmd/e2e-runner/main_test.go` (canonical input, padded whitespace, bare token, empty, whitespace-only; canonical lock file, comments/blank lines tolerated, key/value whitespace trimmed, missing `version=`, duplicate `version=`, unknown key, empty flag value, version-only no-flags pinning `Flags == nil`, missing file is `os.IsNotExist`). The `Run` closure itself is integration-tested by every `make e2e` invocation; its branches are dominated by I/O against `claude` and the filesystem, so unit-testing the helpers cover the part where coverage pays.

Zero deviations from the spec. `pkg/tuidriver` untouched. No new binaries, no new packages, no Makefile change. Two NIT-level code-review observations (no fix required): when both the lock file is missing AND `claude --version` failed at startup, `installed_version` lands as the literal string `"unknown"` (because `parseClaudeVersion("unknown") == "unknown"`); and the stderr messages substitute the runtime `lockPath` flag value rather than the literal `claude-version.lock` the spec quoted — an improvement when an operator overrides `-lock`.

## Patterns established

- **In-process `Check.Run` is the right shape when the check's inputs already live in the runner's scope.** The captured `claude --version` output is in `main`; the in-process closure consumes it without paying a second `claude --version` call (the AC's "no third call site" constraint). The helper-binary precedent from [#35](35.md) does NOT generalise — that check has structural reasons to be its own binary (3-spike orchestration + byte-comparison); this one is two string comparisons. Decision rule for the next check: in-process when the data is already in the runner; helper binary when the work is non-trivial flow that would clutter the runner's `main`.
- **Closure-in-`main` to bridge a Run callback to data populated later in `main`.** `runClaudeVersionLockCheck(ctx, capturedVersion, lockPath)` is the pure function; the closure that `buildChecks` accepts is `func(ctx) { return runClaudeVersionLockCheck(ctx, claudeVersion, *lockPath) }` — `claudeVersion` is a captured-by-reference `string` populated AFTER `buildChecks` returns. This works because `runCheck` doesn't fire the closure until the for-loop body, well after `captureClaudeVersion` has assigned to the variable. Use this pattern when a future in-process check needs runtime context that doesn't exist yet at `buildChecks` time.
- **Strict string equality over semver-aware parsing.** `parseClaudeVersion` is `strings.Fields(raw)[0]`-with-a-length-guard; comparison against the lock's `version=` is `==`. Semver parsing would be over-engineering for a check whose entire job is "is the binary the maintainer pinned still on disk?" The maintainer bumps the lock file deliberately. If claude ever changes its `--version` shape (e.g., adds a `claude ` prefix), the rule is `strings.Fields(raw)[1]` — two characters. Don't reach for `golang.org/x/mod/semver` yet.
- **Plain `key=value` + `#` comments over JSON/TOML/YAML for hand-edited contract files.** The lock file is edited once per claude upgrade; grep-friendliness matters more than data-model expressiveness. Future hand-edited contracts in this repo (a hypothetical `tuidriver-known-issues.lock`, an `e2e-pinned-models.lock`) should default to the same format. Parser convention: comments stripped first, blank lines tolerated, exactly-one-required keys enforced at parse, repeatable keys collected, unknown keys are parse errors with line numbers (so typos surface immediately rather than silently no-op-ing).
- **`fmt.Errorf("at line %d: <reason>")` for parse errors over typed error structs.** `parseLockFile` returns `error`, and every parse-error path wraps the line number in `at line N: ...`. The `Run` closure surfaces the error verbatim via `Fprintf(os.Stderr, ...)`. Trade-off: callers can't `errors.As` for a typed error to inspect the line number programmatically — fine for a check whose only consumer is a human reading stderr. If a future caller needs structured parse-error context, define a typed error then; for now, line-numbered strings are the minimum that satisfies the spec.
- **`skipRest` flag widens the existing wall-budget arm by one clause, not a new control structure.** AC bullet 5 ("first failure short-circuits the slower checks below") landed as `if parentCtx.Err() != nil || skipRest { ... }`. No new status value, no `break`, no second loop. Trade-off: `status="timeout"` is now triply overloaded — "this check timed out", "we never got to this check because wall budget was exhausted", "we never got to this check because version-lock short-circuited." The surrounding `claude-version-lock` `fail` entry disambiguates; report consumers that need to distinguish look at the entry above. Future short-circuit triggers (e.g. a hypothetical "claude binary missing" pre-flight) should reuse the same `skipRest` shape rather than introduce a fourth `status` overload.
- **Always-present `extra` keys for schema uniformity, even when their value is empty.** `installed_version`, `expected_version`, `missing_flags` ride in `extra` on EVERY code path — empty string and empty slice are valid values; the key is never omitted. Map-key alphabetical ordering from `encoding/json` means `duration_ms, expected_version, installed_version, missing_flags, name, status` is a stable schema downstream consumers can depend on. Apply this rule to any future check whose `extra` contributes named fields the schema documents.

## Lessons learned

- **`captureClaudeVersion` returns the unparsed string (e.g. `"2.1.144 (Claude Code)"`), and `Report.ClaudeVersion` preserves that.** Looked tempting to "fix" `captureClaudeVersion` to return just `"2.1.144"`, but `Report.ClaudeVersion` is part of the e2e-report.json schema downstream consumers may already be reading — changing it is a schema break. Parse where the parsed form is needed (inside the check closure → `installed_version` field) and leave the top-level value alone. General lesson: when a captured raw string needs interpretation in a new place, parse at the use site, not at the capture site, unless every consumer wants the parsed form.
- **`parseClaudeVersion("unknown") == "unknown"`** — when `captureClaudeVersion` fails it returns the literal string `"unknown"`, and `strings.Fields("unknown")[0]` is `"unknown"` (a non-empty token). The check explicitly handles this: it checks `capturedVersion == "unknown"` BEFORE parsing and short-circuits with a `claude --version failed at startup` stderr line. If the lock file is ALSO unreadable in this rare double-fault path, `installed_version` does end up as the string `"unknown"` (caught at code review as a NIT, kept as-is — the report consumer sees both the missing-lock-file stderr line AND the surrounding context). Future "first parse, then validate" code in this repo should remember that `strings.Fields("unknown")` is non-empty — distinguishing "valid-looking string token" from "sentinel string indicating earlier failure" is the caller's job.
- **`tos.known` registration is automatic for any check in the slice.** The `-timeout claude-version-lock=DUR` override worked on day one without a single line of new code, because `main()` loops over `checks` and seeds `tos.known[c.Name] = true` before flag-parsing. The spec called this out as "AC bullet 4 free" — confirmed. Lesson for the next check kind: as long as you add your entry to `buildChecks()`, the per-check timeout override surface accepts it automatically. Typo-rejection (`flag.Var.Set` returns an error for an unknown name) also covers you. No additional plumbing required.
- **Closure ordering matters: register the flag before calling `buildChecks`, but dereference inside `Run`.** Subtle ordering bug avoided: `lockPath := flag.String(...)` returns a `*string` BEFORE `flag.Parse()` runs. Calling `buildChecks(runVersionLock)` here passes the closure (capturing `lockPath` and `claudeVersion` by reference); the closure dereferences `*lockPath` lazily inside `Run`, AFTER `flag.Parse()`. Operator `-lock=/foo/bar.lock` overrides flow through. A naive `path := *lockPath; runVersionLock := func(...) { return ...path... }` would have captured the pre-parse default value. Lesson: when capturing flag values into a closure that fires after `flag.Parse()`, always dereference inside the closure body.
- **The lock file's literal flag value is `--permission-mode bypassPermissions`, not split into `--permission-mode` and `bypassPermissions`.** The library passes them as separate argv elements when invoking claude, but `claude --help` prints the joint phrase `--permission-mode bypassPermissions` (and other modes alongside) in one passage. `strings.Contains(help, "--permission-mode bypassPermissions")` is the substring check that matches that printed phrase. Spec called this out as a format rule ("internal whitespace verbatim") and the parser preserves it; the lesson is for whoever next adds a flag to the lock file — match what `claude --help` literally prints, not what argv looks like.
- **Don't unit-test the closure body when its branches are dominated by I/O.** Three of the closure's six early-return arms depend on `os.ReadFile`, `exec.Command`, or `parseLockFile` returning specific errors — wiring up a unit test that fakes those means either (a) refactoring the closure to accept interfaces, paying the abstraction tax this spec explicitly avoids, or (b) `t.TempDir()` + faked PATH manipulation, which is brittle. The two pure helpers (`parseClaudeVersion`, `parseLockFile`) cover the parts where unit coverage is cheap and high-signal; the rest is exercised by `make e2e` against the real installed claude on every CI run. Same testing shape every future in-process check should adopt.
