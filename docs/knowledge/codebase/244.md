# #244 — bind the full-panel co-signals to panel structure (mcp, permissions-config)

[Issue](https://github.com/pyrycode/tui-driver/issues/244) · Blocked by [#245](245.md) (agents arm retirement had to land first, so this ticket touches no agents code) · Code: `pkg/tuidriver/modal.go`, `pkg/tuidriver/picker.go`, `pkg/tuidriver/picker_color.go`, `pkg/tuidriver/anchor_forgery_test.go`

## Summary

`mcp` and `permissions-config` were the last two full-panel `DetectModalClass` classes still gated by `snapHasPickerHighlight` — a colour co-signal that matches its highlight shade **anywhere** in the raw snapshot. The 2026-07-07 review addendum established that shade is a general light blue claude also paints on prose paths/links, present in a large fraction of frames — so the co-signal added almost nothing and the effective protection was the header/tab words alone. Recording `20260703T194012Z-1e437c7a-…-ok.cast` classified `permissions-config` four times on plain transcript prose: the header word and a tab word matched independent locations while the highlight sat elsewhere in the frame.

Fixed with two co-signals, both reused-shape deterministic code, no new dependency:

- **`snapHasRowOpeningHighlight`** (`picker.go`) — segments a snapshot into physical lines (the `findPickerRows` idiom: `StripOSC`, split on `\n` and `\r`) and, per line, walks raw bytes with the same `parseForegroundSGR` state machine `pickerRowOpenColor` uses, testing the colour active at the line's **first visible glyph**. Both real panels satisfy it via their top border rule, which opens in the highlight shade regardless of which content row is selected; the general light-blue on prose paths/links renders **mid-line**, so it no longer supplies the signal. `snapHasPickerHighlight` is untouched and still gates slash-picker chrome (`picker.go:255`).
- **`gridRowContainsAll`** (`modal.go`) — `gridContains` bound to one row: some rendered grid row must contain **all** of a set of substrings, not each matched independently anywhere on the grid. `permissions-config` uses it for the three tab words (`Allow`/`Ask`/`Deny`), which the real panel renders together on its tab row. The header (`"Permissions"`) stays a separate whole-grid `gridContains`, **not** required on the tab row — forced by the committed synthetic fixture (`modal_test.go:334`), which renders the header on row 0 and the tabs on row 1.

Arm shapes after the change:
- mcp: `gridContains(g, anchorMCPSpaced) && snapHasRowOpeningHighlight(snap)` — mcp's header is already one contiguous phrase, so it needed only the row-opening highlight.
- permissions-config: `gridContains(g, anchorPermissionsHeader) && gridRowContainsAll(g, anchorPermissionsTabAllow, anchorPermissionsTabAsk, anchorPermissionsTabDeny) && snapHasRowOpeningHighlight(snap)`.

Both real fixtures (`mcp-snapshot.bin`, `permissions-config-snapshot.bin`) and the synthetic grid fixture still classify — measured, not assumed: both panels' highlight escape opens their border-rule row, independent of selection state. No other arm touched; `snapHasPickerHighlight` kept as-is for slash-picker.

## Patterns established

- **Row-bound colour check as a sibling, not a generalisation, of an existing byte-walk.** The ticket asked to "reuse the byte-walk at `picker.go:128`" (`pickerRowOpenColor`). Rather than generalise that function in place, `lineOpensInHighlight` copies the `parseForegroundSGR` walk shape into a new focused helper — `pickerRowOpenColor`'s caller (`findPickerRows`) depends on its stop-at-`/` semantics and has its own pinned tests (`picker_color_test.go`). When a ticket says "reuse the walk" but the existing function has a narrower contract than the new caller needs, copy the shape rather than widen the existing function's contract.
- **A full-panel class's compound co-signal binds to the row the real panel renders it on, not to "header + tabs together."** `gridRowContainsAll` requires only the three tab words on one row; the header stays a separate whole-grid match. This was forced by the committed synthetic positive control (`modal_test.go:334`), which has the header and tabs on *different* rows — a stricter "header+tabs same row" contract would have broken that committed fixture. When binding a compound co-signal to structure, check every committed positive control's actual row layout before picking the binding granularity, not just the real `.bin` fixture (which happened to have both on one row).
- **Belt-and-suspenders where both guards are independently deterministic, and the negative test proves it non-vacuously.** `TestPermissionsConfigTabForgeryRejectedByRowBoundColor` (`anchor_forgery_test.go`) has two sub-cases: one line satisfying the row-opening-highlight guard vacuously (asserts `snapHasPickerHighlight` true to prove the *old* signal is present) while the tab-compound guard rejects it, and a second reversing which guard does the rejecting. Mirrors the `anchor_forgery_test.go:304` non-vacuity idiom from earlier tickets in this arc.

## Lessons learned

- **"Reuse the byte-walk" in a ticket/spec is about the algorithm shape, not the function.** The architecture doc was explicit that `pickerRowOpenColor` itself must not be modified or generalised (it has its own semantics and test suite) — worth restating because it's an easy shortcut to reach for "just add a parameter" instead of copying ~15 lines.
- **Self-reference tickets in this arc (#219–#227, #242, now #244) stay literal-free in prose/comments/commit messages by symbol reference (`anchorPermissionsHeader`, not the quoted word); the one place literals legitimately appear is test *fixture byte data*.** This ticket's own negative-suite fixtures necessarily embed the literal words being protected against, in test bytes, not in prose — same posture as #242's fixtures.
