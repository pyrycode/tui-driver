# #246 — Raise the rolling buffer cap so an on-screen panel survives ongoing repaints

[Issue](https://github.com/pyrycode/tui-driver/issues/246) · [PR #267](https://github.com/pyrycode/tui-driver/pull/267) · Code: `pkg/tuidriver/buffer.go`, `pkg/tuidriver/buffer_test.go`, `pkg/tuidriver/mcp_test.go`

## Summary

`DefaultBufferCap` (`pkg/tuidriver/buffer.go`) went from 4096 to 16384 bytes. At 4096, a full-screen panel that fills the rolling window exactly (the committed `mcp-snapshot.bin` fixture) stopped classifying while still physically on screen: ordinary status repaints (spinner / token-counter frames) evicted the panel's header bytes from the front of the window even though the panel never scrolled away. This had been carried as a documented "deferred architectural decision" in `buffer.go`'s doc comment (and in [ADR-0002](../decisions/0002-pattern-matching-over-emulation.md)) since the buffer's original 4 KB sizing, blocked on a per-tick render-cost objection that the render-once change (#225) removed.

`DefaultGridRows` stays 40 and region-scoped detectors read only `Grid.LastRows(n)` of the rendered screen, so the larger window only starts VT100 reconstruction further back — strictly more faithful, no detector loses protection (see the architect's security review on the [#246 spec](../../specs/architecture/246-raise-rolling-buffer-cap.md), verdict PASS). No call sites changed: `pyry agent-run` (`BufferCap: 0`) and `cmd/corpus-replay` (`NewBuffer(0)`) both inherit the new default automatically.

**Test fallout.** `buffer_test.go`'s `TestBufferNewBufferDefaultsCap` had a hardcoded `5000`-byte append (`5000 < 16384` → no trim → assertion failure) — the ticket's own AC2 wording called this "unchanged," but the spec flagged it as a wording error, not a scope-creep exemption. Fixed by mirroring `session_test.go`'s already-symbolic `DefaultBufferCap+100` form. A new regression test, `TestParseMcpStatusSurvivesRepaintsAtDefaultCap` (`mcp_test.go`), drives the committed fixture plus ~2 KB of synthetic bottom-row-only repaints through the real `Buffer` at two caps — `NewBuffer(0)` (16384, positive: panel still classifies, `TotalServers==10`) and `NewBuffer(4096)` (negative control, same bytes: classification degrades, `TotalServers!=10`). The two-cap structure is what gives the test value — a test green at both caps would prove nothing.

## Patterns established

- **Two-cap regression test for a capacity-threshold fix.** When a fix is "raise a resource limit so X survives longer," a single-cap test at the new limit doesn't prove the fix did anything — it could pass by coincidence. Drive the same input through the real component at both the old and new limits and assert opposite outcomes (positive at new, negative control at old). Reusable shape for any future buffer/cap/window-size ticket.
- **`buffer_test.go`'s literal-vs-symbolic append pattern is now a landmine to check on any `DefaultBufferCap` change.** `session_test.go:386` was already written symbolically (`DefaultBufferCap+100`) and needed no edit; `buffer_test.go`'s sibling test had a stale hardcoded literal that silently assumed the cap would never grow past it. Any test that appends a fixed byte count to probe trim behavior should use `DefaultBufferCap±N`, not a magic number — this is now the second time (see #182's version-lock precedent for the general shape) that a magic-number test assumption broke on an otherwise-safe constant change.

## Lessons learned

- **The ticket's own AC wording can be wrong — verify, don't transcribe.** #246's AC2 asserted both cap-assertion tests "read the constant symbolically, so they must still pass unchanged." That was true for one of the two tests and false for the other; the architect caught it by reading both test bodies rather than trusting the AC prose. Treat "must pass unchanged" claims in a ticket as a hypothesis to check against the actual test source, not a given.
- **The ticket pointed at the wrong classifier file.** The ticket text says "the existing mcp-panel classifier (`pkg/tuidriver/mcp_banner.go`)" as the regression test's assertion target; the `mcp-snapshot.bin` fixture is actually classified by `ParseMcpStatus` in `mcp.go`, not by `HasMcpFailureBanner` in `mcp_banner.go` (a banner detector for a different UI element). The architect's spec corrected this before the developer wrote the test — worth a quick grep-to-confirm on any ticket that names a specific classifier file for a fixture.
- **A "historical narrative" comment and a "current architecture fact" comment referencing the same number need different treatment on doc-update.** Several `cmd/spike-*/main.go` comments and `docs/knowledge/architecture/system-overview.md` passages cite "the 4 KB rolling buffer" — some describing a specific past incident at a specific claude version (leave as historical record, editing would falsify it — the code reviewer flagged this explicitly as a NIT requiring no action), others describing the buffer's mechanism in present tense as an ongoing property of the system (these were stale and needed the number corrected to 16 KB during this documentation pass). Distinguish "this happened once, at the old cap" from "this is how it works now" before touching cap-number prose in a doc.
