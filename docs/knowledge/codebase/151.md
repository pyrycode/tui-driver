# #151 — Rendered-grid refactor 2/6: grid + chrome slash-picker detection, check modals first

[Issue](https://github.com/pyrycode/tui-driver/issues/151) · [Spec](../../specs/architecture/151-slash-picker-grid-classification.md) · Commit `ac09439` · Related: [#150](150.md) (Grid accessor this builds on), [#152](https://github.com/pyrycode/tui-driver/issues/152) (slice 3/6, grid-ifies the remaining anchors), [#146](146.md)/[#147](147.md) (the `ParseModalContent`/`AnswerModal` gate this protects), [#90](90.md) (Render-vs-StripANSI split), [ADR 0002](../decisions/0002-pattern-matching-over-emulation.md)

**Slice 2/6 of the rendered-grid refactor (Cross-Repo Code Review 2026-07-03).** Fixes CRITICAL A: `DetectModalClass` ran the slash-picker check **first** (`modal.go:98`), and `findPickerRows` treated **any** stripped line beginning `/`+letter as a picker row (`pickerRowStartRe`, `picker.go:78`). Absolute paths (`/Users/x/file.go`) are everyday agent content, so:

- a real **permission modal** with a path on screen was misclassified as the picker → the auto-answer (`answer.go`, gated on `DetectModalClass`) never fired → the session hung, and any in-flight `modalDismissed(Permission)` poll saw `SlashPicker != Permission` and falsely reported "dismissed"; and
- a lone `/path` at idle was a **phantom picker** → `classify()` (`events.go:386`) reported a modal that wasn't there → turn-end was suppressed.

Root cause shared by the whole chain: state was classified by substring/line-matching the raw append-only *history* buffer instead of the rendered *grid*. Slice 1 (#150) shipped the addressable `Grid`; this slice is the first detector to consume it.

## Summary

Two deterministic defenses of **different fabric**, both required (belt-and-suspenders):

1. **Reorder** — the seven specific anchors (mcp, agents, ask-user, trust, permission, model-select, permissions-config) are checked first; slash-picker is the **last resort**. The `switch`'s `default: return ModalClassUnknown` arm was removed; a trailing `if isSlashPicker(snap) { return ModalClassSlashPicker }` + `return ModalClassUnknown` replaces it (`modal.go`). The anchors' relative order and predicates are untouched. Ordering makes a specific anchor win when both it and the picker's signal are on screen.
2. **Grid + chrome** — new unexported `isSlashPicker(snap) bool` (`picker.go`) ANDs two independent signals:
   - **Grid-region location** — `gridHasPickerRow(NewGrid(snap, 0, 0))` matches `pickerRowStartRe` against `Grid.Rows()` (StripANSI'd, on-screen only), so `/`-lines scrolled off into raw history no longer count.
   - **Chrome** — `snapHasPickerHighlight(snap)` walks the raw snapshot SGR-by-SGR via `parseForegroundSGR` and returns true on the first foreground whose RGB is in `pickerHighlightedRGBs` (`rgbIsHighlighted`). A real picker always paints its selected row in a highlight shade; a benign path/command line at idle does not.

`findPickerRows`, `ParsePicker`, and `pickerRowStartRe` are **unchanged** — the raw-byte color path `ParsePicker` reads for highlight RGB is preserved. Classification (grid, color-free) and parsing (raw bytes, color) deliberately **diverge**: `ParsePicker` runs only *after* classification confirms a picker, so the two paths need not share a data representation.

Tests: `go test -race ./...` and `go vet ./...` green; code review PASS. `security-sensitive` (gates the permission auto-answer boundary) — security-review verdict PASS.

## Patterns established

- **The location/parse split — a check that runs strictly before its downstream consumer may use a different data representation.** `findPickerRows` served two masters (classification in `DetectModalClass`, parsing in `ParsePicker`). Because classification is a *precondition* of parsing, #151 moves classification onto the color-free grid while parsing keeps the raw color bytes — no shared representation, no behaviour change to `ParsePicker`. The general lever: when consumer B only ever runs after gate A confirms, A and B can diverge in how they read the same snapshot.
- **Belt-and-suspenders of different fabric, both deterministic code.** Reorder (ordering) and chrome (a second corroborating signal) are two independent code-level defenses, not one stochastic rule plus a duplicate. Reorder makes a specific anchor win; chrome stops a lone path from ever reaching picker classification. This is the "Belt-and-Suspenders Means Different Fabric" pipeline principle made concrete.
- **Reuse the regex, not the row-finder.** Only `pickerRowStartRe` is shared into the new grid path (`gridHasPickerRow`); `findPickerRows` with its `pickerRow{raw, openColor, colorSet}` byte payload stays put for `ParsePicker`. Empirically `pickerRowStartRe` matches rendered grid rows 1:1 (real fixtures render picker rows starting `/figma-use`, `/code-review`, … with no box-drawing prefix).
- **Encoding-agnostic chrome by construction.** `snapHasPickerHighlight` mirrors `pickerRowOpenColor`'s SGR walk but does **not** stop at the first `/` — it scans the whole snapshot. It compares *parsed* RGB (`parseForegroundSGR` resolves both indexed `38;5;153` and truecolor `38;2;177;185;249` to a comparable value), so it matches highlights the two real fixtures carry in *different* encodings. A raw-substring match on the SGR literal would silently miss one encoding.

## Lessons learned

- **The three flipped synthetic cases are the intended behaviour change, not test breakage to paper over.** `TestDetectModalClassSyntheticAnchors` had three picker-positive cases — a bare `/`-line, a normal indexed-color row (`38;5;246` → gray 148), a normal truecolor row (`148,148,148`) — that now correctly classify **Unknown** because none carries a highlight shade. Reconciled by re-labelling them as *negative guards* ("… without chrome is NOT a picker"), never by weakening the assertion to match new behaviour. The genuinely-highlighted cases (`38;5;153`, `38;2;177;185;249`) stay `SlashPicker`.
- **Chrome is a benign-false-positive reducer, not an adversarial barrier — say so plainly.** An attacker who controls claude's output can emit `\x1b[38;5;153m/x` to forge chrome. That is fine: forging `SlashPicker` yields **no** auto-keystroke (`AnswerModal` dispatches only for `Permission`/`TrustFolder`; every other class hits the `default` and sends nothing — `answer.go:80-99`), and it cannot downgrade a real permission modal (the anchor wins first after the reorder). Chrome's actual job is to stop *benign* content — a legitimate absolute path at idle — from phantom-pickering, which it does.
- **The reorder is a net security hardening.** Before, a permission modal carrying an attacker-planted path downgraded to `SlashPicker` → the consumer never gated it (hang) and an in-flight `modalDismissed(Permission)` falsely reported "dismissed". After, the `Permission` anchor wins regardless of any `/`-rows or forged color (verified: a fixture with *both* picker signals present still classifies `Permission`). This closes a real false-dismissal path on the permission gate.
- **vt10x staircase (carried from #150).** Every multi-row synthetic fixture uses `\r\n`, not `\n`, or vt10x renders a diagonal staircase and the grid rows don't start where the test expects.
- **Whole-snap chrome scan is deliberately looser than per-row.** `snapHasPickerHighlight` scans the whole (4 KB-bounded) snapshot, not just the located `/`-row's bytes. A contrived screen with an incidental highlight shade elsewhere **and** an on-screen `/`-path could false-positive. Tightening to per-row color would re-derive `findPickerRows`'s row segmentation for no observed benefit → deferred (evidence-based).

## Follow-ups (pre-spec for slice 3/6, #152)

- **The remaining anchors are still substring-matched over raw history — grid-ify them in #152.** This slice fixed **only** the slash-picker path; mcp/agents/ask-user/trust/permission/model-select/permissions-config still `bytes.Contains` the `StripOSC(StripANSI(snap))` history bytes. That is the ticket's explicit scope boundary. Slice 3/6 (#152) ports those anchors to grid-region matching.
- **#152 also closes this slice's one introduced residual.** After the reorder, an anchor phrase appearing *inside picker content* (e.g. a prompt-injected skill description containing "Do you want to proceed") now classifies as that anchor's modal instead of `SlashPicker`. Bounded today because (a) `AnswerModal` only auto-acts on Permission/TrustFolder and the consumer's ADR-025 logic decides whether to answer at all — the consumer does not drive slash-pickers in the auto-answer path; (b) the anchors are distinctive/compound (`permissions-config` needs a header + a tab; `permission` needs the full phrase). The structural fix is grid-region scoping the anchors so a modal region is distinguished from a picker description — exactly #152's job. Not fixable here without grid-ifying the anchors, which this slice forbids.
- **Chrome brittleness to a future highlight encoding (unobserved, left as-is).** If claude ships a third highlight shade/encoding `parseForegroundSGR` can't resolve, a *real* picker loses chrome → `Unknown`. This fails **safe** (no keystroke, treated as no-modal, turn-end not suppressed) and follows the same "extend `pickerHighlightedRGBs` on demand" posture as #90/`ParsePicker`. Evidence-based deferral.
