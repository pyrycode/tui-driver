# #160 — Honour context cancellation between prompt-delivery attempts

[Issue](https://github.com/pyrycode/tui-driver/issues/160) · [Spec](../../specs/architecture/160-ctx-cancel-between-delivery-attempts.md) · [PR #191](https://github.com/pyrycode/tui-driver/pull/191) · Commit `70f2b29` · Touches [`deliver.go`](../../../pkg/tuidriver/deliver.go) (structural sibling: [#147](147.md)'s `AnswerModal` mirrors this file's seam)

**XS bug fix from the Cross-Repo Code Review 2026-07-03 filing.** `deliverPrompt`'s retry loop re-delivered up to `MaxAttempts` (default 3) without inspecting cancellation between attempts. Threading `ctx` into the pure driver and adding one non-blocking `ctx.Err()` check after the commit poll closes the gap: a cancelled attempt stops without re-pasting into the live PTY. Not `security-sensitive` (verified on the issue labels) — despite the shared review-footer boilerplate that misattributes every Cross-Repo Code Review ticket to the rendered-grid classification root cause, #160 is a `deliver.go` ctx-cancellation bug with no classification / attacker-content surface.

## Summary

`promptDidCommit` (the commit poll) already honours `ctx.Done()` and returns `false` fast on cancel — but on that `false` the loop fell through to the `hasChip()` check, and with a `"Pasted text"` chip still present (plausible when a paste is cut short mid-cancel) the loop re-entered and did `clear()` + `write()` again. A single cancel could therefore drive up to 3 back-to-back writes into the live PTY, re-opening the destructive re-paste failure mode the `#227` no-chip guard exists to prevent (`#227` is a **consumer**-side concept — pyrycode ticket #553 — that was ported into this library with the deliver loop in the high-level Session API refactor).

The fix, all in `pkg/tuidriver/deliver.go`:

- **`deliverPrompt` gained `ctx context.Context` as its first parameter.** `ctx` previously lived only inside the `didCommit` closure (`s.promptDidCommit(ctx, …)`), invisible to the loop. `DeliverPrompt` now passes its own `ctx` straight through; the `didCommit` closure keeps capturing the same `ctx` — no closure change, the loop just references the context it was handed.
- **One non-blocking check, placed after the commit poll and before `hasChip()`:** `if ctx.Err() != nil { logger.Debug(…); return res, nil }`. `ctx.Err() == nil` → genuine commit-timeout → proceed to `hasChip` exactly as before; `ctx.Err() != nil` → cancelled poll → stop, without consulting the chip or beginning a fresh re-delivery. `res.Committed` stays `false`; the caller re-observes `ctx` via the downstream JSONL wait (cancel remains a **non-error** here, per the existing contract).
- **Doc-comment extended one clause** (`deliver.go:91-93`): cancellation "ends the current attempt early **and stops before any further re-delivery**." The cancel-is-not-an-error contract is unchanged.
- **Log level `Debug`, not `Warn`.** The three existing markers (re-deliver, committed-but-slow, gave-up) are `Warn` because they flag anomalies; a cancel is the **expected** shutdown/abort path, so it stays out of the `Warn` stream.

New test `TestDeliverPrompt_CtxCancelledMidLoop` (fakes-only, no PTY): `didCommit` fake does `cancel(); return false` (mirrors real `promptDidCommit` on cancel), `hasChip` fake returns `true` (the `TestDeliverPrompt_ChipPresentReDeliver` path that would otherwise re-deliver), `MaxAttempts: 3`. Asserts `writes == 1`, `clears == 0`, `res.Attempts == 1`, `res.Committed == false`, `err == nil`, the re-deliver marker is **absent** from the logs, and the cancel marker is present. The six existing `deliverPrompt(…)` call sites gained a leading `context.Background()` arg (mechanical; no assertion changes — the live-ctx path is byte-for-byte unchanged). `go test ./pkg/tuidriver -run TestDeliverPrompt` green (7/7).

## Patterns established

- **When a loop must observe cancellation, thread `ctx` — don't wrap it behind a bool seam.** The rejected alternative was adding a `cancelled func() bool` closure to `deliverDeps`. It would merely hide `ctx.Err()` behind a fake, expressing a genuine context dependency as an opaque bool. The canonical Go move is to take the context: `deliverPrompt(ctx, opts, deps)`. The fakes-only test seam is untouched — `ctx` is a plain value the test passes with a real `context.WithCancel` (`promptDidCommit`'s own test already does exactly this), so the PTY-op seams (`write`/`clear`/`didCommit`/`hasChip`) stay closures and the "cancellation is scriptable without a live PTY" property is preserved. Contrast [#147](147.md), where `answerModal` deliberately took **no** `ctx` because its only cancellation point was already captured inside the `dismissed` closure — that reasoning no longer holds for `deliverPrompt` once the *loop itself* (not just the poll) needs to see cancellation, which is why this ticket diverges. (Note: [147.md](147.md)'s "the unexported driver takes no `ctx` — same as `deliverPrompt`" line predates this change and, per the never-edit-a-sibling-ticket-file rule, stays as the historical record of #147's state.)
- **A single after-poll check is sufficient — no top-of-loop guard.** `promptDidCommit` is the *only* blocking point in an iteration and returns `false` on cancel, so a non-blocking `ctx.Err()` read immediately after it is the one place that distinguishes a real timeout from a cancelled poll. Because that check `return`s, the next iteration is unreachable, so there is no second place cancellation can slip through — a top-of-loop pre-write guard would be dead code. This keeps the guard to exactly one added `if`.
- **Deliberate non-goal: the guard suppresses *re-delivery*, not the very first `write()`.** A caller passing an already-cancelled ctx still gets one delivery attempt — within AC2's "at most the already-in-flight write." The check sits after the first `write()`+poll, not before it; no pre-write guard was added.

## Lessons learned

- **`ctx` reachability, not any missing check, was the whole bug.** Both cancellation-honouring pieces already existed — `promptDidCommit` returns `false` on `ctx.Done()`, and the loop had a clear branch structure — but `ctx` was trapped inside the `didCommit` closure and never surfaced to the loop body. The one-line-feeling fix is really "promote a captured value to a parameter"; the `ctx.Err()` check is only meaningful once the loop can see `ctx`. When a retry loop "already handles cancellation" in a helper but re-fires anyway, look for the value the loop *can't reach*, not a missing conditional.
- **Cancel reports `Committed == false`, and that is the safe report.** The caller falls through to the JSONL wait + watchdog on `false`, which honours `ctx.Done()` and unblocks cleanly — so a false negative costs one downstream fall-through, never a corrupted turn. This mirrors the cheap-false-negative posture already documented for `promptDidCommit` and for [#147](147.md)'s `modalDismissed`: on cancel, prefer "report not-done and let the caller re-observe ctx" over "claim success."
