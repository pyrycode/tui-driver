# #47 — `spike-long-prompt`: `WritePrompt` regression rig against real claude

[Issue](https://github.com/pyrycode/tui-driver/issues/47) · [Spec](../../specs/architecture/47-spike-long-prompt.md) · Feature doc: [e2e harness](../features/e2e-harness.md)

## Summary

Adds a seventh spike binary, `cmd/spike-long-prompt`, that drives one interactive `claude` turn end-to-end with a 3.45 KB multi-line embedded fixture sent through `Session.WritePrompt` (the bracketed-paste path shipped in PR #43). The spike asserts that the trimmed assistant `end_turn` text contains the substring `ALPHA_42-GAMMA_88-OMEGA_13` — the three token markers embedded at start/middle/end of the fixture. Any one of three drift surfaces trips the rig: tui-driver's bracketed-paste wire shape, claude's auto-paste-detection heuristic, or claude truncating a multi-KB body. Scaffolding (UUID resolution, PTY spawn, projects-dir resolution, JSONL discovery, tailer, watchdog, shutdown) is a verbatim copy of `cmd/spike-one-turn/main.go` with three localised swaps: `promptText` const → embedded fixture read, `ptmx.Write` → `session.WritePrompt`, unconditional success → substring-contains assertion. Harness wiring is one entry in `cmd/e2e-runner/main.go`'s `buildChecks` (between `spike-ask-user` and `probe-first-prompt-hang`, `SuccessMarker: successSuccess`, default 60 s timeout) plus one token added to the `SPIKES` list in `Makefile`. Run 1 (2026-05-20, claude 2.1.145): `SUCCESS: ALPHA_42-GAMMA_88-OMEGA_13` in 3.23 s wall-clock against a 3454-byte body, well under the watchdog deadlines — no widening warranted.

## Patterns established

- **Embedded fixture as regression-rig contract.** `//go:embed testdata/long-prompt.txt` is preferred over runtime `os.ReadFile` for spike fixtures. Rationale: `go test`, `go run`, and a built binary launched from any cwd all resolve the embed identically; there is no "fixture path" to plumb. More importantly, the embedded bytes ARE the asserted-against contract — the binary cannot drift from its test surface because they ship together. Reuse this shape for any future spike that needs a non-trivial body. Strip a single trailing `\n` before sending (UNIX convention; not part of the test surface); preserve every other byte (interior newlines, indentation, tabs are all intentional).
- **Substring containment, not exact equality, for "did the bytes survive" checks.** The assertion target is "claude received all three tokens", not "claude formatted its response perfectly". Exact-match conflates wire-shape drift with instruction-following drift — exact-match would fail loudly every time claude prepends `OK:`, wraps in backticks, or adds a trailing newline, even though the bracketed-paste path worked. Substring isolates the regression target. Encode the expected payload as a single concatenated constant (`expectedTokens = "ALPHA_42-GAMMA_88-OMEGA_13"`) so the contract is one string, not three.
- **Drift-surface separation: TUI-behavioural vs CLI-surface alarms.** This spike is deliberately NOT wired into `claude-version.lock`. Bracketed-paste markers (`\x1b[200~` / `\x1b[201~`) are an xterm-layer protocol; they do not appear in `claude --help` and so `claude-version-lock`'s flag-verification machinery has nothing to assert about them. Two distinct alarm surfaces, two distinct drift modes: version-lock catches CLI-flag drift cheaply (in-process, no subscription cost); this spike catches TUI-behavioural drift expensively (real claude turn). Future spikes that probe terminal-layer behaviour (mouse modes, alt-screen, CPR) should follow the same posture: their existence in the harness is the alarm, no version-lock entry needed.
- **`Makefile`'s `SPIKES` list is an explicit allowlist, not a glob.** Adding `cmd/spike-foo/` does not auto-enroll it under `make e2e` — the spike's basename must also be appended to the space-separated `SPIKES` variable at the top of the Makefile. The spec's "verify by reading the `Makefile` target itself — do not guess" instruction caught this in time. Reusable lesson: prefer an explicit list over a glob when adding a binary to a fixed-cost run is a deliberate operator decision.

## Lessons learned

- **Dispatcher safety-net auto-commits can silently delete code.** Mid-branch, a `code-review: auto-commit uncommitted changes` commit (9d35a45) dropped the seven-line `Check` entry that wires `spike-long-prompt` into `buildChecks`. Without that entry the binary builds under `make e2e` but the runner never executes it — defeating the regression rig the ticket exists to ship. Caught by re-reading the diff and restored verbatim from the original `feat:` commit in fadd878. The safety-net mechanism is a backstop, not a diff-preserver; treat any commit it produces as a structural review point. If you see a safety-net commit on your branch, diff it against your last known-good commit before signalling completion. (This finding generalises beyond #47.)
- **`/spike-foo` gitignore entries must be added per-spike.** The eight pre-existing cmd binaries (`/spike-one-turn` through `/probe-first-prompt-hang`, plus `/e2e-runner` and `/bin/`) were each explicitly listed; the new spike was not. Running `go build ./cmd/spike-long-prompt` from repo root writes a 4.3 MB Mach-O to cwd, where it slipped past the ignore list and rode into a safety-net auto-commit. Caught by code review on PR #51; fixed in 18b784c. The canonical build target is `./bin/spike-long-prompt` via the Makefile — the explicit `.gitignore` entry enforces that convention. Future spike tickets must add the entry as part of the same change-set as the binary itself.
- **`claude-version.lock` bumps cascade into sibling-fixture failures.** Mid-branch, a commit (42d67af) bumped the lock from 2.1.144 → 2.1.145 to match the locally-installed claude. That bump cascaded: `snapshot-drift` (picker/mcp/agents fixtures), `spike-multi-turn`, `spike-cancel`, `spike-permission`, and `spike-ask-user` all started failing under `make e2e` because their fixtures are tuned to 2.1.144's TUI byte stream. The bump was explicitly out of scope per the spec ("Updating `claude-version.lock` — bracketed-paste is terminal-layer, not CLI-layer") and was reverted in 0a33c82. Reaffirmed pattern: version-lock edits are their own ticket and must coincide with a fixture re-record sweep across every consumer. Adding a new spike does NOT justify a lock bump — verifying that the new spike passes against the *currently locked* version is the acceptance criterion.
- **`tuidriver.EncodeCwd` honours `$PWD` casing literally, not the filesystem-canonical casing.** Observed during Run 1 triage: if a worktree is entered under one casing (`/Users/.../WorkSpace/...`) but the on-disk `~/.claude/projects/` directory was created under another (`-Users-...-Workspace-...`), the deterministic JSONL path resolves to a directory that does not exist and the 10 s `os.Stat` poll trips with `session JSONL did not appear`. Affects every `--session-id`-pinning spike, not just this one — `EncodeCwd` is a byte-level transform with no `filepath.EvalSymlinks` / case-folding step. Operator triage: re-enter under canonical casing (`cd "$(pwd -P)"`). Worth documenting because the failure mode (10 s stat-poll → timeout) is opaque without this hint. Not a defect — the casing-faithful behaviour matches claude's own filesystem layout — but a triage entry worth keeping. Captured in this spike's README § *Surprises / findings* for operator visibility.
- **The "fast path" (no spinner regex match) is the common case for short claude responses.** Run 1 took the same fast path as `spike-one-turn` Run 5: `✻ Brewed for 2s` appeared in raw PTY bytes but the spinner regex never matched (per-character interleaved CSI cursor-positioning, same shape as `spike-one-turn` finding #8), and `end_turn` arrived ~2.6 s after `session-jsonl-opened`. The state machine's `thinkingObserved && !spinnerGone` guard preserves slow-path log order without forcing the fast path to wait for a spinner that may never visibly render. Confirms the `extractAssistantText`-on-final-`end_turn`-only assertion is sufficient for the fixture shape — no streaming via intermediate `assistant` events with `tool_use` observed. If a future fixture or claude version pushes intermediate `tool_use` events into a long-prompt turn, the substring assert would need broadening to scan across records; file a follow-up at that point, not pre-emptively.
