# Spec #251 — `probe-cwd-encoding` times out before it can observe: diagnose + de-gate

**Ticket:** [#251](https://github.com/pyrycode/tui-driver/issues/251) · size:s · bug · split from #250
**One line:** On claude 2.1.199 the probe's `~/.claude/projects/<encoded-cwd>` directory now sometimes never appears within its internal 30s poll, so the observation rig reddens `make e2e` without producing a library signal. Diagnose the non-appearance as the first-prompt-readiness root (structural twin of `probe-first-prompt-hang` / #181), then **de-gate the check with `NonGating: true`** — the terminal, claude-free deliverable — while keeping it running for its recording artifact.

---

## Decision up front (so the developer doesn't re-litigate the fork)

The ticket offers a single fork: **re-anchor the probe** (wait for a real readiness signal before sending its prompt) **or de-gate it** (`NonGating: true`, mirroring #181). This spec selects **de-gate**. The re-anchor path is rejected for concrete reasons recorded in § Design → *Why de-gate, not re-anchor*. Do not implement a re-anchor; do not touch `pkg/tuidriver/` or the probe binary. There is **no spike-from-fix split** — the de-gate is itself terminal and confirmable in the claude-free `make check` gate (per the ticket's own Technical Notes).

## Context

`probe-cwd-encoding` is an **observation rig**: `SuccessMarker: observedSuccess` (`^OBSERVED`), it ships green *when it observes* — even when the observation contradicts `EncodeCwd` (that mismatch is the designed payoff that drove the #206→#207 fix). On claude 2.1.199 it now fails **before** it can observe:

```
probe failed: projects-dir for session <uuid> not found under ~/.claude/projects within 30s: context deadline exceeded
e2e-runner: probe-cwd-encoding -> fail (~30.9s)
```

It fails **identically on PR #249 and its merge-base baseline `9afef9e`** — pre-existing, not introduced by #243/#249. `claude-version.lock` is unchanged at `version=2.1.199` — the same version on which #206 observed the projects-dir cleanly on 2026-07-06 (session `cf16bdbf…`, `Työ😀 → Ty---`). So the encoding and the projects-dir path have not changed; what changed is that the projects-dir now sometimes fails to appear **at all**. A recording rig that cannot record provides no library signal *and* reddens the gate — the exact situation #181 resolved for this probe's structural twin.

## Design

### 1. Diagnosis (AC1 — the primary deliverable)

Record this reasoning in **two places** the developer can write in-gate: (a) the rewritten check-definition comment (§ 2, doubles as AC3), and (b) an issue comment (§ 3). Do **not** write `docs/knowledge/codebase/251.md` — the documentation phase owns it.

**Chain being broken.** claude defers writing the per-session JSONL until it processes the **first input** (spike-one-turn finding #9). That JSONL write is what materialises `~/.claude/projects/<encoded-cwd>/`. The probe's whole sequence exists to trigger it: `WaitUntil(IsIdle)` → `AcceptTrust` → `WaitUntil(!HasTrustModal && IsIdle)` → `SendKeys("hi\r")` → claude processes it → writes JSONL → projects-dir appears → the `discoverProjectsDir` glob matches.

**Root: first-prompt-readiness (most-likely), the structural twin of #181.** If `SendKeys` lands during the **false-idle window** — `IsIdle` reports the `❯` prompt glyph is present, but claude has not finished wiring its input handler after startup/trust-accept — the keystroke is dropped, claude never processes a first input, never writes the JSONL, and the glob-poll times out at 30s. This is the identical mechanism #181 diagnosed for `probe-first-prompt-hang`: "hit a false idle ~0.25s in, sent its prompt before claude was ready, the session JSONL never appeared, exited non-zero at its internal 30s sessionFileWait." The two probes are structural twins — both send a throwaway prompt *only* to materialise the JSONL, both wait on `IsIdle`, both time out at the same 30s `sessionFileWait`.

**An `EncodeCwd`/path change is excluded structurally.** `discoverProjectsDir` globs `~/.claude/projects/*/<session-id>.jsonl` — wildcard on the directory, session-id on the file — so discovery **never** depends on `EncodeCwd` computing the right directory name. A changed encoding would not cause a *timeout*; the glob would still match whatever directory claude created. The timeout means **no directory was created at all** → the JSONL was never written → claude never processed a first input. That points at input-readiness, away from the path. (Stable-version evidence independently corroborates: same 2.1.199 wrote the JSONL cleanly on 2026-07-06.)

**A "changed JSONL creation point" (claude defers the JSONL even longer) cannot be positively ruled out without a live capture** — but it need not be, because it resolves to the **same posture**: a longer, environment/timing-sensitive defer is not fixable within the runner's 60s per-check cap by any in-library signal either. Both roads (false-idle readiness *or* longer defer) lead to de-gate; both exclude an `EncodeCwd` change. The diagnosis is therefore complete for the purpose of selecting the posture, and honest about what a claude-free gate cannot disambiguate.

### 2. The fix: de-gate the check (AC2, AC3)

Single production edit — the `probe-cwd-encoding` `Check` literal in `buildChecks` (`cmd/e2e-runner/main.go:355-373`):

- **Add `NonGating: true`.** `gateFailed` (`:83`) already returns `false` for any `NonGating` check, so its non-pass status still records in the report but no longer reddens the suite. No other runner change.
- **Keep** `SuccessMarker: observedSuccess`, `Kind: "probe"`, `Args: commonArgs`, the `OnFailure` `recording_dir` scraper, and the unset `Timeout` (60s default — the internal 30s poll must fit inside it; do **not** introduce `probeCheckTimeout` here). The probe still runs on every `make e2e` and still emits `OBSERVED:` + records its artifact **when the environment/timing lets it observe**; it just stops gating when it cannot.
- **Rewrite the leading comment** from observation-rig framing to de-gate framing, mirroring `probe-first-prompt-hang`'s comment (`:328-353`). It must state: (a) the diagnosis (first-prompt-readiness / JSONL-non-appearance, twin of #181; `EncodeCwd` excluded); (b) why de-gate not re-anchor (§ below, condensed); (c) that `NonGating` keeps it running for its recording artifact while its status stays informational; (d) the re-gate condition — drop `NonGating`, restore gating — only once it reaches `OBSERVED` reliably against the pinned claude (which requires the deferred re-anchor spike, § Open questions).

This is **not** a library behaviour change: nothing in `pkg/tuidriver/` and nothing in `cmd/probe-cwd-encoding/main.go` changes. Only the check's gating posture in the runner does.

### Why de-gate, not re-anchor

1. **The re-anchor's "real readiness signal" does not exist in-library.** The only idle predicate is `IsIdle` (bare `❯` glyph); it is exactly what produces the false idle. `WaitReady` (#173) waits on `IsIdle` too — it gates on unexpected *modals*, not on pre-ready timing — so it inherits the same false idle. #173 Open Q1 established that a *positive* signature of clean idle that pre-ready chrome fails is "infeasible in claude-free `make check` without a live capture." There is nothing to anchor on.
2. **Any probe-level re-anchor is a live-claude-gated hypothesis the developer cannot confirm.** A best-effort "confirm the prompt landed (`IsThinking`/`InterruptHint`) then resend" loop *might* help, but whether it makes the probe reach `OBSERVED` reliably is a live observation the `make check` gate cannot produce. Shipping it unverified is precisely the trap the spike-from-fix rule guards against. AC4's "green if re-anchored, confirmed across two consecutive runs" is unverifiable by the developer; "non-blocking if de-gated" is **structurally guaranteed** by `NonGating` and confirmable by reading `gateFailed`.
3. **The rig's gate value is already marginal.** Its job — produce the golden cwd-encoding for #207 — is **done** (#207 shipped the pinned unit test against claude's observed behaviour). Its only remaining gate value would be catching a *future* claude encoding change, which is version-bump territory, not something the pinned-2.1.199 gate must guard. `NonGating` keeps it recording, so a future encoding change still surfaces informationally.
4. **Precedent + evidence + simplicity all converge.** Same root, same structural-twin probe, same posture as #181 — the evidence-based, minimal, one-field change.

## Concurrency model

None. The edit is a struct-literal field addition + a comment. `gateFailed` is a pure function; no goroutine, channel, or shutdown-sequence change. The probe's own concurrency (one internal PTY reader, joined by `session.Close()`) is unchanged because the probe binary is not touched.

---

## Error handling

Unchanged in the probe. In the runner, the only behavioural delta is that a non-`pass` `probe-cwd-encoding` result no longer sets the gate red (`gateFailed` → `false`). The result still lands in the report with its status and `recording_dir` extra (the `OnFailure` scraper is retained), so a red observation stays fully visible — it just stops blocking.

| Situation | Before | After (de-gated) |
|---|---|---|
| Probe observes (`OBSERVED:` printed) | pass, green | pass, green (unchanged) |
| Projects-dir never appears within 30s | fail → **gate red** | fail → **recorded, gate stays green** |
| Probe crashes / never idle | fail → gate red | fail → recorded, gate stays green |

## Testing strategy

- **Developer gate (`make check`, claude-free):** `go vet ./...` + `go test -race ./...` compile the runner with the added field (there are no runner unit tests asserting the check list, per repo convention; the `NonGating` mechanism is already covered by `gateFailed`'s existing behaviour used by `probe-first-prompt-hang`). The developer confirms: the field is added to the correct literal, the comment is rewritten to de-gate framing, and `SuccessMarker`/`OnFailure`/unset-`Timeout` are preserved. This is the terminal, in-gate-confirmable deliverable.
- **Live gate (`make e2e`, operator/CI — confirms AC4):** across **at least two consecutive runs**, `probe-cwd-encoding` appears in the report with its status (pass if it happens to observe, fail if the projects-dir did not appear) **and the overall run stays green on it** — i.e. it is non-blocking. This is what AC4 means for the de-gate path; it is structurally guaranteed by `NonGating` and needs no live-claude verification of a *fix*, only confirmation that the flag makes the check non-blocking (visible in the report/exit code).
- **No probe binary tests** — repo convention for live-claude probes (no `_test.go` in any `cmd/probe-*`); the probe is unchanged regardless.

## Open questions

1. **Restoring the gate (deferred spike-from-fix follow-up, not this ticket).** If the operator later wants `probe-cwd-encoding` to gate again, the path is a spike-from-fix pair: **child A** re-anchors the probe (e.g. confirm the prompt landed via `IsThinking`/`InterruptHint`, resend if not) and *observes across N live `make e2e` runs* whether the projects-dir now materialises reliably; **child B**, blocked-by-A, keeps the re-anchor and drops `NonGating` (re-gate) only if A proves it reliable, else confirms the de-gate is permanent. This is out of scope here per the ticket (the de-gate is a terminal, claude-free deliverable; a re-anchor is the live-claude-gated one).
2. **Is the non-appearance intermittent or total on 2.1.199?** The ticket describes it as "now sometimes fails to appear at all," consistent with a timing/environment race (false-idle), which the twin #181 also observed as environment-sensitive. `NonGating` is correct for either intermittent or total non-appearance — it makes the outcome deterministic (non-blocking) regardless. Resolving intermittent-vs-total precisely would need the deferred spike (Q1); it does not change this ticket's posture.
